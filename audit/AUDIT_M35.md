---

## Grade

**FAIL** — ≥1 BLOCKER.

**Counts: 3 BLOCKER / 7 MAJOR / 8 MINOR.**

The spec is unusually well-written, self-aware about PCI/tokenization, PHI-boundary, webhook idempotency, and Stripe-as-source-of-truth — those dimensions are genuinely strong. But it **unilaterally rewrites its own architectural boundary**: it inverts the manifest-and-locked-M34 dependency direction, invents cross-module dependencies and outbox events that do not exist in the authoritative upstream specs, and smuggles the Stripe SDK out of its registered adapter package. ARCHITECTURE WINS: every one of those is a finding against M35, not against the architecture.

## Dimensions A–J Coverage Notes

**A. Architecture conformance — FAIL.** Three blockers here (F01 adapter mandate, F02 inverted/dropped dependency, F03 invented deps/events/meters) plus F04 (direct schema import) and F05 (helper-table/audit-trigger overreach). The spec is candid that it is editing the manifest, which is allowed — but only for `ownedTables` fill, `codePaths` confirm, and a *new-consumed-module* `dependsOn` addition (ARCH-146). Dropping the authoritative `[34]` and inverting a locked edge is exactly what ARCH-146/ARCH-235 forbid. Positive: clean non-overlap with M23/M24 billing schema (correctly asserted, §1.2/§13 cruiser rule `m35-no-cross-billing-imports`); 19 `ownedTables` declared with no collision against the M1-4 pre-claimed lists or any other audited spec; one-subscription-per-org and one-default-PM partial-unique indexes are correct; outbox-only Stripe submission and seam/boot-validation discipline are exemplary.

**B. System design conformance — PARTIAL.** Cursor pagination not specified for PHI-free lists (acceptable since no PHI, but invoice/usage lists should still be cursor-based per SD-052 convention — minor). Latency budgets declared (§9.6) and reasonable. Valkey DB separation / idempotency store unstated (F14). Stateless posture not affirmed (F10).

**C. Security hardening — STRONG with gaps.** Excellent: SAQ-A PCI posture (Stripe Elements tokenization; only PM metadata stored — brand/last4/exp, never PAN/CVV/IBAN — satisfies the "no raw card data" mandate); HMAC webhook signature verification at the route boundary before any DB write; envelope-encrypted webhook payloads at rest; restricted Stripe key scoping; refund 4-eyes + step-up. Gaps: error-envelope/404-discipline (F09), inbound Idempotency-Key (F08), audit-helper routing (F05), IDOR per-`:id` tests not enumerated.

**D. HIPAA — STRONG.** PHI posture is the standout: hard PHI boundary (D14), HMAC pseudonymization of patient/user counters (D6), redactor denylist at ingest, no PHI in Stripe payloads, STRIDE worst-case correctly scoped to commercial-count disclosure. Minimum-necessary is respected in principle. BUT the *means* of obtaining patient counts (F03 — subscribing to raw `m5.patient.*` events) is the wrong pattern even pseudonymized: minimum-necessary favors consuming M5's aggregate `PatientReader.countActiveForOrg` (which the spec itself cites in §4.5) over ingesting a per-patient event stream into a billing module. The pseudonym scheme also creates a (one-way, but real) patient-identity-correlatable artifact in a non-BAA module — defensible but better avoided by not ingesting per-patient events at all. Invoice-retention/erasure model conflicts with the cryptographic-shred deletion contract (F06).

**E. AI governance — PASS (notably strong).** M35 correctly declares an AI-prohibited zone (D8) with a `validateM35AIBlock()` boot gate, no AI capability, no capability-catalog entry needed. This is the right posture — billing is not an AI surface. No findings.

**F. DR/BCP — INCOMPLETE.** No DR section; tier asserted in prose only (F10). Stripe is Tier 3 (correct per INT-005/DR §3.1) and billing-never-blocks-care is stated, but the degraded-mode/statelessness/RPO-RTO formalization is missing. BullMQ idempotency is asserted (good, satisfies DR-022) but per-queue DLQ config is absent (F07).

**G. Operations — PARTIAL.** Queue retry/backoff/DLQ unspecified (F07); alert-as-code YAML missing (F17); partition retention not anchored to §24/OPS-020 (F12); secret inventory incomplete (F15). Migration is single-transaction five-phase additive (consistent with forward-only/expand-contract for a greenfield table set — acceptable for initial creation).

**H. Integrations — PARTIAL.** Stripe integration substance is strong (signature verify, dedup, replay window, native idempotency keys, test clocks, Stripe Tax, no-BAA posture all correct and matching INT §6.11). But the five-step INT-002 conformance is not demonstrated and the adapter package name is inconsistent across manifest/INT/DR/spec (F13 + DOC-CONFLICT). The invented FHIR/HL7 meters (F03) imply integration touchpoints not in the INT inventory.

**I. Medicare hospice regulatory correctness — N/A (correctly).** M35 is SaaS billing, not Medicare/Medicaid claims; the spec is emphatic and correct that it is not M23/M24, does not bill per clinical artifact, and shares no schema with `packages/billing`/`packages/medicaid-adapters`. This separation is the module's strongest correctness property. No hospice-regulation encoding to verify.

**J. Internal quality — MOSTLY GOOD, some defects.** Invalid RLS policy syntax (F11); eraser references a `platform_retained_invoice` table absent from `ownedTables` (F06); §13 summary line says "5 crons registered" then lists six; queue table says "11 BullMQ queues" but §4.9 lists 11 rows while several are crons — minor inconsistencies. The dunning state machine, refund workflow, usage-aggregation idempotency ladder, and reconciler-drift handling are internally coherent and well-specified.

## Cross-Module Suspicions (XMOD)

- **M34 (SaaS Tenant Platform):** M35's D24 directly contradicts M34's locked spec. M34 already ships `m34.tenant.provisioned` (→ M35 creates Stripe Customer) and `m34.tenant.offboarding_initiated` (→ M35 cancels subscription) and exposes `TenantLifecycleProvider.activeStatusForOrg`/`planLabelForOrg` + a `TenantSubscriptionEntitlementReader` deny-stub for M35's entitlements. The cross-module pass must force M35 to consume M34 (restore `dependsOn:[34]` plus any genuinely-new deps) rather than re-deriving org lifecycle from M2 directly.
- **M5 (Patient):** M35's claimed subscriptions to `m5.patient.created/status_changed/deceased/merged` do not match M5's actual events (`patient.created`, `patient.status`, `patient.merged`, `patient.updated`, `patient.address_changed`), and M5 does not list M35 as a consumer. The M5 auditor / cross-module pass should reject any M35 wiring onto M5's outbox; the supported path is M5's `PatientReader` aggregate count.
- **M28 / M29:** M35 declares FHIR-egress and HL7-message meters and dependencies on M28/M29. Neither the architecture meter list nor INT §6.11 includes these. The M28/M29 auditors should confirm they expose no such metering seam to M35; if quota-metering is desired it needs an architecture decision.
- **M1 / M2 schema imports:** M35's direct `packages/db/src/schema` imports of `organization`/`membership` will trip `check-table-ownership.ts`; the foundation/table-ownership pass should catch these.
- **M3:** M35 registers 5 ABAC predicates + 25 permission keys + 2 new tenant roles + several `platform_*` roles. M3/M2 should confirm the `platform_billing_admin`/`platform_support_t2`/`platform_sales` role keys exist or are added to the catalog.
- **VENDOR_ADAPTERS:** If the project standardizes on `packages/saas` (manifest) for Stripe, M34 and M35 both touching Stripe is a boundary question the cross-module pass must settle (who owns the Stripe adapter: M34's `packages/saas`/`packages/saas-tenant-platform`, or a shared `packages/stripe-client`).
