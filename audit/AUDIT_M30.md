# WardenX Module Audit — Module 30: HQRP & Quality

**Auditor:** Principal Architect / Medicare Hospice Compliance / HIPAA Security / Staff Engineer (combined role per AUDITOR_INSTRUCTIONS.md v1.0)
**Spec audited:** `WARDENX_MODULE_30_HQRP_QUALITY_SPEC_v0_5.md` (audited at "Locked v0.4 (Consolidated)"; renamed to v0.5 for the `m30.` event-naming convention review)
**Authoritative sources:** `WARDENX_ARCHITECTURE_v0_11.md`, manifest, SD/SEC/AI/DR/OPS/INT criteria packs.
**Verdict basis:** Architecture WINS over module spec. Module specs are proposals.

---

## GRADE: FAIL

**Counts: 3 BLOCKER / 9 MAJOR / 11 MINOR**

The spec is unusually thorough and gets the regulatory *substance* of HQRP largely right (HOPE/iQIES correctly delegated to M10; 4% APU penalty signal encoded; CAHPS arm's-length vendor posture; SRA per §164.308; org_id + RLS on every table; CAHPS caregiver PII envelope-encrypted; AI-prohibited zone; correct outbox-only seam discipline for the *happy path*). But it FAILS on three architecture-invariant violations: (1) a database trigger that directly reads three other modules' owned tables (`patient`, `medication_order`, `document`) — the exact leak the table-ownership fitness check exists to prevent; (2) a manifest dependency expansion from 5 to 23 modules that, while proposed as an ADR, is structurally unbounded and conflicts with the architecture's foundation-freeze + minimal-seam discipline; and (3) the "Consolidated" v0.2/v0.3 merge was never actually reconciled — the incident state machine, table/column names, and validator numbering exist in two mutually contradictory forms across the document.

## Dimensions A–J Coverage Notes

**A. Architecture conformance — FAIL.** Three structural breaks: cross-module table reads in the Part 2 trigger (F01, BLOCKER), an unratified 5→23 dependency expansion (F02, BLOCKER), and a direct M12→M30 API call (F08). Positives: outbox-only seam discipline for the documented happy path is correct; five published read seams with boot validation (D17) match the seam-registry pattern; `ownedTables` are declared (14 + 1 view) and non-colliding with M1–M4 or any other audited module; helper tables (audit_event/outbox_event/idempotency_key) are routed through M4/M1 helpers; no vendor SDK leaks (CAHPS adapters are hand-rolled, correctly registered intent). The `codePaths` add `packages/quality` + `packages/cahps-vendors` (reasonable) but those packages and the dependency expansion are not yet in the manifest — they are a *proposed* patch (§13), so the spec is not buildable against the current manifest.

**B. System design conformance — PARTIAL.** BullMQ queues declared with concurrency/backoff/idempotency (§4.8) — good. Stateless app tier respected. Gaps: no cursor pagination (F06), PE-scoping gap in RLS/materialized view (F12), `risk_register_view` refresh actor leakage risk (F20). Snapshot store to MinIO `m30/snapshots/...` (§2.8/T-2.8) should use `tenants/<org_id>/` prefix per SD-033/ARCH-082 — currently a flat `m30/snapshots/<orgId>/` path (minor, folded into F16).

**C. Security hardening — PARTIAL.** Strong: org_id on every table, RLS FORCE, envelope encryption (`pgp_sym_encrypt`) for CAHPS caregiver contact + vendor config cipher, audit denylist for free-text PHI, mTLS on the vendor ingest route, double-defense RLS for abuse-allegation visibility, IDOR-as-404 discipline, two-person co-sign with step-up (STEP_UP_POLICY). Gaps: module-local rate limiting (F09), inconsistent 403/422 error semantics (F15), Part 2 segmentation beyond retention not defined (F14). No roll-your-own auth/crypto (uses Better Auth + platform KMS) — good.

**D. HIPAA — PARTIAL.** SRA workflow per §164.308(a)(1)(ii)(A) with NIST 800-66r2 template, 90/60/30/7 reminders, two-person closure — correct and well-modeled (ARCH-182, ARCH-243). Breach 60-day timer encoded (HITECH §13402, §1.3 line 124). Audit on every mutation/PHI read via M4. Destruction workflow + erasers registered for the 4 PHI tables. Gaps: Part 2 redisclosure controls (F14), retention inconsistencies (F11), and the trigger reads patient/document tables to *make* a Part 2 determination — a clean implementation but via an illegal access path (F01). Minimum-necessary CAHPS export minimization (§8.6 #1) is exemplary.

**E. AI governance — PASS (by exclusion).** D18/§8.7 place all M30 mutating surfaces in `AI_PROHIBITED_SURFACES` with a boot validator (`validateM30AIBlock`), mirroring M12 D12 / M13 D15 / M18 D13 — correct posture; AI may only *observe* via read seams. One forward-looking note (F21) on the Phase-2 deny-stub. No PHI-to-model paths, so AI-042/AI-078 not triggered.

**F. DR/BCP — PARTIAL/FAIL.** Tier mis-declared (F07, MAJOR), no degraded-mode/BCP section (F18). Job idempotency present but mis-cited (F17). M30 owns none of the 7 safety-critical BCP data classes, so no Weekly-BCP-Print feed required — correctly not claimed.

**G. Operations — PARTIAL.** Partitioning declared for the 4 PHI tables (monthly) consistent with OPS-020 conventions; migrations are described as additive/3-phase but the v0.3 migration (§3.8) does an `ADD COLUMN ... NOT NULL DEFAULT` on `cahps_sample`/`death_source` (acceptable expand pattern) — though against a table name that doesn't exist in v0.2 (F03). New partitioned tables should be added to `partition.rotate` (OPS-021) — not stated. Cost/metering: N/A (no AI tokens). Alerts (§4.9) are well-formed but should follow the OPS-043 YAML schema with runbook links (not shown).

**H. Integrations — PARTIAL/FAIL.** iQIES/HOPE submission is **correctly NOT owned by M30** — M30 only reads `HopeSubmissionProvider` from M10 (ARCH-160, INT-025); M30 has no `iqies-client` in codePaths — this is right. CAHPS vendor surface is under-catalogued and ADR-jumped (F10, MAJOR). No CMS-webhook-receiver invented (good — INT-044). The CAHPS BAA hard-gate is correctly enforced (`baa_reference_id` required on binding, §8.6 #5).

**I. Medicare hospice regulatory correctness — MOSTLY CORRECT, one MAJOR.** HCI 10-indicator, HVLDL (≥2 visits by qualifying discipline in last 3 days of life, FY-keyed disciplines, EVV-unverified excluded), HOPE-derived FY2028 measures, 4% APU penalty signal (ARCH-160 "4-point APU reduction"), CAHPS sampling rules (≥48h stay, <18 exclusion, size-exemption <50), QAPI per §418.58, infection per §418.60, CoP 23-citation tracking — all encoded substantively correctly and bound to per-FY constants (good defense against CMS spec drift). The one regulatory encoding error: HOPE SFV "timely" window stated as both "2 calendar days" (correct) and "48h" (incorrect) — F04, MAJOR. The "do NOT silently exclude external-source deaths from CMS denominators" posture (§1.2 line 110, D20) is exactly right and commendable.

**J. Internal quality — FAIL.** The "Consolidated" merge is the dominant problem: two incident state machines, two table/column name sets (cahps_sample vs cahps_decedent_sample; death_date vs death_at; org_id vs organizationId; kind_data vs data; retention_class column present in v0.3 but absent in v0.3 base schema), swapped validator numbers (V-11/V-12, V-13), ABAC predicates referencing nonexistent columns, and DB CHECK constraints on nonexistent columns (`closed_by_user_id_2`). Retention figures conflict (7y vs 15y CAHPS). These make the spec un-implementable without a reconciliation pass (F03, F11, F13).
