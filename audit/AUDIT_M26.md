# WardenX Module Audit — Module 26: Cap Management

**Auditor role:** Principal Architect / Medicare Hospice Compliance (42 CFR Part 418) / HIPAA / Staff Eng / QA Director
**Spec audited:** `WARDENX_MODULE_26_CAP_MANAGEMENT_SPEC_v0_2.md` (Spec status: Locked v0.2)
**Authoritative sources:** `WARDENX_ARCHITECTURE_v0_11.md` (+ §25.15 fitness), `module-manifest.ts`, `WARDENX_SECURITY_HARDENING_v0_2.md`, `WARDENX_AI_GOVERNANCE_v0.2.md`, `WARDENX_SYSTEM_DESIGN_v0.3.md`, `WARDENX_DR_BCP_v0.1.md`, `WARDENX_OPS_RUNBOOK_v0.1.md`, `WARDENX_INTEGRATIONS_v0_1.md`, plus M2/M25/M36 locked specs for seam verification.

## GRADE: FAIL

**Counts: 4 BLOCKER / 9 MAJOR / 7 MINOR**

Rationale: The module is regulatorily literate and unusually thorough on the hospice-cap domain, but it (a) overrides an authoritative architecture decision (cap-year window) inside a "Locked" spec rather than via the required ADR; (b) fabricates cross-module contracts that the owning modules do not provide (M36 `cap_watch` channel kind, M2 "biometric-class" step-up, M25 event/seam names, `audit_log` table/`M4.recordAuditEvent` API); (c) directly imports another module's Drizzle schema and FKs to an M1-owned table; and (d) is internally contradictory on its own cap-period state machine across the schema, TypeBox, routes, ABAC, and seams. Per the protocol, ARCHITECTURE WINS and a spec that touches/contradicts another module's contracts FAILS regardless of prose quality.

## Dimension Coverage (A–J)

**A. Architecture conformance — FAIL.** dependsOn deviates from the authoritative `[23,36]` to an 11-module set via a proposed manifest patch (§13); some additions (1/4) are reasonable but the patch also encodes M5/M6/M25/M38/M40 import edges and a `packages/cap-management` codePath not in the manifest (manifest M26 codePaths = `apps/backend/src/modules/26-cap` only) — these are architecture decisions requiring review, not spec assumptions (ARCH-146/235). Direct M2-schema import + M1-owned-table FK (F02). Cycle with M23 (F05). Fabricated M36/M2/M25 contracts (F03/F07). Helper-table discipline violated via `audit_log`/`M4.recordAuditEvent` (F04). ownedTables (12) are non-colliding and correctly declared — that part is conformant. Outbox usage is declared (good), but §4.10 lists 9 events while the text and §7.14 reference a 10th (`cap.year_reopened.v1`) "added for clarity" but not in the table — minor catalog drift.

**B. System design conformance — PARTIAL.** Stateless/queue/partition patterns are mostly right (partition-by-cap_period, advisory locks, FOR UPDATE roll-ups). Misses: idempotency-key middleware (F08), PG16 vs PG18 (F18), cron-timezone convention (F17), no cursor-pagination statement on the accrual-line list (`listAccrualLines` returns a cursor — ok). Cap watch dashboard 60s auto-refresh is fine.

**C. Security hardening — PARTIAL/CONCERNS.** RLS pattern is correct (`org_id = current_org_id()`); platform-constant table correctly platform-scoped with read-all/write-platform-admin. STRIDE table present (good, satisfies SEC-007). Gaps: PS&R bulk-PHI handling (F09), `Idempotency-Key` absent (F08), and `SET LOCAL row_security=off` for "platform analytics" cross-tenant reads is asserted as a pattern (§3.5 line 943) — flagged: any such path is an ARCH-086/SEC-008 cross-tenant exposure surface; spec says "zero such queries in Phase 1," acceptable only if truly absent. IDOR tests specified (good). 404-not-403 discipline stated (good).

**D. HIPAA — CONCERNS.** Retention classes assigned (compliance 7y / operational 13mo) consistent with §24 intent. Eraser registered, but the patient-PHI-redaction approach (UPDATE on append-only tables) is internally contradictory (F04) and the `audit_log`/`M4.recordAuditEvent` invention breaks audit-control integrity (F04, SEC-010/SEC-082). PS&R files are PHI-Critical and under-controlled (F09). No-PHI-in-payload: alert payloads carry `patientDisplayName` "redacted by M36 per recipient" — acceptable IF M36 actually performs per-recipient redaction (out-of-band SMS/email/push must be deep-link-only per ARCH-185; the spec routes via M36 which enforces this — ok, contingent on F03 channel resolution). Minimum-necessary on cap-detail reads via `caseload_or_scope` predicate is a good touch.

**E. AI governance — PASS (with F20 minor).** Correctly deterministic, no AI surface, "what-if" labeled non-decision. Only gap: the AI-011 Medium-risk catalog entry isn't formally closed.

**F. DR/BCP — FAIL on declaration.** No tier, no degraded-mode, no BCP posture (F11). Job idempotency is addressed (DR-022 satisfied — accrual/inpatient/projection jobs are idempotent by source/compute key). But Valkey-as-ephemeral / PostgreSQL-as-SoR posture and recovery participation are unstated.

**G. Operations — PARTIAL.** Partitioning declared; but new partitioned tables (`cap_beneficiary_accrual_line`, `cap_inpatient_day_line`, `cap_projection_snapshot`) are not added to the OPS-021 `partition.rotate` job, and partition retention/`legal_hold` skip behavior (OPS-022/OPS-057) is unstated. Queue DLQ/concurrency missing (F17). Secret inventory: the per-tenant DEK for PS&R storage is referenced but not added to the OPS-036 inventory with a rotation cadence.

**H. Integrations — FAIL.** Invents MAC-region PS&R taxonomy + future PS&R API not in INT-005 (F10). Otherwise M26 has no first-party external integration in Phase 1 (correct — it consumes M25/M23 internally), which is fine.

**I. Medicare hospice regulatory correctness — MIXED.** Strong: aggregate cap = paid (not billed) per §418.308(d) (D4, correct); both streamlined + proportional methodologies per §418.309 (D2, correct in principle); service-continuity floor per §418.52 (D14, correct and survey-defensible); warn-only validation (D6) aligns with cap-as-payment-cap. The cap-year window is *regulatorily correct* (Oct 1–Sep 30 post-BBA-2018) but conflicts with the authoritative architecture (F01). Weak/incorrect: inpatient-cap denominator and overage-reduction math imprecise (F13); proportional proration denominator ("election days in period") is plausible but the cross-hospice streamlined "counts once per tenant, overlapping allocations across tenants" (D10) needs SME confirmation against CMS streamlined counting (the streamlined method counts a beneficiary fully in the cap year of *first election*, with no proration — the spec's "full allocation regardless of days, per tenant" is a reasonable reading but the cross-hospice double-count claim should be validated).

**J. Internal quality — FAIL.** Pervasive state-machine vocabulary contradiction (F06/F19), undefined column (F15), audit-denylist self-disagreement (F16), event-name inconsistency (F07), 9-vs-10 outbox event drift. This is the most fixable-but-currently-blocking class of defect for a doc claiming "Locked."
