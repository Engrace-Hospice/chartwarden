## GRADE: FAIL

**Counts: 3 BLOCKER / 9 MAJOR / 8 MINOR**

Module 37 is a thorough, well-reasoned spec that encodes the *substantive* Medicare hospice IPU regulation correctly (GIP 0656/Q5005/Q5007, IRC 0655, IRC 5-day stop-billing trigger, GIP per-encounter reassessment, 24/7 RN coverage, CoP 418.112 arranged-IPU, restraint with physician order, biomed inspection). The level-of-care encoding consumed by billing is **correct** — no LOC mis-encoding was found. It fails on three structural architecture invariants: (1) the cross-module seam graph it asserts is **cyclic and unbuildable** as specced (consumers of M37's seams cannot import them without M37 being in their `dependsOn`, which cycles with M37's own expanded `dependsOn`); (2) **no `Idempotency-Key` middleware on any mutating route** (ARCH-263); (3) a **hard "no order may be executed during an uncovered hour" mutation-block** that over-encodes ARCH-188 ("alerts when coverage gap projected") into a patient-safety hazard that fail-closes clinical orders during system faults, contradicting DR-064/DR-069.

## Dimensions A–J Coverage Notes

**A. Architecture conformance — FAIL.** The decisive failures live here. (1) **Cyclic/unbuildable seam graph (F01)** — the central structural defect: consumers of `packages/inpatient` seams (M23/26/27/28/30/34) cannot import them without entering M37's `dependsOn`, which cycles with M37's own `dependsOn` on 23/26/27. (2) **`dependsOn` over-broadened (F06)** to 23 modules, conflating outbox/SeamRegistry relationships with imports (same class as AUDIT_M27 M27-F04). (3) **Owned-table count contradiction 18-vs-26 (F07)**. *Positives:* ownedTables (26) are non-colliding with M1–M4's pre-claimed set (ARCH-143) and with no other specced module's declared tables; helper-only tables (`audit_event`/`outbox_event`/`idempotency_key`) are correctly accessed via M4/M1 helpers (ARCH-144); the outbox-only D17 discipline and the AI-block boundary rules are well-specified; XState state machines per aggregate (ARCH-260) are present; no generic workflow engine. The manifest-patch process is correctly framed as an explicit reviewed edit (ARCH-146/235).

**B. System design conformance — PARTIAL.** BullMQ queues declared with schedules (§4.8) but **retry/backoff/concurrency/DLQ not specified per queue** (SD-059 shape) — the 12 crons list only schedule+purpose. Valkey 60s TTL on the RN-coverage predicate cache is reasonable (SD-032 pattern). Performance budgets (§9.6) are present and plausible. Census/coverage watchdogs are correctly sharded. Idempotency middleware missing (F02). No invented persistent stores.

**C. Security hardening — PARTIAL.** RLS install pattern correct (§7.1, every table `organization_id` + `USING (… current_setting('app.current_org_id'))`); RLS isolation tests for every table (§9.4) — good. requirePermission on every route (§4.1) and step-up on consequential actions (§7.4) — good. **Gaps:** no `Idempotency-Key` (F02); ABAC minimum-necessary/discipline-scope not composed on reads (F10); `provider_entity_id`/`location_id` missing (F04). PHI denylist on free-text audit diffs (§3.6) is thorough and a genuine strength. STRIDE map present (§7.8, SEC-007).

**D.
