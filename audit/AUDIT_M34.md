Module 34 *defines the org_id/RLS tenancy invariant and the tenant-isolation / support-access / cryptographic-destruction model* that every other module depends on — so any deviation from the architecture's tenancy/support-access invariant is treated as a BLOCKER because it propagates to every module.

## GRADE: FAIL

**Counts: 3 BLOCKER / 7 MAJOR / 8 MINOR**

The spec is unusually thorough and well-reasoned — the lifecycle state machine, the cryptographic-shred sequencing, the DSAR/tenant-export split, and the destruction-cert seam wiring are genuinely strong. But it earns a FAIL on three architecture-invariant violations: (1) it decouples WardenX-support PHI access from break-glass, contradicting the architecture's mandated "break-glass + tenant consent" dual control for Tier-2 platform staff; (2) the majority of its tenant-scoped, PHI-referencing tables carry **no `organization_id` column** and scope via FK-join subqueries, violating the architecture's "every PHI table carries `organization_id`" invariant — the exact invariant this module is supposed to enshrine; (3) its entire platform-ops authorization surface gates on a `platform_ops` *session class* that does not exist in Module 2 (M2 has four session classes; `platform_ops` is an RBAC role), so the ABAC predicates as written can never evaluate true and the surface is unbuildable as specced.

## Dimension A–J Coverage Notes

**A. Architecture conformance.** Mixed. Positives: M34 correctly routes destruction through M4's `requestDestruction()`/`eraseFn` registry (D6, matches M4 D4 verbatim), correctly registers `TenantKeyProvider` for boot-time `validateSeams()` (ARCH-233/234), does not import clinical schemas (adds a dependency-cruiser rule to prove it), and consumes other modules via seams not schemas. Negatives: the manifest `dependsOn` expansion (F04) and `packages/saas` rename (F05) are framed as patches (good per ARCH-235) but the rename collides with the Stripe `VENDOR_ADAPTERS` binding. The seam `TenantKeyProvider` consumed-by-M1 relationship is correct in direction (M1 imports the interface, M34 ships the runtime), satisfying ARCH-233's "fail loud" intent.

**B. System design conformance.** The org_id-on-every-PHI-table rule (SD-029/SD-036) is the headline failure (F02). Partitioning convention (SD-027/SD-028) is violated on the three event tables (F10). BullMQ queues (§4.3) declare concurrency + idempotency keys (SD-059/SD-060 spirit) but do not declare retry/backoff/DLQ per queue (SD-059 requires all five) — noted within F10/operations. Cursor pagination (SD-052) not asserted on the list routes. Idempotency middleware reuse (SD-053) is correct.

**C. Security hardening.** The support-access decoupling (F01) and the fictitious `platform_ops` session class (F03) are the two structural failures. Bulk-export workflow (F06) under-implements SEC-052. Step-up (F07) misuses M2's factor model. Positives: `valueCaptureDenylist` on `tenant_key_ring` ciphertext in the audit trigger (§3.11) is exactly right and prevents the audit log from becoming a ciphertext oracle; the SECURITY DEFINER `tenant_platform_writer` pattern matches M4/M40 precedent (D22); ciphertext column-masking via `tenant_key_ring_metadata_v` view is sound. KEK-in-HSM posture (§8.1) aligns with SEC-023/SEC-026.

**D. HIPAA.** §164.524 (DSAR, 30-day + one extension), §164.528 (accounting via M4 + auditRead on platform reads), §164.310(d)(1) (cryptographic shred) are well-mapped (§1.3 driver table). Gaps: the Part 2 eraser-refusal vs DEK-destruction conflict (F08) is a real Part 2 *legal-exposure* issue; the support-access dual-control removal (F01) is the canonical vendor HIPAA finding the spec *claims to solve* but actually weakens by decoupling break-glass; Part 2 redaction-by-default in DSAR exports unaddressed (F13).

**E. AI governance.** N/A — M34 is platform control plane and explicitly touches no AI capability. It does feed AI-spend metering gating via `TenantLifecycleProvider.activeStatusForOrg` (M32 consults it), which is appropriate. No AI feature bypasses a gate because there is no AI feature. Clean.

**F. DR/BCP.** §8.6 assigns tiers (tenant_account/key_ring/baa = Tier 1; onboarding/support/exports = Tier 2; signup = Tier 3) — consistent with DR-010 (the spine must be Tier 1). The cryptographic-shred-holds-across-DR property (§8.6, §7.2 acceptance #6) is correctly reasoned (backup carries ciphertext; destroyed DEK makes it inaccessible). Shred-worker idempotency across four phases (DR-022) is specified. Minor: the bundle/export jobs' degraded-mode and the export worker behavior under MinIO outage (DR-035) are only lightly covered.

**G. Operations.** Migrations additive (mostly fine; F16). Job retry/DLQ semantics under-declared per OPS-035 (queues list concurrency + idempotency but not retry/backoff/DLQ). Partition rotation registration missing (F10, OPS-021). Secret inventory: M34 introduces `tenant_platform_writer` role + three SECURITY DEFINER functions + per-tenant DEK lifecycle — these need OPS-036 secret-inventory entries with rotation cadence (the KEK rotation is mentioned but not wired to the OPS-037 October rotation cadence).

## Cross-Module Suspicions (XMOD)

- **M35 ↔ M34 dependency-direction & manifest conflict.** Both M34 and M35 propose *contradicting* manifest patches. M34 (D23) lists M35 as a `forwardSeamConsumers` and reads M35's `TenantSubscriptionEntitlementReader`. M35 (D23/D24) asserts the architecture's `M35.dependsOn=[34]` was "build-sequence shorthand," that M35 does **not** depend on M34 at code level, that the correct direction is M34→M35, and that M35 owns `packages/subscription-billing` (not `packages/saas`). The cross-module pass must reconcile: who owns `packages/saas`, where the Stripe `VENDOR_ADAPTERS` binding points after both renames, and whether M34→M35 or M35→M34 is the operative `dependsOn`. As written, the two manifest patches cannot both be applied cleanly.
- **M1 `packages/foundation` vs manifest codePaths.** M1's spec owns `packages/foundation` (envelope crypto, RLS gen, idempotency, withOrgContext/withPlatformContext), but the manifest's M1 codePaths do not list `packages/foundation`. Every module that imports the envelope/idempotency helper (M34, M36, and others) may fail the import-boundary fitness check even with M1 in `dependsOn`. The cross-module/foundation pass should confirm `packages/foundation` is added to M1 codePaths in the manifest.
- **M2 must define a platform-ops access model (F03).** M34 assumes a `platform_ops` session class that M2 does not provide. Either M3's `platform_ops` role on a `staff` session is sufficient (then F03 is an M34 fix), or a fifth session class is needed (then M2 must add it). The M2 auditor / cross-module pass should rule.
- **Every PHI-bearing module's `TenantExportShard` (F02 corollary).** M34 makes `TenantExportShard` a seam every PHI module must implement and registers it in M34's boot.
