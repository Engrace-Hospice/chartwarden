## Module Grade: **FAIL**

**Counts: 3 BLOCKER / 7 MAJOR / 8 MINOR**

Rationale: The spec is unusually thorough and gets the *domain* (X12 835 hierarchy, CARC/RARC two-layer taxonomy, CMS appeal tiers, recoupment, EVV back-link) substantially right. But it (1) silently rewrites an architecture-authoritative dependency edge on a false justification, (2) writes types into another module's owned package and claims a consumer relationship that module's spec does not acknowledge, and (3) ships an internally incoherent §7 acceptance-criteria section whose field names, event names, state names, seam names, and error codes contradict the normative §2/§3/§4 — i.e., the spec's own machine-readable contract surface is self-inconsistent in the section that is supposed to be the test plan's ground truth. Any one of these is disqualifying for a "Locked" spec. A beautifully written spec that touches another module's package and contradicts itself FAILS.

## Dimension A–J Coverage Notes

**A. Architecture conformance — FAIL.** Manifest dep-edge rewritten on false premise (F01); writes into M22's `packages/forms` (F02); invents an M23 channel-pull seam not published by M23 (F06); helper-only `outbox_event` referenced from a feature trigger (F11). On the positive side: the M25→M23/M24 outbox event contract (`m25.remittance.claim_paid/.claim_partial_paid/.claim_denied/.claim_adjusted/.claim_recouped`) is **corroborated** by M23 (consumer `m25-remit-posted.consumer.ts`, lines 447/2593) and M24 (lines 1806–1807); the 835-parse/post ownership is corroborated by M23 §1 ("the 835 posting worker is M25-owned") and M24 D11; the eight reader seams and the M36 recipient-resolver registration follow the platform pattern; `validateSeams()` boot gate and deny-stub pattern for unlocked downstreams (M23/M24/M22/M32) are correctly applied. The `payer_kind` discriminator and `m25.edi.835_received(payerProgram)` correction of the prior dangling `m23/m24.edi.835_received` subscription is a genuine improvement.

**B. System design conformance — PARTIAL.** Partitioning (monthly on `received_at` for line/service_line/adjustment/remark) matches SD-027 conventions; BullMQ queues declared with idempotency keys (§4.8); the parse-and-post concurrency 4 / cron concurrency 1 is reasonable. Gaps: no `Idempotency-Key` request middleware (F05), cursor-pagination unconfirmed (F12), no DR tier/degraded mode (F07), bespoke RLS clause on taxonomy overlay (F09). Performance targets (§9.7: 1000-line 835 < 30s, denial worklist < 250ms) are stated and align with SD-066 spirit.

**C. Security hardening — PARTIAL.** RLS on all 11 tables (mostly standard template), step-up on 5 consequential actions (D15), STRIDE table present, IDOR/step-up-bypass/RLS-isolation tests specified (§9.3–9.5), audit denylist for PHI/free-text columns (§3.6, D10). Gaps: bulk export not bound to SEC-052 (F12), step-up window expressed bespoke vs SESSION_POLICY (F13), STRIDE not mapped to SEC §3.4 / SEC-008 layer-6 rls_denied alerting (F15), the §8.1 RLS text uses `app.tenant_id`/`set_config` while §3.5 uses `app.org_id`/`current_setting` — a within-spec inconsistency (the architecture canonical is `app.org_id`, ARCH-012/SD-029). No roll-your-own auth/crypto/rate-limit observed (uses M2/M3/M1 primitives) — good.

**D. HIPAA — PARTIAL/PASS-leaning.** Minimum-necessary via RLS + `provider_entity_scope` ABAC; PHI/free-text audit denylist; no-PHI-in-M36-out-of-band-payload (§4.9 sanitization wrapper); 7-year compliance retention with object-lock on raw 835 in MinIO; eraser registered with M4 destruction-cert workflow; `auditRead()` on raw-835 download. The 835/remittance is correctly classed billing-substantiating (ARCH-250 "remittances (835) 7 years; object-lock"). No 42 CFR Part 2 surface in M25 (remittance carries no SUD clinical content directly) — acceptable. Gap: export controls (F12) and the `app.tenant_id` vs `app.org_id` inconsistency could weaken the RLS guarantee if implemented literally.

**E. AI governance — PARTIAL.** Phase-1 no-AI posture is correct and well-motivated (D14, §8.6); deny-stub for the Phase-2 `DenialOutcomePredictionProvider`. But §4.4 and §8.6 name different seams (F08), no capability-catalog registration or kill-switch flag for the reserved capability (AI-011/AI-014). No PHI-to-cloud-AI path exists in Phase 1 — good (no OPEN-013 Anthropic-BAA exposure).
