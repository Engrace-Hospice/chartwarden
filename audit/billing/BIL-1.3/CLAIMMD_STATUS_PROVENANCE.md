# Claim.MD source and status provenance

The [official `/services/response/` contract](https://api.claim.md/) says updates are account-wide, keyed by `ResponseID`, and each nested `messages` element has its own `responseid`. Its example has `CLMMD` / `ACK` / `A` followed by payer-like updates, including payment-like free text. The [vendor X12 FAQ](https://docs.claim.md/docs/which-x12-claim-status-and-acknowledgment-transactions-are-supported-by-claimmd) states that the API returns normalized XML/JSON, 277 transactions are SFTP-only, and 999 transactions are not returned.

`apps/backend/src/modules/23-billing-medicare/claimmd-ack/interpret.ts` implements a pure interpreter. Its only proposed business action is `record_clearinghouse_receipt` when the captured message-level `responseid` matches, parent `senderid=CLMMD`, `mesgid=ACK`, and both parent and message status are `A`. This is classified `documented_example`, which is narrower than a contractual guarantee. `A` from another sender, `R`, a mismatched response ID, or an unknown code is informational. Free text never authorizes a transition. Payer acceptance and rejection await verified sender/transaction semantics.

The source representation is always `claimmd_normalized_api`; the code does not manufacture a 999 or 277CA. The interpreter carries account/environment, captured event UUID, message response ID, original sender ID/name, message code, original statuses, response timestamp and vendor claim IDs in memory. The original message text and full response remain in the encrypted BIL-1.1 page (`claimmd_response_batch.payload_cipher`, migration 1350). The application ledger stores only bounded code-shaped sender/status fields plus event/claim links. M41 acknowledgment rows explicitly identify normalized API provenance; historical M41 rows default to `unknown_legacy` because their origin cannot safely be inferred.

Known limitation: the API example alone does not certify production sender IDs, rejection semantics, payer stage, or `response_time` timezone. The dispatcher uses capture time for its transition timestamp and keeps the original vendor time in the protected source. No paid-like wording reaches M25.
