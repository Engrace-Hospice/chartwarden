## 1. SYSTEM DESIGN CRITERIA (SD-###)

### 1.1 Logical Topology & Component Boundaries (SD §1.1)

- **SD-001 (§1.1)** — Client tier consists of exactly four apps: Web (`apps/frontend`, TanStack Start), Mobile (`apps/mobile`, Capacitor iOS/Android), Admin (`apps/admin`, ChartWarden ops console), Portal (`apps/portal`, Patient/Caregiver PWA). Modules must not introduce additional client applications outside this set.
- **SD-002 (§1.1)** — All client traffic enters through the Pangolin reverse proxy edge (TLS termination, WAF, rate limiting). No client connects directly to backend, workers, or data tier.
- **SD-003 (§1.1, §8.1)** — Application tier is a single Backend service (`apps/backend`): Fastify 5 serving REST + Socket.IO, N stateless instances. Modules do not stand up their own HTTP servers in the application tier.
- **SD-004 (§1.1)** — Worker tier is Python sidecars limited to: `docling-worker` (PDF parsing + OCR), `langextract-worker` (structured extraction), `x12-worker` (EDI 837I, 835, 999, 277CA, 270/271), `ecr-worker` (cost report ECR generation), `ml-worker` (predictions, classifier), `embeddings-worker` (pgvector embedding generation). New worker types are an architecture change, not a module-local decision.
- **SD-005 (§1.1, §7.3)** — Async tier is BullMQ on Valkey. Modules requiring background jobs MUST use BullMQ queues; no module-local cron daemons, ad-hoc pollers, or alternative brokers.
- **SD-006 (§1.1, §4.1)** — Data tier: PostgreSQL 18 with pgvector + pgcrypto (primary + read replica); Valkey 8.x (cache + Socket.IO adapter + BullMQ broker); MinIO S3-compatible object storage with per-tenant buckets; MLflow model registry. Modules may not introduce other persistent stores.
- **SD-007 (§1.1, §11)** — Observability stack: OpenTelemetry collector → Grafana + Loki + Prometheus + Tempo; Sentry self-hosted. Backend and workers must emit to both OTel and Sentry.
- **SD-008 (§1.1)** — External services are enumerated and operate "over BAA": DoseSpot, Anthropic API, Twilio (SMS/Voice), Postmark (email), Stripe (subscription), MAC/Medicaid portals, Xero, Gusto. Any module integrating a new external service triggers the vendor security review path (SEC-140) and cannot self-approve.
- **SD-009 (§1.2, §3.4)** — Inter-tier transport invariants: clients→Pangolin TLS 1.3 (Let's Encrypt); Pangolin→backend mTLS (private CA); backend→workers mTLS (private CA); backend/workers→PostgreSQL TLS with client-cert verification (private CA); →Valkey TLS with `requirepass` (private CA); →MinIO TLS (private CA); backend→external TLS 1.3 with cert pinning (public CA); inbound webhooks TLS + signed payloads. Private CA lives offline/sealed-box; cert rotation via cert-manager-style cron jobs.

### 1.2 Critical Flow Invariants (SD §1.3)

- **SD-010 (§1.3.1)** — Login flow: credentials → Better Auth → session row in PostgreSQL with `(org_id, user_id, expires)` → session cached in Valkey with TTL → HttpOnly cookie. Multi-org users must select an organization (`POST /api/v1/auth/select-org`) before an org-bound session exists.
- **SD-011 (§1.3.2)** — Encounter finalize flow invariants: HearthNote `assembleLayer1(selections)` produces a deterministic narrative FIRST; LLM enhancement runs only if enabled at tenant AND clinician level; LLM output passes `diffAndValidate(layer1, llm_output)` with HARD BLOCK on factual changes; `complianceGate(encounter)` must pass before COMMIT; failure returns 422 with remediation. Drafts cached in Valkey with 90-day TTL; PHI writes occur inside `SET LOCAL app.org_id` transactions.
- **SD-012 (§1.3.3)** — Claim submission: ValidationFramework runs 30+ default rules pre-submission; any failure without documented override → 422; pass → status READY + `validation_result` row + enqueue `claim.submit`; 837I generation/999 parsing performed only by x12-worker; ack recorded and broadcast to billing channel.
- **SD-013 (§1.3.4)** — DocLens intake: uploads land in MinIO `tenants/<org>/intake/<job>/`; pipeline = docling parse → ml-worker classify per page → langextract extract (candidates + page refs + confidence) → Anthropic vision verification of high-risk fields only; extracted candidates are NEVER auto-committed — admissions staff approve/edit/reject per field; approved fields commit to Modules 5/7/9/11/12 WITH provenance.
- **SD-014 (§1.3.5)** — EVV check-in: server-side geofence check against patient address; outside geofence → 422 `outside_geofence` requiring a reason; with-reason check-ins recorded and `evv.geofence_violation` emitted to supervisor/safety rooms.
- **SD-015 (§1.3.6)** — HOPE SFV trigger: J2051 moderate or severe → symptom follow-up visit due in **2 calendar days**; creates `symptom_followup_visit`, enqueues `sfv.scheduled`, schedules clinician task, fires `clinical_urgent`/high alert with Socket.IO push + SMS per preferences.
- **SD-016 (§1.3.7)** — IDG packet build: nightly cron → BullMQ `idg.build_packets`; per-patient Layer 1 one-pagers built deterministically; LLM polish only if enhancement enabled and diff-validated; packets stored with provenance to source encounters.
- **SD-017 (§1.3.8)** — All alerting routes through the Module 36 Alert Engine: rule lookup by event type + tenant, recipient resolution with preferences, per-recipient alert row (status pending→delivered), parallel delivery in-app (Socket.IO room `user:<id>`), web-push (if enabled + endpoint registered), SMS (urgent + SMS enabled). Modules must not deliver notifications directly.

### 1.3 Deployment Topology (SD §2)

- **SD-018 (§2.1)** — Local dev is single-host Docker Compose on one bridge network; canonical port map: frontend 4180, backend 4181, admin 4182, portal 4183, postgres 5432, valkey 6379, minio 9000 (console 9001), mailpit 1025 (UI 8025), mlflow 5000, drizzle studio 4983, Python workers 8001–8006, grafana 3001 (optional `observe` profile with prometheus 9090, loki 3100, tempo 3200). Mac dev: ARM64 images, Postgres `shared_buffers=256MB`, MinIO single-node.
- **SD-019 (§2.2)** — Production target is a Proxmox cluster with exactly this VM allocation: edge-01 (4 vCPU/4 GB/40 GB, Pangolin+WAF); app-01 and app-02 (8/16 GB/80 GB each; instance #2 hot standby, load-balanced); workers-01 (8/16 GB/100 GB, docling/langextract/x12/ecr); workers-02 (16/32 GB/200 GB + optional GPU passthrough, ml-worker + embeddings-worker; Phase 1 CPU-only q4-quantized 8B models, Phase 2 recommended NVIDIA RTX 4090 24 GB VRAM, production-scale A100/H100 with vLLM); db-01 (8/32 GB/500 GB, PostgreSQL primary + PgBouncer); db-02 (8/32 GB/500 GB, streaming replica); data-01 (4/8 GB/200 GB, Valkey + MLflow); storage-01 (4/8 GB/4 TB, MinIO); obs-01 (4/16 GB/500 GB, Grafana/Loki/Prometheus/Tempo/Sentry); backup-01 (2/4 GB/8 TB, pgBackRest + MinIO replication target). Totals ≈78 vCPU, ≈200 GB RAM, ≈14 TB across 11 VMs.
- **SD-020 (§2.3)** — Cloud portability is mandatory: every component containerized; storage interfaces portable (S3-compatible, standard PostgreSQL, standard Redis protocol); cloud migration is a deployment-target change with no code change. PHI-bearing cloud equivalents (RDS/Neon, S3/R2) require HIPAA BAA.
- **SD-021 (§2.4)** — Kubernetes is explicitly NOT used initially; the design must remain K8s-compatible (containerized, health checks, env-var config, stateless app tier). Modules must not assume K8s primitives.

### 1.4 Network Architecture (SD §3)

- **SD-022 (§3.1, §3.3)** — Five trust zones with VLAN segmentation: DMZ VLAN 10 (10.10.10.0/24, edge-01); App VLAN 20 (10.10.20.0/24, app + workers); Data VLAN 30 (10.10.30.0/24, db/data/storage) — TLS from App only, NO Internet egress; Admin VLAN 40 (10.10.40.0/24, obs + backup) — no Internet; Mgmt VLAN 99 (10.10.99.0/24) — SSH/Proxmox admin only. App zone is the only zone with Internet egress (to external vendors).
- **SD-023 (§3.2)** — The single-bridge no-zone local dev network is dev-only and MUST NOT be replicated in production.
- **SD-024 (§3.5)** — Secrets: local dev `.env.local` (gitignored); production SOPS-encrypted YAML in repo + age key per VM, decrypted by systemd at service start; future cloud secret managers via workload identity. Invariant: no secrets in code, container images, or environment dumps; secrets reach containers as ephemeral mounted files (`/run/secrets/<name>`) or in-memory env vars set at process start.

### 1.5 Data Architecture (SD §4)

- **SD-025 (§4.1)** — Connection model: PgBouncer in transaction-pooling mode in front of every backend instance; each backend instance pool = 20 connections to PgBouncer; PgBouncer→Postgres pool = 50 (configurable); read replica is opt-in per query via `db.read()` helper, default to primary for consistency.
- **SD-026 (§4.1, §8.5)** — Connection budget: §4.1 states 2 backend × 20 + 8 workers × 5 = 80 connections to PgBouncer; §8.5 budget table states Backend 20×2=40, Worker containers 10×6=60, Admin/portal 10×2=20, Monitoring 5, Migrations 5, Headroom 30 → total 160 via PgBouncer, ~50 actual Postgres connections, `max_connections=200`. (Auditor note: the two worker-pool figures conflict — see audit-lead list; module specs should cite §8.5 as the governing budget.)
- **SD-027 (§4.1)** — Partitioning is mandatory for: `audit_event` (RANGE `created_at`, monthly); `claim` (LIST `provider_entity_id` + RANGE `created_at` quarterly); `claim_line` (co-partitioned); `encounter` (LIST `organization_id` + RANGE quarterly); `encounter_note` (co-partitioned); `hope_assessment` (LIST org + RANGE annually); `message` (LIST org + RANGE monthly, 6-yr retention); `extraction_job` (RANGE monthly).
- **SD-028 (§4.1)** — Index standards: every PHI table has composite index `(organization_id, <natural_key>)`; B-tree on FKs; GIN on filtered JSONB (e.g., `audit_event.diff`); HNSW on embedding columns; partial indexes on common filters (e.g., `WHERE status='active'`).
- **SD-029 (§4.1)** — Canonical RLS policy template: `ENABLE ROW LEVEL SECURITY`; policy `USING/WITH CHECK (organization_id = current_setting('app.org_id', true)::uuid)`; `GRANT ALL ... TO wardenx_app` — EXCEPT the audit table, which is INSERT/SELECT-only for the app role (UPDATE/DELETE never granted).
- **SD-030 (§4.1)** — Vacuum standards: autovacuum on; aggressive settings (scale factor 0.05) on hot tables (`audit_event`, `encounter`, `message`); weekly `VACUUM FULL` on heavily-updated tables in maintenance window; pgBackRest snapshot before any DDL migration.
- **SD-031 (§4.2)** — pgvector usage: encounter-note semantic search and similar-case lookup use 1536-dim embeddings (`text-embedding-3-small` or local model) with HNSW (m=16, ef_construction=64); HearthNote vocabulary similarity and DocLens reference matching use 384-dim smaller local models with HNSW. Embeddings generated only by `embeddings-worker`, stored in dedicated `*_embedding` tables FK-linked to source rows, refreshed via trigger→job on row change.
- **SD-032 (§4.3)** — Valkey key patterns and TTLs are fixed: `session:<id>` (TTL = session expiry); `rate:<route>:<user>:<window>` (TTL = window); `draft:encounter:<id>` (90 days); `tenantcfg:<org_id>` (5 min); `flags:<org_id>` (5 min); `socket.io#<event>` (adapter-managed); `bull:<queue>:*` (per-queue); `lock:<resource>` (TTL = max operation time). BullMQ and Socket.IO data live on a separate Valkey instance OR separate DB number (db 0 = cache+session, db 1 = BullMQ, db 2 = Socket.IO); maxmemory policy `allkeys-lru` for cache evictions.
- **SD-033 (§4.4)** — MinIO layout: `tenants/<org_id>/{documents,generated,intake,claims,cost-reports,exports,recordings}` and `platform/{form-templates,ml-models}`. Per-tenant IAM access key/secret scoped to `tenants/<org_id>/*`; backend uses platform credentials only for cross-tenant operations, with audit.
- **SD-034 (§4.4)** — Object lifecycle: versioning enabled on `documents/`, `generated/`, `claims/`, `cost-reports/`; object lock (compliance mode) on `claims/` and `cost-reports/` for **7-year retention**; `intake/` artifacts deleted 30 days after job completion; `platform/`, `claims/`, `cost-reports/` replicated to the backup VM.
- **SD-035 (§4.5)** — MLflow: backend store in PostgreSQL (separate schema, same DB); artifact store MinIO `platform/ml-models/`; single tracking server (not per-tenant); model versioning per (capability × tenant) only when tenant-specific calibration exists, otherwise platform-default.
- **SD-036 (§4.6)** — Exactly three data-scoping patterns exist: (1) tenant-scoped (`organization_id` column + org-isolation RLS — all PHI); (2) platform-shared read-only (`USING (true)` SELECT for `wardenx_app`; mutations only via `wardenx_admin` — terminology, form templates, ML models, default validation rules); (3) platform-shared canonical + tenant-scoped overlay (Module 40 entities: canonical table SELECT-only to app role; overlay table with full org-isolation RLS and `UNIQUE (entity_id, organization_id)`). Module specs must declare which pattern each table uses; PHI must always be pattern (1).
- **SD-037 (§4.6)** — Module 40 operational invariants: NPPES sync is a nightly platform-role job (`wardenx_admin` / `withPlatformContext`) emitting `nppes.sync_completed` audit with change counts and tenant alerts via Module 36; merges flow through a `merge_request` table with platform-admin approval, reference re-pointing in batched per-table jobs, duplicate marked `status='merged'` + `merged_into_id`, overlay migration with per-field conflict resolution, and `mdm.merge_completed` audit with full provenance; service-layer queries always follow `merged_into_id` transparently.
- **SD-038 (§4.7)** — Feature-flag evaluation order (high→low precedence) is fixed: (1) kill switch active → disabled, bypass everything, record evaluation; (2) expired migration flag → default + warning log; (3) targeting rule match (role, userId, locationId, providerEntityId, segment); (4) rollout percent via `hash(flagKey + organizationId + userId) % 100`; (5) default value. Flag bundle cached 5 minutes per org.
- **SD-039 (§4.7)** — Kill-switch cache bypass: when any flag has `kill_switch_active=true` for a tenant, the flag cache is NOT used — every request re-evaluates from PostgreSQL. Cache invalidation: 5-min TTL; `feature_flag.updated` / `feature_flag.kill_switch_activated` Socket.IO events delete `flagcache:<orgId>` immediately; frontend TanStack Query stale time 5 min with kill-switch event invalidation.
- **SD-040 (§4.7)** — Flag-evaluation recording rules: `product` flags not recorded; `rollout` flags recorded for first 14 days; `kill_switch` flags every evaluation while active; `migration` flags every evaluation.
- **SD-041 (§4.8)** — Local AI inference: runs on workers-02 ml-worker (Ollama); PHI never leaves ChartWarden; sync path backend→ml-worker→Ollama, async via BullMQ `ai.infer`; audit event is `ai.local_inference` (with `backend=local`) instead of `ai.phi_disclosed`; expected latency 2–4× cloud for 8B on CPU, comparable on GPU; no vendor rate limits or vendor cost.
- **SD-042 (§4.8)** — Local model storage/lifecycle: models in MinIO `platform/ml-models/` (ollama/, embeddings/, classifiers/, manifests/current.yaml); new versions uploaded to versioned paths; `current.yaml` updated on promotion; ml-worker reads manifest at startup, pulls missing models, verifies checksums; old versions retained **30 days** for rollback; all models tagged in MLflow with full provenance (training-data version, base model + quantization, calibration results).
- **SD-043 (§4.8)** — Local AI capacity planning tiers: embeddings-only 100+ qps on CPU; classifier+embeddings 50+ qps CPU; 8B LLM on CPU 1–3 qps per worker (serialized); 8B on RTX 4090 5–20 qps; 70B on A100 1–5 qps; multi-tenant scale via vLLM on dedicated llm-worker VM (Phase 2+).

### 1.6 Identity & Context Propagation (SD §5)

- **SD-044 (§5.1)** — Authentication is Better Auth only: session record in PostgreSQL `(user_id, organization_id, expires_at)`; session ID in HttpOnly Secure SameSite=Strict cookie (web) or Capacitor SecureStore (mobile); backend middleware resolves session → `(user_id, organization_id, membership_roles, location_memberships)` into request context. Modules must not implement their own auth.
- **SD-045 (§5.2)** — Every request constructs a `RequestContext` (correlationId, userId, organizationId, providerEntityIds, locationIds, roles, ABAC AttributeBag, ip, userAgent, startTime) propagated through: every Fastify handler, every domain-service call (explicit), every repository call (sets `app.org_id`), every BullMQ job payload, every worker HTTP call (`X-Correlation-ID`, `X-Org-ID`, `X-User-ID`), every Pino log line, every OTel span, every Sentry breadcrumb.
- **SD-046 (§5.3)** — RLS context invariant: all PHI queries run inside `withOrgContext()` which executes `SET LOCAL app.org_id` and `SET LOCAL app.user_id` within a transaction. `SET LOCAL` scopes to the transaction; queries outside a transaction or without context are denied (default DENY).
- **SD-047 (§5.4)** — Mobile auth: same Better Auth session model; token in Capacitor SecureStore (iOS Keychain / Android EncryptedSharedPreferences); biometric unlock gate at launch; app-level 15-minute idle timer (independent of session expiry) re-prompting biometric/password; 8-hour absolute session timeout same as web; offline mode uses a short-lived signed offline ticket cryptographically tied to the session, allowing cached record viewing and encounter drafting; sync requires online + valid session.
- **SD-048 (§5.5)** — Backend→worker calls carry `X-Correlation-ID`, `X-Org-ID`, `X-User-ID` and `Authorization: Bearer <internal-service-token>`; the worker validates the token (mTLS or regularly rotated shared secret) and propagates correlation/org/user IDs into its logs and downstream calls.

### 1.7 API Conventions (SD §6)

- **SD-049 (§6.1)** — URL structure: `https://<tenant-slug>.wardenx.app/api/v<version>/<resource>[/<id>][/<subresource>]`. Tenant identity comes ONLY from the resolved subdomain mapped to `organization_id` via the Better Auth session; the backend never trusts URL or body for tenant identity.
- **SD-050 (§6.1)** — API versioning is explicit (`/api/v1`, `/api/v2`); breaking changes increment the version; deprecation overlap minimum **12 months**.
- **SD-051 (§6.2)** — Every error returns the standard envelope: `error.code`, `error.message`, `error.details[] {field, code, message}`, `error.correlationId`, `error.documentationUrl`. Status code semantics fixed: 400 validation/malformed; 401 unauthenticated; 403 authorized-but-forbidden; 404 not-found OR hidden-by-RLS (identical response to avoid info leak); 409 conflict; 422 semantic validation failure; 429 rate limited; 500 internal (always with correlation ID); 503 degraded mode.
- **SD-052 (§6.3)** — Pagination is cursor-based, NEVER offset-based for PHI lists; cursor is opaque base64 of `(last_id, last_sort_value)`; response carries `pagination.next_cursor` + `has_more`.
- **SD-053 (§6.4)** — Every mutating endpoint accepts `Idempotency-Key`; backend stores `(org_id, idempotency_key, response_hash, expires_at)` in Valkey for **24 hours**; same key + same body → cached response; same key + different body → 409.
- **SD-054 (§6.5)** — `?fields=` sparse responses supported; default response is the full canonical representation.
- **SD-055 (§6.6)** — Rate limits: unauthenticated 30 req/min (IP-based); authenticated user 600 req/min (user-based); backend→worker 10,000 req/min (service-to-service); webhook receivers per partner contract with IP allowlist + signature; AI capability calls (Anthropic) per-tenant configured monthly token-budget ceiling. 429 responses include `Retry-After`.
- **SD-056 (§6.7)** — Inbound webhook signing: DoseSpot HMAC-SHA256 body signature (`X-DoseSpot-Signature`); Stripe `Stripe-Signature` (timestamp + HMAC); Twilio `X-Twilio-Signature` HMAC-SHA1 over URL + form params; Postmark DNS-based + bearer token. All webhooks rejected on invalid signature; replay protection via 5-minute timestamp window + payload idempotency key.

### 1.8 Event & Queue Conventions (SD §7)

- **SD-057 (§7.1)** — Socket.IO events follow `<domain>.<action>` naming and target the documented rooms (e.g., `encounter.signed` → `patient:<id>` + `careteam:<patientId>`; `evv.geofence_violation` → `supervisor:<locationId>` + `safety:<orgId>`; `alert.new` → `user:<userId>`; `field_safety.sos` → `safety:<orgId>` urgent).
- **SD-058 (§7.2)** — Room taxonomy is fixed: `user:<userId>`, `careteam:<patientId>` (assigned clinicians + portal caregivers per consent), `location:<locationId>`, `discipline:<orgId>:<discipline>`, `idg:<locationId>`, `billing:<providerEntityId>`, `safety:<orgId>` / `oncall:<providerEntityId>`, `org:<orgId>` (announcements only). Room membership computed at connection time from current memberships + active shifts; updated when shifts change.
- **SD-059 (§7.3)** — BullMQ queue topology with exact parameters: `claim.submit` (high, 5 retries, exponential, concurrency 4); `claim.parse_ack` (high/5/exp/4); `claim.parse_remit` (high/5/exp/4); `noe.submit` (urgent — 5-day regulatory window — 10 retries/exp/4); `intake.process` (normal/3/exp/8); `hope.batch_submit_iqies` (normal/5/exp/2); `idg.build_packets` (low/2/exp/4); `embedding.generate` (low/3/exp/16); `ml.train` (low scheduled/1/–/1); `report.generate` (normal/3/exp/4); `cost_report.ecr_generate` (low/3/exp/2); `notification.deliver` (high/5/linear/16); `audit.archive` (low/3/exp/4); `data_export.subject_access` (low/2/exp/2). Every queue has a DLQ; DLQ entries surfaced in admin console for manual triage.
- **SD-060 (§7.4)** — Job IDs include a deterministic key (e.g., `claim.submit:<claimId>:<attempt>`); workers check job state before executing; retries must be idempotent.
- **SD-061 (§7.5)** — Backend→worker HTTP contract: request carries correlation/org/user headers + bearer service token; response shape `{ok, data, error, duration_ms, model_versions}` (error variant `{ok:false, data:null, error:{code,message}, duration_ms}`). Workers must respond within their declared SLO; backend timeout = SLO + 50%.

### 1.9 Concurrency & Scaling (SD §8)

- **SD-062 (§8.1)** — Backend is stateless: no in-memory sessions, no in-memory locks; N ≥ 2 instances in production behind Pangolin (round-robin or least-connections); `/health` returns 200 only when DB AND Valkey AND MinIO are reachable; graceful shutdown = SIGTERM → stop accepting → drain in-flight → close DB pool → exit.
- **SD-063 (§8.2)** — Socket.IO scales via `@socket.io/redis-adapter` over Valkey; sticky sessions NOT required; clients reconnect with exponential backoff; connection/disconnect events drive presence.
- **SD-064 (§8.3)** — BullMQ workers are separate processes from the API backend; one worker container per queue family; per-queue concurrency per SD-059; multiple replicas allowed (BullMQ distributes); job locks ensure single execution.
- **SD-065 (§8.4)** — Python sidecars: N=1 in dev, 2–4 per worker type in production, behind internal LB (HAProxy or Pangolin internal upstream); stateless except ephemeral file workspace; heavy workers (ml, embeddings) more resources/fewer replicas; light workers (docling, langextract) scale horizontally.

### 1.10 Performance Budgets & SLOs (SD §9)

- **SD-066 (§9.1)** — Endpoint latency budgets (p50/p95/p99): simple read 50/150/300 ms; list query 100/300/600 ms; mutation 100/250/500 ms; HearthNote draft save 80/200/400 ms; HearthNote finalize Layer 1 150/350/700 ms; HearthNote finalize Layer 2 2 s/5 s/10 s; claim validation 500 ms/2 s/5 s; DocLens upload+queue 200/500 ms/1 s; DocLens 50-page processing 60/120/180 s; signed-URL gen 30/80/150 ms; semantic search 200/500 ms/1 s; report generation 500 ms/2 s/5 s.
- **SD-067 (§9.2)** — Web page budgets (FCP/TTI): login 1/2 s; dashboard 1.5/3 s; patient chart 1.5/3 s; encounter note 2/4 s; reporting dashboard 2/5 s.
- **SD-068 (§9.3)** — Mobile targets: cold launch→login 2 s; login→dashboard 3 s; encounter note ready 2 s; EVV check-in tap→confirm 1 s; full encounter flow must work offline without round-trips.
- **SD-069 (§9.4)** — Socket.IO delivery: p95 < 500 ms emit→recipient; p99 < 2 s; reconnect after network blip < 5 s.
- **SD-070 (§9.5)** — Batch completion targets: nightly IDG packet build (50 patients/location) < 30 min total; nightly embedding refresh < 30 min; HOPE batch submission < 5 min per window; ML training < 4 h per model; monthly audit archive < 2 h.
- **SD-071 (§9.6)** — Uptime SLOs (rolling 30 days): Backend API 99.9%; Socket.IO 99.5%; Workers 99%; Database 99.95%; MinIO 99.9%.

### 1.11 Failure Modes, DR & Degraded Operation (SD §10)

- **SD-072 (§10.1)** — Component failure behaviors are prescribed (table in §10.1). Key invariants: total backend outage still permits offline mobile drafting with sync on recovery; PostgreSQL primary failure → manual replica promote, pgBackRest PITR, RTO < 1 h / RPO < 5 min (component-level); Valkey loss → sessions force re-login, queues resume from 5-min-RPO snapshot; MinIO loss → drafting continues (text in DB), documents "temporarily unavailable" with retry; ml-worker down → DocLens falls back to Claude Haiku classifier and predictions hidden with "temporarily unavailable"; Anthropic outage → Layer 2/copilot disabled, Layer 1 continues with degraded-AI banner; x12-worker down → high-priority alert (NOE 5-day window risk) with manual file-generation fallback; MAC portal down → claims queue and auto-resume.
- **SD-073 (§10.2)** — DR targets: RTO 4 hours; RPO 15 minutes (PostgreSQL) / 1 hour (MinIO). Backups: pgBackRest continuous WAL archiving to backup-01, full nightly + incremental every 2 hours; MinIO mirror replication per-bucket; Valkey AOF + snapshots every 15 min; SOPS-encrypted app config in Git; weekly Proxmox VM disk backups. Monthly restore drill: restore PG snapshot to isolated VM, verify integrity, smoke tests, document time.
- **SD-074 (§10.3)** — Degraded mode shows a UI banner driven by the `system_status` table, updated from the ops console.
- **SD-075 (§10.4)** — All external service calls are wrapped in circuit breakers: default 5 failures in 30 s → open 60 s → half-open with 1 test → close on success; per-service configuration; open circuit returns degraded response immediately without blocking.

### 1.12 Observability (SD §11)

- **SD-076 (§11.1)** — Trace propagation: Pangolin injects `X-Request-ID` and W3C `traceparent`; backend root span propagates to Drizzle DB queries, Valkey ops, external HTTP (undici), worker calls, and BullMQ jobs (span links); Python workers continue spans via OTel SDK.
- **SD-077 (§11.2)** — Mandatory span attributes: `tenant.organization_id`, `tenant.provider_entity_id`, `tenant.location_id`, `user.id` (or `system`), `user.role`, `wardenx.module`, `correlation.id`. **PHI never appears in span attributes or names.**
- **SD-078 (§11.3)** — Log lines include correlationId, organizationId, userId, module, trace_id, span_id; patient references logged only as `patient_id_hash`. Pino redact rules: patient names/addresses/phones/MRNs/DOBs never logged plain; patient IDs only as one-way hash with per-environment salt; drug names and dose values never logged; free-text clinical fields never logged; token-bearing config values redacted.
- **SD-079 (§11.4)** — Sentry: self-hosted on obs-01; `beforeSend` PHI scrub; user context limited to userId + organizationId (no email/name); performance sampling 10% prod / 100% dev; PagerDuty routing for `critical` only.
- **SD-080 (§11.5–11.6)** — Required dashboards: System Health, per-tenant Tenant Health, Business Metrics, Claim Pipeline, HOPE Compliance, AI Cost Watch, Worker Performance, Database Health. Alert routing: Critical → PagerDuty 24/7; High → Slack + email; Medium → email; Low → dashboard only.

### 1.13 Build & Deployment Pipeline (SD §12)

- **SD-081 (§12.1)** — CI DAG is mandatory: lint (Biome) + typecheck (tsc) + unit tests (Vitest) → integration tests (Testcontainers PG/Valkey/MinIO) → **RLS isolation tests (cross-tenant denial)** → build Docker images → Playwright e2e → SBOM (CycloneDX artifact) → PR mergeable. On main: re-run CI, publish to GHCR, semver tag, deploy staging, smoke tests, MANUAL APPROVAL gate, blue-green production deploy, post-deploy synthetic verification.
- **SD-082 (§12.2)** — Image standards: multi-stage Dockerfiles; base `node:22-bookworm-slim` (TS) / `python:3.12-slim` (Python); distroless final where feasible; tags `<service>:<git-sha>`, `:<branch>`, `:latest` (main only); cosign signing with verification on deploy; SBOM attached as manifest annotation.
- **SD-083 (§12.3)** — Migrations: Drizzle in `packages/db/migrations/`; forward-only, never destructive in the same release; two-phase breaking changes (N: nullable column + dual-write; N+1: backfill + switch reads; N+2: drop old); migration runner as init container before backend rollout; `down` migrations are emergency-only (prefer roll-forward).
- **SD-084 (§12.4–12.5)** — Blue-green mechanics: new version registered at weight 0%; health 200 for 60 s required; ramp 5% → 25% → 50% → 100% over 5 minutes; old version drains in parallel; after 10 min clean, old containers stop; rollback path (old containers resident) kept 1 hour after cutover. Auto-rollback on error-rate spike > 5% within 10 min of cutover; non-rollbackable DB migrations are forward-fix-only via hotfix.
- **SD-085 (§12.7)** — Pre-commit (lefthook): Biome check, typecheck, related tests; pre-push: full test suite.

## 2. SECURITY CRITERIA (SEC-###)

### 2.1 Principles & Governance (SEC §1–2)

- **SEC-001 (§1.4)** — Five binding principles: (1) defense in depth — no single control trusted as sufficient; (2) least privilege for every identity (human, service, role); (3) privacy by design — PHI defaults most-restrictive, data minimization in collection/retention/disclosure; (4) **fail closed** — security-check failure denies access, never default-allow on error; (5) auditable and verifiable — every privileged action logged, every control testable.
- **SEC-002 (§1.2/1.3)** — This document is the threat-and-control layer; ops procedures live in OPS_RUNBOOK, AI governance in AI_GOVERNANCE, vendor reviews in INTEGRATIONS. Module specs must not redefine these layers.
- **SEC-003 (§2.1)** — Defined security roles: Security Owner, Compliance Officer, Vulnerability Manager, Incident Responder, Penetration Tester (Phase 2 requirement), Bug Bounty Triage (future). Currently consolidated in Fabrice with documented future-state separation.
- **SEC-004 (§2.2)** — Decision authority matrix is binding: threat-model changes — Security Owner; crypto standard changes — Security Owner; new external integration with PHI exposure — Security Owner + Compliance (customer-signed BAA); vuln-remediation timeline waiver — Security Owner; break-glass usage — Security Owner + Compliance after the fact; incident classification — Incident Commander; pentest remediation priority — Security Owner.
- **SEC-005 (§2.3)** — Documentation hierarchy: Architecture/SystemDesign → Security Hardening → module-spec §6 Permissions → code/infrastructure → tests/audits. Module specs sit BELOW this document.
- **SEC-006 (Appendix A.3)** — Security Owner approval is ALWAYS required for: changes to authentication mechanism; changes to authorization model; changes to cryptographic standards; new vendor with PHI access; granting `platform_ops` to a new individual; break-glass use; disabling any security control even temporarily. A module spec proposing any of these without that approval path is non-compliant.

### 2.2 Threat Model Controls (SEC §3)

- **SEC-007 (§3.1)** — STRIDE is the mandatory threat-modeling framework at platform level AND per module; every module spec must document its top STRIDE threats (the §3.4 table lists expected top threats per module — auditors should check the module spec addresses at least these).
- **SEC-008 (§3.2.1)** — Cross-tenant isolation is a six-layer defense: (1) database RLS on every PHI table (`organization_id = current_setting('app.org_id')`); (2) application authorization (Module 3 RBAC+ABAC); (3) session binding to `active_organization_id` (not client-manipulable); (4) `wardenx_app` role RLS even under app bugs; (5) audit of every PHI access with org context, RLS denials logged as `security.rls_denied` (~zero expected in production); (6) Prometheus `rls_denials_total` alerting at ANY nonzero rate.
- **SEC-009 (§3.2.1)** — Validation requirements: automated RLS isolation test suite required in EVERY module spec; manual code review of `organization_id` handling on every PHI-touching PR; annual cross-tenant penetration test (Phase 2).
- **SEC-010 (§3.2.2, §13.1)** — Audit immutability: `wardenx_app` has INSERT + SELECT only on `audit_event` (UPDATE/DELETE never granted); append-only schema partitioned by `created_at` with no application path to modify history; elevated access to the audit table itself emits meta-event `audit.elevated_access`; pgBackRest backups encrypted and retained **7+ years** as tamper cross-reference; cryptographic hash chain is a future (Phase 3) enhancement.
- **SEC-011 (§3.2.2)** — Audit-integrity validation: test that `wardenx_app` UPDATE/DELETE on `audit_event` fails with permission error; quarterly random sample of 100 audit events compared to backup; monthly review of all `audit.elevated_access` events.
- **SEC-012 (§3.2.3)** — Account-takeover controls: 12-char minimum passwords with breach-corpus check; 2FA required for clinical roles (TOTP preferred, SMS fallback for accessibility, passkey/WebAuthn preferred highest assurance); session controls per SEC-027; suspicious-activity detection (new geography/device, off-hours) triggers re-auth + alert; lockout thresholds per SEC-033; passkeys REQUIRED for `platform_ops` and `org_admin`; account recovery never restorable solely via email link.
- **SEC-013 (§3.2.4)** — Privilege-escalation controls: server-side authorization always (never client-trusted); Module 3 RBAC+ABAC with server-side predicate evaluation using server-controlled context; every membership change emits `membership.role_changed` audit; users CANNOT modify their own membership roles (org_admin required); every module spec must include authorization test cases (each role gets expected access, each role denied unexpected access, edge cases); RLS as backstop.
- **SEC-014 (§3.2.4)** — Escalation validation: code review of explicit authorization on every new endpoint; custom Biome lint rule for missing authorization decorators; integration tests covering every role × action combination; pentest privilege-escalation attempts.
- **SEC-015 (§3.2.5)** — PHI-disclosure-via-external-services controls: Pino redact list; Sentry `beforeSend` scrub; OTel span attribute filter (IDs/codes/hashes only); **PHI in URLs prohibited** (UUIDs OK); error messages generic to client with detail only in scrubbed logs; Anthropic PHI minimization per AI governance; Anthropic Zero Data Retention when contractually available; BAA inventory current for every PHI-exposed vendor (tracked in INTEGRATIONS).
- **SEC-016 (§3.2.5)** — Disclosure validation: unit tests for Pino redaction with PHI-bearing payloads; quarterly Sentry-event sample review for accidental PHI; quarterly Anthropic API log review for minimization compliance; BAA tracking in vendor management review.
- **SEC-017 (§3.2.6, §19)** — Insider-threat controls: tightly scoped `platform_ops` with break-glass extra step; separation of duties (backup keys and encryption keys held separately; no single individual can unilaterally access all data); all admin actions audited with retention class `compliance` (6+ years); quarterly access review; departing-employee revocation within 1 hour; anomaly detection on bulk exports/off-hours/unusual patterns; background checks for engineering hires (§164.308(a)(3)); documented workforce sanctions policy (§164.308(a)(1)(ii)(C)).
- **SEC-018 (§3.2.7)** — Supply-chain controls: pinned dependency versions with Renovate PRs (reviewed); SBOM (CycloneDX) in CI attached to image manifests; cosign image signing with deploy verification; dependency scanning blocking merge on Critical CVEs; container scanning (Trivy/Grype); vendor BAA + security review for every PHI vendor; network segmentation limiting vendor blast radius.
- **SEC-019 (§3.2.8)** — DoS controls: edge rate limiting (Phase 1 Pangolin; Phase 2 CDN + DDoS protection); per-route/per-user rate limits (SD-055); server-enforced query timeouts; per-tenant resource quotas (bulk-export limits, request rates, AI token budgets); graceful degradation sheds non-critical features (AI, reporting) before clinical features.
- **SEC-020 (§3.2.9)** — AI-specific threat controls (cross-reference to AI governance, but binding here): deterministic Layer 1 always available; LLM never trusted with factual changes (hard block on med/vital/code changes); prompt-injection detection and rejection; PHI minimization in prompts; output validation against authoritative sources; human-in-loop for safety-critical outputs.
- **SEC-021 (§3.3)** — Threat model reviewed quarterly and updated on: new module with novel attack surface, new PHI vendor, post-incident unmodeled vector, regulatory change.

### 2.3 Cryptographic Standards (SEC §4)

- **SEC-022 (§4.1)** — Approved algorithms (NIST SP 800-131A): symmetric AES-GCM or AES-CBC+HMAC at 256-bit; asymmetric RSA-OAEP (≥3072) / ECDH P-256; signatures RSA-PSS (≥3072), ECDSA P-256, Ed25519; password hashing Argon2id (m=64 MB, t=3, p=4) preferred or bcrypt cost 12; HMAC-SHA-256/512; OS CSPRNG only; TLS 1.3 preferred (TLS 1.2 only with strict suites for interop). **Prohibited:** MD5 for security, SHA-1 signatures, DES/3DES, RC4, TLS ≤1.1, custom cryptographic algorithms.
- **SEC-023 (§4.2)** — Encryption at rest, per data type: PostgreSQL data files — LUKS full-disk (key in Proxmox TPM; break-glass copy sealed offline); pgBackRest backups — AES-256-CBC with **three independent keys per backup repo**; MinIO — SSE-S3 with site key derived from master in secure enclave, **rotated annually**; compliance-locked buckets additionally object-locked; Valkey AOF/snapshots — LUKS per VM; secrets in Git — SOPS with age (per-environment age key; backups in sealed envelopes); TLS private keys — filesystem ACL mode 0400 owned by service user; `tax_id`/`ssn` — pgcrypto field-level encryption with site key **rotated annually**; stored vendor tokens (DoseSpot, OAuth refresh) — field-level encryption with site key.
- **SEC-024 (§4.3)** — Encryption in transit per hop (matches SD-009) plus: PG primary→replica replication TLS 1.3 (private CA). HSTS on all customer-facing endpoints: `max-age=63072000; includeSubDomains; preload`, submitted to the preload list. TLS 1.2 fallback restricted to ECDHE-{ECDSA,RSA}-AES256-GCM-SHA384 and ECDHE-{ECDSA,RSA}-CHACHA20-POLY1305; all non-PFS/non-AEAD suites disabled.
- **SEC-025 (§4.4)** — Hashing/KDF rules: passwords Argon2id (bcrypt cost 12 fallback for migration); session tokens are 256-bit CSPRNG values stored as SHA-256 hashes; idempotency keys stored as SHA-256 of `(org_id, key, body)`; backup files and documents integrity-hashed with SHA-256.
- **SEC-026 (§4.5–4.7)** — Key hierarchy: root keys (backup masters ×3, SOPS age private key, private-CA root, field-encryption master) offline/sealed and NEVER on production systems; operational keys (LUKS keyslots, per-tenant MinIO keys, per-service mTLS, Better Auth session signing secret, JWT service-token keys, webhook HMAC keys) in secret stores with bounded blast radius. RNG: `crypto.randomBytes()/randomUUID()`, `gen_random_uuid()/gen_random_bytes()`, Python `secrets` only; `Math.random()`, custom PRNGs, predictable seeds prohibited. Crypto code: vetted libraries only; no custom primitives; all crypto code reviewed by Security Owner; `crypto.timingSafeEqual` for secret comparisons; per-message CSPRNG IVs/nonces never reused; authenticated encryption (GCM/AEAD) always.

### 2.4 Authentication & Sessions (SEC §5)

- **SEC-027 (§5.1.4, Doc Control note)** — Session policy (reconciled in v0.2; all timeouts derive from one `SESSION_POLICY` constant): session ID 256-bit CSPRNG; storage DB (canonical) + Valkey (hot cache); cookie HttpOnly, Secure, SameSite=Strict, Path=/, signed; CSRF token required for all state-changing requests (double-submit pattern); **idle timeout 15 minutes for ALL clinical sessions** (mobile biometric re-auth); absolute timeout 8-hour work-session / **24-hour maximum**; UI screen-lock is a separate 5-minute soft re-auth; concurrent sessions allowed but trackable and user-terminable; session binding to IP prefix + user-agent (loose match for mobile carrier IP changes); logout = server-side invalidation clearing Valkey + marking DB; "sign out everywhere" available.
- **SEC-028 (§5.1.1–5.1.2)** — Factor requirements by role: `platform_ops` — password + passkey (preferred) or password + TOTP, passkey strongly recommended; `org_admin` — password + TOTP minimum (passkey preferred); `clinical_*` — password + TOTP (required at first sign-in setup); `field_staff` — password + TOTP (SMS allowed for accessibility, per agency policy); `patient_portal_user` — password, 2FA optional but strongly recommended; `external_collaborator` — single-use, time-bound magic link + email verification. SMS is fallback-only and being phased out per NIST SP 800-63B.
- **SEC-029 (§5.1.3)** — Password policy (NIST SP 800-63B): minimum 12 characters; maximum no lower than 64; all printable ASCII + Unicode allowed; NO composition rules; breach-corpus check (HaveIBeenPwned k-anonymity) on creation and change; top-10,000 common password rejection; NO password expiration; account-bound rate limiting.
- **SEC-030 (§5.1.5)** — Account lifecycle events must produce audit + notification per the table: e.g., email change audited with before/after + emails to BOTH old and new addresses; password change audited (no values) + email + re-auth; 2FA disable → email + admin alert + re-auth + extended grace check; reactivation → re-auth on first use.
- **SEC-031 (§5.1.6)** — Account recovery: enumeration-safe generic response; time-limited (15-minute) magic link; second-factor (TOTP) or security-question gate at link click; new password meets creation rules; ALL existing sessions invalidated; audit + email. High-privilege roles (platform_ops, org_admin) require out-of-band identity verification.
- **SEC-032 (§5.1.7)** — External-collaborator magic links: single-use, time-limited (30 min–24 h by scope); scope embedded in link signature; recipient verified via known email/phone; session limited to that scope with no escalation; full audit; invalidatable by issuing org_admin.
- **SEC-033 (§5.3.1, §3.2.3)** — Brute-force/credential-stuffing thresholds: 5 failed attempts per username per 10 min → 15-min lockout; 30 failed attempts per IP per 10 min → temporary block; captcha (invisible Turnstile preferred) after 3 failed attempts; velocity monitoring across accounts triggers defensive mode (mandatory captcha for all).
- **SEC-034 (§5.2, §5.3.2–5.3.3)** — Session-theft defenses: token rotation on privilege escalation; re-authentication for sensitive actions (export, role change, password change); same-session-from-two-IPs → forced re-auth; mobile biometric re-auth on foreground after 15 min; session list + per-session revocation. Phishing: HSTS preload; DMARC/SPF/DKIM; passkeys for high-privilege; annual workforce training (§164.308(a)(5)); ChartWarden emails link only to `*.wardenx.app`. Token storage: HttpOnly cookies; NEVER `localStorage`/`sessionStorage` (lint-blocked); mobile SecureStore only.

### 2.5 Authorization (SEC §6)

- **SEC-035 (§6.1)** — Three independent authorization layers: RBAC (coarse, Module 3, roles in code + DB), ABAC (fine, server-side predicates), RLS (database org-context enforcement). Application authorization is the primary gate; RLS is the backstop. **A single layer failing must not cause data exposure.**
- **SEC-036 (§6.2)** — Every API endpoint MUST: (1) declare explicit authorization in the route definition (role + ABAC predicate via `preHandler` chain: `authenticate`, `requireRole`, `requireAbac`); (2) return 401 unauthenticated; (3) return 403 unauthorized; (4) not leak resource existence (404 vs 403 discipline); (5) log authorization decisions to audit at appropriate severity. Handlers performing PHI access run inside `withOrgContext`.
- **SEC-037 (§6.3)** — Bypass defenses: frontend role-hiding is cosmetic only — server independently authorizes every request; object-level authorization on every `:id` route (authorization to THAT resource, not the type); IDOR testing on every PR adding a resource endpoint (enumerate IDs, attempt as unauthorized user, verify 403/404); authorization predicates belong in `WHERE` clauses, not fetch-then-filter.
- **SEC-038 (§6.4)** — Privileged operations (org_admin minimum, audit + notification, often step-up re-auth): role changes; patient record exports (DSAR, portability); bulk operations; feature flag changes; tenant configuration changes; external collaborator invitations; magic-link issuance; proxy signing for others; validation-rule overrides. All audited at `severity=warn` or `critical` and notified to org_admin/platform_ops.
- **SEC-039 (§6.5)** — Service-to-service: mTLS identifies the calling service AND a short-lived (minutes), signed bearer token authenticates the specific request carrying correlation/org/user context; workers verify BOTH before processing.

### 2.6 Network Security (SEC §7)

- **SEC-040 (§7.1)** — Trust-zone table is binding (mirrors SD-022); critical invariant: **Data zone has NO Internet egress** — exfiltration must pivot through the App zone where audit/monitoring catch it.
- **SEC-041 (§7.2)** — Firewall posture: default deny, explicit allow per rule, documented in `infra/firewall/rules.yaml`; outbound App-zone HTTP restricted to known vendors (e.g., `api.anthropic.com:443`).
- **SEC-042 (§7.3)** — Network monitoring: Pangolin access logs to Loki; nft accounting (NetFlow equivalent); IDS (Suricata) Phase 2 (Phase 1: manual log review); anomaly detection on unusual egress (esp. Data-zone→Internet attempts), inbound patterns, connection-volume spikes.
- **SEC-043 (§7.4)** — Edge protection: Phase 1 Pangolin rate limiting per IP/route + known-abuse patterns; Phase 2 Cloudflare-class CDN, OWASP Top 10 WAF rules, network-edge DDoS protection, geo-blocking if appropriate.
- **SEC-044 (§7.5)** — DNS controls: DNSSEC (Phase 2); CAA records restricting permitted CAs; TTLs 60 s for failover-critical / 300 s stable; DMARC reject policy after SPF/DKIM verified; SPF allow-list of Postmark sending IPs; per-environment DKIM keys.
- **SEC-045 (§7.6)** — Internal mesh: all backend↔worker traffic mTLS; service discovery via internal DNS (10.10.X.X); no service exposes ports outside its trust zone; health endpoints on internal-only ports.

### 2.7 Data Security & PHI Handling (SEC §8)

- **SEC-046 (§8.1)** — Six data classes: PHI-Critical (strictest — encryption everywhere, minimum-necessary, audit every access); **PHI-Sensitive (42 CFR Part 2 SUD records, mental health, HIV status, abuse history — additional controls beyond standard PHI)**; Confidential; Restricted; Internal; Public. Module specs must classify their data and apply the matching handling tier; SUD/Part 2 data must be flagged PHI-Sensitive (see OPEN-022 — the specific extra controls are not enumerated in the source docs; module specs proposing Part 2 data must define them and cannot treat Part 2 data as ordinary PHI).
- **SEC-047 (§8.2.1–8.2.4)** — PHI lifecycle rules: collect only what the documented purpose requires, with purpose documented at point of collection and consent captured where required (Module 39); access need-to-know via RBAC+ABAC with every access audited (Module 4) and minimum-necessary querying; disclosure internal per authorization model (audited), external per consent + technical safeguards, to business associates ONLY via signed BAA; retention per Architecture §24 with destruction certification (§164.310(d)(2)(i)) via cryptographic erasure (keyed data) or secure deletion.
- **SEC-048 (§8.2.5)** — PHI-in-special-contexts table is binding: never PHI in plain logs (Pino redact); never PHI in OTel span names/attributes; Sentry `beforeSend` redaction; Anthropic prompts per AI governance minimization; never PHI in email subject lines (generic only); email body minimal PHI with full chart only via authenticated portal link; **never PHI in push-notification bodies** ("You have a new message" + link); never PHI in SMS bodies; URLs may carry resource UUIDs but never names/MRNs/DOBs; never PHI in browser console (lint-blocked); never PHI in backup file names (UUIDs/timestamps only).
- **SEC-049 (§8.3)** — Data minimization: endpoints return only requested/needed fields; field-level access controls within authorized records (e.g., SSN visible to billing role only); bulk operations return summaries unless full records explicitly needed; background jobs use minimum-necessary projections.
- **SEC-050 (§8.4)** — De-identification for analytics/research/AI training: HIPAA Safe Harbor (18 identifiers removed) or Expert Determination (qualified statistician); anonymized datasets segregated from identifiable data with controlled-access recombination; ChartWarden AI improvement (e.g., HearthNote drift monitoring) uses de-identified data only or operates within tenant scope — **never cross-tenant pooled**.
- **SEC-051 (§8.5.1)** — PHI export types and authorization: single clinical record — RN/MD/admin in tenant, audit `phi.exported`; patient DSAR — org admin or DSAR officer with identity verification first, `phi.dsar_fulfilled`; tenant migration export — org admin + ChartWarden support, `phi.tenant_export`; bulk research export — org admin + IRB documentation + research consent (Module 39) + de-identification step, `phi.research_export`; analytics dataset — platform_ops only, de-identified only, `phi.analytics_export`.
- **SEC-052 (§8.5.2)** — Bulk-export workflow (any export >10 records): free-text justification; approving authority recorded; rate limit 1 export per hour per user; size limit 10,000 records default (exceeding requires elevated approval); file encrypted at rest in `tenants/<org>/exports/`; download tracked (who/when/IP); time-limited download URL (24 hours); auto-delete after 7 days; audit severity=warn moderate / severity=critical for >1,000 records.
- **SEC-053 (§8.6)** — Cross-tenant isolation validation: per-module RLS isolation test suite; CI blocks merge on RLS test failure; quarterly random sample of 100 queries verified RLS-policy-evaluated; Phase 2 pentest cross-tenant attempts.
- **SEC-054 (§8.7)** — PHI in backups: encrypted with keys not on production systems; backup access requires `wardenx_admin` + break-glass; restores audited severity=warn; test restores to sandbox verify decryption + integrity.

### 2.8 Application Security (SEC §9)

- **SEC-055 (§9.1.1–9.1.2)** — Secure SDLC design/implementation: threat modeling for every new module; security review for any PHI-touching module; ADR for security-affecting architecture decisions. Mandatory implementation patterns: `withOrgContext()` for PHI queries; typed error classes (no string throws); idempotency keys on mutations; authorization decorators on every route; audit emission for state changes.
- **SEC-056 (§9.1.3)** — Security Owner review REQUIRED for PRs touching: authn/authz changes; new PHI endpoints; new external integrations; logging/observability changes; cryptographic code; RLS policy changes; migrations modifying access controls.
- **SEC-057 (§9.1.4–9.1.5)** — Required security testing: unit tests for security logic; Testcontainers integration tests; RLS isolation tests; E2E security flows (login, MFA, session timeout); load tests with security observability; input-validation/injection/IDOR tests. Pre-deploy: all security scans pass; SBOM generated and signed; cosign-signed containers; vuln scan within tolerance.
- **SEC-058 (§9.2)** — SAST: Biome with custom security rules (no `eval`, no `Math.random` for security, RLS-context-required pattern rule); Semgrep (Phase 1 manual, Phase 2 CI); CodeQL (Phase 2 CI). Finding gates: Critical blocks merge; High blocks merge absent explicit Security Owner waiver; Medium triaged before merge (deferrable with ticket); Low tracked.
- **SEC-059 (§9.3)** — SCA: npm/bun audit in CI; Snyk or Dependabot advisories; Renovate updates; Trivy/Grype image scanning. CVE patch SLAs: Critical (CVSS ≥9.0) 72 hours; High (7.0–8.9) 7 days; Medium (4.0–6.9) 30 days; Low (<4.0) next minor release.

- **SEC-064 (§9.6.3–9.6.5)** — XSS: React escaping + DOMPurify for any user HTML (rich-text notes) + CSP. CSRF: SameSite=Strict + double-submit token + Origin/Referer validation. Storage: session tokens never in localStorage/sessionStorage (lint-blocked); Capacitor SecureStore only.
- **SEC-065 (§9.7)** — API security baseline: explicit `/api/v1/` versioning; rate limits per SD-055; **request size limit 10 MB default** (larger only on specific upload routes with explicit limits); TypeBox validation of every request AND response body; idempotency keys on mutations; webhook signature verification on all inbound webhooks.

### 2.9 Container & Image Security (SEC §10)

- **SEC-066 (§10.1)** — Image build standards: distroless runtime base (no shell/package manager); `USER nonroot:nonroot`; no secrets in images (runtime injection only); multi-stage builds; base images pinned by digest (never `:latest`); minimum packages.
- **SEC-067 (§10.2)** — Image signing: CI cosign-signs every image on push to main; production deploy verifies signature before pull; signing key in HSM/KMS (currently GitHub Actions OIDC keyless).
- **SEC-068 (§10.3–10.4)** — SBOM: CycloneDX via syft in CI, attached as manifest annotation, stored as build artifact, reviewed monthly for new high-CVE components, provided to customers on request. Trivy scan gates: CRITICAL or HIGH in production image blocks merge; MEDIUM requires triage; LOW tracked.
- **SEC-069 (§10.5–10.6)** — Runtime: `--read-only` filesystem where possible with writable mounts limited to `/tmp`/log paths; `--cap-drop=ALL` with specific `--cap-add`; `--security-opt=no-new-privileges`; egress-restricted networking; per-service CPU/memory limits. Lifecycle: production images retained 1 year in GHCR; EOL base images not used; vulnerable tags removed.

### 2.10 Infrastructure & Host Security (SEC §11)

- **SEC-070 (§11.1)** — CIS baselines: Ubuntu Server CIS, PostgreSQL CIS, Docker CIS, Proxmox community best practices; enforced by Ansible at provisioning; automated weekly compliance check in audit mode; deviations require Security Owner approval with documented rationale.
- **SEC-071 (§11.2)** — Host hardening checklist per production VM: SSH key-only with allowed users; default-deny firewall; automatic security patches (unattended-upgrades); AIDE file-integrity monitoring on critical paths; auditd; rsyslog→Loki; NTP/chrony; CIS sysctl hardening; unused services disabled; `noexec,nosuid,nodev` mounts where applicable; ulimits.
- **SEC-072 (§11.3–11.4)** — SSH: all access via bastion (`wardenx-bastion-01`); per-engineer keys (no shared), hardware-backed (YubiKey) where possible; bastion records sessions (retained per Ops Runbook §16.1); annual key rotation; production VM SSH disabled except from bastion network. Sudo: auditd-audited; no NOPASSWD in production; time-bound grants where possible.
- **SEC-073 (§11.5–11.6)** — EDR: Phase 1 none (compensating: distroless, hardened hosts, segmentation, audit-based detection); Phase 2 commercial EDR on PHI hosts; Phase 3+ XDR/SIEM. Drift: weekly Ansible check-mode; findings require explanation (documented planned change OR unauthorized → investigation); auto-remediation only for known-safe drift.

### 2.11 Mobile Device Security (SEC §12)

- **SEC-074 (§12.2)** — Device posture gates for the app to run: iOS 16+ / Android 12+; no jailbreak/root (app refuses on compromised devices and emulators); biometric available; OS screen lock enabled; SecureStore/EncryptedSharedPreferences supported.
- **SEC-075 (§12.3.1)** — Mobile data at rest: session/refresh tokens + biometric secret in SecureStore (hardware-backed Keychain / Keystore-backed EncryptedSharedPreferences); offline encounter drafts in encrypted SQLite (sqlcipher); cached patient context encrypted and evicted on logout; photos encrypted in sandbox, deleted after upload.
- **SEC-076 (§12.3.2–12.3.3)** — Mobile auth: biometric required at launch; re-prompt after 15-minute idle and on foreground if previous foreground >15 min ago; failed biometric → password fallback; **5 failed biometric attempts → app sign-out**. Server-enforced session: 15-min idle, 8-hour work-session, 24-hour absolute.
- **SEC-077 (§12.3.4–12.3.6)** — Screen capture: iOS `UIScreen.isCaptured` listeners with warning/obfuscation; Android `FLAG_SECURE` on PHI activities. Certificate pinning to specific cert/CA via Capacitor Network config, updated on rotation. Anti-tamper: release-build obfuscation (R8 / Swift), native integrity checks at launch, backend-signed critical responses.
- **SEC-078 (§12.4)** — Jailbreak/root/emulator detection (RootBeer/IOSSecuritySuite-equivalent) blocks the app; acknowledged as defense-in-depth (not infallible) combined with server-side anomaly audit.
- **SEC-079 (§12.5)** — Lost/stolen device: user can sign out per-device, sign out everywhere, and forget device; org_admin can view active sessions with device fingerprint + last activity, revoke specific sessions, and lock the user (sign-out-everywhere + forced password reset). MDM remote wipe of app data is Phase 3.
- **SEC-080 (§12.7–12.8)** — Mobile audit adds device fingerprint (model, OS), app version, connection state (online/offline at action time), and geofence status (EVV). Update cadence: security patches force-updated within **7 days**; critical features within 30 days; standard opt-in; mechanism = backend returns minimum-app-version in API responses.

### 2.12 Audit Security (SEC §13)

- **SEC-081 (§13.1)** — Audit integrity control set: DB-layer append-only (INSERT/SELECT-only grants); architectural append-only (no code path modifies history); partition immutability (partitions detached for archival, never modified); pgBackRest backups as tamper cross-reference; meta-audit of elevated audit-table access; hash-chain seal planned Phase 3.
- **SEC-082 (§13.2)** — Audit completeness invariant: EVERY PHI access and EVERY state change produces an audit entry, via the `audit()` helper in `packages/db/src/audit.ts`; service-layer pattern calls `audit()` before commit; enforced by code review, a custom lint rule flagging PHI-table mutations without a nearby `audit()` call, and integration tests verifying expected emission.
- **SEC-083 (§13.3)** — Audit review cadence: daily automated real-time alerting of high-severity events; weekly on-call anomaly summaries; monthly Compliance Officer random sample of high-risk events (admin actions, exports, RLS denials); quarterly cross-category pattern review; annual external audit-of-audit when SOC 2 sought.
- **SEC-084 (§13.4.1)** — Monitored anomaly patterns (exact thresholds): any export >100 records flagged; access 22:00–06:00 local agency time flagged; login from a country not seen in past 90 days flagged; ANY nonzero RLS denial rate alerted; every platform_ops/org_admin privilege use logged + reviewed; per-user API rate spikes; same-user concurrent sessions from different IPs → flagged for re-auth.
- **SEC-085 (§13.4.2)** — Anomaly detection implemented (Phase 2) as scheduled BullMQ jobs over Module 4 data, emitting `security.anomaly_detected` events with per-rule severity, routed to ops + compliance.

### 2.13 Vulnerability Management (SEC §14)

- **SEC-086 (§14.1–14.2)** — Sources: CVE feeds (Snyk/Dependabot), GHSA, vendor bulletins, CISA KEV catalog, internal findings. Triage/remediation SLAs: Critical (CVSS ≥9.0) or KEV — same-day investigation, emergency patch if exploitable, remediate within 72 hours; High — 1-business-day investigation, 7 days; Medium — 1-business-week investigation, 30 days; Low — next release. Severity may be downgraded only for network isolation or compensating controls, with documented justification reviewed quarterly.
- **SEC-087 (§14.3)** — Patch process must end with a security-log entry: CVE/advisory ID, description, affected component, remediation, verification, sign-off.
- **SEC-088 (§14.4)** — Inbound disclosure: `security@wardenx.app` with published PGP key; acknowledge within 24 hours; remediate per SLA; coordinated disclosure standard 90 days; reporter credit with consent.

### 2.14 Penetration Testing (SEC §15)

- **SEC-089 (§15.1)** — Cadence: pre-launch manual exploratory only; Phase 1 (Engrace go-live) one-time external pre-launch pentest; Phase 2 annual full + quarterly targeted; Phase 3 continuous bug bounty + annual + targeted on major releases.
- **SEC-090 (§15.2)** — Mandatory scope: external attack surface; web app (OWASP Top 10, business logic, authn/authz); mobile binaries/runtime/network; full `/api/v1/` surface incl. IDOR and injection; explicit cross-tenant isolation attempts; privilege escalation; **AI features (prompt injection, data exfiltration via AI)**. Out of scope: physical security, social engineering of customer staff, DDoS testing.
- **SEC-091 (§15.3–15.4)** — Remediation: Critical/High before next annual cycle with retest within 30 days of remediation; Medium prioritized in backlog with planned timeline; Low batched; annual full retest.

### 2.15 Security Incident Response (SEC §16)

- **SEC-092 (§16.1–16.3)** — Security-incident scope: suspected unauthorized access, PHI exposure, compromised credential, malicious code, insider threat, vendor incident, ransomware. Triage tree: confirmed/strongly-suspected PHI exposure → SEV-1 with HIPAA breach assessment and **counsel engaged within 1 hour**; confirmed unauthorized access → SEV-1/2 by scope; system-integrity compromise → SEV-1; vulnerability without exploit → §14 triage.
- **SEC-093 (§16.4–16.6)** — Containment preserves forensics (disconnect network rather than shut down); immediate credential revocation; attacker-IP edge block; logs from affected period archived separately. Investigation: forensic preservation before remediation, scope, root cause, impact, attribution. Recovery: remove vulnerability, restore from clean backups if needed, **reissue every credential touched by the incident**, verify clean before production.
- **SEC-094 (§16.7)** — Notification duties: internal per severity; customer per BAA terms and HIPAA breach rule; **regulator per HIPAA breach rule 60-day window**; law enforcement (FBI/IC3) for criminal activity; public disclosure coordinated with reporter.
- **SEC-095 (§16.8)** — Post-incident review within 7 days of resolution: timeline, what worked/didn't, action items with owners/dates, threat-model and control updates, customer-facing PIR for SEV-1s affecting customers.
- **SEC-096 (Appendix A.2)** — Severity quick-reference is binding: confirmed PHI exposure SEV-1; suspected unauthorized PHI access SEV-1; single-user account takeover SEV-2 (many users SEV-1); unpatched Critical CVE in production SEV-2; vendor incident with PHI implications SEV-1; suspected insider threat SEV-1; cross-tenant access attempt SEV-2→SEV-1 by success; suspected audit tampering SEV-1.

### 2.16 Break-Glass (SEC §17)

- **SEC-097 (§17.1–17.2)** — Break-glass credentials: `postgres` superuser; `wardenx_admin` outside migration-runner context; MinIO root; SSH bypassing bastion; off-site SOPS age key; pgBackRest off-site repo credentials. Authorization per table (Security Owner, plus Incident Commander for `postgres` during incidents; secondary holder for the age key); required documentation: reason, expected duration, planned actions (envelope inventory check for the age key).

Routine use prohibited. Monthly Compliance review + quarterly forensic-detail Security Owner review.

Ongoing: annual HIPAA refresher; annual security awareness; quarterly access review; phishing simulation (quarterly when team grows).

## 3. AI GOVERNANCE CRITERIA (AI-###)

### 3.1 Principles (AI §1–2)

- **AI-001 (§1.1)** — Positioning invariant: AI is augmentation, not replacement. The deterministic core (HearthNote Layer 1, DocLens review workflow) ALWAYS operates without AI; AI layers on with clinician verification gates.
- **AI-002 (§2.1.1)** — Clinical Safety First: if AI failure could harm a patient, AI is augmentation only — deterministic fallback for every clinically-touching AI capability; HITL gates for safety-critical outputs; **hard blocks on AI-introduced changes to medications, vitals, and codes**; explicit clinician acknowledgment for AI-suggested clinical interventions.
- **AI-003 (§2.1.2)** — Patient autonomy: tenant-level opt-in (default OFF); per-patient consent where appropriate (e.g., portal AI); AI-generated content visibly labeled in the clinical record ("AI-assisted narrative — reviewed by RN Smith"); patient access to information about AI use via portal disclosures.
- **AI-004 (§2.1.3)** — Transparency: every AI output records capability, model version, prompt version, inputs (PHI-aware), output; source attribution where applicable (DocLens shows source document/page per field); confidence scores surfaced for verification-worthy outputs; "why did the AI say this?" answerable via provenance for every output.
- **AI-005 (§2.1.4)** — Privacy minimization: field-level prompt minimization; Anthropic ZDR where contractually available; patient identifiers excluded from prompts where the capability functions without them; pre-prompt redaction of identifiers in free text where feasible.
- **AI-006 (§2.1.5)** — Continuous validation: drift monitoring against benchmarks; clinician flag-as-wrong/harmful feedback loops; periodic held-out re-evaluation; quarterly AI capability review.
- **AI-007 (§2.1.6)** — Reversibility: per-capability kill switch (Module 1 §13.7); tenant opt-out always available; per-clinician opt-out; model-version rollback procedure; AI content marked for retrospective re-evaluation.
- **AI-008 (§2.2)** — Explicit rejections (module specs violating any of these are non-compliant): autonomous clinical decision-making by AI (regardless of benchmark accuracy); hidden AI use; one-shot deployment without evaluation/monitoring/review cadence; relabeling deterministic logic as "AI-powered."

### 3.2 Roles & Decision Authority (AI §3)

- **AI-009 (§3.1, §3.3)** — Roles: AI Safety Owner, Clinical Reviewer, AI Engineer, Privacy Officer, CS/AI Liaison. Decision matrix is binding: new capability ships only with AI Safety Owner + Clinical Reviewer + Privacy Officer approval; kill switch — AI Safety Owner or on-call IC (compliance review after); model version upgrade — AI Engineer with AI Safety Owner sign-off after re-evaluation (Clinical Reviewer for clinical capabilities); prompt template change — AI Engineer with AI Safety Owner approval (Clinical Reviewer for clinical capabilities); calibration threshold adjustment — AI Safety Owner (Clinical Reviewer for safety thresholds); tenant authorization — tenant org_admin after ChartWarden confirms tenant BAA covers AI use; hallucination response — AI Engineer triage, escalating to AI Safety Owner on clinical impact, Compliance if PHI involved.
- **AI-010 (§3.2)** — Single-person-owner risk is acknowledged with mitigations: clinical advisor contracted before Phase 1 launch; reassessment trigger = contracted clinical reviewer separate from engineering before second customer. Auditors should not flag the dual-role as undocumented, but SHOULD flag module specs assuming an independent reviewer exists before this trigger fires.

### 3.3 Capability Catalog & Risk Classes (AI §4)

- **AI-011 (§4.1)** — Registered capability inventory with fixed risk classes: HearthNote Layer 2 (Module 8, High); HearthNote IDG aggregation Layer 2 (Module 14, High); DocLens classifier (Module 22, Medium); DocLens extractor (Module 22, High); DocLens vision verification (Module 22, High); AI Copilot clinical (Module 32, High); AI Copilot administrative (Module 32, Medium); semantic search (32+22, Medium); embeddings generation (32, Low); mortality/decline prediction (32, High — ADR-004 open); falls risk prediction (32, High, future); aggregate cap projection (Module 26, Medium). The catalog lives at `docs/ai/capability-catalog.yaml`; ANY module AI feature must appear in (or be added to) this catalog.
- **AI-012 (§4.2)** — Risk-class control bar: High → full §5 approval workflow, HITL, deterministic fallback, explicit consent, full audit, periodic re-evaluation; Medium → scaled approval, HOTL, audit, periodic re-evaluation; Low → lightweight approval, audit. Risk class assigned at design and reassessed if usage shifts (e.g., reliance for decisions upgrades the class).
- **AI-013 (§4.3)** — Lifecycle states: PROPOSED → DESIGN_REVIEW → EVALUATION → PILOT → APPROVED → MONITORING → DEPRECATED → RETIRED, with usage gates per state (no one before EVALUATION-internal; pilot tenants only at PILOT; opt-in tenants from APPROVED; no new opt-ins at DEPRECATED; no one at RETIRED).
- **AI-014 (§4.4)** — Every capability requires a structured doc at `docs/ai/capabilities/<capability-id>.md` covering: purpose; risk class + rationale; architecture refs; foundation model (vendor, model name, pinned y/n + rationale); prompt template (ID `prompt:<capability>:v<n>`, path, version, history); inputs (structured/free-text, PHI presence, max context window in tokens); outputs (schema, confidence y/n, provenance fields); calibration thresholds (hallucination, precision, recall, latency p95); HITL/HOTL design (acknowledgment, hard blocks); monitoring (drift metric/threshold/frequency, feedback channel, re-eval schedule); cost (tokens typical/max, monthly per-tenant estimate); tenant opt-in (default, audience, per-clinician availability); kill switch (flag `ai.<capability>_kill`, activation triggers); approval history; open issues.

### 3.4 Approval Workflow (AI §5)

- **AI-015 (§5.1)** — Stage 1 Proposal: problem statement, AI approach, **alternative non-AI implementations considered**, initial risk class, cost estimate, success criteria; AI Safety Owner formally approves entry into Design Review.
- **AI-016 (§5.2)** — Stage 2 Design Review outputs: architecture spec (model choice, prompt strategy, control flow); STRIDE + AI-specific threat model (prompt injection, hallucination, data exfiltration via prompt, model bias); PHI flow with minimization; calibration plan (metrics, benchmark, thresholds); HITL design; audit/observability design; **vendor BAA confirmation**. Approvers: AI Safety Owner + Clinical Reviewer (High risk) + Privacy Officer.
- **AI-017 (§5.3)** — Stage 3 Evaluation: build, curate evaluation dataset (§13), benchmark suite, manual clinical review of sample outputs (**minimum 100 examples reviewed by Clinical Reviewer for High risk**), adversarial testing (prompt injection, edge cases), cost validation. Pass criteria: ALL calibration thresholds met; zero safety-critical hallucinations in clinical sample; zero observed PHI leakage; no exploitable prompt-injection; cost within envelope.
- **AI-018 (§5.4)** — Stage 4 Pilot: selected tenants with explicit consent + clinical-staff briefing; daily output review by AI Engineer; clinician feedback; calibration verified under real usage. Pass: sustained metrics over **30–90 days**; acceptable feedback; zero safety incidents; zero PHI handling incidents.
- **AI-019 (§5.5–5.6)** — Stage 5 GA: catalog + tenant docs updated, opt-in activated, monitoring continues. Re-approval required on: annual schedule (High; biennial Medium); major model upgrade; major prompt-template change; material input-distribution change; post-incident if AI failure was material.
- **AI-020 (§5.7)** — Low-risk fast track: single combined Proposal+Design+Evaluation doc, AI Safety Owner sign-off, no Clinical Reviewer, no pilot, standard monitoring — permitted ONLY for non-clinical, non-meaningfully-PHI-bearing capabilities.

### 3.5 Calibration Thresholds & Drift (AI §6)

- **AI-021 (§6.1.1)** — HearthNote Layer 2 thresholds (cloud): diff-validation pass rate ≥99%; compliance-gate first-try pass ≥95%; hallucination rate ≤0.5% (independent clinical review of samples); latency p95 ≤5 s; token efficiency ≤2× Layer 1 byte length.
- **AI-022 (§6.1.2)** — DocLens extractor thresholds: precision ≥95% on common fields (med name, dose, allergies, diagnoses); recall ≥90%; confidence calibration — reported confidence ≥0.9 implies actual accuracy ≥95%; 50-page bundle latency ≤90 s; PHI leakage rate 0% (no PHI in output unrelated to input documents).
- **AI-023 (§6.1.3)** — AI Copilot thresholds: refusal-when-appropriate ≥95% on the adversarial "ask AI for a clinical decision" set; source citation present for 100% of factual claims about a patient; off-topic answer rate ≤5%.
- **AI-024 (§6.1.4)** — Prediction thresholds (if deployed): AUROC ≥0.75 on held-out test set; calibration error ≤10%; demographic fairness — AUROC variance across protected groups ≤0.05.
- **AI-025 (§6.2.1)** — Performance-drift alerting (vs initial benchmark AND trailing 4-week average): 10% degradation in any primary metric → SEV-3 + AI Engineer review; 20% → SEV-2 + AI Safety Owner + consider rollback; 30% → SEV-1 with **auto-activation of the kill switch pending investigation**.
- **AI-026 (§6.2.2–6.2.4)** — Input drift (document/encounter/query-type distribution, patient demographics), output drift (confidence distribution, length/tokens, refusal rate, error rate), and user-feedback drift (flag rate vs pilot baseline; pattern drill-downs) are all monitored; significant drift triggers re-evaluation against current production data.
- **AI-027 (§6.3)** — Continuous evaluation cadence: weekly smoke set 10–50 examples per capability; monthly 100–500 examples measuring calibration metrics; quarterly full set typically 1,000+ examples. Eval datasets versioned and curated separately from training/prompt-iteration data to prevent overfitting.
- **AI-028 (§6.4)** — Drift response: <10% — AI Engineer investigation + capability-log entry; 10–20% — AI Engineer + AI Safety Owner, RCA, mitigation (prompt tuning / prior model fallback / extra validation), tenant communication if user-visible, re-evaluate; >20% — AI Safety Owner declares, consider kill switch, tenant notification, full eval re-run, potential rollback (§14.3), post-incident review.

### 3.6 Clinical Safety Review & Human-in-Loop (AI §7)

- **AI-029 (§7.1–7.2)** — Clinical safety review required for: every new High-risk capability before pilot; major prompt or model changes affecting High-risk capabilities; clinically-relevant hallucination investigations; annual High-risk re-evaluation; pilot reviews. Process: stratified sample of 100+ outputs (common, edge, adversarial, demographically diverse); blinded review where applicable; per-output correctness/appropriateness/citation/safety assessment; aggregate findings with approve / approve-with-conditions / reject recommendation; documented in the capability doc.
- **AI-030 (§7.3.1)** — HearthNote HITL pattern: Layer 1 shown first; Layer 2 offered as optional improvement; clinician accepts/edits/rejects BEFORE signing; the final signed narrative is the clinician's work product, not the AI's; AI provenance attached audit-only (not user-facing in the clinical record).
- **AI-031 (§7.3.2)** — DocLens HITL pattern: AI proposes structured entries; **never auto-commits**; per-field approval for High-risk fields (medications, allergies, diagnoses); batch acceptance only for Low-risk fields (demographics, contacts) behind an explicit toggle; source citation (document/page) shown next to each proposed entry; clinician edit before accept.
- **AI-032 (§7.3.3)** — Prediction HITL pattern: shown with explicit confidence and limitations; always "AI suggests", never "the answer"; clinician documents any influence on their decision; predictions are logged and **do not generate alerts or automatic actions**.
- **AI-033 (§7.4)** — HOTL is permitted only when individual errors are recoverable and don't directly affect patient care (Copilot operational answers, semantic search ranking, document-classification routing with user flagging).
- **AI-034 (§7.5)** — Mandatory refusal behaviors: clinical decision requests (diagnosis, treatment plan) → refuse + suggest clinician consultation; requests to override compliance checks → refuse + explain; requests to act on another patient's data → refuse (cross-tenant boundary); confidence below threshold → decline with explanation rather than guess; prompt-injection-looking input → refuse + log for analysis; system-prompt/training extraction attempts → refuse.
- **AI-035 (§7.6)** — Clinical Reviewer independence (Phase 2+): financially independent of feature outcome; empowered to block deployment regardless of business pressure; AI Safety Owner / Clinical Reviewer disagreement escalates to the medical advisory board when established.

### 3.7 Prompt Management (AI §8)

- **AI-036 (§8.1)** — Prompt templates versioned in Git at `packages/prompts/templates/<capability>/v<N>.txt` with a `current.txt` symlink, plus metadata `v<N>.meta.yaml` capturing: capability, template, version, model compatibility list, author, date, originating PR/change, calibration results (benchmark name, precision/recall), AI Safety Owner approval, clinical-review fields (required flag, reviewer, date), status (active|deprecated|archived).
- **AI-037 (§8.2)** — Prompt change process: branch → run benchmark evaluation → compare to current → abandon/iterate on degradation → §3.3-matrix approval → deploy behind a rollout-kind feature flag for gradual rollout → monitor → promote symlink when stable. Module specs proposing direct/unversioned prompt edits violate this.
- **AI-038 (§8.3)** — Prompt provenance: every invocation records `ai.capability_invoked` with capability, prompt_template + sha256 hash, model + version hash, input/output token counts, duration_ms, organization_id, patient_id_hash, correlation_id — making outputs reproducible within model non-determinism.
- **AI-039 (§8.4)** — Prompt security: NO PHI in templates (runtime population only); NO secrets in prompts; template review required for High-risk capability changes; injection-defensive design (system/user separation).
- **AI-040 (§8.5)** — Prompt-injection defenses required: clear delimiters between system instructions and user content; instructions to ignore meta-instructions in user content; output-schema validation as format-break detection; refusal patterns in the prompt; extraction prompts must refuse documents containing embedded instructions.
- **AI-041 (§8.6)** — Output validation: structured outputs parsed against declared JSON schema; on validation failure → retry ONCE, then fall back to deterministic processing or refuse; value sanity checks (e.g., medication dose must be parseable); length/content checks on text outputs.

### 3.8 PHI Handling with AI Vendors (AI §9)

- **AI-042 (§9.1)** — Absolute gate: NO PHI to any AI vendor without (a) signed HIPAA BAA, (b) documented vendor security review (SEC §18), (c) documented data-handling terms (retention, training use, sub-processors), and (d) tenant authorization for the capability.
- **AI-043 (§9.2)** — Anthropic-specific required terms: BAA in force (status: in negotiation as of Phase 1 design — see OPEN-013); Zero Data Retention for PHI-bearing traffic; explicit no-training-on-customer-data; US-region processing when contractually available; sub-processor disclosure with ChartWarden review.
- **AI-044 (§9.3.1)** — Identifier minimization table is binding: patient name not sent (only if output must reference patient by name — rare); MRN NEVER; DOB sent as age in years (months for pediatric) and only when clinically relevant; SSN NEVER; address NEVER; phone/email NEVER; diagnosis codes sent (always relevant); diagnosis text sent if necessary.
- **AI-045 (§9.3.2–9.3.3)** — Free text sent only when the task requires textual reasoning: prefer structured data; trim to the relevant time window; per-capability length limits. Optional pre-send redaction (names→[PATIENT]/[CAREGIVER]/[RN], addresses→city/state, phones→[PHONE], dates→relative) is a per-capability decision balancing privacy vs quality.
- **AI-046 (§9.4)** — Every PHI-sending AI invocation logs `ai.phi_disclosed` (capability, vendor, organization, hashed patient_id, token count, correlation ID), subject to monthly compliance sample review.
- **AI-047 (§9.5)** — AI outputs containing PHI are stored with full clinical-record protections; may not be replayed/shared without the same authorization as the underlying PHI; cached outputs carry appropriate retention class and TTL.
- **AI-048 (§9.6, §9.8)** — Cross-tenant pooling PROHIBITED for cloud AND local: a Tenant A prompt must not include Tenant B data; Tenant A embeddings must not inform Tenant B results; per-tenant models where customization needed; platform-default models trained on de-identified or synthetic data only; local model state must not blend tenants (per-tenant embedding indexes, no shared inference state, no cross-tenant fine-tuning).

### 3.9 Local AI Governance (AI §9.7–9.13)

"Cloud" = external vendor (Anthropic) under BAA; vendor operates, ChartWarden is responsible for use.

- **AI-052 (§9.7.5)** — Local models follow the SAME §5 approval workflow plus: Stage 2 additionally documents parameter count, quantization scheme, license terms, known limitations vs cloud; Stage 3 includes side-by-side cloud benchmark on the same eval set with quantified quality gap; Stage 4 pilots explicitly with `local_only`/`prefer_local` tenants; per-backend calibration thresholds may be looser for local with informed tenant trade-off.
- **AI-053 (§9.7.6)** — License compliance confirmed per model at Stage 2 (Llama 3.1 — Meta Community License with agreement; Mistral — Apache 2.0; Phi-3.5 — MIT; Gemma 2 — Gemma Terms) and documented in the capability catalog.
- **AI-054 (§9.7.7)** — When local, ChartWarden assumes operational responsibility: serving uptime and latency budgets; artifact integrity (checksums; vendor signatures verified where available); Ollama/vLLM security patching per SEC §14 cadence; hardware health monitoring + failover; capacity for projected load; calibration maintenance on model updates (test before rolling); model artifacts backed up like infrastructure.
- **AI-055 (§9.9)** — Local PHI flow: no PHI disclosure; audit event `ai.local_inference` with backend identifier (e.g., `ollama-llama-3.1-8b`) instead of `ai.phi_disclosed`; **minimum-necessary principle still applies locally**; no BAA needed; no sub-processors; no cross-border transfer.
- **AI-056 (§9.10)** — Backend-specific tenant disclosures required: cloud-backed (vendor name, BAA, ZDR, encrypted channel, single-request processing, vendor security review link); local-backed ("entirely within ChartWarden's secure infrastructure; not transmitted to any third party"); hybrid disclosed per-capability and aggregated in tenant settings.
- **AI-057 (§9.11)** — Per-backend calibration: same capability gets separate thresholds and separate eval runs per backend (reference values — HearthNote Layer 2: cloud hallucination ≤0.5%, diff-validation ≥99%, latency p95 5,000 ms, acceptance ≥90%; local hallucination ≤1.5%, diff-validation ≥97%, latency p95 8,000 ms, acceptance ≥80%); drift monitored per backend; tenants informed of the calibration delta pre-opt-in.
- **AI-058 (§9.12–9.13)** — Local drift monitoring covers hardware drift (GPU degradation/thermal throttling), library drift (Ollama/vLLM updates), and data-distribution drift; ChartWarden controls update timing. Local rollback: prior version retained (Ollama tags + MinIO archive), rollback = tag switch with mandatory post-rollback calibration verification.

### 3.10 Tenant & Clinician Opt-In (AI §10)

- **AI-059 (§10.1)** — All Layer 2 / High-risk capabilities default OFF for new tenants; tenant org_admin must explicitly opt in.
- **AI-060 (§10.2)** — Opt-in process (all five steps): (1) pre-opt-in disclosures — what it does, what data goes to which vendor, clinical-safety review performed, calibration results, limitations/failure modes, per-clinician opt-out, cost implications; (2) org_admin acknowledgments — reviewed safety docs, understands augmentation-only, will inform staff, agency BAA addendum addressing AI use; (3) audit `ai.tenant_opted_in`; (4) feature flag activated; (5) all tenant clinicians notified.
- **AI-061 (§10.3)** — Per-clinician opt-out: profile setting "Use AI assistance"; default ON at opted-in tenants; toggle-off proceeds with Layer 1 only; toggle audited (`ai.clinician_opted_out`).
- **AI-062 (§10.4)** — Patient-level consent: required for portal AI features (Module 39); AI-assisted content shared with patients carries standard AI-involvement disclosure; internal clinician documentation AI generally needs no per-patient consent but the agency's Notice of Privacy Practices should mention AI use.
- **AI-063 (§10.5–10.6)** — Opt-out effects: flag deactivated; previously generated AI outputs remain with provenance marking; no new invocations. Withdrawal: any time, immediate, no questions, confirmed via email + audit.
- **AI-064 (§10.8–10.10)** — Routing preferences (chosen at opt-in; changeable with re-confirmation + audit): `prefer_cloud` (default), `prefer_local`, `cloud_only` (no-cloud-backend capabilities hidden), `local_only` (no-local-backend capabilities hidden). Preference-specific disclosures per §10.9; `prefer_local`/`local_only` tenants must receive and the org_admin must ACKNOWLEDGE the per-capability calibration comparison (§10.10) before activation.
- **AI-065 (§10.7)** — Activation includes customer training: written clinician guide, video walkthroughs, sample outputs with validation guidance (Q&A office hours Phase 2).

### 3.11 Hallucination Handling (AI §11)

- **AI-066 (§11.1–11.2)** — Hallucination = fluent, plausible, factually wrong, potentially misleading. Detection channels are mandatory: automated (HearthNote diff-and-validate hard block; DocLens schema rejection; Copilot uncited-factual-claim flagging; low-confidence flagging); user-reported ("Report this output" button on EVERY AI-generated content, typed factually-wrong/misleading/inappropriate/other, routed to AI Engineer); periodic sampling (weekly Clinical Reviewer random samples for High-risk capabilities).
- **AI-067 (§11.3)** — Severity response: Critical (led/could lead to patient harm) → SEV-1, kill switch, clinical safety review, tenant notification, HIPAA breach assessment if data integrity affected; High (clinical record affected but clinician-caught) → SEV-2, investigation, possible kill switch, calibration re-run; Medium → SEV-3, logged, next re-evaluation; Low → SEV-4, categorized into eval refinement.
- **AI-068 (§11.4–11.5)** — Critical/High investigation: reproduce; classify cause (model / prompt / input / edge case); mitigate accordingly (rollback+vendor escalation / prompt iteration+re-eval / upstream validation / calibration-set extension); communicate to affected users; document; re-evaluate before resuming a killed capability. Clinical-safety hallucinations: participate in agency incident reporting (state QIO etc.); maintain internal AI incident registry; share de-identified learnings with industry safety bodies when appropriate.

### 3.12 AI Incident Response & Kill Switch (AI §12)

- **AI-069 (§12.2)** — AI incident types with primary owners are enumerated (clinical hallucination; successful prompt injection — Security Owner + AI Safety Owner; PHI leak to vendor — Privacy Officer + AI Safety Owner; model rollback; calibration drift; vendor outage — graceful degradation; cost spike at 10× normal; misuse for autonomous decisions; bias detection).
- **AI-070 (§12.3)** — Kill-switch activation triggers: confirmed critical hallucination with unsafe capability; active prompt-injection campaign; vendor outage exceeding tolerable degraded-mode duration; unexplained cost spike; audit-revealed unauthorized capability use. Procedure: AI Safety Owner (or IC) authorizes → toggle flag (e.g., `ai.doclens_kill`) → audit `ai.kill_switch_activated` severity=critical → status page if customer-facing → tenant notification if material → **capability falls back to Layer 1 / deterministic / unavailable** → investigation. Reactivation requires root cause understood + fix verified + AI Safety Owner approval + `ai.kill_switch_deactivated` audit.
- **AI-071 (§12.4–12.5)** — Tenant communication on AI incidents: status page, org_admin email summary, specific manual-workflow guidance, resolution notice. AI PIR additions: was the pattern previously seen in evaluation; why didn't calibration catch it; is the eval dataset insufficient; should HITL design change; do similar capabilities share the risk.

### 3.13 Evaluation Datasets (AI §13)

- **AI-072 (§13.2–13.3)** — Per capability: held-out evaluation set (never used for prompt iteration/training), training/iteration set (separate), synthetic adversarial set (edge cases, injection attempts, ambiguous inputs). Composition mirrors production: input-type distribution, patient demographics, clinical complexity, identified edge cases.
- **AI-073 (§13.4–13.5)** — Sources: de-identified production data (with tenant consent), clinical-expert synthetic data, public clinical datasets (MIMIC etc., adapted), vendor benchmarks. Labeling: clinical experts; inter-rater reliability Cohen's kappa ≥0.8 target; disagreements resolved by senior clinician.
- **AI-074 (§13.6–13.7)** — Versioned datasets (same version across re-evaluations for apples-to-apples; new version on material distribution change; old versions retained). Refresh: weekly smoke-set as needed; monthly mid-size augmentation; quarterly full review; annual structural methodology review.

### 3.14 Model Lifecycle (AI §14)

- **AI-075 (§14.1–14.2)** — New foundation-model versions are NEVER auto-adopted: monitor announcement → evaluate in test env with current prompts + eval set → performance and cost comparison → adopt/defer/skip decision → feature-flagged gradual per-tenant rollout; explicit AI Safety Owner approval required. Production model versions PINNED where vendor supports (e.g., `claude-opus-4-7`, never `-latest`); pinned versions periodically reviewed for security patches.
- **AI-076 (§14.3)** — Rollback: AI Safety Owner declares; feature flag points to prior model version; operational verification; audit event. Forced vendor deprecation: track timeline, adopt within it if possible; if the new model fails calibration → capability paused via kill switch pending fix + tenant communication.
- **AI-077 (§14.4)** — Retirement: DEPRECATED = no new opt-ins, grandfathered transition **typically 90–180 days** with replacement onboarding offered; RETIRED = flag permanently off, code removed next quarterly release, historical outputs preserved per retention rules.

### 3.15 Vendor Selection & Management (AI §15)

- **AI-078 (§15.1.1)** — Approved cloud AI vendor inventory: Anthropic ONLY in Phase 1 (Claude Opus / Haiku for HearthNote Layer 2, DocLens, DocLens vision verification cloud-only, Copilot, predictions where applicable); BAA in negotiation as of Phase 1 design. OpenAI/Google/others are "possible future" and would each require a BAA. **A module spec routing PHI to any cloud AI vendor other than Anthropic is non-compliant absent a new vendor review + BAA.**
- **AI-079 (§15.1.2)** — Local backend inventory with approval status: BGE-small-en-v1.5 — Approved; all-MiniLM-L6-v2 — Approved; Llama 3.1 8B / Mistral 7B / Phi-3.5 Mini — **Pending Stage 3 evaluation**; custom distilBERT DocLens classifier — Pending training. Module specs may not assume pending backends are usable in production.
- **AI-080 (§15.2)** — Vendor selection criteria (all required unless noted): HIPAA BAA available; ZDR or equivalent (strongly preferred for PHI); US-region processing; sub-processor disclosure; at least one security certification (SOC 2 Type II / ISO 27001 / HITRUST) for PHI vendors; quality benchmarks; predictable pricing (token-based preferred); API stability commitments with reasonable deprecation; documented bias/safety practices; 72-hour incident-notification SLA.
- **AI-081 (§15.3)** — Annual per-vendor review: security posture (SEC §18), BAA renewal, performance/reliability, cost trend, strategic alignment.

### 3.16 Audit, Explainability, Bias, Regulatory (AI §16–18)

- **AI-082 (§16.1)** — Mandatory AI audit events (Module 4): `ai.capability_invoked` (with capability, model:version, prompt_template:version, token counts, duration, user_id, patient_id_hash, hitl_required, hitl_outcome ∈ {accepted, edited, rejected, pending}); plus `ai.output_accepted`, `ai.output_edited`, `ai.output_rejected`, `ai.output_flagged`, `ai.kill_switch_activated/deactivated`, `ai.tenant_opted_in/out`, `ai.clinician_opted_out`, `ai.hallucination_reported`. (Plus `ai.phi_disclosed` per AI-046 and `ai.local_inference` per AI-055.)
- **AI-083 (§16.2–16.3)** — Explainability: provenance (model version, prompt version, PHI-aware input snapshot) for every output; feature importance (e.g., SHAP) for predictions where supported; source citations for extractions; Layer 1 selection linkage for narratives. Reproducibility: full prompt, model version, output, timestamp stored; semantic-equivalence reproduction expected (bit-perfect not guaranteed).
- **AI-084 (§17.2–17.4)** — Fairness requirements for predictions/clinical-decision-affecting capabilities: equalized odds, calibration parity, statistical parity (when appropriate) across race/ethnicity (where collected + consented), age, gender/sex, primary language, geography (rural/urban), insurance status, diagnosis category. Pre-deployment bias testing REQUIRED before approval (stratified eval, per-group metrics, documented disparities; exceeding thresholds → mitigation or rejection). Deployed predictions: quarterly bias monitoring; drift toward bias triggers investigation and potential rollback.
- **AI-085 (§17.5)** — Honest documentation of fairness limitations required (small populations, biased historical referral data, non-representative ChartWarden data) in capability docs.
- **AI-086 (§18.1)** — SaMD design constraint: all ChartWarden AI is designed to remain IMDRF Class I or II — augmentation with clinician decision authority ("AI suggests, clinician decides"; "AI proposes, clinician signs"; "AI extracts, clinician approves"). No feature is intended as an autonomous medical decision-maker; capability evolution toward SaMD triggers FDA pre-submission, premarket pathway, 21 CFR Part 820 QMS, and post-market surveillance. No Phase 1–3 capability anticipated to require FDA submission; continuously monitored.
- **AI-087 (§18.2)** — FTC marketing claim rules: "AI-assisted" not "AI-powered" when AI is supplementary; no accuracy claims without documented, validated calibration; no FDA-approval claims; no "human-quality" claims without basis; clinical-safety claims evidence-backed.
- **AI-088 (§18.3–18.5)** — Regulatory tracking: state AI laws (CA transparency, CO AI Act 2026, IL, NY) tracked in compliance traceability. HIPAA in AI context: PHI use for AI must be a permitted use under §164.502; AI vendors are Business Associates with BAAs; minimum-necessary applies to prompts; AI activities audited per §164.312(b); AI risks included in the §164.308(a)(1)(ii)(A) risk analysis. ONC: patient access to AI-use information via portal; AI-assisted content documented with provenance; AI never used to obstruct EHI access.
