## 1. Document Governance & Spec Process

- **ARCH-001** (§Doc Control, §26): Architecture sign-off blocks structural changes during the build cycle. Module-level changes go through ADRs in `docs/adr/`. A module spec MUST NOT silently alter architecture-level decisions; it must reference an ADR.
- **ARCH-002** (§11, §22): Every module gets a dedicated spec document under `docs/modules/`, produced **before** that module's build cycle starts.
- **ARCH-003** (§20.B): Every per-module spec MUST follow the Module Spec Template: header (Module ID, Phase, Depends on, Consumed by, Spec status: Draft | Locked | Implemented | Frozen) and 12 sections — 1. Purpose & Scope; 2. Domain Model; 3. Drizzle Schema (incl. enums, indexes, FK on-delete/update behavior, RLS policies, partition definitions, migration file content); 4. API Routes (route inventory: method, path, auth required, RBAC roles, ABAC checks; per-route TypeBox request/response schemas, success/error codes, idempotency support, pagination; webhook signing schemes; Socket.IO events emitted/consumed; BullMQ jobs created/consumed); 5. Frontend Screens (incl. WCAG 2.1 AA accessibility notes, mobile Capacitor variants, portal variants); 6. Permissions Matrix (Action × Role × ABAC condition; override workflows); 7. Workflow Acceptance Criteria (incl. concurrency scenarios); 8. Audit & Observability (audit events catalog with retention class; Prometheus metrics; OTel spans); 9. Test Plan (unit, integration via Testcontainers, RLS isolation cross-tenant denial, Playwright E2E, fixtures, performance targets); 10. Implementation Tasks (S/M/L); 11. Open Questions; 12. Acceptance Sign-Off checklist (schema migrated, routes tested, RLS verified, audit emitted, alerts wired, mobile variant working, documentation written, ADRs resolved).
- **ARCH-004** (§22): Per-module spec contents MUST also cover: state machines (every state, transition, guard); RBAC bindings per action; ABAC rules; RLS policy specification; AI integration points with calibration requirements; external integration points with protocol/auth/retry/idempotency; audit events captured; migration plan from ChartWarden/Hospici where domain logic is harvested; known unknowns.
- **ARCH-005** (§20.C): Four cross-cutting documents complement module specs and are NOT module specs: CHARTWARDEN_OPS_RUNBOOK, CHARTWARDEN_INTEGRATIONS, CHARTWARDEN_SECURITY_HARDENING, CHARTWARDEN_AI_GOVERNANCE. A module spec may reference them but must not duplicate or contradict them.
- **ARCH-006** (§1): Scope is hospice-only. Non-goals: home health, palliative-only, SNF clinical workflows; general inpatient hospital EHR (Module 37 IPU is hospice inpatient only); long-term care; pharmacy management (DoseSpot is used); general-purpose accounting/GL (Xero); payroll (Gusto). A module spec proposing features in these areas is out of scope.

## 2. Tenancy Model

- **ARCH-010** (§3): Three-tier hierarchy is fixed: **Organization** (tenant, billing customer, security boundary) → **ProviderEntity** (CCN-bearing: NPI, MAC, tax ID, files its own cost report) → **Location** (physical site under the CCN). NOE/NOTR, 837I claims, and cost reports are scoped by ProviderEntity; scheduling, on-call rotation, IDG, route optimization are scoped by Location; Locations drive Q-code selection at the visit level.
- **ARCH-011** (§3 cross-cutting rules): Every PHI table carries `organization_id`, `provider_entity_id`, and `location_id` — the latter two nullable **only** on org-level entities.
- **ARCH-012** (§3, §8): RLS policies enforce `organization_id` match against the session variable (`app.org_id`, set via `SET LOCAL`). All RLS scopes by `organization_id`.
- **ARCH-013** (§3): Application-level checks enforce ProviderEntity and Location scoping based on RBAC. "All-locations" access is a flag on the membership, not a separate role.
- **ARCH-014** (§3): One user record (one email) MAY hold Memberships in multiple Organizations. **Each session is scoped to exactly one Organization** — picked at login; no in-session org switcher; switching requires logout/login. Per-Organization Memberships carry their own roles, location memberships, and audit trail; login to Org A produces audit entries only in Org A's log. Better Auth's organization plugin enforces this. Passkeys and 2FA seeds MAY be shared across Organizations (authentication, not authorization).
- **ARCH-015** (§3): A user belongs to an Organization and has memberships at one or more Locations within ProviderEntities of that Organization.
- **ARCH-016** (§3): Engrace v1 reference configuration: 1 Organization (Engrace Hospice LLC), 1 ProviderEntity (CCN 381588, NGS J6 MAC), N Locations (Pendleton OR primary). Multi-CCN tenants: 1 Organization, N ProviderEntities (possibly different MAC jurisdictions), M Locations each.

## 4. Architectural Principles (§6 — all binding)

- **ARCH-040** (§6.1): The domain model is the source of truth, not FHIR. FHIR is a representation; internal code never imports FHIR types.
- **ARCH-041** (§6.2): Every PHI access — read or write — is logged. Enforced at the DB layer (audit trigger) and API layer (middleware).
- **ARCH-042** (§6.3): Multitenancy is enforced in the database via RLS; application bugs must not be able to leak data across tenants.
- **ARCH-043** (§6.4): Clinical workflows use explicit state machines with declared transitions (admission status, election period, certification, level of care, claim lifecycle, etc.).
- **ARCH-044** (§6.5): Claim submission is idempotent. Every claim has a deterministic ID; retries never double-bill.
- **ARCH-045** (§6.6): Workers are separate processes, not in-process jobs — resumable, observable, independently scalable.
- **ARCH-046** (§6.7): No business logic in UI components. UI is rendering and event dispatch only.
- **ARCH-047** (§6.8): TypeBox schemas derived once — producing TS types and runtime validators. No Zod/TS duplication.
- **ARCH-048** (§6.9): AI features must show calibration, not just scores. Every prediction surface shows the calibration curve and validated timeframe. No black-box scores in clinical decision surfaces.
- **ARCH-049** (§6.10): Per-tenant configurability is first-class. Anything that varies between agencies lives in tenant configuration, not code branches.

## 5. Identity, Authorization & Access Control

### 5.1 Identity & sessions (§7)
- **ARCH-050** (§7): Identity via Better Auth: email + password (with breached-password check); passkeys (preferred for clinicians); 2FA TOTP **required for all roles except read-only**; SSO via OIDC deferred until first enterprise customer (OPEN-008).
- **ARCH-051** (§7, §14): Session limits: **15 min idle, 8 hr absolute, 5 min UI screen lock**. (Note: §24.1 "Sessions" row states "default 8 hours max idle, 24 hours absolute" — internal conflict; see OPEN-020. Module specs should follow §7/§14 unless an ADR resolves otherwise.)
- **ARCH-052** (§7): Role catalog: ~60 roles in 12 categories (A Internal Clinical, B Clinical Leadership, C Operations, D Administrative/Executive, E Billing & Finance, F Compliance/Quality/Privacy, G Volunteers, H Patient/Family/Caregiver, I External Regulatory & Audit, J External Clinical Collaborators, K ChartWarden Platform Staff, L Temporary/Special). Per-tenant configurable: each Organization can disable, rename, or add to the defaults. Modules MUST bind permissions to roles from this catalog, with documented scope (Organization / ProviderEntity / Location / patient-level).
- **ARCH-053** (§7): ABAC attributes layered on RBAC: patient case-load (clinician sees own assigned patients unless covering); on-call active window (time-bound elevation to ProviderEntity-wide patient access — denied when shift not active); bereavement window (counselor sees patients in 13-month bereavement only); discipline scope (chaplain doesn't see meds; aide doesn't see billing).
- **ARCH-054** (§7): Break-glass: "view any patient" requires reason text, immediate notification to Compliance Officer, prominent audit entry. Per-tenant policy may require Compliance Officer co-sign for non-emergency break-glass.
- **ARCH-055** (§7, Module 4): Audit log: append-only `audit_event` table partitioned monthly; trigger-based capture on all PHI table writes (INSERT/UPDATE/DELETE); application-layer capture on PHI reads (DB-level read auditing rejected as too expensive). Captures actor, organization, provider_entity, location, action, resource type, resource ID, before/after diff (scrubbed where needed), IP, user agent, timestamp, correlation_id. **7-year retention; encrypted at rest; immutable (DB user has no UPDATE/DELETE grant).** Tenant-scoped queries; ChartWarden support cannot query another tenant's audit without break-glass + audit-on-the-audit.
- **ARCH-056** (§7 cat. K): ChartWarden platform staff are PHI-walled by design; Tier 2 support and Security Officer PHI access requires break-glass + tenant consent; Billing Administrator and Sales have no PHI. Platform Owner access is all audited.
- **ARCH-057** (§7 cat. L): Student/Intern role: supervised, **all writes co-signed**. LPN/LVN notes co-signed by RN (cat. A).

### 5.2 Auditor Mode (§7.5)
- **ARCH-058** (§7.5): Auditor Mode is a separate session class, not an RBAC tweak. Constraints: time-bound engagement window (sessions cannot be created outside it; auto-revoke at expiry); scoped (tenant-wide, ProviderEntity-wide, or specific patients/claims/cost-report years); **read-only always** (UI hides all edit affordances); every PDF download watermarked with auditor name, agency, date, engagement ID; **no bulk export** (no `$export`, no CSV dumps, no archive downloads — one document at a time); every page view audited (patient ID, time on page, fields viewed); no copy-paste of PHI where browser supports (JS clipboard disable + DRM hint); **10 min idle timeout**; no concurrent sessions per auditor; Compliance Officer notified on first access of any patient chart.
- **ARCH-059** (§7.5): Grant workflow: Compliance Officer creates Engagement record (agency, contact, scope, start/end, reason) → per-auditor magic-link invitations + 2FA enrollment → identity confirmation, BAA acceptance, 2FA enrollment → access within scope until end timestamp → engagement summary report (every patient touched, every document downloaded, time on each).
- **ARCH-060** (§7.5): Pre-configured engagement types: CMS Survey (full org, **14 days**, all current census + **12 months back**); State Survey (same shape); TPE Probe (specific claims, **60 days**); UPIC Investigation (variable, often **90+ days**); Cost Report Field Audit (one CCN, one fiscal year, supporting docs); Financial Audit (no PHI, financial reports + GL only, **30 days**).

### 5.3 External Collaborator Pattern (§7.6)
- **ARCH-061** (§7.6): External clinical collaborators get per-patient/per-case scoped magic-link sessions, not persistent accounts (by default). Magic link valid **30 minutes, one-time use**. Session scope: one patient; permissions per role; duration **default 8 hours**, configurable. Clean termination + audit entry at expiry. 2FA challenge if previously logged in; else email/SMS verification. Optional persistent account (passkey-based) requires Tenant Admin approval.
- **ARCH-062** (§7.6): Role scopes: Attending Physician — full clinical view, CTI signing, order signing, telehealth join; Hospital Physician — clinical read + messaging + ADT linkage; SNF/ALF Staff — care plan view, medication list, visit schedule, secure messaging; Specialty Pharmacy — medication orders, refill requests, allergies, admin records (read); Lab Staff — active lab orders only; submit results; Interpreter — encounter participation, language + interpreter name documented on encounter.

### 5.4 Volunteer Compliance Gates (§7.7)
- **ARCH-063** (§7.7): Per CoP 418.78, volunteer compliance requirements are enforced as **scheduling gates**: a volunteer cannot be scheduled for any patient-facing activity with any gate unmet. Gates: background check (onboarding + per agency policy, typically annual); TB screening (annual); confidentiality agreement (onboarding); initial training (HIPAA, hospice philosophy, role-specific); annual continuing education; specific patient assignment training; TB/HepB/flu vaccination per agency policy (annual).
- **ARCH-064** (§7.7): Gate behavior: volunteer status auto-changes to Inactive on any gate expiry; scheduler cannot select an inactive volunteer; Volunteer Coordinator notified **30 / 14 / 7 / 1 days** before any gate expiry; coordinator dashboard shows gate status grid. CoP 418.78(e) volunteer time/cost-savings evidence auto-generated from logged visit data.

### 5.5 Funeral Home Access (§7.8)
- **ARCH-065** (§7.8): Funeral home staff get a tightly scoped per-deceased-patient session. Data scope (everything else hidden): decedent name/DOB/MRN; date and time of death; attending physician name + contact; body location at death; hospice contact person; pronouncement/disposition documentation; body release authorization form. Out of scope: clinical history, medications, encounter notes, family relationships, financial info. Access: magic-link, single-use or short-lived (configurable, **default 72 hours from death**); optional persistent account (Tenant Admin); all page views audited; no editing except the disposition acknowledgement form.

### 5.6 Three-Layer Authorization (§7.9)
- **ARCH-066** (§7.9): Three layers are each required; none substitutes for another: **RLS** (database, per query — which rows can this tenant see), **RBAC** (API layer, per request — is this action permitted for this role), **ABAC** (API layer + UI gating — is this user allowed this resource right now given context / HIPAA minimum-necessary).
- **ARCH-067** (§7.9): Implementation locations: RLS via `packages/tenancy` policy template generator (**every PHI table gets a standard policy**); RBAC via `packages/auth` role catalog and permission check API (**every API route declares required permission(s)**); ABAC via `packages/auth` attribute policy engine evaluated per-resource at request time. **Decision order: RLS (DB) → RBAC (route middleware) → ABAC (resource handler) → response.**

## 6. Tenant Isolation — Defense in Depth (§8)

- **ARCH-080** (§8.1): RLS at the database: every PHI table has `organization_id`; session sets `app.org_id` via `SET LOCAL`; policies enforce match.
- **ARCH-081** (§8.2): Envelope encryption for sensitive columns (SSN, financial account numbers, high-sensitivity narrative blocks) — DEK per tenant, KEK held by app, rotation supported.
- **ARCH-082** (§8.3): Per-tenant object storage scope: MinIO bucket prefix `tenant/<org_id>/` with IAM policies preventing cross-tenant signing.
- **ARCH-083** (§8.4–8.5): Per-tenant DoseSpot clinic registration (credentials in `packages/dosespot/credentials` keyed by tenant); per-tenant Xero OAuth tokens with isolated refresh.
- **ARCH-084** (§8.6): Tenant boundary in logs: every log line carries `tenant_id`; Sentry events tagged; Grafana dashboards filtered.
- **ARCH-085** (§8.7): HIPAA data subject access & deletion: tenant offboarding job exports all data (NDJSON + PDFs) and shreds via cryptographic DEK destruction.
- **ARCH-086** (§8.8): **Cross-tenant queries are forbidden in app code.** Repository helpers refuse `WHERE organization_id IN (...)`; only single-tenant queries pass.

## 7. Domain Layering & FHIR Direction (§9)

- **ARCH-090** (§9): Layering is fixed: HTTP/Fastify routes → application services (orchestration) → domain layer (`packages/domain`, pure, **no I/O**) → repositories (`packages/db/src/repos`, Drizzle) → PostgreSQL (RLS-enforced). FHIR mapping is separate and optional (`packages/fhir` with `r4/mappers`, `r5/mappers` stub, `r6/mappers` when published, `common/`).
- **ARCH-091** (§9, depcruise `fhir-direction`, `domain-is-pure`, `domain-no-node-io`): Domain types NEVER import from `packages/fhir`. FHIR mappers import from `packages/domain`. R6 adoption is a new mapper module, not a domain rewrite. `packages/domain` may not import db/auth/audit/tenancy/messaging/fhir/dosespot/saas/ai-platform/billing/cost-report packages, nor node I/O builtins (`fs`, `net`, `http`, `https`, `child_process`, `dgram`, `tls`).
- **ARCH-092** (§9): Core domain entity catalog (non-exhaustive) per §9 — module specs MUST use these entity names where they exist rather than inventing synonyms (e.g., ElectionPeriod, CertificationPeriod, LevelOfCarePeriod, EvvEvent, RemittanceAdvice, BreakGlassEvent, TenantSubscription).

## 8. AI Platform, HearthNote, DocLens, Backend Abstraction

### 8.1 AI discipline rules (§10 — apply to ALL AI features)
- **ARCH-100** (§10): Module 32 is a typed SDK in `packages/ai-platform/` consumed by other modules; it is not a separate user-facing module.
- **ARCH-101** (§10): Calibration over accuracy: every probabilistic surface shows the calibration curve from the most recent retraining and the training population. UI explicitly notes "model trained on Engrace data through MM/YYYY" and warns when applied to new tenants until tenant-specific calibration exists.
- **ARCH-102** (§10): **No autonomous action** — AI suggests; humans decide and sign.
- **ARCH-103** (§10): Per-tenant opt-in for training: a tenant's data is never used to train models for other tenants without explicit BAA-level consent. **PHI never leaves the perimeter for training** (local ML worker only); LLM inference goes to Anthropic under BAA.
- **ARCH-104** (§10): Cost ceiling per tenant: per-tenant token budgets with soft and hard caps; alerts before hard cap. (HearthNote-specific: soft alert at **80%**, hard cap at **100%** with auto-disable of Layer 2 — §10.5.6.)
- **ARCH-105** (§10): Validation framework: every predictive model has an `ml_model` record with version, training data window, AUROC, calibration plot, feature importance; new versions shadow-deploy with **canary 5% by default**; drift detection on input distributions with automatic alert. Predictive models (mortality 30/90/180-day, hospitalization 30-day, LOC) rebuilt **quarterly**.

### 8.2 HearthNote Narrative Engine (§10.5)
- **ARCH-106** (§10.5.1): Three layers: Layer 1 Deterministic Core (**always on**; bounded clinical vocabulary, template per encounter type × discipline, clinician-selected inputs only, rules-based assembly; pure function — same selections → byte-identical output; every sentence attributable to a selection or free-text entry; no hallucination possible); Layer 2 LLM Enhancement (**tenant opt-in, default off**; default-on for clinicians within an opted-in tenant with per-clinician disable and per-encounter-type override); Layer 3 Compliance Gate (**always on**; blocks signing if non-compliant).
- **ARCH-107** (§10.5.3): Layer 2 forbidden outputs: new clinical facts not in Layer 1; removed clinical facts; speculation on diagnosis/prognosis/treatment beyond the chart; quotes attributed to patient/family unless in Layer 1 selections. Hallucination defenses: LLM output diffed against Layer 1; new "facts" in the diff trigger warning + explicit clinician acceptance; **hard block on medication doses, diagnostic codes, vital sign values — LLM modifications to these are stripped**.
- **ARCH-108** (§10.5.3): Layer 2 audit: every LLM call records prompt, model version, timestamp, clinician, encounter ID; BOTH Layer 1 and Layer 2 narratives preserved; diff explicitly stored; clinician accept/edit/reject of each modification logged; token cost attributed to tenant.
- **ARCH-109** (§10.5.4): Layer 3 gate before signing: required sections per encounter type × discipline populated; required HOPE items captured (Module 10); required assessment scales completed (Module 9); required signatures/cosignatures per RBAC; clinician attestation ("I have reviewed all content, including any system-assisted material…"); for LLM-enhanced notes, explicit acceptance of every flagged modification; failure blocks signing with specific remediation pointers.
- **ARCH-110** (§10.5.5, Module 14): IDG aggregation: nightly job + on-demand pre-meeting; packets available **24 hours before** meeting; aggregated content always attributable to source encounter and clinician; aggregator summarizes, never overwrites; IDG packet is a derived view, not separate documentation. Post-meeting IDG decisions automatically generate care plan updates (Module 7), order tasks (Module 11), and follow-up flags.
- **ARCH-111** (§10.5.6): Performance/cost: Layer 1 in-process, sub-millisecond, no external calls; Layer 2 ~$0.01–$0.05 per call typical; per-tenant configurable monthly cap with 80% soft alert / 100% hard cap auto-disabling Layer 2.

### 8.3 DocLens (§10.6)
- **ARCH-112** (§10.6.1): Pipeline order is fixed: upload → Docling pass (docling-worker) → classifier pass (ml-worker, per page/page-range; multi-document fax bundles auto-split, split presented for human confirmation; ambiguous classifications go to manual labeling queue) → per-type extraction (langextract-worker; source page + bounding-box + confidence per field) → Claude verification on high-risk fields (meds, allergies, doses, code status — vision against source image) → discrepancy detection → side-by-side review UI → chart writeback with full provenance.
- **ARCH-113** (§10.6.3): Each of the 11 v1 document type schemas lives in `packages/intake-extraction/schemas/`; every field declares: TypeBox type + validation, source page reference (always required), bounding-box coordinates (always required), risk level (low/medium/high), confidence threshold for auto-approve eligibility, target chart entity/field.
- **ARCH-114** (§10.6.5 — non-negotiable guardrails): **Never auto-commit** — extraction produces candidates, not chart facts; nothing reaches the chart without explicit clinician approval. **Per-field approval required for HIGH-risk fields** (medications, allergies, doses, code status, advance directive content, DPOA agents — no bulk-approve). Bulk-approve permitted only for LOW-risk fields above the confidence floor, with audit of the bulk action. Source highlight mandatory (clickable link to source PDF page with bounding box). Discrepancy flags block commit until resolved. Chart-overwrite requires side-by-side diff + explicit per-field confirmation. Fields below the configurable confidence floor cannot be bulk-approved. 42 CFR Part 2 SUD content detection auto-triggers Module 5 PrivacyFlag workflow. PHI never leaves the perimeter for classification or extraction (local workers); Claude verification only under BAA.
- **ARCH-115** (§10.6.6): Chart writeback targets are fixed per the §10.6.6 table (demographics/insurance/photo ID/allergies/DPOA agent → Module 5; diagnoses → Module 7 Problem; medications → Module 12 MedicationOrder **held for prescriber confirmation, no auto-prescribe**; code status/AD/imaging/consults → Module 22; lab values/vitals → Module 8; HPI/PMH narrative → HearthNote Layer 1 selection seed).
- **ARCH-116** (§10.6.7, §23.13): Every committed chart field carries provenance: source ExtractionJob, Document + DocumentVersion, page + bounding box, ExtractedCandidate with confidence, reviewer User + timestamp, accept/edit/reject decision (with edit content), classifier and extractor model versions. Stored in dedicated `extraction_provenance` table linked from every chart entity supporting extraction-sourced creation. Extraction-sourced fields are tagged AI-touched and filterable by auditors.
- **ARCH-117** (§10.6.8): Performance targets: Docling ~5–30 s/document; classifier sub-second/page; LangExtract ~3–15 s/document; Claude verification ~$0.05–$0.15/document; end-to-end for a typical referral bundle (50 pages, 5 documents) **under 90 seconds** upload→review-ready. Per-tenant cost ceiling applies; downgrade to LangExtract-only allowed for budget-constrained tenants with UI warning of reduced verification rigor.

### 8.4 Model Backend Abstraction (§10.7)
- **ARCH-118** (§10.7): Every AI capability is implemented against the pluggable `ModelBackend` interface (`id`, `kind: 'cloud' | 'local'`, `supportedModalities`, `complete`/`embed?`/`classify?`, `health()`, `capabilities()`); backend selection is per-capability and per-tenant. ## 17. Data Retention, Destruction & Legal Hold (§24)

- **ARCH-250** (§24.1 — exact retention values; module specs must assign each data class/table a retention class consistent with this matrix):
  - Clinical record (encounter notes, assessments, care plans, orders, MAR): **6 years from last patient contact** default (HIPAA §164.530(j)(2)); Oregon **7 years**; minors until age 21 (state config table holds overrides); AES-256 at rest; cryptographic partition erasure + certificate; tiering hot (PG) 2 years → warm (MinIO) years 3–7 → cold years 8+. Patient demographics/election records: same.
  - HOPE assessments + HIS: 6 years from submission.
  - Claims (837), remittances (835), acks (999, 277CA): **7 years** (some states 10); object-lock enforced on MinIO; hot current + prior fiscal year.
  - Cost reports + workpapers: **7 years**; warm immediately on submission.
  - `audit_event` retention_class=operational: **1 year** (hot 3 months); retention_class=compliance: **7 years default** (HIPAA floor 6 — §164.316(b)(2)); hot 6 months, warm 6.5 years, cold thereafter; retention_class=legal_hold: indefinite until release.
  - Consent records + signed PDFs: lifetime of patient relationship + 6 years; tamper-evident metadata; warm immediately.
  - Secure messages (Module 36): **6 years**; hot 6 months, warm 5.5 years.
  - Push notification tokens: **90 days from last successful delivery** (Valkey only).
  - Sessions: session expiry (per §24: "default 8 hours max idle, 24 hours absolute" — see OPEN-020 conflict with §7's 15 min/8 hr).
  - Idempotency keys: **24 hours** (Valkey + PG mirror). Outbox events: **30 days post-dispatch** (PG).
  - DocLens working files: **30 days from job completion** (MinIO lifecycle auto-delete).
  - Telehealth recordings (if enabled + consented): per-tenant config + consent terms; **default 90 days**; some states prohibit recording.
  - AI prompts/responses to Anthropic: no-PHI **6 months**; PHI **6 years** (compliance class); Anthropic ZDR where contracted.
  - ML model artifacts: indefinite in production; archived **7 years after deprecation**. MLflow run metadata: **3 years**.
  - Backups: **daily for 30 days; weekly for 12 weeks; monthly for 7 years; annual for 10 years**; backups inherit the retention of the longest-retention data class they contain.
  - System logs (Loki): **90 days hot; 1 year cold** (PHI-scrubbed before ingestion). Security event logs (auth failures, RLS denials, suspicious activity): **6 years** (compliance class). Prometheus: **15 days raw; 6 months downsampled; 2 years aggregated**. Tempo traces: **14 days**.
  - Email: Postmark default 30 days events / 7 days content. SMS: Twilio configured to **30 days**. Stripe billing records retained **7 years** in our DB (Stripe handles no PHI).
- **ARCH-251** (§24.2 — destruction certification workflow, HIPAA §164.310(d)(2)(i)): retention job identifies expired partitions/objects → pre-destruction report (data class, record count, date range, encryption status, method) → compliance officer reviews and approves or holds → destruction by cryptographic erasure or secure delete → Certificate of Destruction stored in `compliance` class (persists 6 years after destruction) → audit event `data.destruction_certified` emitted.
- **ARCH-252** (§24.3 — legal hold): any data class can be flipped to `legal_hold` by compliance officer action; retention jobs skip `legal_hold` records; audit events `data.legal_hold_applied` / `data.legal_hold_released`; release returns records to original class with adjusted clock.
- **ARCH-253** (§24.4): State-specific retention rules live in the `state_retention_override` table (state_code, data_class, retention_years, citation — e.g., OR clinical_record 7 ORS 192.553; TX clinical_record_minor until_age_21+7). The patient's address state determines override applicability. (Note: table owned by Module 4 per manifest; §25.9 attributes retention overrides to "Module 39" — see OPEN-022.)
- **ARCH-254** (§24): Retention matrix drives audit partition retention classes (Module 1), MinIO bucket lifecycle policies, Valkey TTLs, and the destruction certification workflow. Legal hold overrides everything; state law overrides defaults where longer.

## 18. Patterns Catalog (§25 — every module follows these)

- **ARCH-260** (§25.1 State machines): Use XState (or equivalent typed library) — one state machine per aggregate with a lifecycle (Claim, Election, Admission, Order, Encounter, Care Plan, …); explicit state names, transition events, guards, side effects in TypeScript. Current state is a column on the aggregate row; transitions occur via service functions committing the new state **in the same transaction as the side effects**. REJECTED anti-pattern: a generic "Workflow Engine" service.
- **ARCH-261** (§25.2 Validation frameworks): Rules-as-data per domain with a shared **interface only** in `packages/rules-engine/` (no shared implementation). Each domain implements its own typed rule registry (`ClaimValidationRule`, `CostReportValidationRule`, `IntakeValidationRule`, …). REJECTED: a generic rules engine.
- **ARCH-262** (§25.3 Async work): BullMQ on Valkey. Every queue declares: explicit name, priority, retry policy, backoff strategy, concurrency limit, dead-letter queue. REJECTED: raw `Promise.all` chains for complex async; fire-and-forget HTTP without job tracking.
- **ARCH-263** (§25.4 Idempotency): Every mutating route accepts an `Idempotency-Key` header. Backend stores `(org_id, key, request_hash, response)` in Valkey for **24 hours** with PG mirror for crash safety. Same key + same body → cached response. **Same key + different body → 409.** Implemented by Module 1 §4.6 middleware.
- **ARCH-264** (§25.5 Outbox): Every cross-module event goes through the `outbox_event` table; producer commits the event **in the same transaction** as the domain change; dispatcher worker reads, delivers (Socket.IO emit, BullMQ enqueue, internal HTTP), marks dispatched. Module 1 §3.10 schema + dispatcher worker.
- **ARCH-265** (§25.6 Audit): Every PHI access and mutation calls the `audit()` helper **in the same transaction** as the action; the row records actor, action, target, before/after (PHI-redacted), correlation ID, source IP, outcome, retention class. Module 1 §8.2 helper API. REJECTED: "add audit logging later."
- **ARCH-266** (§25.7 Errors): Typed error classes only — `ChartWardenError`, `ValidationError`, `NotFoundError`, `UnauthorizedError`, `ForbiddenError`, `ConflictError`, `DegradedError`. Never throw strings. Handlers convert to the standard error envelope via the Fastify error handler (Module 1 §4.3 contract).
- **ARCH-267** (§25.8 Logging): Pino with structured fields and explicit redact paths. Every log line carries correlation ID, organization ID (when known), user ID, module name, trace/span IDs. PHI never logged in plain; patient IDs hashed with per-env salt if needed for debugging.
- **ARCH-268** (§25.9 Config vs flags vs tenant variation): env vars for operational config (never tenant-specific); `feature_flag` table (Module 1) for product toggles (global or per-tenant); `organization.settings` jsonb for tenant configuration; state-specific behavior via state registry/adapter. **FORBIDDEN: `if (tenant === 'engrace')`-style branches** — any tenant-specific behavior must be a configuration value.
- **ARCH-269** (§25.10 Tenancy): ALWAYS use `withOrgContext()` for any code path touching PHI tables — sets `app.org_id` and `app.user_id` PostgreSQL session variables read by RLS policies. RLS is the safety net, not the only guard. Module 1 §3.13 helper.
- **ARCH-270** (§25.11 Testing): Unit tests for pure functions; integration with Testcontainers (real PG, Valkey, MinIO); **RLS isolation tests required for every PHI-bearing module** (cross-tenant denial cases); Playwright E2E for critical flows; snapshot tests for SQL migrations (catch accidental destructive changes).
- **ARCH-271** (§25.12 Migrations): Forward-only Drizzle migrations. Two-phase pattern for breaking changes: Release N add nullable + dual-write; Release N+1 backfill + switch reads; Release N+2 drop old. FORBIDDEN: destructive migrations in the same release as dependent code changes.
- **ARCH-272** (§25.13 Cross-module communication): Modules communicate via Socket.IO events (real-time), BullMQ jobs (async), and outbox (durable). Direct cross-module function calls allowed within `packages/`, but PHI-touching reads still go through `withOrgContext()`. **FORBIDDEN: reaching into another module's database tables — always go through the owning module's service API.**
- **ARCH-273** (§25.14 External service calls): Wrap every external call in a circuit breaker with configured timeout, retry, backoff. Failures propagate as `DegradedError`, never raw `fetch` rejections. **Per-vendor adapter package** so the rest of the system depends on an interface, not a vendor (registered list: ARCH-145).
- **ARCH-274** (§25.15 Mobile): Capacitor apps assume intermittent connectivity: draft state cached locally, sync on reconnect; **EVV check-in/check-out must work offline** (store locally, sync later, server reconciles); biometric unlock at app launch; app-level idle timer (**15 min**) re-prompts auth.

## 19. Architecture Fitness Pipeline (§25.15 / ARCHITECTURE_25_15_FITNESS)

- **ARCH-280** (§25.15): Principle: every boundary the architecture cares about is converted into a CI check that runs on every PR; a deadline-driven shortcut must be unmergeable. `architecture/module-manifest.ts` is the **single source of truth** (codePaths, dependsOn verbatim from §20, ownedTables); every fitness check reads it; a dependency or table addition is a one-line reviewed manifest edit.
- **ARCH-281** (§25.15 — the nine checks, all error-severity in CI):
  1. **Module import boundaries** — dependency-cruiser rules generated from the manifest; a module may import only its declared deps + leaves (e.g., M8 may import 6, 7, 36, 38 + leaves; importing M12 fails).
  2. **Adapter mandate** — vendor SDKs (`stripe`, `twilio`, `@anthropic-ai/sdk`, …) only inside their adapter package.
  3. **Domain purity + FHIR direction** — `packages/domain` may not import I/O, app packages, or FHIR (locks §9).
  4. **Leaves stay leaves** — `shared`/`types`/`ui` may not import feature packages.
  5. **Helper-only tables** — no direct schema import of `audit_event`/`outbox_event`/`idempotency_key` outside the helper.
  6. **Table ownership** — `scripts/check-table-ownership.ts`; same-tenant cross-module table access (the leak RLS cannot catch); cross-module reads through the owner's repository, never its schema.
  7. **No cycles** — dependency-cruiser `no-circular`.
  8. **Explicit authz** — Biome rule `require-explicit-authz` (Module 3): no PHI route ships without `requirePermission` + ABAC.
  9. **Read-audit** — Biome rule `require-read-audit` (Module 4): no PHI route ships without read-audit capture.
- **ARCH-282** (§25.15): Rationale for check 6 (binding interpretation): RLS enforces the tenant boundary (`app.org_id` match) and says nothing about module-to-table mapping; table ownership is enforced independently — a module may touch only its `ownedTables`; cross-module access goes through the owner's exported repository/service, never its Drizzle schema.
- **ARCH-283** (§25.15, manifest note): The manifest is currently authoritative for Modules 1–4 (specced) and encodes the full §20 dependency graph for all 40. As each module is specced, its `ownedTables` are filled and `codePaths` confirmed; the checks tighten automatically.
- **ARCH-284** (depcruise): Generated module-boundary rule semantics: for each module, imports into any `^(apps|packages)/` path NOT in `allowedImportPaths(id)` (= own codePaths + dependsOn codePaths + LEAF_PACKAGES) are error-severity. Vendor rules: from anywhere except the owner package, to `node_modules/<pkg>` is error-severity. Helper-table rules: from anywhere except `packages/audit`, `packages/shared`, `packages/db`, to `packages/db/src/schema/.*<table>` is error-severity.
