# M36 Secure Messaging & Alerts — STRIDE, DR tier & Integration inventory (M36-T10)

Captures the three non-code M36-T10 deliverables that have no gate of their own: the §4.10 STRIDE
threat model (SEC-007 / M36-F09), the disaster-recovery tier, and the integration inventory. The
authoritative text is the module spec (`docs/modules/WARDENX_MODULE_36_MESSAGING_SPEC_v0_4.md`);
this file is the in-repo pointer that travels with the code and names where each control lives.

## STRIDE threat model (spec §4.10)

M36 is the platform's realtime nervous system — it routes PHI-adjacent alerts, manages multi-tenant
channel membership, and exposes inbound vendor webhooks. Ten threats across S/T/R/I/D/E; each control
already lives in code or in a sibling task.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| S-1 | Spoofing | Forged Twilio/Postmark webhook | §4.9 replay window + signature/IP-allowlist — `packages/messaging/src/webhooks` (`assertReplayWindow`, `verifyTwilioSignature`, `verifyPostmarkWebhook`); enforced in `routes/webhook-routes.ts` before any handler logic |
| S-2 | Spoofing | Cross-tenant DM | `channel` RLS on `app.org_id` (migration 0017) + within-tenant DM validation in the route service |
| T-1 | Tampering | `body_cipher` replacement | `body_sha256` + `messaging.hash_verify` nightly job (`jobs/integrity-jobs.ts` `runHashVerifyForOrg`, scheduled by `jobs/integrity-workers.ts`); M4 write-audit trigger on `message` |
| T-2 | Tampering | `channel_member` tampering | M4 write-audit trigger (compliance-class) on `channel_member`; `canViewChannel` (active-membership check) at read time |
| T-3 | Tampering | Alert-rule loosening | `enforce_alert_routing_tighten_only` DB trigger (migration 0017); additive-only override columns |
| R-1 | Repudiation | Author denies send/delete | M4 write-audit trigger on `message` (sent/edited/tombstone); `body_sha256` anchors plaintext |
| I-1 | Info disclosure | PHI in out-of-band payload | `sanitizeForOutOfBand` is the only path out-of-band (`notification/`); §7.2 golden test; dependency-cruiser blocks direct vendor calls |
| I-2 | Info disclosure | Presence enumeration | `presence_self_or_coworker` RLS; Socket.IO rooms computed from `channel_member` at connect (`realtime/computeRoomSet`) |
| D-1 | DoS | Alert-suppression flood | API-gateway rate limit; separate BullMQ queues w/ fixed concurrency; `system_locked` SOS at `priority: 10` (`jobs` queue params) |
| D-2 | DoS | Webhook replay flood | Replay window + idempotency on `vendor_message_id`; webhook handler enqueues and returns 200 (`jobs`/webhook routes) |
| E-1 | EoP | Break out of `care_team` ABAC | The shared effective-access policy used by `listChannels` and `canViewChannel` (`messaging-route-service-db.ts`): active organization membership, an active `channel_member` row, plus — for a `care_team` channel and an `auto` member — a live `CareTeamProvider.careTeamMembers` roster check (GAP-104; `manual` admin-override members are authorized by the override itself). Channel detail/history/send routes compose `canViewChannel`; RLS remains the tenant backstop. There is NO direct M5 schema import and no M3 `evaluate('caseload_membership')` call. |
| E-2 | EoP | Disable a `system_locked` rule | `alert_rule_update` RLS `WITH CHECK (system_locked = false)` (migration 0017); §7.4 invariant test |

### SBAR messages (WP 3.3, ADR-0060)

The SBAR threats below are scoped to the `messaging.sbar` flow. The controls are in the files named, and they are
built on `feat/m36-wp33-sbar` and not yet merged.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| I-3 | Info disclosure | PHI in SBAR sections leaks beyond the message (previews, search, notifications, logs, audit) | The `sbar` node lives inside the encrypted rich body (`body_cipher`, `body_sha256`), so there is no new column or PHI store. Previews, search and notifications see only the fixed plain-text projection (`SBAR_SECTION_LABELS`), which is the same exposure as an ordinary body. Audit and error responses carry field and code only: `SBAR_INVALID` never echoes section text. Structure is checked by the sanitiser in `packages/types/src/messaging-rich-body.ts` and lengths by `validateSbar` in `packages/types/src/messaging-sbar.ts`. |
| T-4 | Tampering | Hint text injection: a tenant or a crafted hint carries markup, a fake instruction, or an emergency-looking claim into the composer | Tenant hint text is plain text only. It is linted with `lintTemplateText` on save and on read, and falls back to the platform hint when the lint fails. The hint is never projected into the body, so it cannot become part of the stored message. The static fallback is the platform hint text, which is fixed. |
| E-3 | EoP | Tenant loosening: a tenant lowers a section minimum or disables SBAR to weaken a clinical structure | `tenant_sbar_policy` is tighten-only. The DB CHECK sets the platform floor (`situation_min_chars BETWEEN 1 AND 500`, and the same for each section). `effectiveSbarPolicy(stored)` takes the larger minimum and ORs the booleans on every read, so a stored lower value cannot win. A write below the floor returns `422 SBAR_POLICY_FLOOR_VIOLATION`. There is no disable column, and the ops flag `messaging.sbar` is the only off switch. Policy edits require `messaging.template.manage`. Live proof: a raised floor beats a stored lower value (`m36-sbar.live.test.ts`). |
| E-4 | EoP | Urgency mistaken for escalation: a sender marks `urgent` and believes that someone is paged, or a reader treats the label as an alarm | `urgencyHint` is a sender-marked label only. It has no column, alert, notification, acknowledgment or event. The form always shows that messaging is not the emergency path, and it adds that marking urgent does not page or escalate anyone. The static test `m36-sbar-no-escalation.test.ts` fails the build if any M36 code outside the codec and validator reads `urgencyHint`. Mapping urgency to escalation is Phase 4 work under ADR-0057. WP 4.1 (ADR-0068) adds the `message.urgency` column, set only by the "Urgent clinical" entry; the hint is still never read, and the new threats are E-17, S-5, T-14, I-20, E-18, D-11 and R-8 below. |

### Communication tasks (WP 3.4, ADR-0061)

The task threats below are scoped to the `messaging.tasks` flow. The controls are designed in ADR-0061 and are being
built on `feat/m36-wp34-tasks`; the live suite (`m36-tasks.live.test.ts`) passes on a private container.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| I-5 | Info disclosure | Assignment as a side door: a user assigns a task to someone who cannot read the message, or a task keeps showing a message after access is lost | The assignee must be an active user who passes `canViewChannel` (including the Part 2 gate) at create and at reassign, else the uniform `422 TASK_ASSIGNEE_INVALID`. Visibility is checked again on every read and action, and only the creator or assignee can see a task, including on a replay of a convert (anyone else gets a generic `409 TASK_ASSIGNEE_ALREADY_HAS_ACTIVE` with no body). Accepted: no per-user alert throttle on convert; a self-reassign still sends the generic alert; the list limit applies before the visibility filter; a participant removed from the channel other than by offboarding keeps an active task hidden from them. The row has no title and no text, so it holds no message content; the message is read through the conversation. The alert text is fixed and generic, and the consumer re-checks channel access before it emits. |
| I-6 | Info disclosure | The open-tasks tile or the list acts as an existence oracle: it shows that clinical concerns exist in conversations the viewer cannot read | The tile counts only the caller's own active tasks (assigned or created) on channels the caller can see, and is dropped when the flag is off. The patient-context guard is unchanged (`patient.read` plus caseload or scope, break-glass not honoured). Missing, not a participant, hidden channel and deleted message all return the same 404. |
| T-5 | Tampering | Dismissing a clinical concern: a task about a patient is closed without anyone acting on it | A patient task is always clinical (`patient_id` is server-derived and a CHECK ties it to `clinical_concern`). A clinical task cannot move to `done` or `cancelled` without a closing reason code (service check, `422 TASK_CLOSE_REASON_REQUIRED`, and a database CHECK that holds against raw SQL). The reason is recorded and audited. A reason such as `no_action_needed` is allowed and is not judged (accepted limit). |
| T-6 | Tampering | Rewriting task history or protected fields | `chartwarden_app` has column-level UPDATE only on the changing columns, so `patient_id`, `created_by` and `message_id` cannot be rewritten. The event table is append-only (no UPDATE, no DELETE). No DELETE on either table for the app role. Write-audit triggers on both tables, with `patient_id` scrubbed. |
| R-2 | Repudiation | A duplicate or retried request creates two tasks, or a person denies having closed one | A partial unique index allows one active task per message and assignee, and a replay changes nothing and writes no event. Every move writes an event with the actor (a user, or the system actor for offboarding). A trigger refuses any update of a closed task, even via raw SQL. |
| D-3 | DoS / safety | An orphan task: the assignee is revoked or deactivated and an urgent item has no owner | The access-revocation consumer calls `reassignTasksForLeaver` on `m2.membership.revoked` and `m2.user.deactivated`. It picks the creator, then a care-team member, else flags `needs_owner` and alerts the creator. The realtime disconnect runs before, and even if, the reassignment fails (the failure is then rethrown for a retry and logged with ids only). It runs without the feature flag, converges on redelivery, and a failure on one task does not stop the others. Gap: if the creator and the assignee both lost access or left, the task stays flagged with no organisation-level view until the Phase 4 ownership model (ADR-0057). |
| E-5 | EoP | Tasks mistaken for escalation: a user believes an assignment pages someone, or an overdue task is treated as an alarm | There is no paging, timer, escalation or auto-close; overdue is a display state only. The convert dialog and the list always say that tasks do not page anyone and are not for emergencies. Mapping tasks to escalation is Phase 4 work under ADR-0057. |
| E-6 | EoP | A cross-module write: M36 task code reaches into M14 action items | A static test fails the build if code under `tasks/` imports `14-idg` or `@chartwarden/idg` or names `idg_action_item`. Delegation to M14 is a reserved extension that needs a new M14 seam (ADR-0061, decision 2). |

### Clinical handoffs (WP 3.5, ADR-0062)

The handoff threats below are scoped to the `messaging.handoffs` flow. The controls are designed in ADR-0062 and are being built on `feat/m36-wp35-handoffs`; the live suites (`m36-handoffs.live.test.ts`, `m36-handoff-lifecycle.live.test.ts`) have not been run yet.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| I-7 | Info disclosure | A handoff as a side door to patient identity: the sender names a patient label and open-work status to a colleague who should not see it | The receiver must be an active messaging user holding `messaging.read`, `messaging.send` and `patient.read`, and must pass the 42 CFR Part 2 gate for every patient, at offer and again at accept; otherwise the whole offer is refused with the uniform `422 HANDOFF_RECIPIENT_INVALID` and no reason. The gate is applied again on every read; a failing or unreadable patient renders as `restricted` with no label. The sender must have each patient on their own caseload. A gate or seam outage on a write fails closed. Accepted: the receiver may be off the caseload on purpose, so the owning module's caseload ABAC is not applied to them, and accepting grants no chart access. Data already fetched cannot be recalled if a release is revoked mid-offer. |
| I-8 | Info disclosure | A wrong-recipient offer, or a probe of other people's handoffs by id or by item | Only the sender and the receiver can read or act on a handoff; missing and not a participant return the same 404. The pending-item index gives a generic `409 HANDOFF_ITEM_CONFLICT` with no data about the other offer, and an offer replay can only return the caller's own record. Accepted risk: because the index is organisation-wide, a caseload peer who shares a patient can learn from that 409 that an open handoff exists for the patient, and is blocked from re-offering until it resolves or expires (at most 15 to 240 minutes); the alternative is double accountability for one item (ADR-0062). The detail read and accept, decline and cancel re-check `patient.read`, and every reply that carries patient labels (including the POSTs and prefill) is read-audited once per patient. The row holds pointers and no text. Events, alerts and audit carry no patient id and no item reference. The sender can withdraw a mistaken offer (`cancelled`). |
| I-9 | Info disclosure | An existence oracle: a tile or team view shows non-participants that a handoff exists for a patient | There is no patient-context tile and no team-wide or supervisor view. Supervisors receive an alert with ids only. |
| T-7 | Tampering | Moving accountability without acceptance, rewriting parties, or editing a closed handoff | Each item carries `accountable_user_id`, the sender until the item is accepted. A database guard trigger allows `accepted` only with the receiver as accountable user, keeps the accountable user unchanged for every other move, and refuses any change to an item that is no longer `pending`. A second trigger refuses any update of a closed handoff. `chartwarden_app` has column-level UPDATE only on the changing columns and no DELETE on any handoff table. The server re-verifies every item against the same sources as pre-fill and fails closed when a source is unavailable. |
| R-3 | Repudiation | A duplicate offer, or a person denying they accepted or declined | A partial unique index allows one open offer per sender and receiver pair, and a replay writes no event; an open offer already past its deadline is expired first, so a repeat offer is never answered with a dead one. A `BEFORE INSERT` trigger on the item table refuses a new item that is not `pending` or not owned by the offering sender. Every move appends an event with the actor (a user, or the system actor for the timer and offboarding). The item table has a write-audit trigger that scrubs `patient_id` and `ref_id`. |
| D-4 | DoS / safety | An offer nobody accepts: the patients are believed covered, or the supervisor alert reaches nobody | A per-minute timer (`messaging.handoff_expiry`) expires due offers, and accept and decline also refuse past the deadline, so an unopened offer cannot stay open. The tenant policy is tighten-only (15 to 240 minutes) and is re-applied on every read. On any unaccepted outcome the sender is alerted and the supervisor rule is alerted; if that reaches nobody, a `needs_attention` event is recorded and the sender gets a second alert. The timer and the sweep run with the flag off. Gap: the alerts are in-app only; nothing pages anyone (Phase 4). |
| D-5 | DoS / safety | An orphan handoff: the receiver or the sender is revoked or deactivated while an offer is open | The access-revocation consumer attempts task and handoff reassignment, then rethrows the first error, and the socket disconnect still runs first. An open offer to a leaver is declined as `recipient_left` and the sender is alerted. An open offer from a leaver gets one `sender_left` event and supervisors are alerted. It converges on redelivery and isolates a failure to its own handoff. |
| T-8 | Tampering | An expiry race: accept and the timer act on the same handoff at once | Accept, decline and expiry take a row lock on the handoff, so the first to lock wins and the other sees a closed or changed row. Guarded `UPDATE ... WHERE state = 'pending'` writes decide replay versus conflict. A task transfer that cannot complete fails the whole accept and changes nothing. |
| E-7 | EoP | Policy loosening: a tenant lengthens the deadline | `tenant_handoff_policy` is tighten-only: a CHECK of 15 to 240, and the effective value (and the deadline derived from it) is applied again on every read, so a hand-edited longer row cannot win. Policy edits need `messaging.template.manage`. |
| E-8 | EoP | Handoffs mistaken for paging or escalation, or a cross-module write: a user believes the receiver was paged, or handoff code writes into another module | There is no paging, retry or escalation chain. The compose screen always says that handoffs do not page anyone and that the sender stays responsible until the receiver accepts. A static test fails the build if code under `handoffs/` imports another module or calls a mutating seam method; the only write outside its own tables is the communication task store. |

### Chart promotion (WP 3.7, ADR-0063)

The promotion threats below are scoped to the `messaging.promotions` flow. The controls are designed in ADR-0063 and built on `feat/m36-wp37-chart-promotion`; the live suites (`m36-promotions.live.test.ts`, `m36-promotion-targets.live.test.ts`) were run on a private container after the code-review fixes. All wording is provisional pending clinical-lead sign-off.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| I-10 | Info disclosure | A promotion as a side door: a requester pushes a message to IDG or M8 reviewers who cannot read the channel or the patient | The request needs `messaging.promote`, channel visibility and the Part 2 gate for the patient at request time. The M14 item stores a pointer and attribution only (no text) and there is no link back to the message from the agenda. The M8 snapshot text is handed out only by the seam, only to a caller that passes `withText` (the M8 owner), only for `m8`, only while the message is unchanged (an edited message gives `edited_since` and no text), and only after the reviewer passes the Part 2 gate and holds `patient.read` and `encounter.addendum_sign`. The M14 list returns no message or channel ids. Reads are limited to the requester and people who can view the channel and pass Part 2; everyone else gets the uniform 404. Events, alerts and audit carry no patient id, hash or text. Accepted: an M14 reviewer alert reaches every `idg.coordinate` holder in the organisation, with ids only. |
| I-11 | Info disclosure | Part 2 at review: a reviewer who may not see a Part 2 patient's message reads it through the promotion, or a release is revoked after the request | `forReview` and `pendingForPatients` apply the Part 2 gate again for the reviewer and the patient; a deny, a throw or a missing reviewer permission returns `null` or leaves the row out; a caller that does not ask for text never causes a decrypt, and the M8 list decrypts at most 10 bodies per GET under a read-audit event that names the encounter. Detail reads re-check `patient.read`, and replies that carry the patient are read-audited with a resource id. Gap: text already fetched by a reviewer cannot be recalled after a later revocation. |
| S-3 | Spoofing | A spoofed outcome event: an event from the wrong owner module, or a forged `decided` event, marks a request accepted | M36 never decides. `result_ref`, `decided_by_user_id` and `decided_at` are set only by the M36 consumer of `m8.chart_promotion.decided` and `m14.chart_promotion.decided`, which are published only inside the owner's own transaction (sign, or add to agenda). The consumer takes the tenant from the envelope only and checks that the event owner equals the request's target module; a mismatched event is ignored. A different result on an accepted row is logged with ids and ignored. |
| T-9 | Tampering | A hash or revision mismatch, or an erased source: the reviewer is shown text that is not what was requested | The row keeps the SHA-256 of the body at request time and no text. At review the text is re-read from the live message if its hash matches, otherwise from the one `message_revision` with that hash (append-only), and is checked against the hash. Missing, erased or mismatching gives `null` and nothing is shown (fail closed). A request after an edit supersedes the old one. M8 content enters the chart only as the reviewer's own signed addendum, with the attribution columns recorded. |
| R-4 | Repudiation | A withdraw-versus-sign race: the requester withdraws while the reviewer signs, or the same request gets two results | Both paths lock the request row and use guarded `UPDATE ... WHERE status = ...`. A database trigger lets only a `superseded` or `withdrawn` row move to `accepted` (a signed record exists, so the truth beats the intent) and refuses any change to an `accepted` or `rejected` row. Partial unique indexes allow one live M8 addendum and one M14 item per request, and one `proposed` request per message and target. A replay returns the existing request and publishes nothing. The audit trigger records who and what, with the actor `system` for the consumer. Draft versus decision (review M1): the M8 and M14 insert guards take a share lock on the proposal row; the M8 sign guard re-checks under a share lock that the request is not rejected or accepted; the owner reject routes refuse (409) while a draft or item exists; accepting a superseded or withdrawn row closes its same-text proposed siblings. Residual: an unapplied reject event can still be followed by a draft and a signature (the consumer logs the conflict). |
| E-9 | EoP | A path from chat to an order (M11) or a medication, or an unreviewed copy into the chart | The targets are exactly `m8`/`encounter_addendum` and `m14`/`idg_agenda_item`, enforced by a CHECK, a TypeBox enum, a constant and the seam. A static test fails the build if the M11 or M12 trees, the orders package or the medications package mention chart promotion, or if promotion code or the migration CHECK names `m11`, `order` or `medication`. A route test sends `m11` and expects 422. Nothing is written in M8 or M14 until the reviewer acts there with the owner's own guards (and a fresh step-up to sign). An aide path does not exist: aides, compliance and admin-only roles do not hold `messaging.promote`. |
| E-10 | EoP | Permission loosening: a tenant or a role widens who can promote, or the flag is used to bypass review | `messaging.promote` is a separate permission granted by the migration only to clinical role templates; a tenant can only remove the grant. The flag is default off and a tenant cannot turn on a target that does not exist. The M36 code writes no M8 or M14 table and calls no mutating seam (static test, 3.5 pattern); the seam is read-only. The outcome consumer runs with the flag off so that a signed addendum always closes its request. |

Flag off, or a channel that is not `care_team`, answers `200` with an empty list. There is no tile, cross-patient or per-meeting view, so no oracle beyond the channel the caller can already read. |
| I-13 | Info disclosure | 42 CFR Part 2: an IDG thread shows a restricted patient to someone without a release | The list route and the thread use the channel-view guard, which applies the Part 2 gate on every read, and the read audit attributes each patient. The pairing and the meeting link carry ids only. |
| D-6 | DoS / safety | A thread stays open after the meeting is adjourned or cancelled, or a rescheduled meeting has no forward pointer | Accepted limit (D4): there is no lock and no lifecycle consumer, and the chip shows the live meeting status each time it is opened. A decision is never taken from the thread; it is recorded in IDG. |

### Lifecycle review queue (WP 3.8, ADR-0065)

The lifecycle threats below are scoped to the review queue (`messaging_review_item`, migration `1103`) and the `m36.patient-lifecycle-review` consumer. The controls are designed in ADR-0065 and built on `feat/m36-wp38-lifecycle`; the live suite is `m36-lifecycle-review.live.test.ts`. IDs follow the WP 3.6 block; WP 3.9 and 3.10 add theirs on other branches, so expect a renumber on rebase. All wording is provisional pending clinical-lead sign-off.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| I-16 | Info disclosure | The queue as an org-wide PHI list: a permission holder sees every departed patient with open tasks, beyond their own caseload | Accepted limit (D7): the audience is the supervisor role set, the same shape as the handoff supervisor alert. The permission `messaging.review` is clinical-only, granted by the migration to supervisor role keys and never to `org_admin`; the routes also need `messaging.read` and `patient.read`. The list is read-audited per patient (`patientIdsPayload`), a label appears only in an authorised response, no message body is shown, and events, alerts, correlation ids and logs carry ids and enums only. Location scoping is a recorded follow-up. |
| I-17 | Info disclosure | 42 CFR Part 2: a restricted patient appears in the queue, or a restricted row is acted on | The Part 2 gate runs for the caller on every row; a deny or a throw makes the row `restricted` (no label, `task` null except `item_id`, no actions) and it is still listed and counted so it is never silently invisible. An action on a restricted, missing, foreign or flag-off row is the same byte-identical `404`. A reassign target must pass the same gate for the task channel. |
| D-7 | DoS / safety | A supervisor closes or reassigns a clinical task without context, so a follow-up is lost | A decision needs one of the five existing close-reason codes (no free text, no empty close); a clinical task cannot be closed without a code (CHECK `communication_task_clinical_close_needs_reason`). A reassign target must be active, able to view the channel and not already hold an active task on the message. The code is kept on the task, its event and the review row, and resolved rows are final (trigger). The queue shows task metadata only (known limit). |
| D-8 | DoS / safety | Alert suppression or dedupe hides the review: the correlation id swallows a needed alert, or no supervisor is reachable | The correlation id is `review:<sha256 prefix of source and trigger>:<alert type>[:<user>]`, so only the two death events and redeliveries collapse; a later discharge has a different trigger and alerts again. The assignee alert is an always-on fallback; when the supervisor audience resolves to nobody a warning is logged (ids only) and assignees are still alerted. The row is queued whether or not the flag is on, so the queue itself is the record. There is no paging (Phase 4). |
| R-5 | Repudiation | A double death event or a redelivery double-queues a task, or a decision is replayed | An M6 death and the cascaded `m5.patient.deceased` share the patient id as trigger reference; a unique index on (organisation, source, trigger, item kind, item) plus a partial unique index on one open review per item make the second insert a no-op. Replaying the same action by the same user on a resolved row returns the current row; anything else is `409 REVIEW_ITEM_STATE_CONFLICT`. The service locks the task then the review row, so a racing close cannot deadlock or double-resolve. |

| I-36 | Info disclosure | The candidate lists disclose care-team colleague display names for a request whose channel the supervisor cannot open | Only eligible colleagues (care-team member who can see the channel, `messaging.urgent.receive`, Part 2 gate passed, not the sender, not the current assignee), only user id and display name, capped at 50, same party and visibility rules as the normal reassign for the card read. When the Part 2 gate walls the supervisor off from the patient the candidates read is an empty list and the POST is the same uniform 422, so the care team is not named to them (OPEN, compliance / Part 2 review). The candidate reads carry no patient id, so there is no patient-level read-audit: request-level audit only. **OPEN (compliance review):** same class as the assignee name, unconfirmed. |
| D-24 | DoS / safety | A supervisor (or a bug) floods reassigns, ping-ponging a request between people so nobody holds it, or notifies a colleague repeatedly | The same fail-closed limiter as reassign (ADR-0069 decision 13): 20 per minute per user, 200 per minute per organisation, 5 per 5 minutes per (actor, colleague) pair (the pair bucket on the POST body only); both candidate GET routes use the per-user and per-organisation buckets. A per-request cap of 5 supervisor reassigns in a rolling 24 hours (`409 ACK_SUPERVISOR_REASSIGN_LIMIT`, generic message: ask the clinical lead) stops two supervisors passing a request back and forth (provisional number, OPEN). Each reassign starts a new window and re-arms the timer, so a moved request is never left unwatched; `failed_unreachable` moved this way is watched again (G-5 for the reassign path only; for requests nobody reassigns G-5 stays open, D-17). |
| E-28 | EoP / safety | A supervisor acknowledges, resolves or cancels on someone's behalf, reads the thread through the reassign, or "acknowledged by phone" is recorded out-of-band (G-1) | The route and the guard cannot write `acknowledged`, `resolved` or `cancelled` for a person other than the assignee/sender (ADR-0069 actor rules unchanged); the route reads no message and grants no channel access; a request in `acknowledged`, `resolved` or `cancelled` is `409 ACK_STATE_INVALID`. "Acknowledged by phone on behalf of" is rejected (ADR-0078 decision 8) and nothing writes it. **OPEN for the clinical lead to revisit.** |

### Unwatched requests and the supervisor page (M36 gap closure part B, ADR-0079)

The unreachable watch (per-minute sweep) re-raises an overdue `failed_unreachable` request to the supervisors on a bounded schedule; the supervisor attention alert (`m36.ack.supervisor_attention`) tells the supervisor audience and, with the notification policy on, plans a page to their verified endpoints; a stalled-escalation gauge and watchdog report a dead escalation worker; ops notices are claimed once across the fleet on Valkey. No new table, route or migration.

| # | Class | Threat | Control (where it lives) |
|---|-------|--------|--------------------------|
| I-37 | Info disclosure | The supervisor alert, its page or an ops notice leaks the patient, the message, the sender or a name | The alert payload is an allowlist (`reason`, `requestId`, `ackClass`, one fixed sentence, a link to the queue); no channel, message or user id. Every ops notice carries organisation id, request id, class, counts and codes only; the failed-page notice carries a delivery id and a channel. Pinned by the unit and live tests (key lists asserted, a planted secret string absent). The out-of-band sanitiser still applies to a planned push. |
| T-21 | Tampering / safety | A failed supervisor page is treated as a failed route to the assignee, so a request is escalated or marked unreachable because a supervisor's phone failed | The attention alert is in `SUPERVISOR_PAGE_EVENT_TYPES`, **not** in `DESIGNATED_EVENT_TYPES` or `ACK_ASSIGNEE_ALERT_EVENT_TYPES`; the delivery-failure consumer answers it with an ops notice and returns before any service call (unit test). |
| D-25 | DoS / safety | The watch hot-loops, floods supervisors, loses a stage, or re-sends to a failing transport | Eight stages at most per request and version (windows 1, 2, 4, 8, 16, 24, 24, 24 h; opening at 0, 1, 3, 7, 15, 31, 55, 79 h from the anchor, the later of the deadline and the failure instant; stage 0 skipped when it failed after its deadline). The alert is emitted idempotently (unique correlation id) until this process has emitted it, so a crash after a claim cannot lose a stage; the ops notice and the unpaged notice are each claimed under their own key, once per stage **per fleet only while Valkey is up** (otherwise once per process per stage: fail-open duplicates). The read is bounded in SQL to the live schedule, 500 rows per organisation per tick, so exhausted rows never starve fresh ones. The watch never writes the request and never sends to the assignee. |
| D-26 | DoS | The ops-notice claim store (Valkey) fails, is slow or is flushed and notices repeat or vanish, or a slow Valkey stalls the sweep | Each call has a 200 ms deadline; an error or timeout opens a 30 s breaker (local fallback, no waiting); expired local entries are pruned. Fail-open to a per-process claim: a duplicate notice is preferred to a silent breach; a flush repeats a notice at most once per key. The alert rows converge regardless. |
| R-13 | Repudiation / safety | A dead escalation worker goes unreported because the check lives inside the dead sweep, or the check itself is blind | The watchdog is a plain timer in every backend process, independent of BullMQ, over the guarded cached sampler of the gauges, with a fleet-wide tick claim (one audited platform enumeration per minute with Valkey up; per process otherwise) and an in-flight guard. **It can be unmeasured** (platform pool or database unreachable, timeout, an organisation not countable): after 3 consecutive unmeasured ticks it raises `m36.ack.escalation_stall_unmeasured` (claim-deduped); a process that cannot reach the database cannot send even that, so the gauge reading `-1` (alert on it) is the backstop. Two plain limits: the consecutive-unmeasured counter is **per process** (each process counts its own ticks; with the tick claim only the process that holds it samples, so a flapping claim holder can reset the count), and a sample in which **any one organisation fails (`orgsFailed > 0`) is treated as unmeasured**, so one unreadable tenant hides a stall in all the others until it is readable (the gauge shows -1 for the same reason). It cannot say which of the two queues is dead (ADR-0079). |
| E-29 | EoP | A supervisor alert or page reaches someone outside the tenant or outside the supervisor roles, or a tenant row re-aims it at a stranger | Recipients come from `role_set` under the tenant's RLS (`membership_role`); the endpoint reader enforces the session tenant and returns channel names only; a tenant may re-aim the rule only to its own roles. The attention alert is deliberately not pinned (the audience is the tenant's call), unlike the four assignee alerts. Live: another tenant's supervisor receives nothing. **Limit:** because the rule is not pinned, a tenant row can re-aim or disable it and nothing detects that (`supervisor_unpaged` covers only a missing page); a tenant that re-aimed the old `ladder_exhausted` / `failed_unreachable` rules can receive two alerts per event until it re-aims the new one (ADR-0079, chosen over a per-tenant rule-scan notice as disproportionate). |

### Workforce offboarding (WP 5.9, ADR-0084)

An officer previews and runs the offboarding of a departed user (`messaging.offboarding.manage`, and for the run also `messaging.read` + `messaging.review` + a fresh step-up). Nothing is stored: each step recounts the live rows and the record of a run is its audit row.

| # | Class | Threat | Control (where it lives) |
|---|---|---|---|
| WO-1 | Info disclosure | The preview becomes a way to look at active staff or to probe another tenant's users | The user must have a membership in the officer's organisation; another tenant's user and an unknown id are the same 404; an active user is a 409 that reveals nothing but "has not left". The response is counts and fixed keys, no name, message or patient. Live: foreign = unknown, nothing changes. |
| WO-2 | DoS / safety | An urgent request keeps waiting on a departed person and nobody knows | A waiting request is moved through the ADR-0078 supervisor reassign; one nobody can take stays assigned and visible in the unacknowledged queue and raises the shared supervisor attention alert (`assignee_departed`) once per request and version. An acknowledged-but-unresolved request and an urgent message with no request are reported `needs_person`, never dropped. **Limit:** the on-call roster is M19's and M36 cannot read it (the router seam is a deny-stub), so a vacated seat is advisory only. |
| WO-3 | EoP | The run is a way around the reassign checks (a request moved to someone who cannot see the patient, or by someone walled off) | It calls the same supervisor reassign, so the eligibility (active, can view, qualified, Part 2) and the update guard of migration 1126 apply; the officer is the actor and must hold the reassign's own keys. A walled-off officer moves nothing for that patient and the request stays visible. |
| WO-4 | Repudiation | A run cannot be tied to a person, or a repeat double-notifies | One `m36.offboarding.executed` row per run (actor, target, per-item state and counts, complete), plus the audited rows of the services it reuses (session revoke, reassign event naming the officer and reason). The attention alert is idempotent on request and version; a re-run changes and notifies nothing (live). |
| WO-5 | Tampering | Offboarding deletes what must be kept, or sends as the departed person | Past messages, drafts and the attribution of what they sent are never touched (pinned by `offboarding-static.test.ts`); scheduled sends are deleted (never sent), reminders and snoozes removed, endpoints expired not deleted. A scheduled send of a person who has left is also refused by the dispatcher's membership check. |
| WO-6 | EoP | A session or push endpoint of a departed person keeps working | The ADR-0083 revoke deletes every live staff session (next REST call 401), closes its sockets and expires its endpoints; endpoints no session links to are expired too. **Limit:** sessions bound to another organisation are not touched (the officer's rule); M2 reaps those on a platform deactivation. |

## Disaster-recovery tier

**SOS field-safety voice escalation is the platform's single Tier-1 dependency** (architecture /
integrations §6.13; spec §7.7). Tier-1 = life-safety: the `messaging.send_voice` queue runs at
`priority: 10`, and on three failed voice attempts the `field_safety.escalated` system alert fires,
supervisor SMS+push are escalated explicitly, and WardenX ops are paged (spec §4.4 voice queue row).
The **in-app Socket.IO floor** is the always-available delivery path — no external vendor outage can
prevent an alert reaching a connected client (spec §2.4 invariant 1). All other channels (push, SMS,
email) are additive and degrade to `partial` outcomes without blocking the dispatch.
