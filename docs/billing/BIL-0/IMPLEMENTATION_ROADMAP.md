# BIL-1 through BIL-5 roadmap

This is a proposal. No code is authorized by BIL-0. Keep the billing feature flag inactive for shared-account production until release criteria below are met. All PRs are independently reviewable and preserve M23/M24/M41/M25 boundaries.

| Phase | First deliverable and dependencies | Acceptance and rollback |
|---|---|---|
| **BIL-1** | Inactive Claim.MD account response/ERA inbox, usage-separated account cursor, lease, page-atomic capture, raw PHI protection, quarantine. Reuse adapter wire/parser and port types. Dependency: confirm vendor pagination/retention and permitted read modes. | Synthetic account pages with mixed tenants, malformed item, 20k boundary, crash, replay; cursor never passes uncaptured content. Rollback disables poller, leaves captured data/cursor intact. **First PR** is response capture only, no live consumption. |
| **BIL-2** | Identity registry/snapshots and router; typed provenance for normalized Claim.MD statuses; feed existing M23/M41 apply via idempotent fan-out. Correct M23 per-claim Claim.MD payer route; preserve separate notice rules. | Two orgs, four entities, mixed M23/M41 response: only intended claim changes; unmatched stays quarantined. Dual-read parity before switch. Rollback stops fan-out, keeps inbox for reconciliation. |
| **BIL-3** | Account ERA capture and safe routing into existing M25; whole-file/transaction/payee checks, correct payer kind, explicit manual match; CAS/recoupment/reversal fixtures. | Mixed provider 835 never auto-posts to wrong org; exact match posts once, ambiguity stays manual; ledger balances; duplicate/resend safe. Rollback stops ingestion; financial entries use existing compensating operations, never delete/replay blindly. |
| **BIL-4** | Provider onboarding and payer readiness: claims/ERA/eligibility statuses with evidence and provenance, Claim.MD hosted enrollment workflow, payerlist reconciliation, location/entity mapping where proven. M23 HETS/M24 state capabilities remain separate. | Local `enrolled` alone cannot send; only verified transaction/payer activation can. Old EDI snapshots unaffected by identity edit. |
| **BIL-5** | Tenant UX and operations: per-entity/location selector, rejected/denied/in-doubt/paid/partial states, ERA/unmatched worklist, A/R, safe admin portal actions, account budget and lag dashboards, DR/cursor replay runbook. | Staff can resolve every quarantined/in-doubt item without cross-tenant raw access. Staged test → synthetic production → limited tenant cohort → general launch, with signed reconciliation and rollback rehearsal. |

**Non-regression:** no patient or vendor data in logs; no source-to-source module table reads; preserve M23 NOE/NOTR/transfer and MAC logic, M24 state-specific routing, M41 commercial authorization/routing, M25 exactly-once posting. Both test and production have independent account cursors/credentials. Validate source gates later: `bun run build`, `bun run typecheck`, `bun run arch:fitness`, `bun run test`, `bun run check:boot:platform` (see `AGENTS.md`), then relevant private-DB live suites and Docker changed-route probes. No test ran during BIL-0. A new live suite needs a `package.json` script and CI job. Use a private pgvector/pg18 instance with `max_locks_per_transaction=1024`, the NOBYPASSRLS app role, and fresh DB per suite per repository guide.

Production launch gates: written vendor support for each hospice 837I notice/claim workflow; per-payer Claim.MD IDs and enrollment confirmation; tested complex 835 and response pagination; permission probes; account budget failure test; dual-read reconciliation; explicit operations owner and rollback authority. Source inspection cannot certify any of these external states.
