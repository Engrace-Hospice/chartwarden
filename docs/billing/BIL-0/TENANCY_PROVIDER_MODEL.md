# Tenant, location and billing identity

The **current** M1 spine is `organization 1→many provider_entity 1→many location`: `packages/db/migrations/0000_foundation_initial.sql:14-59,223,240-243`. Provider entity carries CCN, legal name, NPI and encrypted Tax ID (`:27-40`); a location has one provider-entity FK and no independent organization ID (`:43-59`). Consequently several locations can share an entity, and one tenant can have several entities. A location mapped to two billing identities is **not** expressed by the core FK; a claim's chosen billing entity must be validated against admission/service siting and effective payer rules. Distinct entities with different NPI/TIN are already possible. Current global NPI uniqueness (`:240-241`) prevents a second tenant record with the same NPI, but historical reassignment/correction behavior was not certified.

A1/A2 could both default to E1; a payer-specific A2 mapping to E2 needs an effective date and explicit validation. Future tests must generate checksum-valid synthetic identifiers and keep all API calls disabled in BIL-0.

**Security evidence and limit.** Billing EDI profile and commercial enrollment use `app.org_id` FORCE RLS (`1269...sql:28-36`, `1265...sql:68-79`), as do acknowledgment and remittance cursor tables (`1267...sql:19-29`, `1254...sql:12-15`). M41 reads/apply use organization/provider/control predicates (`apps/backend/src/modules/41-billing-commercial/jobs/ack-apply.ts:169-179`); M25 match seams take org/provider/payer (`apps/backend/src/modules/25-remittance/ingest/claim-match-adapter.ts:39-56,158-180`).
