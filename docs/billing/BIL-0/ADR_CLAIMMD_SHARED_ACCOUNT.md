# Proposed ADR — one Claim.MD account, account-scoped inbound ingestion

**Status: proposed, not accepted or implemented.** One centrally managed Claim.MD account per usage (`test`, `production`) serves multiple ChartWarden tenants. The vendor key is platform-held; tenant staff use WardenX, and only authorized platform staff may have portal access. Claim.MD's [quickstart](https://docs.claim.md/v1/docs/test-account-quickstart-guide) explicitly supports this model and says `/response/` and `/eralist/` cursors are for all account claims/ERAs. Pricing and provider enrollment remain contractual/vendor facts ([pricing](https://www.claim.md/pricing/), [provider enrollment](https://docs.claim.md/docs/add-provider)).

## Decision

1. Keep `ClearinghouseTransport` for submission, validation, eligibility and per-claim status reads. Add an **internal Claim.MD account-stream capture seam** for inbound response and ERA pages. Do not overload provider-scoped `fetchAcknowledgments(ctx,cursor)` with an account-wide responsibility. Preserve the old port for Stedi/direct MAC and compatibility during rollout (`packages/x12-837-client/src/clearinghouse/types.ts:343`; `claimmd-transport.ts:701-729,805-875`).
2. One poller lease and one durable cursor per `(vendor account identity, usage, stream kind)`; separate test and production. Account identity is an internal opaque identifier, not the key. Capture each complete response page into a protected append-only inbox with vendor response ID, Claim.MD claim ID, PCN/CLM01, sender, raw status/stage, billing NPI/TIN, payer ID, timestamp and source hash. Store malformed/unrecognized records as bounded raw envelopes with PHI controls. Commit page items and cursor atomically; if capture fails, cursor does not move. A full page is repolled until exhausted. ERA list item and raw 835 must be durable before advancing `last_eraid`; implement explicit `Page` pagination and account-level budget/circuit breaker.
3. Resolve identity against **durable outgoing submission registry and sent identity snapshot**, then current provider history only as a secondary clue. Require unambiguous `(usage, vendor account, Claim.MD claim id or PCN/control, billing identity, payer)` agreement. If multiple/no candidates, quarantine without tenant-visible raw content; never attribute by caller org/provider or NPI alone. Vendor normalized status retains `origin=claimmd_normalized`; only a verified literal X12 document may be labeled 999/277CA.
4. Delivery to existing M23/M41 apply logic is idempotent by vendor event ID plus origin and account usage. An inbox row can have distinct module delivery state; no module can advance the vendor account cursor. M25 receives a verified org/provider/payer transaction set after payee and all CLP identities pass. Mixed identity files are quarantined or split only where the 835 structure proves independent safe boundaries. Preserve M25's transaction/dedupe/ledger guards (`apps/backend/src/modules/25-remittance/ingest/service-drizzle.ts:606-699,909-984`).
5. Account credentials stay in a managed secret store with least-privilege deployment access, rotation and separate modes. No account key in DB, logs, URLs, errors or audit diff. Require distributed rate counter at production boot: source currently falls back to process-local (`claimmd-transport.ts:313-315`; `apps/backend/src/index.ts:3917`). Outage/403 pauses reads and new uploads as policy dictates; maintain per-stream lag, quarantine, DLQ, retention/replay and manual reconciliation dashboards. Account-wide alerts must not expose PHI across tenant workspaces.

## Compatibility and rollout

Deploy schema/capture code inactive; backfill account streams into inbox with no tenant fan-out. Run dual-read comparison with existing per-provider cursors, recording only safe counts/IDs; do not allow two consumers to post the same ERA. Switch one usage/test account, then a tiny synthetic production cohort with explicit reconciliation, then tenant groups. Preserve existing cursor tables for rollback and audit, but freeze their Claim.MD writers after switch. Rollback stops fan-out and restores old readers only after reconciling the new account cursor; never blindly reset to zero or replay monetary postings. No production activation until vendor contract, test matrix and NOBYPASSRLS live proofs pass.

## Alternatives rejected

* Keep per-provider `/response/` polling: it repeats an account-wide read and filters/drops unrecognized records (`claimmd-transport.ts:697-729`), with independent M23/M41 cursors.
* Use NPI as tenant isolation: NPI is vendor metadata, can change, and is insufficient to authorize a tenant record (`claimmd-transport.ts:697-699`).
* Merge Medicare, Medicaid and commercial into one claim state machine: payer-specific notice, state adapter, enrollment and posting rules differ (`docs/adr/ADR-0100-commercial-billing-module-41.md`; `apps/backend/src/modules/24-billing-medicaid/jobs/submission-jobs.ts:250-275`).

Tradeoff: one account inbox adds protected storage and routing complexity, but provides one authoritative capture point, replay and a bounded account API budget. Account-wide failure becomes more visible; lease, DLQ and operations ownership are required.
