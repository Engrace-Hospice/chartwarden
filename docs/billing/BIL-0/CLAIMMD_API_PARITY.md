# Claim.MD API parity (published contract versus source)

Official primary contract: [Claim.MD API](https://api.claim.md/); workflow: [API quickstart](https://docs.claim.md/v1/docs/test-account-quickstart-guide). The API says 100 requests/minute per account, `Accept` selects XML/JSON, `/response/` covers **all account claims**, and `/eralist/` supports `ERAID`, `NPI`, `NewOnly`, `Page`. Source uses `https://svc.claim.md/services`, POST, body `AccountKey`, JSON accept, URL encoded reads and multipart upload (`claimmd-wire.ts:18-92`). 30-second local timeout and no redirect (`:19,51-68`). A 200 `error` is classified by codes, with vendor text omitted (`:182-193`; `claimmd-transport.ts:232-240`). This is source behavior, not a live guarantee for all response shapes.

One claim/file; vendor allows batches, which is optional. |

`claimmd-rate-limit.ts:19-75` budgets 7/5 seconds by usage; adapter fallback is process local (`claimmd-transport.ts:313-315`). 403/429 are retryable unavailable (`claimmd-transport.ts:211-229`). It is not certified that several workers share a counter. Production/test separation is one key for the configured usage (`claimmd-transport.ts:135-150,329-345`), not two simultaneous keys from one env factory. Published pricing has plans and possible extra billing-provider TIN charges; no flat per-tenant fee is established ([pricing](https://www.claim.md/pricing/)).

**Vendor-specific open facts:** documented generic 837I does not prove hospice NOE/NOTR/transfer support, payer-specific Claim.MD IDs, provider registration automation, response retention/replay beyond outstanding windows, or whether an ERA can contain multiple billing identities. Obtain written support/sandbox evidence before enabling the matching assumptions.
