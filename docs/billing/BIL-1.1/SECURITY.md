# Security and data handling

## Platform-owned capture (migration 1350)

- The new tables contain no `organization_id`; an account response may concern any tenant, so exposing it through ordinary tenant queries would be unsafe. The migration FORCEs RLS and grants access only to a `NOLOGIN NOBYPASSRLS` `claimmd_capture` role. The app role receives no grants or policy.
- Access in code is through `withPlatformContext` and the injected `PlatformBypassAuditor`, with fixed job identity. The database role membership is conditional on `chartwarden_platform` existing at migration time. This code is inactive until platform-context registration and role binding are verified in the actual deployment topology.
- Full vendor pages are encrypted with AES-256-GCM; stream ID and cursor are authenticated as AAD. Encryption key material is injected. This change does not load keys from environment/configuration, provision a KMS key, rotate keys, or wire key recovery. Do not activate until those controls exist.
- Logs expose bounded counts and stable error codes only; exceptions do not copy vendor body/message text. The reader preserves raw response content only inside the encrypted batch. No payload is printed in tests/docs.
- Event metadata carries digests, indexes, response IDs and capture states; it does not contain raw vendor message fields. It can still be sensitive operational metadata and needs retention/access auditing.
- No runtime SQL/RLS certification was performed. `FORCE ROW LEVEL SECURITY` and grants in migration source are evidence of intended controls, not proof against superuser/bypass role behavior, table ownership, or actual deployment grants.
- Tenant-owned account pages are not currently written to these tables. The table/role/key model is platform-only; reusing it for a tenant account would not establish tenant-scoped authorization or tenant-key ownership. The existing tenant poller remains the sole reader until a reviewed schema, encryption, lease/cursor, and downstream-handoff design exists.
- No secrets, PHI, account keys, or production payloads were read, emitted, or transacted.
## Tenant-owned inbox (CM-5A.3A; migration 1503)

Tenant evidence is stored in separate `claimmd_tenant_response_*` tables (migrations 1503–1504), not in the platform-owned `claimmd_capture` tables. Every row is organization-scoped with RLS enabled and forced; the tenant application role has no platform capture cursor/key access through this repository. Composite foreign keys bind account, tenant configuration, usage, batch, item and processing outcome. SQL guards enforce active Claim.MD configuration/BAA and active organization membership at account verification, prevent account identity edits other than retirement, and make credential bindings, captured pages, item provenance and processing outcomes append-only/immutable. Audit writes scrub ciphertext and credential fingerprints.

Raw source JSON/XML is encoded in a versioned envelope and AES-256-GCM encrypted with the tenant's M36 DEK provider. AAD includes organization, account identity, usage, immutable batch ID, source cursor and key version. Decryption verifies the envelope and source digest. No plaintext fallback exists. Credential fingerprints are one-way configuration bindings, not secrets or account IDs; an operator must explicitly confirm that credential rotation still refers to the same external account. The current configuration has no authoritative vendor account identifier, so that external identity proof remains an operational prerequisite, not something inferred from API key text, payer ID or organization alone.

The archive API is internal and organization/account scoped; repository construction requires explicit poll-owner authorization for capture, consumer authorization for evidence reads, and separate downstream authorization for outcome writes, in addition to database RLS/account-binding checks. Denied reads return the same typed not-found outcome. There is no generic public endpoint for decrypted pages. Platform-shared uncorrelated evidence remains inaccessible through tenant readers. Processing and quarantine reasons use closed code values in a separate append-only ledger; the encrypted source and item provenance remain immutable. The archive-before-ACK adapter is not wired to live polling; the legacy poller remains sole owner. No RLS runtime claim is made until migrations 1503–1504 run against the actual NOBYPASSRLS application role in the approved isolated PostgreSQL environment.
