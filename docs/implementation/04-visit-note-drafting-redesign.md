## 1. Problem

A competitor's headline feature is that the visit note writes itself. A nurse in a public hospice-documentation group said of FireNote: "it pulls everything from your assessment and Careplan and inputs it into your note." (LinkedIn thread, not retrievable by our research; the wording is unconfirmed against FireNote's own material.) Our visit note is thin by comparison: the clinician taps phrases and nothing from the patient's record reaches the note.

### 2.2 The draft

| ID | Decision |
|---|---|
| VN-D5 | Beyond the clinician's own selections, the draft pulls four sources, each shown with its origin and individually deselectable: (1) care-plan goals and interventions linked to the visit, auto-selected; (2) the latest **scale readings** with the change since the last visit; (3) vitals; (4) medication and order changes since the last visit. |
| VN-D6 | No text copy-forward. "Changes since last visit" is computed from structured data. Anything carried over needs per-item re-attestation. |
| VN-D7 | A **section** is the unit of **confirmation**. The clinician confirms, edits or deselects each drafted section. Signing is blocked until every drafted section is resolved. Each section's source ids are kept in the audit trail only; the signed text reads as the clinician's narrative with no inline labels. The word "block" is retired for this (it collides with the note-closure "blocked" state). |
| VN-D8 | Deselecting a care-plan goal or intervention means it is not linked to this visit, through the same links the signed event already carries. A note never changes the care plan. The audit trail records the deselection. |
| VN-D9 | A section with no source stays empty with a visible "nothing to draft from" state. It is never filled with a default phrase. In the later AI slice an AI suggestion may offer text for an empty section: clearly labelled, never auto-inserted, accepted per passage, behind the AI-governance gates. |
| VN-D10 | The draft is computed per author when the author opens the visit, so 42 CFR Part 2 redaction holds. A refresh shows "inputs changed since drafted" and never overwrites a section the clinician has touched. It is not computed once at seed time. |
| VN-D11 | The draft is computed as of the visit time: the care-plan version in effect then, readings recorded up to then, medications as of then. A late entry never describes today's patient state. The current seams are now-reads, so this needs as-of variants (§4.1). |
| VN-D12 | A confirmation binds to the draft snapshot version, the phrase-corpus version and a hash of the section's rendered content. If a source or the corpus changed by sync or signing, the server returns that section as "needs re-confirmation" and signing stays blocked until it is re-confirmed. An offline confirmation is never silently accepted against newer data. |
| VN-D13 | A cosigner without Part 2 access sees source-derived sections redacted for them, never the author's unredacted text. |
| VN-D14 | The phrase corpus is platform-curated and versioned, approved by a named platform-side reviewer: ADA (named by the owner, 2026-11-18). No per-tenant or per-user phrase editing in v1. |

## 3. How a draft works

1. The visit is published (`m17.visit.published`) and seeds an encounter as today.
2. The author opens it. The server builds the draft for that author, as of the visit time (VN-D10, VN-D11): linked care-plan goals and interventions, scale readings with deltas, vitals, medication and order changes (VN-D5), each section carrying its source ids.
3. A section with no source renders as empty with a visible state (VN-D9). The clinician's own selections work as they do today.
4. The clinician resolves every drafted section: confirm, edit or deselect (VN-D7, VN-D8). Each confirmation binds to the snapshot version, corpus version and content hash (VN-D12).
5. Sign: step-up (existing, online), attestation acknowledged (check 9), every drafted section resolved (new check). A stale confirmation returns that section for re-confirmation.
6. Source ids stay in the audit trail only (VN-D7). After signing, the note changes only by amendment (VN-D30).

### 3.1 Frozen text, per-viewer view and amendments (S1 step 0 design)

Within the decisions above; no decision changes. The M8 spec makes a signed encounter immutable with changes through addenda (M8 spec D2); VN-D30 extends that addendum path to carry section-level amendments.

- **Frozen text.** `hearthnote_assembled_outputs.final_cipher` stays the legal text of a signed note. At sign, S1 also writes one sealed row per section (`hearthnote_signed_sections`): section id, position, sealed rendered text, a SHA-256 of the canonical text, a `part2_derived` flag and the source ids. The ordered rows must equal `final_cipher`; a test pins that invariant.
- **Per-viewer view (VN-D13).** A viewer with Part 2 disclosure, or a note with no `part2_derived` section, gets `final_cipher`. Any other viewer gets the section rows with each `part2_derived` section replaced by a withheld marker. A section is `part2_derived` unless every source behind it is proven not SUD-related, failing closed as `redactStateSnapshot` does in M7. A clinician's own free text is not classified. Built in PR E1 (§3.2 "Per-viewer view").
- **Amendment (VN-D30).** An addendum (its own draft, finalized, signed lifecycle; the parent stays signed) that names the sections it amends. Its section rows reference the amended section, so the current view shows the latest signed text per section and the history shows every version. Original rows are never updated. Each amended section is confirmed like a drafted one (VN-D12), signing needs step-up, and a cosign request is created for the addendum when the parent needed cosign.
- **As-of inputs (VN-D11).** Care plan: the `care_plan_version` in effect at the visit time (`signed_at` at or before it, `superseded_at` null or after it), read from its frozen `state_snapshot` with the existing per-viewer Part 2 redaction. Scale readings: the existing `ScaleSeriesProvider.series(from, to)` with `to` set to the visit time, so no new M9 seam. Medications: a new changes-between and active-as-of read on `MedicationOrderProvider`.
- **Settled in PR E2** (see "Amendments" in §3.2): `amends_section_id` is a nullable self-reference to the amended ORIGINAL row, beside a nullable `addendum_id`, and an amendment row hangs off the addendum's own assembled output; the addendum's cosignature request is a sibling table, not a column, because the note's own is `UNIQUE (encounter_id)`, and the one cosignature workflow serves both subjects (PR E2b); M22 keeps the note's original text as the note and appends each amending addendum's amended sections to that addendum's text, withheld where Part 2.

### 3.2 Backend design for PR C (S1)

Within the decisions above; no decision changes.

- **No stored draft.** The draft is recomputed from the sources on every read, for the reading author, as of the visit time. Nothing PHI-derived is cached, so Part 2 redaction is applied per request (VN-D10). The section's content hash (which covers its text and source ids) plays the part of the draft snapshot version in VN-D12; a stored per-author snapshot arrives with the offline slice (VN-D22).
- **Visit time (`asOf`).** The earlier of now and the last millisecond of the encounter's service date in the organization's time zone. `started_at` and `clock_started_at` do not matter: a note written after checkout, or later that day, still gets the visit's own vitals, scores and medication changes, while one written days late does not pull in the days since, and a service date still in progress is capped at now.
- **Resolution.** A drafted section is resolved by `confirmed` (bound to the content hash the clinician saw, which the request carries) or `deselected` (the drafted sentences stay out of the note; the clinician's own selections and free text stay). "Edit" is the existing selection and free-text save, which changes the hash; the clinician then confirms. A confirmation that no longer matches the recomputed hash, or whose corpus version is not current, reads as `needs re-confirmation` and blocks signing; this holds for `deselected` too. `edited` is recorded as whether the section carried the clinician's own text at confirmation (the rubber-stamp indicator, VN-D18).
- **Care-plan items.** The draft shows the elements `relevantElementsAsOf` returns, minus any with a removed link on this encounter. Confirming a section writes live `encounter_care_plan_link` rows for its care-plan source ids (idempotent). Deselecting one element soft-removes its link, or inserts an already-removed row when it was never linked, so a re-open does not bring it back. A note never changes the care plan (VN-D8). The deselect unit is the section, and for care-plan elements the link; scale readings, vitals and medication changes are deselected with their section.
  - **The deselect-hash trap, resolved (PR C2b1).** Removing a section's care-plan elements changes the section, so the hash the clinician saw is not the hash a later read computes. A `deselected` row bound to the hash SEEN would read `needs_reconfirmation` the moment the draft was reopened, and a deselected section could never stay deselected. So the deselect writes the link changes first, recomputes the draft for the same viewer inside the same transaction (the store port `removedCarePlanElementIds` reads the transaction's own writes), and binds the `deselected` row to the hash of the section AS RECOMPUTED. What remains in the section (the medication changes or other sentences of a mixed section such as `interventions`) is deselected with it. A section that is empty after the removal (a care-plan-only section such as `plan`) writes no bound row and reads `not_drafted` (a resolution the clinician left earlier is withdrawn, below). The explicit audit event carries ids, enums and counts only, never a content hash (an unsalted hash of low-entropy section text is a guessing oracle for anyone with `audit.read`).
  - **Retry.** A deselect that removed elements changed the section, so a retry carries the old hash. It is a no-op success while the section is already `deselected` and current (a mixed section), and `409 DRAFT_SECTION_STALE` when the removal left the section empty (nothing is drafted to match against); the client refetches and reads `not_drafted`.
  - **A deselect that empties a section the clinician had resolved withdraws that resolution (fix pass).** A section that is empty after the removal normally keeps no row, but a row the clinician left earlier (a `confirmed` at hash H) would outlive the removal: link the goal again through the picker and the section hashes to H once more and reads `confirmed` with no new confirmation. So when a row exists, the deselect writes it as `deselected` with no source ids, bound to `sha256("withdrawn:" + sectionId + ":" + corpusVersion)`, a hash no recomputed section can equal, and a re-link reads `needs_reconfirmation` (the clinician resolves it afresh). With no earlier row nothing is written and a re-link reads `unresolved`. The explicit audit event records only that the resolution was withdrawn.
  - An element is "removed" for the draft only while it has a removed link and no live one, so linking it again through the picker brings it back.
- **Scope.** Which templates draft is one predicate read off the corpus, `templateHasDraftedSection(encounterType, discipline)` in `@chartwarden/hearthnote` (`draft/scope.ts`): a section is drafted for a pair when its template has it, the sources feed it (`draftSectionPhrases`) and every corpus phrase it is built from is tagged for the pair. The draft phrases are tagged for the RN routine visit alone, so that is the only template S1 drafts; tagging them for another pair is what makes that pair draft, with no list to keep in step (a test compares the predicate with the compiler for every legal pair). It is asked BEFORE any source is read, by finalize, sign, the gate check and the draft routes, and the compiler obeys it (an undrafted template compiles to all-empty sections even when every source is supplied). A template with none behaves exactly as with the switch off: no source read, no draft, no check 13, `final_cipher` is Layer 1 text, no sealed rows and no confirmation asked, whatever the seams do. Before this rule the draft was read for every encounter type, so a failing source blocked the sign of a type S1 does not draft, and a template with a care-plan-fed section (a CHHA `plan`) could draft RN-routine phrases.
- **Gate.** A new check `draft_sections_resolved` (the 13th id in the register) runs when the tenant switch is on and the template has a drafted section (Scope). Unresolved sections give `DRAFT_SECTION_UNRESOLVED`; stale ones give `DRAFT_SECTION_STALE`. A draft that cannot be computed is `COMPLIANCE_GATE_UNAVAILABLE`, never a pass.
- **Sign.** The draft is recomputed for the signer and each confirmed section's hash must equal the stored one, else 409 `DRAFT_SECTION_STALE` naming the sections. The assembled narrative uses the confirmed draft text for `confirmed` sections and the clinician's selections only for `deselected` and undrafted sections. At sign one sealed `hearthnote_signed_sections` row per section is written in the same transaction as `final_cipher`, and the ordered rows must equal it (PR E1 adds the per-viewer view on top, amendments are PR E2). Built in PR C2b2; `final_cipher` is in fact first pinned at finalize, so see "Gate and sign" below for how finalize and sign share the one text.
- **Tenant switch.** One row per organization, default off, written by a holder of a new permission with step-up, mirroring the ADR-0113 policy service. Enabling is refused while `CORPUS_CLINICAL_REVIEW.status` is not `approved`. A tenant with the switch off sees today's behaviour exactly, and every new route answers 404 for it, with two stated exceptions to the corpus release that ships with the slice:
  - **The authoring menu** (`GET /encounters/{encounterId}/template`) offers the 25 phrases of `narrative-vocab@2026.11.0` (`DRAFT_VOCAB_CODES`) only where the switch is on: they are unreviewed draft wording (VN-D14). With the switch off the menu is what it was before that corpus, including the RN routine visit's `chief_concern`, `vitals_review` and `plan` sections as open as they were (`resolveTemplate(..., { draftWording: false })` leaves the VN-D15 category wiring off). A switch cannot be turned on while the corpus review is pending, so the wording reaches a tenant only after it is approved. The menu is the only place the categories bite; `PATCH .../selections` still accepts any code the corpus holds.
  - **The vocabulary version.** `VOCAB_VERSION` moves to `narrative-vocab@2026.11.0` for every tenant at deploy, switch or no switch, as any corpus release does. A draft whose selections were last saved before the deploy carries `template_version` `narrative-vocab@2026.06.0`, so `POST /encounters/{encounterId}/finalize` answers `409 VOCAB_VERSION_MISMATCH` until the author saves the selections again (any `PATCH .../selections` restamps the version; the web composer saves before it finalizes, so it does so on its own). Nothing else reads the stored version: a note already finalized keeps its pin, and the draft is computed against the running corpus.
- **Part 2.** Medication orders carry `isSudTreatment` unredacted from the M12 seam (PR A), so M8 drops SUD orders for an author without disclosure, using the same disclosure check the care-plan reader applies, and marks the rest `sudRelated` so a section's `part2Derived` fails closed.
- **Sealed rows** are encrypted with the same key path as `final_cipher`. **Source ids** reach the audit trail through the confirmation row's audit trigger and never the signed text.

#### Input rules (PR C2a, `08-encounters/drafting/inputs.ts`)

- **Care plan.** `relevantElementsAsOf(patient, type, discipline, admission, viewer, asOf)` with the session identity as the audience, so M7 redacts per viewer. Goals and interventions whose link was removed for this encounter (`removedCarePlanElementIds`, supplied by the store) are left out. A `null` plan is `carePlan: null`. A plan of another patient is refused. A plan M7 flagged `redacted` (Part 2 content withheld from this viewer) is drafted reduced only for a viewer the draft's own Part 2 verdict (below) does not clear; for a viewer it clears, the plan was cut by an M39 outage or a consent change between the two reads, so the draft is `DRAFT_UNAVAILABLE` (503) rather than silently short of content the viewer may read. A goal or intervention takes its parent problem's SUD flag; a parent the reader did not return leaves the flag unset, which reads as Part 2. Encounter disciplines `md`/`np` map to `md_np` and `slp` to `st`.
- **Previous visit.** The patient's most recent SIGNED encounter of the SAME DISCIPLINE as the encounter being drafted (any encounter type) on an earlier service date, supplied by the store port `previousSignedVisitAt` as the instant that encounter's own note described the patient at (`previousVisitAsOf`: `visitAsOf` of its service date, same zone and now, and never later than its `signed_at`), so the picture at the previous visit plus the changes since is exactly the picture now. Without the signing cap a change made after the previous signing but before midnight would be in neither note. The recompute at sign reads its clock a few milliseconds after `signed_at`, so the two windows can overlap by that much (a change in it is in both notes), never leave a gap. One later than this visit time is refused. The discipline matters because an intervening chaplain or aide visit would otherwise become "the last visit": a medication change between two RN visits would fall into the window of a note that never described medications and be missing from the RN's next draft (owner decision, 2026-11-19). `encounter.discipline` is NOT NULL, so the match is plain equality and there is no null case. With no earlier signed visit of that discipline there is no previous visit (`previous` is null, as before).
- **Scale readings.** For `pps` and `esas_r`: the latest reading captured at or before `asOf` (`series` with `to = asOf`, cut again in code), `previous` the latest at or before the previous visit time, else null; no previous visit means `previous` is null. A latest reading captured at or before the previous visit time is not drafted at all: the previous note already carried it, so it is not new since then (VN-D6, VN-D9) and, as its own `previous`, it would read "unchanged from itself". A latest reading without a score is not drafted and an older one does not stand in. The M9 series carries one score per ESAS-r capture, so it is drafted as the `total`. Dates are org-local.
- **Vitals.** The encounter's own latest row captured at or before `asOf`; no merging across rows. Vitals and PPS/ESAS-r readings carry `sudRelated: false` (M9 redacts only AIMS taken in a SUD context).
- **Medication changes.** `getMedicationChangesBetween(patient, previousVisitAt, asOf)`. With no previous signed visit of the same discipline there is no window and none are drafted (an honest empty section, VN-D9). A completed course is drafted as discontinued (the corpus has no "completed" phrase). A change's source id is `<orderId>:<kind>`, because one order can start and stop inside a window.
- **Part 2.** An order with `isSudTreatment !== false` (fail closed) is dropped unless the viewer has Part 2 disclosure; kept orders carry `sudRelated = (isSudTreatment !== false)`. The verdict is M7's per-actor decision (`sudDisclosureAllowedForActor`: M39 `evaluateForInternalAccess`, then the RN case manager carve-out where no release names others), asked as `callerModule: "m8"` so M39's evaluation audit attributes the check to M8, and at most once per draft: when an order could be withheld, or the care plan came back `redacted`. An M39 failure is NOT a "no": the checker rethrows (`defaultInternalSudAccessChecker({ onError: "throw" })`), so the draft is `DRAFT_UNAVAILABLE` instead of quietly shrinking.
- **Failure.** A seam that throws, or returns something unusable (an instant that is not one, another patient's plan), is `DRAFT_UNAVAILABLE` (503), never a partial draft. The message names the read; the upstream cause stays on the error for the log. Every read, seam or store, is bounded by `DRAFT_SOURCE_READ_TIMEOUT_MS` (5 s, `unavailable.ts`): a read that does not answer in time is `DRAFT_UNAVAILABLE` too, so a hung source cannot hold the sign transaction open. No retry, no fallback: the abandoned read is not cancelled and its late answer is ignored, and the gate and sign still fail closed.
- **Visit time.** `visitAsOf({ serviceDate, orgTimeZone, now })` is the earlier of `now` and the last millisecond of the service date in the organization's zone (DST-safe).

#### Store and routes (PR C2b1, `08-encounters/drafting/`, `08-encounters/routes/draft-section-routes.ts`)

- **Store ports** (`db-draft-store.ts`, one `withOrgContext` transaction per request, so RLS scopes every statement). `organizationTimeZone` is `organizationTimezone`. `previousSignedVisitAt` is the patient's most recent encounter of the same discipline as the encounter being drafted, with status `signed`, `cosign_pending` or `cosigned`, on a strictly earlier service date (a later-signed one wins a tie on the date; a draft, a voided, a later, a same-day, another patient's and another discipline's encounter do not count), returned as that encounter's own `previousVisitAsOf`. Every encounter type counts (all seventeen are visit types, `packages/types/src/encounter.ts`), but only the same discipline does (`previousVisitWhere` in `db-draft-store.ts`). `latestVitals` is the encounter's own `vitals` row with the latest `captured_at` at or before the visit time (ties by `created_at`, then id), never merged; a temperature needs a unit of `f` or `c`, and a pain score counts only on the `nrs_0_10` scale (one on another scale, or with no scale, is not drafted). `removedCarePlanElementIds` reads `encounter_care_plan_link` (see "Care-plan items"). `loadSelection` is what the Layer-1 assembly reads: the stored tree with its prose opened through the tenant free-text cipher (the shared reader is `selection-tree.ts`), the patient slot `Patient` and the service date. Sealed prose with no cipher bound is refused (`DRAFT_UNAVAILABLE`), never drafted without the clinician's own text.
- **`GET /api/v1/encounters/:encounterId/draft`** (`encounter.read` plus the source domains' read keys `care_plan.read`, `prescribing.read` and `assessment.read_trend`, because the seams apply no permission check of their own; caseload scope; the PUT requires the same keys, so GET, PUT and sign compute one full draft per patient and visit). The draft for the SESSION viewer (roles and active membership from the server-assembled session, never the request), every template section with `state`, `text`, `contentHash`, `corpusVersion`, `part2Derived` and `origins`. VN-D7: source ids are NOT on the wire (the ids stay in the audit trail); `origins` carries only the kinds, which is what VN-D5's "shown with its origin" needs. The text is what the seams returned for this viewer (M7 and M12 redact per viewer), so no section is withheld a second time here; `part2Derived` is the compiler's fail-closed flag, for the signed-note view of PR E1. A state is read against the VIEWER's recomputed draft, so a viewer whose redaction differs from the author's sees the author's confirmation as `needs_reconfirmation`. Read-audited as `encounter_draft.viewed` (`resourceIdParam` is the encounter; the patient is attributed from the response; field names only).
- **`PUT /api/v1/encounters/:encounterId/draft/sections/:sectionId`**, body `{ resolution: confirmed | deselected, contentHash, corpusVersion }` (one idempotent route for both resolutions). The selections save's permission and caseload scope (`encounter.author`, `encounter.scope`) but the AUTHOR's own rule (`is_author`, not `is_author_or_supervisor`: the note is signed by its author alone and sign refuses a draft the signer has not resolved, so a confirmation by anyone else, a supervisor included, would let the author sign a draft they never opened; the draft READ is unchanged), without `If-Match` (the section hash is the lock) and with the AI-principal refusal. The encounter row is locked `FOR NO KEY UPDATE` (see "Locking and connections" below), so confirmations of one encounter, a selection save, the picker's link and unlink, finalize and sign run one after the other. Allowed on any encounter that is not signed, cosigned or voided (the selections save's own rule, `checkMutableForEdit`): a `finalized` note can still be re-confirmed, since it can only go on to `sign`, which refuses a stale confirmation. `edited` is recorded as whether the stored selection tree holds the clinician's own text for the section (an entry, or the `hasFreeText` marker), read without opening the prose. Every write records `m8.encounter.draft_section_resolved` beside the confirmation row's trigger record; an idempotent repeat writes neither.
- **A template that drafts nothing (Scope).** `GET` answers `200` with every template section `not_drafted` (`text`, `contentHash`, `corpusVersion` and `part2Derived` null, `origins` empty), the same shape as a drafted template, so a client needs no special case; `asOf` is the read time (now), since no visit-time source is read, and no zone, source or stored selection is read. `PUT` on a section of such a template is `409 DRAFT_SECTION_STALE` (nothing is drafted to confirm, as for any section with nothing drafted), `422 UNKNOWN_TEMPLATE_SECTION` for a section the template lacks, and nothing is written. The tenant switch still decides first (404 when off).
- **Per-tenant switch.** Both routes answer `404 NOT_FOUND` when `isVisitNoteDraftEnabled` is false, read inside the request's transaction before the encounter or any source (no cache), with the same body an absent encounter gets.
- **Errors.** `409 DRAFT_SECTION_STALE` (new, `M8_ERROR_STATUS`), `503 DRAFT_UNAVAILABLE`, `422 UNKNOWN_TEMPLATE_SECTION`, `409 IMMUTABLE_AFTER_SIGN`.

#### Gate and sign (PR C2b2, `08-encounters/drafting/` and `gate/`)

- **Gate check 13.** `draft_sections_resolved` is registered `evaluated` (`gate/checks.ts`) and decided by the pure gate over a fact, `draftSectionActions`: the drafted sections that are `unresolved` (`DRAFT_SECTION_UNRESOLVED`) or `needs_reconfirmation` (`DRAFT_SECTION_STALE`), from `sectionStates` exactly as §3.2 "Resolution" decides them. `not_drafted`, `confirmed` and `deselected` (while current) pass. The fact is absent when the tenant switch is off or the template has no drafted section (Scope), so the gate is then as it was. Within a template that drafts, a section with no source this time is `not_drafted`: with nothing drafted the list is empty and the check passes. The check runs at both finalize (a 422 preview, for the author) and sign.
- **Reading the draft** (`note-draft.ts`, `note-draft-flow.ts`): `readNoteDraft` is `null` for a template with no drafted section (Scope, before anything is read, the switch included) and with the switch off, and reads nothing else; otherwise it recomputes the draft for the viewer inside the caller's transaction and sets it against the stored confirmations. A switch that cannot be read, a source that cannot be read or a draft that cannot be compiled is `503 COMPLIANCE_GATE_UNAVAILABLE`, never a pass and never "off". The three selection-assembly codes (`UNKNOWN_VOCAB_CODE`, `VOCAB_VERSION_MISMATCH`, `INVALID_ENCOUNTER_DISCIPLINE_PAIR`) keep their own codes, the ones the clinician's save and finalize already answer with.
- **Check 9.** `attestation_confirmed` is reclassified from `deferred` to `elsewhere`: `SignEncounterSchema` (and `AttestationSchema` on the cosignature and addendum signatures) declares `attestationConfirmed: Type.Literal(true)`, so a body that omits it or sends anything else is a 422 before the service runs. `encounter-compliance-gate.test.ts` pins that the schema refuses each of those bodies. The `deferred` blocker ("nothing carries the clinician's confirmation") was stale (§1.1).
- **Viewers.** The draft is read for the member acting: the author at finalize (`finalize` takes `args.viewer`, the session's roles and active membership from the route) and the signer at sign (`SigningActor.roles` beside the membership). Both come from the server-assembled session, never the body. A caller that supplies none is read as a member with no role and no Part 2 release, so a Part 2 difference makes the section stale rather than hiding it. Sign stays author-only today (GAP-028), so the signer is the author; the recompute is the signer's own regardless, and a test confirms as a viewer holding the Part 2 disclosure and signs without it (409), then with it.
- **Sign refusal.** Before any write, sign recomputes the signer's draft and answers `409 DRAFT_SECTION_STALE` for any drafted section that is unresolved or stale (the one code for both, with `details` naming each section and `DRAFT_SECTION_UNRESOLVED` or `DRAFT_SECTION_STALE`), ahead of the gate's own 422. A note finalized before the tenant switched the draft on therefore cannot sign until its sections are resolved; sections can be resolved on a finalized note.
- **The one text.** `finalNoteOf` (`final-note.ts`) builds the note from the signer's `ComputedDraft` and its states: `confirmed` sections contribute the draft text (the drafted sentences and the clinician's own words, as seen); `deselected` and undrafted sections contribute only the clinician's own selections and free text, rendered as Layer 1 renders them; a section with no body is not in the note. With nothing drafted the text is byte for byte what `assembleSelections` produces. The block and separator come from `assembleBlocks` and `joinBlocks` in `@chartwarden/hearthnote`, which `assembleLayer1` now also uses, so there is one rule. It refuses (409 `DRAFT_SECTION_STALE`) if any drafted section is unresolved: a note is never built from content the clinician did not confirm.
- **Where `final_cipher` is written.** It is first written at finalize (`hearthnote_assembled_output`, kind `primary_finalize`), not at sign, so §3.2's "in the same transaction as `final_cipher`" needed a rule: finalize pins the author's confirmed text (when the switch is on), and sign, in its own transaction, recomputes for the signer and UPDATEs `layer1_cipher` and `final_cipher` to the signer's text (the application role already holds UPDATE on that table; the UPDATE is guarded to a row Layer 2 did not take part in, else the sign is refused) and inserts the rows. The finalize pin is thus the author's text at finalize and sign's text is the note that was signed, even if a source moved or the selections were edited between the two (an edit to a drafted section is refused as stale first). This is also why a finalized note signs with the draft's text after the switch is turned on.
- **Sealed rows** (`signed-sections.ts`). One row per section the note carries, `position` its place among them. `text_cipher` seals the section block (its heading, a line break and its body) with the narrative envelope; the ordered rows unsealed and joined by a blank line (`NOTE_BLOCK_SEPARATOR`) are exactly the narrative, which `final_cipher` also holds. `content_hash` is SHA-256 of that same text, so anyone holding an unsealed row can check it. `source_refs` are ids and kinds of a confirmed section's sources only (never text; the row trigger carries them into the audit trail). `part2_derived` is the compiler's fail-closed flag for a confirmed section and `false` for a section made only of the clinician's own words (not classified, §3.1) or of a deselected section (its sources are out of the text). The rows are written with `final_cipher` in the sign transaction: any failure (a seal, the key ring, the UPDATE guard) fails the sign as one, leaving the note finalized with no row and no signature. Rows are written whenever the switch is on and the template drafts, including a note with nothing drafted, so every such note signed under the switch has them; with the switch off, or for a template with no drafted section, none are written.
- **Locking and connections (fix pass).** *Locks.* Every request that decides something from the encounter's draft takes the encounter row `FOR NO KEY UPDATE` first, in the same order (the row, then its satellites): the section PUT (`db-draft-unit.ts`), finalize, sign, the picker's link and unlink and the selections save (`loadEnc(..., { lock: true })` in `encounters-route-service-db.ts`). A sign therefore reads its draft after every section PUT that held the row has committed (a deselect between sign's read and its UPDATE would otherwise be sealed), and a second concurrent sign waits at the lock, then finds the note `signed` and answers `409 ILLEGAL_TRANSITION` instead of dying on the `(assembled_output_id, section_id)` unique constraint. `NO KEY UPDATE`, not `UPDATE`, so the foreign-key checks of vitals, mileage and signature inserts (`KEY SHARE`) are not held up. The status UPDATEs of finalize and sign also carry `AND status = <loaded status>`, mapped to the same 409 (unreachable behind the lock; the guard keeps a double sign clean if a path ever skips it). The picker's duplicate check and the PUT's link read each see the other's committed rows, so live links stay unique per element without a new index (a partial unique index on live links is not clean: the picker legitimately writes `(problem, goal)` and `(goal)` rows for one goal). *Connections.* Every seam read (M7, M9, M12, M39) opens its own pooled transaction (`withOrgContextFromRequest`), so with the request's own transaction held, one draft read used to take up to six pooled connections at once (M7 and the M39 check it makes inside, both M9 series, M12), and a sign sealed N + 2 texts at once, each resolving the tenant DEK in a pooled transaction of its own. Now the source reads take turns (`serial-seams.ts`, one in flight per request) and overlapping seals share one key-ring read (`hearthnote-crypto.ts`; nothing is cached past the read, so a rotation is seen by the next seal). A draft request peaks at its own connection plus two (one read, and M7's M39 check inside it); a sign's seals add one. The two draft GETs (the note's and the amendment's) now DO hold no transaction while the sources are read (S3): the encounter and every store read go in one short transaction that closes, the sources are read with no connection held, and the confirmations are read in a second short one (`snapshotStorePorts` in `compute.ts`); `GET /encounters/{encounterId}` likewise reads its rows, closes the transaction, then opens the pinned narrative and asks the Part 2 verdict. A write cannot: the lock must cover the confirmation reads the draft is compared with, so the writes keep holding their transaction across the seam reads, and a request that cannot get a connection within the acquisition timeout fails 503 (limit recorded in `M8_DR_INT_INVENTORY.md`). *Sizing.* The pool defaults to 10 per process (`packages/db/src/client.ts`, 10 s acquisition timeout). Budget three connections per concurrent draft or sign request, so ten requests in flight at once can still hold all ten connections while each waits for a seam read; the acquisition timeout then ends the wait as `DRAFT_UNAVAILABLE` (503, fail closed), never a pass. Raise `max` (or cap draft concurrency at the edge) before enabling the switch for a tenant whose peak is more than about three simultaneous signers per instance. The link statements of a section PUT are batched (one INSERT per kind, one UPDATE), so the lock is held for a fixed number of round trips whatever the number of care-plan elements.
- **Not here.** The web screens (PR D) stay with a later PR; the encounter eraser's `tombstoneEncounters` fix is merged here and proven in `m8-encounter-eraser.live.test.ts`. Amendments and the cosign re-trigger are PR E2 (below).

#### Per-viewer view and the pin (PR E1, `08-encounters/drafting/pinned-note.ts`)

- **What a reader gets.** Every reader of `hearthnote_assembled_output.final_cipher` goes through `readPinnedNote`. A viewer with Part 2 disclosure, or a note with no `part2_derived` section, gets `final_cipher` byte for byte (the sealed rows joined by a blank line are that same text, and a live test pins it). Any other viewer gets the sealed rows in order with each `part2_derived` section replaced by `PART2_WITHHELD_MARKER`, a generic sentence that names no clinical content and says nothing of the section (not even its heading); the sealed text of a withheld section is never opened. The verdict is asked only when the note has a `part2_derived` section, so a note without one never asks M39.
- **The viewer and the verdict.** The viewer is the session's roles and active membership (`draftViewerOf(request)`, never the request body); the verdict is the M7 per-actor decision the draft already uses (`DraftSeamPorts.part2DisclosureAllowed`: M39 `evaluateForInternalAccess` as `callerModule: "m8"`, then the case-manager carve-out, `onError: "throw"`). A check that fails is `503 NOTE_VIEW_UNAVAILABLE` (new, `M8_ERROR_STATUS`), never a silent denial and never a disclosure; it is bounded by the same 5 s as the draft's source reads. A caller with no viewer is read as a member with no role and no release.
- **The pin records it (migration 1522).** The sealed rows are written at sign, so between finalize and sign the pin holds the author's draft text and no row says which section is Part 2. `hearthnote_assembled_output.part2_derived` (NOT NULL, default false) is written with the pin at finalize from the author's confirmed text (`FinalNote.part2Derived`: any confirmed section carries the compiler's flag) and rewritten at sign from the signer's text. A pin that carries Part 2 text and has no rows yet (finalized, not signed) cannot be cut by section, so it is withheld whole from a viewer without disclosure. The column is a boolean, never content, and the frozen-after-sign trigger (1521) still guards the ciphers only.
- **Readers covered.** `GET /api/v1/encounters/:encounterId` (`finalDocumentation`, per viewer); `GET /api/v1/internal/encounters/:encounterId/render-payload` (route 31); and `SignedEncountersReader.renderPayloadFor` (`seams/drizzle-store-ops.ts`, the same payload through the seam). The addendum texts the render payload carries are the clinician's own words (an addendum is never drafted) and are unchanged. The cosignature queue and view, the addendum parent view, the list reads and the exports read no narrative text: the encounter row views carry no `final_cipher`, and no other module reads the table. A new reader of `final_cipher` must go through `readPinnedNote`.
- **M22 limit (fail closed).** M22 stores the rendered document under the template's own retention class (`encounter` is `clinical_record`) and serves it to every holder of document read access. Its only per-render signals are the lab-results variants' `retentionClassOverride` and the consent gate on an event's `isSudClass` flag, and neither exists for the `encounter` template: nothing M22 carries would keep a Part 2 section out of a broadly readable document. So the document consumers are never entitled: for a note with a `part2_derived` section the render payload is ALWAYS the withheld view, the entitled author included, and it asks no one. This is a limit, not a design: a rendered signed note for such an encounter shows markers where Part 2 text is. Lifting it needs an M22 Part 2 document path (the `compliance_42cfr_part2` class at INSERT with Part 2 gated reads) and a per-event signal from M8. Today the `m8.encounter.signed` event carries `documentRenderPayload.final` as an empty string, so no note text reaches M22 through the event either.

#### The draft switched off between finalize and sign (PR E1)

- **Refused, not sealed short.** A note finalized with the draft on pins the author's text; sign with the draft off (the switch, or a template the corpus does not draft) used to leave that pin as it was, with no sealed rows and no `part2_derived` record, so nothing could withhold it. Sign now refuses with `409 DRAFT_OFF_AFTER_FINALIZE` and a remediation (switch the draft back on for the organization, then sign again) when the pinned output carries `part2_derived`, before any write; the note stays finalized. A finalized note has no way back to draft (`finalized` only goes to `sign`), so switching the draft on is the one remedy; a pin made without the draft, or with the draft on but no Part 2 text, signs as before.
- **The signal is the pin's own flag, not a confirmation row.** An `encounter_draft_confirmation` row exists whenever the author resolved a section, including a note finalized after the switch was turned off, and a `deselected` row says the pin has no drafted text; refusing on any row would block a rollback (switch off, then sign the in-progress notes). `part2_derived` on the pin is written by the finalize that produced the text, so it is true exactly when the pinned text carries Part 2 content.

#### Required sections and confirmed text (PR E1; the owner confirmed this rule on 2026-11-19)

- Gate check 1 (`required_sections`) used to look only at the clinician's own selections and free text, so after the author confirmed every drafted section the gate still demanded a statement in each required section. With the draft active for the template and the switch on, a drafted section in state `confirmed` (the bound hash matches the viewer's recomputed draft) satisfies its required section: `confirmedSectionIds(draft)` feeds the gate the fact `draftConfirmedSectionIds`. A `deselected` section does not (the clinician's own selections and free text still can), nor do `unresolved`, `needs_reconfirmation` and `not_drafted`. With the draft off or the template undrafted the fact is absent and check 1 is exactly as it was. The gate's per-check result shape (`GateRemediation`) is unchanged; check 13 still reports an unresolved section beside a missing one. The owner confirmed on 2026-11-19 that a confirmed drafted section satisfies its required section, exactly as built (no behaviour change).

#### Amendments (PR E2, `08-encounters/drafting/amendment-*.ts`, `note-versions.ts`, migration 1523)

Within VN-D30; the decisions of the owner are not re-opened. An amendment is the existing addendum path plus a naming of sections; nothing about an addendum that names none changes.

- **Naming.** `POST /encounters/{encounterId}/addenda` takes an optional `amendsSectionIds` (1 to 12 unique section ids). It is valid only with the tenant switch on and a note that has sealed rows: a switch that is off is the same non-leaking `404` the draft routes answer, and a section the note's own sealed rows do not carry (or a note with no sealed rows) is `422 UNKNOWN_TEMPLATE_SECTION`. The names are `encounter_amendment` rows, one per (addendum, section), INSERTed in the addendum's create transaction; the row's resolution columns stay null until the author resolves the section. An addendum with no `amendsSectionIds` is a free addendum: no draft is read, no row is written, its sign is what it was. Only the signed note's author or a supervisor may name its sections (`403` before any write, whether or not the tenant has the draft on; a free addendum is anyone's with the addendum permission): once signed, an amendment is the current text of the section for every reader. An author without 42 CFR Part 2 disclosure cannot name ANY section of a note that holds Part 2 content in any section at any version (its pin is `part2_derived`, or any sealed row is: an original, or an amendment of any section): their redraft would exclude the SUD sources and silently shorten the note's current view, so the create is refused with `422 AMENDMENT_PART2_NOT_ENTITLED`. The refusal is the same whichever section is named (a refusal only for a Part 2 section, or "unknown section" for one, would tell the author which sections hold Part 2: template section ids are public); the message is the generic "this note cannot be amended by this signer", with no section id, no content and no word of Part 2. An unknown section id keeps its own `422 UNKNOWN_TEMPLATE_SECTION`, and a free addendum is unaffected. The verdict is the draft's own, M7's per-actor decision through the seam as caller module m8, asked once and only when the note has Part 2 content; one that cannot be decided is `503 DRAFT_UNAVAILABLE`, never a denial and never a pass. The same check runs again at sign for the signer, because the verdict can change between naming and sign (`422 AMENDMENT_PART2_NOT_ENTITLED`, or `503 COMPLIANCE_GATE_UNAVAILABLE` when it cannot be decided), before any draft is read and before any write.
- **Storage, the settled shape.** `hearthnote_signed_section` gains `addendum_id` and `amends_section_id`, both nullable and both set (an amendment) or both null (an original), enforced by the guard trigger. `amends_section_id` references the amended ORIGINAL row (ON DELETE CASCADE, indexed); an amendment of an amendment names the original row again, never the amendment's row, so every version of a section points at one row. The guard also requires: the amended row belongs to the same organization and encounter and to the parent's own `primary_finalize` pin, has the same section id and position, and is itself an original; the addendum is the encounter's and is `finalized` (the rows are written in its sign transaction, before it flips, so a signed addendum can never gain a row). Original rows are never updated: the application role still holds SELECT and INSERT only on the table. An amendment row hangs off the addendum's own `addendum_finalize` assembled output (reused, unchanged: its ciphers keep the addendum's own text and stay frozen by 1521; the unique `(output, section)` and `(output, position)` keys then hold per addendum). It is sealed with the same envelope and hashed the same way as an original, and its audit image is the same (the text and hash scrubbed, a `part2_derived` row's source ids withheld), so no audit-trigger change was needed. A sealed amendment row is only ever written from a CONFIRMED draft section (hash-bound); never from free text.
- **Re-confirmation (VN-D12) through the one pipeline.** The addendum's owner runs through `readNoteDraft` for the PARENT encounter, as the signer, as of the visit time, against the addendum's own resolutions (`createAmendmentDraftStore` presents `encounter_amendment` as the `DraftStore` the pipeline reads: its confirmations, its save, and no care-plan link changes, since the links went out with the signed event and an amendment has no consumer for a changed one). `resolveSection` is unchanged. The routes are `GET|PUT /encounters/{encounterId}/addenda/{addendumId}/draft[/sections/{sectionId}]`. For a NAMED section: `confirmed` is amended; `deselected` or nothing drafted leaves the section as signed (the author declined the redraft; there is nothing to write); `unresolved` or `needs_reconfirmation` refuses the sign with the note's own `409 DRAFT_SECTION_STALE` (details `DRAFT_SECTION_UNRESOLVED` / `DRAFT_SECTION_STALE`). The same fail-closed rules and the same 5 s source timeout: a source that cannot be read is `503 COMPLIANCE_GATE_UNAVAILABLE`; the draft switched off since the addendum was created is `409 DRAFT_OFF_AFTER_FINALIZE` (named sections are never signed away). A resolution may be made while the addendum is a draft or finalized, by its author only, and the guard trigger freezes it once the addendum is signed or voided.
- **Sign.** The addendum sign already needs step-up (the route's `requireStepUp`, and the machine's `STEP_UP_AUTH_REQUIRED` guard, both pinned by tests). Lock order: the encounter row `FOR NO KEY UPDATE` FIRST, as sign and finalize do, then the addendum; a second concurrent sign waits at the lock and answers `409 ILLEGAL_TRANSITION`. Then the signer's draft is read and the named sections checked, the gate runs, a note that needed a cosigner needs one for its amendment (below), the amendment rows are inserted (a failed seal, the key ring or the guard fails the whole sign), and only then does the addendum flip to `signed` (guarded by `AND status = <loaded status>`), followed by the signature, `m8.encounter.addendum_signed`, one `m8.encounter.section_amended` outbox event per amended section and one `m8.encounter.section_amended` audit event for the addendum, all in the one transaction.
- **Cosign (settled and worked, PR E2b).** Cosignature requests are keyed by encounter (`cosignature_request.encounter_id` is `UNIQUE`), so a nullable `addendum_id` on that table cannot carry a second request, and relaxing the key is a DROP CONSTRAINT, a `contract` migration. The amendment's request is therefore a sibling table, `addendum_cosignature_request` (same columns and lifecycle, `UNIQUE (addendum_id)`), which keeps 1523 an `expand` and leaves the note's own request and clock untouched by construction. It is opened only for an addendum that amended at least one section of a note that has a cosignature request, routed to the patient's RN case manager (resolved like the note's own sign; `422 NO_ELIGIBLE_COSIGNER` before any write when there is none or the signer or the note's author is that RN: the cosign service refuses the author at acknowledge and sign, so a request routed to them would stay pending for ever), with `routed_at` as its own clock, and `m8.encounter.cosignature_routed` is published for it naming the addendum. The workflow that works the request is the NOTE's, generalised by subject (`cosignature/subject.ts`, `cosignature/db-cosignature.ts`): one state machine (`transitionCosignature`, unchanged), one set of statements over the two tables (they have the same columns, pinned by a test), the same permissions, the same step-up, the same error codes. The four cosignature routes exist once per subject (`.../cosignature` for the note, `.../addenda/{addendumId}/cosignature` for an amendment, one implementation behind literal paths). Acknowledge and sign need an RN who authored neither the note nor the addendum (the `m8.cosigner_role_match` predicate reads the addendum when the route names one, and the service refuses again). Sign needs a fresh step-up and writes the provenance row (`encounter_signature` of kind `addendum_cosignature`, migration 1524, the addendum in `addendum_id`: the note's own `cosignature` kind is unique per encounter and its index stays); it leaves the encounter's status as it is, and publishes `m8.encounter.addendum_cosigned` instead of `m8.encounter.cosigned` so no billing consumer reads it (an amendment never re-opens billing). Release past the 48h cap needs a supervisor, a reason of at least 40 characters and a fresh step-up, and the releasing membership is recorded. Every request is locked `FOR UPDATE` before it is read for a decision, so a concurrent second sign is `409 ILLEGAL_TRANSITION` (the note's own cosign path gains the same lock). The queue (`GET /encounters/cosignature-queue`) lists both kinds: each entry is the encounter plus `cosign { subject: note | addendum, addendumId, requestId, status, routedAt }` (an amendment's entry is its parent encounter, which stays signed or cosigned). The SLA cron sweeps both tables with one body: the 12h overdue alert, the 24h escalation and the 48h hard cap name the addendum in their alerts and events (`cosignature_overdue | escalated | hard_cap_reached` carry an optional `addendumId`), and M36's cosignature alerts say "amendment" for them. `addenda[].cosignStatus` and each amendment version of `noteHistory` carry `not_required | pending | cosigned | released`.
- **Views.** `GET /encounters/{encounterId}`: `finalDocumentation` is the CURRENT view, the latest signed text per section in the section's place (the legacy string, the marker in it where Part 2); `finalDocumentationView` is the same view as structured data (a withheld section, or a whole withheld note, carries `text: null`, so no marker reaches a client as data; `amendedByAddendumId` and `signedAt` name the version shown); `noteHistory` lists, per amended section, every version oldest first with kind, addendum, author, date and `current`. Both come from one pass over the sealed rows (each text is opened once). The Part 2 rule applies to EVERY version, per viewer, as ONE decision computed once per read: a viewer without disclosure gets a section with a Part 2 derived version AT ANY TIME (the original or any amendment, whatever the latest text holds) withheld whole, and its text is never opened. A viewer without disclosure is also told nothing of a Part 2 section's identity (S1): in `finalDocumentationView` a withheld section keeps its place and carries `sectionId`, `amendedByAddendumId` and `signedAt` of `null`; `noteHistory` OMITS every such section (and is `null` when none is left); `addenda[].amendsSectionIds` drops its id, signed or not, and an addendum whose every named section is withheld reads as a free addendum (`cosignStatus` `not_required`: only an amendment has a cosignature request, so any other status would say it amended a section); one with a visible named section keeps its status. That a section is withheld, and the generic marker, are what the viewer is shown. A viewer's verdict is asked ONCE per read for the view, the history and the addenda together (not once per part) and only when some version is Part 2 derived; an M39 failure is `503 NOTE_VIEW_UNAVAILABLE`.
- **M22 (settled).** The document keeps "parent unchanged, addendum appended in chronological order" (M8 spec 7.9): the note's `final` stays the ORIGINAL pinned text (withheld view for a Part 2 note, the document consumer never being entitled, as in PR E1), and each signed addendum's `text` is its own text followed, for an amending addendum, by its amended sections, a Part 2 derived one as the withheld marker. An addendum that names no section carries exactly its own text. Route 31 returns no addenda today and is unchanged.
- **Audit trail (settled).** The row triggers record every step with the actor: the naming (`encounter_amendment.insert`), each resolution (`.update`, the content hash scrubbed, a Part 2 row filed under the Part 2 class with its source ids withheld), the sealed amendment row, the addendum's signature (`encounter_signature` of kind `addendum`, with the step-up method and time) and the cosignature request. The existing addendum events stay, and `m8.encounter.section_amended` is both an AUDIT event and an outbox event: the audit event (`encounterId` as the resource, `after` = `{ addendumId, sectionCount }` and nothing else; ONE per signed addendum that amended a section, written in the addendum's sign transaction) is in the M8 audit action catalog, NOT Part 2 eligible and filed under the standard `compliance` class, because `audit.read` is not Part 2 gated and an event that named a section, carried a flag or filed under the Part 2 class would tell an audit reader which sections hold Part 2 content (the per-section trail is the row trigger of the sealed amendment row, actor and scrubbed image); the OUTBOX event published beside `m8.encounter.addendum_signed` (no consumer is declared yet) is one per amended section and carries the three ids and no flag, for the same reason. The writes before a sign (the addendum's creation and its naming rows, its finalize, a note's finalize and a vitals capture and edit) are filed under the acting user too, not `system`. The amendment's section PUT writes the same `m8.encounter.draft_section_resolved` audit event a note's resolution does, with the `addendumId`, and a cosignature acknowledge or release is audited under the acting user, not `system`.
- **Billing (settled).** An amendment never re-opens billing: it touches no claim and no billability read (`BillableEncounterReader` reads the note's own status, which an addendum never changes), no event M23 or M24 consumes is added, and a cosignature pending on an amendment does not hold the note.
- **Eraser.** An amendment row carries the encounter id, so the existing shred (`text_cipher` to the empty sentinel, by encounter) and delete already cover it; `encounter_amendment` and `addendum_cosignature_request` are deleted before the addenda they reference (`EncounterEraseCounts.amendments`, `.addendumCosignatureRequests`). A live assertion proves the shred and the delete.
- **Limits, recorded.** (1) Any amendment of a note that holds Part 2 content by a viewer without Part 2 disclosure is REFUSED (naming and sign, above); an amendment by an author WITH disclosure can still carry no Part 2 content when its sources no longer hold any (a corrected order), and a viewer without disclosure still gets the section withheld whole, because it had a Part 2 version. The amendment draft (`GET .../addenda/{addendumId}/draft`) is the addendum author's view alone (`403` for anyone else, whether the addendum is free, amending or absent). The writes the S1 review did not list stay filed under the system actor: the selections saves (a note's and an addendum's), the mileage writes and the EVV reconciliation. (2) Only a section the draft can redraft (one with a drafted source, as recomputed now) can be amended; a section of the clinician's own words cannot, and naming one is accepted but amends nothing. (3) No billing re-open, no M22 Part 2 document path (a rendered document shows markers where Part 2 text is), the web, the mobile app and other note types stay out of scope. (4) The amendment's own text is never free text: correcting something the draft does not carry is the free addendum, as before. (5) The web works the amendment's cosignature (S1 PR E4: the addendum panel, the shared ceremony, the queue entry and the `cosignStatus` fields); the mobile app does not.

### 3.3 S2 design: the recertification visit (VN-D31 to VN-D34)

Designed 2026-11-20 against `main` at `6a527be45`; built in the PRs of the S2 plan. Within the decisions above; the S1 pipeline (confirmation, gate checks 1 and 13, sign, sealed rows, per-viewer Part 2, amendments, the switch, the eraser) is reused unchanged and adds no table.

- **Which templates draft.** Still read off the corpus tags (`draft/scope.ts`). `recert_visit:rn` drafts `pps`, `esas`, `prognosis` and `recert_summary`, and its base sections from S1's sources (S1's vitals, care-plan and medication phrases are tagged for it too). `face_to_face:md|np` drafts `prognosis` only.
- **A source map per template.** `draft/sources.ts` maps each section to its sources once for all templates today (PPS to `assessment`, ESAS-r to `symptom_management`). S2 makes the map per template. In a recertification PPS feeds `pps` and ESAS-r feeds `esas`; S1's PPS and ESAS-r phrases are tagged for it too (`pps` and `esas` are built from them), but its phrase map gives `assessment` and `symptom_management` none, so they draft nothing and no reading is stated twice. The routine visit is unchanged, and a template with no map of its own is read as the routine visit, so tagging S1's phrases for another pair still makes that pair draft.
- **Menus.** The recertification's `pps`, `esas`, `prognosis` and `recert_summary` and the face-to-face's `prognosis` are wired to an empty menu: they take the clinician's own words as free text, and a phrase that carries a reading, a weight or a date is never typed by hand. The recertification's `vitals_review` and `plan` use the routine visit's categories. `buildTemplateMenu` offers a draft phrase only in a section wired to its category; a section with no wiring (the recertification's `chief_concern`, the face-to-face's other sections) stays open to the legacy phrases alone. Found by a menu test during the build: with the draft on, the open `chief_concern` was listing the draft-only phrases.
- **Web.** The draft panel is generic. It gains a label for each new source kind (`origins` is validated strictly, so an unknown kind would read as an unavailable draft). The composer's score trend already reads the 90 days before the service date, which covers a 60- or 90-day benefit period, so it needs no change.
- **Sections and their sources.**

| Section | Fed by | Rule |
|---|---|---|
| `pps` | PPS readings | the latest reading at or before the visit time and new since the previous visit (the S1 rule), with the change from the benefit period's first reading |
| `esas` | ESAS-r readings | as `pps`, per symptom |
| `prognosis` | decline evidence | PPS change from the benefit period's first reading; weight change over the period; the attested F2F's facts when it was attested at or before the visit. Numbers and dates only (VN-D32) |
| `recert_summary` | benefit period | sequence, kind, start and end, the day of the period at the visit, the level of care on the visit date, the CTI's status and signing date when signed by then |

- **Module 6 facts, as of the visit (VN-D11).** Built with M6's four existing readers, no new seam: `listPeriodsForAdmission` (the period covering the service date), `getLevelOfCareDays` over that one day (named only when exactly one level counted), `getAttestedF2fForPeriod` and `getActiveCertification`. They answer by date or by period, so the as-of cut is made in `inputs.ts` and the compiler: a F2F attested, or a certification signed, after the service date is not drafted, and a certification that is not signed now is not drafted either (silence, never a stale claim). The plan had one new composite seam; the readers already answer by date, and four sequential reads (they take their turn per request) cost a few milliseconds under the sign lock. The F2F fields are structured facts only (VN-D32). The draft of a recertification visit needs M6's own read keys for the four facts (`election.read`, `cti.read`, `f2f.read`, `loc.read`) and the face-to-face visit's draft `election.read`, checked by the service by template (`drafting/admission-reads.ts`), so the routine visit's draft needs no new key. The same keys are asked wherever the draft is recomputed for a caller: finalize, sign, and an addendum's finalize and sign answer `403` naming the key, after the switch check and before any source is read, so a refusal list never tells a caller what the admission holds that they cannot read.
- **Baseline.** `series(from = period start, to = visit time)` through the existing M9 seam; no new seam. A latest reading at or before the previous visit is still not drafted (S1), so a recertification with no new PPS reads "nothing to draft from" and prompts the RN to record one.
- **Weight.** A store port over M8's own `vitals`: the patient's weight rows at or before the visit across the benefit period, not only this encounter's. Its sources are this encounter's own weights and those of the patient's signed encounters (an unsigned draft of another visit is not yet part of the record). The weight parses strictly as a positive decimal with a unit of `kg` or `lb`; a row with no text at all was never captured and is left out, but any other row in the period that does not parse or has no usable unit means no weight is drafted at all, and so do weights in two units (nothing is converted, and "the first" and "the only weight recorded" would be false).
- **Part 2.** Every S2 source carries `sudRelated: false`, as S1's PPS and vitals do. M9 still redacts only an AIMS taken in a SUD context.
- **The corpus.** A new release, `narrative-vocab@2026.12.0`, carries the recertification wording. Its wording is draft until ADA reviews it, and the approval names the release (VN-D34). The deploy moves `VOCAB_VERSION` for every tenant, so a draft whose selections were saved before it answers `409 VOCAB_VERSION_MISMATCH` at finalize until the selections are saved again (S1 §3.2).
- **No migration** is planned and the eraser is unchanged. If the weight read needs an index, it is one `-- compat: expand` migration.
- **Not in S2.** The admission sections (VN-D31), the CTI narrative, FAST, NYHA, labs and hospitalisations (VN-D33), mobile, offline, dictation and AI.

### 3.4 S2b design: the RN admission visit (VN-D35 to VN-D38)

Designed 2026-11-20 against `main` at `096e01f5e`. Within the decisions above; the S1/S2 pipeline (per-author draft recomputed as of the visit time, confirmation bound to the content hash and corpus version, gate check 13, sealed rows, per-viewer Part 2, amendments, the switch, the per-template read keys) is reused unchanged.

- **Which templates draft.** Still read off the corpus tags (`draft/scope.ts`). `admission_visit:rn` drafts `med_reconciliation`, `advance_directive`, `caregiver_overview` and `baseline_symptoms`, and its base `vitals_review`, `interventions` and `plan` from S1's sources. `assessment` and `symptom_management` draft nothing there: the PPS phrases are not tagged for it, and ESAS-r feeds `baseline_symptoms`, so no reading is stated twice.
- **A source map per template**, as S2's: `admissionVisitMap` in `draft/sources.ts`, with its phrase map. A sentence per source, ordered by a fixed key so a database that returns rows in another order cannot change the draft or its hash.

| Section | Fed by | Rule |
|---|---|---|
| `med_reconciliation` | the orders in effect (M12) | one sentence per order: drug, strength, form, route, and "as needed" where it is (the order's flag, or a PRN frequency code, as M13 reads it). No frequency, no dose schedule, no word about reconciliation. A SUD-treatment order is left out for a viewer without Part 2 disclosure (as the medication changes are) and marks the section Part 2. If any order that remains has a blank field or no as-needed flag, no list is drafted: a list with an order missing would read as complete |
| `advance_directive` | the acknowledgment on file (M39) | one sentence that an advance directive acknowledgment was on file at the visit time. Nothing is drafted when none was. Never whether the patient has or wants a directive, never code status |
| `caregiver_overview` | the caregivers on record (M5) | name and relationship in words, the primary first, then by name. No phone, email or language. If any entry has a blank name or a relationship the draft has no word for, nothing is drafted |
| `baseline_symptoms` | ESAS-r readings (M9) | the S1 reading sentences (`nv.scale.esas_*`, retagged), as of the visit time |

- **Reads, as of the visit (VN-D11).** M12 `getMedicationsAsOf(visit instant)` decides from each order's own instants, never its status today. M39 `ConsentEvaluator.evaluate` is a pure read (no audit write), asked with `historical: true`: without it the evaluator reads a record's status today, so an acknowledgment revoked, renewed or expired by the patient's death after the visit would vanish from the draft and a finalized note could not be signed. With it a record counts when it was effective at the visit instant and had not ended then (a revoked or superseded row ends at its own `revoked_at` / `superseded_at`; an expired one at the earlier of its `expires_at` and its last update, which the death cascade stamps); an ended record with no end instant never counts. A record also counts only if it had been entered by the visit instant (the later of `created_at` and `signed_at`, both set by the server), because its effective date is the caller's to backdate: an acknowledgment entered after the visit, or created before it and signed after it, never reads as on file at it. No other caller passes it, and a test pins the one source file that does, so every disclosure gate keeps the status-today answer. M5's roster had only a current-links read, so S2b adds `caregiversOn(day)`: a link counts when `involvement_from <= day` and it has no end or `involvement_to >= day` (the end day is included). Each read takes its turn in `serialSeams`.
- **Permissions (VN-D37).** `patient.read` is the key of M5's `GET /patients/{id}/caregivers`, `consent.read` of M39's consent reads. The orders need `prescribing.read`, which the draft routes already guard on and which the admission template names as well, so finalize, sign and an addendum's recompute ask it. The check is by template, after the switch and tenant checks and before any source is read.
- **Menus.** The new phrases are in a draft-only category (`admission_record`) no menu lists, so no order, caregiver or acknowledgment is typed by hand. The four sections keep the menus they had. The care-plan phrases tagged for this visit share the category `med_reconciliation` already offered its legacy phrases through, so they also appear in that menu with the switch on, as `interventions` and `plan` share it in the routine visit (S1).
- **The corpus.** `narrative-vocab@2026.12.1`: 5 new phrases (`nv.adm.*`) and the `admission_visit` tag on 16 S1 entries. The wording is draft until ADA reviews it, and the approval names the release (VN-D34). The deploy moves `VOCAB_VERSION` for every tenant, so a draft whose selections were saved before it answers `409 VOCAB_VERSION_MISMATCH` at finalize until they are saved again.
- **No migration.** The eraser is unchanged.
- **Not in S2b.** The face-to-face visit's `med_reconciliation`, code status, the content of an advance directive, caregiver contact details, home-medication history, mobile, offline, dictation and AI.

## 4. Constraints found

### 4.1 Backend and tenancy

- M8 reaches other modules by seam only (ADR-0007, ADR-0043). RECON: the M9 store throws outside a request context, so any worker-time computation needs org-explicit `...ForOrg` seams, as M14 does (`14-idg/jobs/packet-build.ts`). The per-author draft is computed in a request, which avoids that.
- VN-D11 needs as-of reads (§3.1): the care plan from the frozen version in effect at an instant (M7), medication orders as of an instant (M12, a new method), and scale readings through the existing `series(from, to)` (M9, no new seam). The other current seams return the present state.
- RECON: `CarePlanReader` already redacts Part 2 per actor. The draft inherits that and must never cache an unredacted result across authors.
- AI is blocked platform-wide (`ai.full` off, M32 inference seams are deny-stubs). A deterministic draft is not AI and does not meet that gate. The later AI slice is a separate decision.
- New tables follow the repo rules: three-column tenancy, RLS enabled and FORCEd, PHI audit triggers, `-- compat: expand`, manifest `ownedTables` (`.ts` and `.cjs`).

### 4.2 Compliance

- A new sign-blocking gate and any offline vault are security controls. Each needs its row in `compliance/controls.yaml` in the same change as the build, and `controls.yaml` edits need the owner's approval.
- Source ids per section go to the M4 audit trail; the read of a drafted section needs a read-audit config with a `resourceIdParam`.

### 4.3 Mobile

RECON, from `chartwarden-mobile` `main` at `77f450d` (2026-11-06):

- Expo SDK 57, React Native 0.86. The composer renders the server-built `layer1Preview`; it imports nothing from this monorepo. Contracts for several modules are generated from a pinned OpenAPI commit; encounters, EVV and orders are hand-written. The client sends no contract-version header, although ADR-0072 says it should.
- No offline clinical cache exists. The only persistent store is the EVV outbox (SQLCipher), behind a flag that defaults off, with its device QA matrix not yet run and its backend route not confirmed deployed.
- Encounter, signature, order and clinical-document mutations are explicitly not queued. Unsaved note text is memory-only, and the app cannot cold-start offline.
- No dictation exists and the microphone permission is off. ADR-0094 (Proposed) rejects browser speech and says a native app must extend or supersede it.
- The repo has no CI.
- ADR-0072 makes the mobile app a separate React Native/Expo repo and supersedes ADR-0035; the owner ratified that supersession on 2026-11-18. The security owner's sign-off on its decisions 8-12 as controls (push, SQLCipher store, app lock) and its device-evidence items are still unsigned, and the offline slice (M3) depends on them. ADR-0072 names the repo `wardenx-mobile`; the repo is now `chartwarden-mobile`.
