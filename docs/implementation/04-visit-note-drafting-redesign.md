## 1. Problem

A competitor's headline feature is that the visit note writes itself. A nurse in a public hospice-documentation group said of FireNote: "it pulls everything from your assessment and Careplan and inputs it into your note." (LinkedIn thread, not retrievable by our research; the wording is unconfirmed against FireNote's own material.) Our visit note is thin by comparison: the clinician taps phrases and nothing from the patient's record reaches the note.

### 1.1 What our note does today

| ID | Decision |
|---|---|
| VN-D5 | Beyond the clinician's own selections, the draft pulls four sources, each shown with its origin and individually deselectable: (1) care-plan goals and interventions linked to the visit, auto-selected; (2) the latest **scale readings** with the change since the last visit; (3) vitals; (4) medication and order changes since the last visit. |

| VN-D8 | Deselecting a care-plan goal or intervention means it is not linked to this visit, through the same links the signed event already carries. A note never changes the care plan. The audit trail records the deselection. |

| VN-D12 | A confirmation binds to the draft snapshot version, the phrase-corpus version and a hash of the section's rendered content. ## 3. How a draft works

1. The visit is published (`m17.visit.published`) and seeds an encounter as today.
2. The author opens it. The server builds the draft for that author, as of the visit time (VN-D10, VN-D11): linked care-plan goals and interventions, scale readings with deltas, vitals, medication and order changes (VN-D5), each section carrying its source ids.
3. A section with no source renders as empty with a visible state (VN-D9). The clinician's own selections work as they do today.
4. The clinician resolves every drafted section: confirm, edit or deselect (VN-D7, VN-D8). Each confirmation binds to the snapshot version, corpus version and content hash (VN-D12).
5. Sign: step-up (existing, online), attestation acknowledged (check 9), every drafted section resolved (new check). A stale confirmation returns that section for re-confirmation.
6. Source ids stay in the audit trail only (VN-D7). After signing, the note changes only by amendment (VN-D30).

### 3.1 Frozen text, per-viewer view and amendments (S1 step 0 design)

PROPOSED within the decisions above; no decision changes. The M8 spec makes a signed encounter immutable with changes through addenda (M8 spec D2); VN-D30 extends that addendum path to carry section-level amendments.

- **Frozen text.** `hearthnote_assembled_outputs.final_cipher` stays the legal text of a signed note. At sign, S1 also writes one sealed row per section (`hearthnote_signed_sections`): section id, position, sealed rendered text, a SHA-256 of the canonical text, a `part2_derived` flag and the source ids. The ordered rows must equal `final_cipher`; a test pins that invariant.
- **Per-viewer view (VN-D13).** A viewer with Part 2 disclosure, or a note with no `part2_derived` section, gets `final_cipher`. Any other viewer gets the section rows with each `part2_derived` section replaced by a withheld marker. A section is `part2_derived` unless every source behind it is proven not SUD-related, failing closed as `redactStateSnapshot` does in M7. A clinician's own free text is not classified. Built in PR E1 (§3.2 "Per-viewer view").
- **Amendment (VN-D30).** An addendum (its own draft, finalized, signed lifecycle; the parent stays signed) that names the sections it amends. Its section rows reference the amended section, so the current view shows the latest signed text per section and the history shows every version. Original rows are never updated. Each amended section is confirmed like a drafted one (VN-D12), signing needs step-up, and a cosign request is created for the addendum when the parent needed cosign.
- **As-of inputs (VN-D11).** Care plan: the `care_plan_version` in effect at the visit time (`signed_at` at or before it, `superseded_at` null or after it), read from its frozen `state_snapshot` with the existing per-viewer Part 2 redaction. Scale readings: the existing `ScaleSeriesProvider.series(from, to)` with `to` set to the visit time, so no new M9 seam. Medications: a new changes-between and active-as-of read on `MedicationOrderProvider`.
- **Open until built:** the exact `amends_section_id` shape, the addendum cosign link, and how M22 renders amended sections.

### 3.2 Backend design for PR C (S1)

PROPOSED within the decisions above; no decision changes.

- **No stored draft.** The draft is recomputed from the sources on every read, for the reading author, as of the visit time. Nothing PHI-derived is cached, so Part 2 redaction is applied per request (VN-D10). The section's content hash (which covers its text and source ids) plays the part of the draft snapshot version in VN-D12; a stored per-author snapshot arrives with the offline slice (VN-D22).
- **Visit time (`asOf`).** The earlier of now and the last millisecond of the encounter's service date in the organization's time zone. `started_at` and `clock_started_at` do not matter: a note written after checkout, or later that day, still gets the visit's own vitals, scores and medication changes, while one written days late does not pull in the days since, and a service date still in progress is capped at now.
- **Resolution.** A drafted section is resolved by `confirmed` (bound to the content hash the clinician saw, which the request carries) or `deselected` (the drafted sentences stay out of the note; the clinician's own selections and free text stay). "Edit" is the existing selection and free-text save, which changes the hash; the clinician then confirms. A confirmation that no longer matches the recomputed hash, or whose corpus version is not current, reads as `needs re-confirmation` and blocks signing; this holds for `deselected` too. `edited` is recorded as whether the section carried the clinician's own text at confirmation (the rubber-stamp indicator, VN-D18).
- **Care-plan items.** The draft shows the elements `relevantElementsAsOf` returns, minus any with a removed link on this encounter. Confirming a section writes live `encounter_care_plan_link` rows for its care-plan source ids (idempotent). Deselecting one element soft-removes its link, or inserts an already-removed row when it was never linked, so a re-open does not bring it back. A note never changes the care plan (VN-D8). The deselect unit is the section, and for care-plan elements the link; scale readings, vitals and medication changes are deselected with their section.
  - **The deselect-hash trap, resolved (PR C2b1).** Removing a section's care-plan elements changes the section, so the hash the clinician saw is not the hash a later read computes. A `deselected` row bound to the hash SEEN would read `needs_reconfirmation` the moment the draft was reopened, and a deselected section could never stay deselected. So the deselect writes the link changes first, recomputes the draft for the same viewer inside the same transaction (the store port `removedCarePlanElementIds` reads the transaction's own writes), and binds the `deselected` row to the hash of the section AS RECOMPUTED. What remains in the section (the medication changes or other sentences of a mixed section such as `interventions`) is deselected with it. A section that is empty after the removal (a care-plan-only section such as `plan`) writes no bound row and reads `not_drafted` (a resolution the clinician left earlier is withdrawn, below). The explicit audit event carries ids, enums and counts only, never a content hash (an unsalted hash of low-entropy section text is a guessing oracle for anyone with `audit.read`).
  - **Retry.** A deselect that removed elements changed the section, so a retry carries the old hash. It is a no-op success while the section is already `deselected` and current (a mixed section), and `409 DRAFT_SECTION_STALE` when the removal left the section empty (nothing is drafted to match against); the client refetches and reads `not_drafted`.
  - **A deselect that empties a section the clinician had resolved withdraws that resolution (fix pass).** A section that is empty after the removal normally keeps no row, but a row the clinician left earlier (a `confirmed` at hash H) would outlive the removal: link the goal again through the picker and the section hashes to H once more and reads `confirmed` with no new confirmation. So when a row exists, the deselect writes it as `deselected` with no source ids, bound to `sha256("withdrawn:" + sectionId + ":" + corpusVersion)`, a hash no recomputed section can equal, and a re-link reads `needs_reconfirmation` (the clinician resolves it afresh). With no earlier row nothing is written and a re-link reads `unresolved`. The explicit audit event records only that the resolution was withdrawn.
  - An element is "removed" for the draft only while it has a removed link and no live one, so linking it again through the picker brings it back.
- **Scope.** Which templates draft is one predicate read off the corpus, `templateHasDraftedSection(encounterType, discipline)` in `@chartwarden/hearthnote` (`draft/scope.ts`): a section is drafted for a pair when its template has it, the sources feed it (`DRAFT_SECTION_PHRASES`) and every corpus phrase it is built from is tagged for the pair. The draft phrases are tagged for the RN routine visit alone, so that is the only template S1 drafts; tagging them for another pair is what makes that pair draft, with no list to keep in step (a test compares the predicate with the compiler for every legal pair). It is asked BEFORE any source is read, by finalize, sign, the gate check and the draft routes, and the compiler obeys it (an undrafted template compiles to all-empty sections even when every source is supplied). A template with none behaves exactly as with the switch off: no source read, no draft, no check 13, `final_cipher` is Layer 1 text, no sealed rows and no confirmation asked, whatever the seams do. Before this rule the draft was read for every encounter type, so a failing source blocked the sign of a type S1 does not draft, and a template with a care-plan-fed section (a CHHA `plan`) could draft RN-routine phrases.
- **Gate.** A new check `draft_sections_resolved` (the 13th id in the register) runs when the tenant switch is on and the template has a drafted section (Scope). Unresolved sections give `DRAFT_SECTION_UNRESOLVED`; stale ones give `DRAFT_SECTION_STALE`. A draft that cannot be computed is `COMPLIANCE_GATE_UNAVAILABLE`, never a pass.
- **Sign.** The draft is recomputed for the signer and each confirmed section's hash must equal the stored one, else 409 `DRAFT_SECTION_STALE` naming the sections. The assembled narrative uses the confirmed draft text for `confirmed` sections and the clinician's selections only for `deselected` and undrafted sections. At sign one sealed `hearthnote_signed_sections` row per section is written in the same transaction as `final_cipher`, and the ordered rows must equal it (PR E1 adds the per-viewer view on top, amendments are PR E2). Built in PR C2b2; `final_cipher` is in fact first pinned at finalize, so see "Gate and sign" below for how finalize and sign share the one text.
- **Tenant switch.** One row per organization, default off, written by a holder of a new permission with step-up, mirroring the ADR-0113 policy service. Enabling is refused while `CORPUS_CLINICAL_REVIEW.status` is not `approved`. A tenant with the switch off sees today's behaviour exactly, and every new route answers 404 for it, with two stated exceptions to the corpus release that ships with the slice:
  - **The authoring menu** (`GET /encounters/{encounterId}/template`) offers the 25 phrases of `narrative-vocab@2026.11.0` (`DRAFT_VOCAB_CODES`) only where the switch is on: they are unreviewed draft wording (VN-D14). With the switch off the menu is what it was before that corpus, including the RN routine visit's `chief_concern`, `vitals_review` and `plan` sections as open as they were (`resolveTemplate(..., { draftWording: false })` leaves the VN-D15 category wiring off). A switch cannot be turned on while the corpus review is pending, so the wording reaches a tenant only after it is approved. The menu is the only place the categories bite; `PATCH .../selections` still accepts any code the corpus holds.
  - **The vocabulary version.** `VOCAB_VERSION` moves to `narrative-vocab@2026.11.0` for every tenant at deploy, switch or no switch, as any corpus release does. A draft whose selections were last saved before the deploy carries `template_version` `narrative-vocab@2026.06.0`, so `POST /encounters/{encounterId}/finalize` answers `409 VOCAB_VERSION_MISMATCH` until the author saves the selections again (any `PATCH .../selections` restamps the version; the web composer saves before it finalizes, so it does so on its own). Nothing else reads the stored version: a note already finalized keeps its pin, and the draft is computed against the running corpus.
- **Part 2.** Medication orders carry `isSudTreatment` unredacted from the M12 seam (PR A), so M8 drops SUD orders for an author without disclosure, using the same disclosure check the care-plan reader applies, and marks the rest `sudRelated` so a section's `part2Derived` fails closed.
- **Sealed rows** are encrypted with the same key path as `final_cipher`. **Source ids** reach the audit trail through the confirmation row's audit trigger and never the signed text.

#### Input rules (PR C2a, `08-encounters/drafting/inputs.ts`)

- **Care plan.** `relevantElementsAsOf(patient, type, discipline, admission, viewer, asOf)` with the session identity as the audience, so M7 redacts per viewer. Goals and interventions whose link was removed for this encounter (`removedCarePlanElementIds`, supplied by the store) are left out. A `null` plan is `carePlan: null`. A plan of another patient is refused. A plan M7 flagged `redacted` (Part 2 content withheld from this viewer) is drafted reduced only for a viewer the draft's own Part 2 verdict (below) does not clear; for a viewer it clears, the plan was cut by an M39 outage or a consent change between the two reads, so the draft is `DRAFT_UNAVAILABLE` (503) rather than silently short of content the viewer may read. A goal or intervention takes its parent problem's SUD flag; a parent the reader did not return leaves the flag unset, which reads as Part 2. Encounter disciplines `md`/`np` map to `md_np` and `slp` to `st`.
- **Previous visit.** The patient's most recent SIGNED visit-type encounter on an earlier service date, supplied by the store port `previousSignedVisitAt` as the instant that encounter's own note described the patient at (`previousVisitAsOf`: `visitAsOf` of its service date, same zone and now, and never later than its `signed_at`), so the picture at the previous visit plus the changes since is exactly the picture now. Without the signing cap a change made after the previous signing but before midnight would be in neither note. The recompute at sign reads its clock a few milliseconds after `signed_at`, so the two windows can overlap by that much (a change in it is in both notes), never leave a gap. One later than this visit time is refused.
- **Scale readings.** For `pps` and `esas_r`: the latest reading captured at or before `asOf` (`series` with `to = asOf`, cut again in code), `previous` the latest at or before the previous visit time, else null; no previous visit means `previous` is null. A latest reading captured at or before the previous visit time is not drafted at all: the previous note already carried it, so it is not new since then (VN-D6, VN-D9) and, as its own `previous`, it would read "unchanged from itself". A latest reading without a score is not drafted and an older one does not stand in. The M9 series carries one score per ESAS-r capture, so it is drafted as the `total`. Dates are org-local.
- **Vitals.** The encounter's own latest row captured at or before `asOf`; no merging across rows. Vitals and PPS/ESAS-r readings carry `sudRelated: false` (M9 redacts only AIMS taken in a SUD context).
- **Medication changes.** `getMedicationChangesBetween(patient, previousVisitAt, asOf)`. With no previous signed visit there is no window and none are drafted (an honest empty section, VN-D9). A completed course is drafted as discontinued (the corpus has no "completed" phrase). A change's source id is `<orderId>:<kind>`, because one order can start and stop inside a window.
- **Part 2.** An order with `isSudTreatment !== false` (fail closed) is dropped unless the viewer has Part 2 disclosure; kept orders carry `sudRelated = (isSudTreatment !== false)`. The verdict is M7's per-actor decision (`sudDisclosureAllowedForActor`: M39 `evaluateForInternalAccess`, then the RN case manager carve-out where no release names others), asked as `callerModule: "m8"` so M39's evaluation audit attributes the check to M8, and at most once per draft: when an order could be withheld, or the care plan came back `redacted`. An M39 failure is NOT a "no": the checker rethrows (`defaultInternalSudAccessChecker({ onError: "throw" })`), so the draft is `DRAFT_UNAVAILABLE` instead of quietly shrinking.
- **Failure.** A seam that throws, or returns something unusable (an instant that is not one, another patient's plan), is `DRAFT_UNAVAILABLE` (503), never a partial draft. The message names the read; the upstream cause stays on the error for the log. Every read, seam or store, is bounded by `DRAFT_SOURCE_READ_TIMEOUT_MS` (5 s, `unavailable.ts`): a read that does not answer in time is `DRAFT_UNAVAILABLE` too, so a hung source cannot hold the sign transaction open. No retry, no fallback: the abandoned read is not cancelled and its late answer is ignored, and the gate and sign still fail closed.
- **Visit time.** `visitAsOf({ serviceDate, orgTimeZone, now })` is the earlier of `now` and the last millisecond of the service date in the organization's zone (DST-safe).

#### Store and routes (PR C2b1, `08-encounters/drafting/`, `08-encounters/routes/draft-section-routes.ts`)

- **Store ports** (`db-draft-store.ts`, one `withOrgContext` transaction per request, so RLS scopes every statement). `organizationTimeZone` is `organizationTimezone`. `previousSignedVisitAt` is the patient's most recent encounter with status `signed`, `cosign_pending` or `cosigned` on a strictly earlier service date (a later-signed one wins a tie on the date; a draft, a voided, a later, a same-day and another patient's encounter do not count), returned as that encounter's own `previousVisitAsOf`. All seventeen encounter types are visit types (`packages/types/src/encounter.ts`), so every type counts. `latestVitals` is the encounter's own `vitals` row with the latest `captured_at` at or before the visit time (ties by `created_at`, then id), never merged; a temperature needs a unit of `f` or `c`, and a pain score counts only on the `nrs_0_10` scale (one on another scale, or with no scale, is not drafted). `removedCarePlanElementIds` reads `encounter_care_plan_link` (see "Care-plan items"). `loadSelection` is what the Layer-1 assembly reads: the stored tree with its prose opened through the tenant free-text cipher (the shared reader is `selection-tree.ts`), the patient slot `Patient` and the service date. Sealed prose with no cipher bound is refused (`DRAFT_UNAVAILABLE`), never drafted without the clinician's own text.
- **`GET /api/v1/encounters/:encounterId/draft`** (`encounter.read` plus the source domains' read keys `care_plan.read`, `prescribing.read` and `assessment.read_trend`, because the seams apply no permission check of their own; caseload scope; the PUT requires the same keys, so GET, PUT and sign compute one full draft per patient and visit). The draft for the SESSION viewer (roles and active membership from the server-assembled session, never the request), every template section with `state`, `text`, `contentHash`, `corpusVersion`, `part2Derived` and `origins`. VN-D7: source ids are NOT on the wire (the ids stay in the audit trail); `origins` carries only the kinds, which is what VN-D5's "shown with its origin" needs. The text is what the seams returned for this viewer (M7 and M12 redact per viewer), so no section is withheld a second time here; `part2Derived` is the compiler's fail-closed flag, for the signed-note view of PR E1. A state is read against the VIEWER's recomputed draft, so a viewer whose redaction differs from the author's sees the author's confirmation as `needs_reconfirmation`. Read-audited as `encounter_draft.viewed` (`resourceIdParam` is the encounter; the patient is attributed from the response; field names only).
- **`PUT /api/v1/encounters/:encounterId/draft/sections/:sectionId`**, body `{ resolution: confirmed | deselected, contentHash, corpusVersion }` (one idempotent route for both resolutions). Same permission and ABAC as the selections save (`encounter.author`, `encounter.scope`, `is_author_or_supervisor`), without `If-Match` (the section hash is the lock) and with the AI-principal refusal. The encounter row is locked `FOR NO KEY UPDATE` (see "Locking and connections" below), so confirmations of one encounter, a selection save, the picker's link and unlink, finalize and sign run one after the other. Allowed on any encounter that is not signed, cosigned or voided (the selections save's own rule, `checkMutableForEdit`): a `finalized` note can still be re-confirmed, since it can only go on to `sign`, which refuses a stale confirmation. `edited` is recorded as whether the stored selection tree holds the clinician's own text for the section (an entry, or the `hasFreeText` marker), read without opening the prose. Every write records `m8.encounter.draft_section_resolved` beside the confirmation row's trigger record; an idempotent repeat writes neither.
- **A template that drafts nothing (Scope).** `GET` answers `200` with every template section `not_drafted` (`text`, `contentHash`, `corpusVersion` and `part2Derived` null, `origins` empty), the same shape as a drafted template, so a client needs no special case; `asOf` is the read time (now), since no visit-time source is read, and no zone, source or stored selection is read. `PUT` on a section of such a template is `409 DRAFT_SECTION_STALE` (nothing is drafted to confirm, as for any section with nothing drafted), `422 UNKNOWN_TEMPLATE_SECTION` for a section the template lacks, and nothing is written. The tenant switch still decides first (404 when off).
- **Per-tenant switch.** Both routes answer `404 NOT_FOUND` when `isVisitNoteDraftEnabled` is false, read inside the request's transaction before the encounter or any source (no cache), with the same body an absent encounter gets.
- **Errors.** `409 DRAFT_SECTION_STALE` (new, `M8_ERROR_STATUS`), `503 DRAFT_UNAVAILABLE`, `422 UNKNOWN_TEMPLATE_SECTION`, `409 IMMUTABLE_AFTER_SIGN`.

#### Gate and sign (PR C2b2, `08-encounters/drafting/` and `gate/`)

- **Gate check 13.** `draft_sections_resolved` is registered `evaluated` (`gate/checks.ts`) and decided by the pure gate over a fact, `draftSectionActions`: the drafted sections that are `unresolved` (`DRAFT_SECTION_UNRESOLVED`) or `needs_reconfirmation` (`DRAFT_SECTION_STALE`), from `sectionStates` exactly as §3.2 "Resolution" decides them. `not_drafted`, `confirmed` and `deselected` (while current) pass. The fact is absent when the tenant switch is off or the template has no drafted section (Scope), so the gate is then as it was. Within a template that drafts, a section with no source this time is `not_drafted`: with nothing drafted the list is empty and the check passes. The check runs at both finalize (a 422 preview, for the author) and sign.
- **Reading the draft** (`note-draft.ts`, `note-draft-flow.ts`): `readNoteDraft` is `null` for a template with no drafted section (Scope, before anything is read, the switch included) and with the switch off, and reads nothing else; otherwise it recomputes the draft for the viewer inside the caller's transaction and sets it against the stored confirmations. A switch that cannot be read, a source that cannot be read or a draft that cannot be compiled is `503 COMPLIANCE_GATE_UNAVAILABLE`, never a pass and never "off". The three selection-assembly codes (`UNKNOWN_VOCAB_CODE`, `VOCAB_VERSION_MISMATCH`, `INVALID_ENCOUNTER_DISCIPLINE_PAIR`) keep their own codes, the ones the clinician's save and finalize already answer with.
- **Check 9.** `attestation_confirmed` is reclassified from `deferred` to `elsewhere`: `SignEncounterSchema` (and `AttestationSchema` on the cosignature and addendum signatures) declares `attestationConfirmed: Type.Literal(true)`, so a body that omits it or sends anything else is a 422 before the service runs. `encounter-compliance-gate.test.ts` pins that the schema refuses each of those bodies. The `deferred` blocker ("nothing carries the clinician's confirmation") was stale (§1.1).
- **Viewers.** The draft is read for the member acting: the author at finalize (`finalize` takes `args.viewer`, the session's roles and active membership from the route) and the signer at sign (`SigningActor.roles` beside the membership). Both come from the server-assembled session, never the body. A caller that supplies none is read as a member with no role and no Part 2 release, so a Part 2 difference makes the section stale rather than hiding it. Sign stays author-only today (GAP-028), so the signer is the author; the recompute is the signer's own regardless, and a test confirms as a viewer holding the Part 2 disclosure and signs without it (409), then with it.
- **Sign refusal.** Before any write, sign recomputes the signer's draft and answers `409 DRAFT_SECTION_STALE` for any drafted section that is unresolved or stale (the one code for both, with `details` naming each section and `DRAFT_SECTION_UNRESOLVED` or `DRAFT_SECTION_STALE`), ahead of the gate's own 422. A note finalized before the tenant switched the draft on therefore cannot sign until its sections are resolved; sections can be resolved on a finalized note.
- **The one text.** `finalNoteOf` (`final-note.ts`) builds the note from the signer's `ComputedDraft` and its states: `confirmed` sections contribute the draft text (the drafted sentences and the clinician's own words, as seen); `deselected` and undrafted sections contribute only the clinician's own selections and free text, rendered as Layer 1 renders them; a section with no body is not in the note. With nothing drafted the text is byte for byte what `assembleSelections` produces. The block and separator come from `assembleBlocks` and `joinBlocks` in `@chartwarden/hearthnote`, which `assembleLayer1` now also uses, so there is one rule. It refuses (409 `DRAFT_SECTION_STALE`) if any drafted section is unresolved: a note is never built from content the clinician did not confirm.
- **Where `final_cipher` is written.** It is first written at finalize (`hearthnote_assembled_output`, kind `primary_finalize`), not at sign, so §3.2's "in the same transaction as `final_cipher`" needed a rule: finalize pins the author's confirmed text (when the switch is on), and sign, in its own transaction, recomputes for the signer and UPDATEs `layer1_cipher` and `final_cipher` to the signer's text (the application role already holds UPDATE on that table; the UPDATE is guarded to a row Layer 2 did not take part in, else the sign is refused) and inserts the rows. The finalize pin is thus the author's text at finalize and sign's text is the note that was signed, even if a source moved or the selections were edited between the two (an edit to a drafted section is refused as stale first). This is also why a finalized note signs with the draft's text after the switch is turned on.
- **Sealed rows** (`signed-sections.ts`). One row per section the note carries, `position` its place among them. `text_cipher` seals the section block (its heading, a line break and its body) with the narrative envelope; the ordered rows unsealed and joined by a blank line (`NOTE_BLOCK_SEPARATOR`) are exactly the narrative, which `final_cipher` also holds. `content_hash` is SHA-256 of that same text, so anyone holding an unsealed row can check it. `source_refs` are ids and kinds of a confirmed section's sources only (never text; the row trigger carries them into the audit trail). `part2_derived` is the compiler's fail-closed flag for a confirmed section and `false` for a section made only of the clinician's own words (not classified, §3.1) or of a deselected section (its sources are out of the text). The rows are written with `final_cipher` in the sign transaction: any failure (a seal, the key ring, the UPDATE guard) fails the sign as one, leaving the note finalized with no row and no signature. Rows are written whenever the switch is on and the template drafts, including a note with nothing drafted, so every such note signed under the switch has them; with the switch off, or for a template with no drafted section, none are written.
- **Locking and connections (fix pass).** *Locks.* Every request that decides something from the encounter's draft takes the encounter row `FOR NO KEY UPDATE` first, in the same order (the row, then its satellites): the section PUT (`db-draft-unit.ts`), finalize, sign, the picker's link and unlink and the selections save (`loadEnc(..., { lock: true })` in `encounters-route-service-db.ts`). A sign therefore reads its draft after every section PUT that held the row has committed (a deselect between sign's read and its UPDATE would otherwise be sealed), and a second concurrent sign waits at the lock, then finds the note `signed` and answers `409 ILLEGAL_TRANSITION` instead of dying on the `(assembled_output_id, section_id)` unique constraint. `NO KEY UPDATE`, not `UPDATE`, so the foreign-key checks of vitals, mileage and signature inserts (`KEY SHARE`) are not held up. The status UPDATEs of finalize and sign also carry `AND status = <loaded status>`, mapped to the same 409 (unreachable behind the lock; the guard keeps a double sign clean if a path ever skips it). The picker's duplicate check and the PUT's link read each see the other's committed rows, so live links stay unique per element without a new index (a partial unique index on live links is not clean: the picker legitimately writes `(problem, goal)` and `(goal)` rows for one goal). *Connections.* Every seam read (M7, M9, M12, M39) opens its own pooled transaction (`withOrgContextFromRequest`), so with the request's own transaction held, one draft read used to take up to six pooled connections at once (M7 and the M39 check it makes inside, both M9 series, M12), and a sign sealed N + 2 texts at once, each resolving the tenant DEK in a pooled transaction of its own. Now the source reads take turns (`serial-seams.ts`, one in flight per request) and overlapping seals share one key-ring read (`hearthnote-crypto.ts`; nothing is cached past the read, so a rotation is seen by the next seal). A draft request peaks at its own connection plus two (one read, and M7's M39 check inside it); a sign's seals add one. A GET could drop its own transaction while the sources are read, but a write cannot: the lock must cover the confirmation reads the draft is compared with. *Sizing.* The pool defaults to 10 per process (`packages/db/src/client.ts`, 10 s acquisition timeout). Budget three connections per concurrent draft or sign request, so ten requests in flight at once can still hold all ten connections while each waits for a seam read; the acquisition timeout then ends the wait as `DRAFT_UNAVAILABLE` (503, fail closed), never a pass. Raise `max` (or cap draft concurrency at the edge) before enabling the switch for a tenant whose peak is more than about three simultaneous signers per instance. The link statements of a section PUT are batched (one INSERT per kind, one UPDATE), so the lock is held for a fixed number of round trips whatever the number of care-plan elements.
- **Not here.** Amendments (the `amends` column) and the cosign re-trigger (PR E2), the web screens (PR D) and the encounter eraser's `tombstoneEncounters` stay with later PRs and the eraser fix.

#### Per-viewer view and the pin (PR E1, `08-encounters/drafting/pinned-note.ts`)

- **What a reader gets.** Every reader of `hearthnote_assembled_output.final_cipher` goes through `readPinnedNote`. A viewer with Part 2 disclosure, or a note with no `part2_derived` section, gets `final_cipher` byte for byte (the sealed rows joined by a blank line are that same text, and a live test pins it). Any other viewer gets the sealed rows in order with each `part2_derived` section replaced by `PART2_WITHHELD_MARKER`, a generic sentence that names no clinical content and says nothing of the section (not even its heading); the sealed text of a withheld section is never opened. The verdict is asked only when the note has a `part2_derived` section, so a note without one never asks M39.
- **The viewer and the verdict.** The viewer is the session's roles and active membership (`draftViewerOf(request)`, never the request body); the verdict is the M7 per-actor decision the draft already uses (`DraftSeamPorts.part2DisclosureAllowed`: M39 `evaluateForInternalAccess` as `callerModule: "m8"`, then the case-manager carve-out, `onError: "throw"`). A check that fails is `503 NOTE_VIEW_UNAVAILABLE` (new, `M8_ERROR_STATUS`), never a silent denial and never a disclosure; it is bounded by the same 5 s as the draft's source reads. A caller with no viewer is read as a member with no role and no release.
- **The pin records it (migration 1522).** The sealed rows are written at sign, so between finalize and sign the pin holds the author's draft text and no row says which section is Part 2. `hearthnote_assembled_output.part2_derived` (NOT NULL, default false) is written with the pin at finalize from the author's confirmed text (`FinalNote.part2Derived`: any confirmed section carries the compiler's flag) and rewritten at sign from the signer's text. A pin that carries Part 2 text and has no rows yet (finalized, not signed) cannot be cut by section, so it is withheld whole from a viewer without disclosure. The column is a boolean, never content, and the frozen-after-sign trigger (1521) still guards the ciphers only.
- **Readers covered.** `GET /api/v1/encounters/:encounterId` (`finalDocumentation`, per viewer); `GET /api/v1/internal/encounters/:encounterId/render-payload` (route 31); and `SignedEncountersReader.renderPayloadFor` (`seams/drizzle-store-ops.ts`, the same payload through the seam). The addendum texts the render payload carries are the clinician's own words (an addendum is never drafted) and are unchanged. The cosignature queue and view, the addendum parent view, the list reads and the exports read no narrative text: the encounter row views carry no `final_cipher`, and no other module reads the table. A new reader of `final_cipher` must go through `readPinnedNote`.
- **M22 limit (fail closed).** M22 stores the rendered document under the template's own retention class (`encounter` is `clinical_record`) and serves it to every holder of document read access. Its only per-render signals are the lab-results variants' `retentionClassOverride` and the consent gate on an event's `isSudClass` flag, and neither exists for the `encounter` template: nothing M22 carries would keep a Part 2 section out of a broadly readable document. So the document consumers are never entitled: for a note with a `part2_derived` section the render payload is ALWAYS the withheld view, the entitled author included, and it asks no one. This is a limit, not a design: a rendered signed note for such an encounter shows markers where Part 2 text is. Lifting it needs an M22 Part 2 document path (the `compliance_42cfr_part2` class at INSERT with Part 2 gated reads) and a per-event signal from M8. Today the `m8.encounter.signed` event carries `documentRenderPayload.final` as an empty string, so no note text reaches M22 through the event either.

#### The draft switched off between finalize and sign (PR E1)

- **Refused, not sealed short.** A note finalized with the draft on pins the author's text; sign with the draft off (the switch, or a template the corpus does not draft) used to leave that pin as it was, with no sealed rows and no `part2_derived` record, so nothing could withhold it. Sign now refuses with `409 DRAFT_OFF_AFTER_FINALIZE` and a remediation (switch the draft back on for the organization, then sign again) when the pinned output carries `part2_derived`, before any write; the note stays finalized. A finalized note has no way back to draft (`finalized` only goes to `sign`), so switching the draft on is the one remedy; a pin made without the draft, or with the draft on but no Part 2 text, signs as before.
- **The signal is the pin's own flag, not a confirmation row.** An `encounter_draft_confirmation` row exists whenever the author resolved a section, including a note finalized after the switch was turned off, and a `deselected` row says the pin has no drafted text; refusing on any row would block a rollback (switch off, then sign the in-progress notes). `part2_derived` on the pin is written by the finalize that produced the text, so it is true exactly when the pinned text carries Part 2 content.

#### Required sections and confirmed text (PR E1, project-lead decision)

- Gate check 1 (`required_sections`) used to look only at the clinician's own selections and free text, so after the author confirmed every drafted section the gate still demanded a statement in each required section. With the draft active for the template and the switch on, a drafted section in state `confirmed` (the bound hash matches the viewer's recomputed draft) satisfies its required section: `confirmedSectionIds(draft)` feeds the gate the fact `draftConfirmedSectionIds`. A `deselected` section does not (the clinician's own selections and free text still can), nor do `unresolved`, `needs_reconfirmation` and `not_drafted`. With the draft off or the template undrafted the fact is absent and check 1 is exactly as it was. The gate's per-check result shape (`GateRemediation`) is unchanged; check 13 still reports an unresolved section beside a missing one.

## 4. Constraints found

### 4.1 Backend and tenancy

- M8 reaches other modules by seam only (ADR-0007, ADR-0043). RECON: the M9 store throws outside a request context, so any worker-time computation needs org-explicit `...ForOrg` seams, as M14 does (`14-idg/jobs/packet-build.ts`). The per-author draft is computed in a request, which avoids that.
- VN-D11 needs as-of reads (§3.1): the care plan from the frozen version in effect at an instant (M7), medication orders as of an instant (M12, a new method), and scale readings through the existing `series(from, to)` (M9, no new seam). The other current seams return the present state.
- RECON: `CarePlanReader` already redacts Part 2 per actor. The draft inherits that and must never cache an unredacted result across authors.
- AI is blocked platform-wide (`ai.full` off, M32 inference seams are deny-stubs). A deterministic draft is not AI and does not meet that gate. The later AI slice is a separate decision.
- New tables follow the repo rules: three-column tenancy, RLS enabled and FORCEd, PHI audit triggers, `-- compat: expand`, manifest `ownedTables` (`.ts` and `.cjs`).

### 4.2 Compliance

- A new sign-blocking gate and any offline vault are security controls. Each needs its row in `compliance/controls.yaml` in the same change as the build, and `controls.yaml` edits need the owner's approval.
- Source ids per section go to the M4 audit trail; the read of a drafted section needs a read-audit config with a `resourceIdParam`.

### 4.3 Mobile

RECON, from `chartwarden-mobile` `main` at `77f450d` (2026-11-06):

- Expo SDK 57, React Native 0.86. The composer renders the server-built `layer1Preview`; it imports nothing from this monorepo. Contracts for several modules are generated from a pinned OpenAPI commit; encounters, EVV and orders are hand-written. The client sends no contract-version header, although ADR-0072 says it should.
- No offline clinical cache exists. The only persistent store is the EVV outbox (SQLCipher), behind a flag that defaults off, with its device QA matrix not yet run and its backend route not confirmed deployed.
- Encounter, signature, order and clinical-document mutations are explicitly not queued. Unsaved note text is memory-only, and the app cannot cold-start offline.
- No dictation exists and the microphone permission is off. ADR-0094 (Proposed) rejects browser speech and says a native app must extend or supersede it.
- The repo has no CI.
- ADR-0072 makes the mobile app a separate React Native/Expo repo and supersedes ADR-0035; the owner ratified that supersession on 2026-11-18. The security owner's sign-off on its decisions 8-12 as controls (push, SQLCipher store, app lock) and its device-evidence items are still unsigned, and the offline slice (M3) depends on them. ADR-0072 names the repo `wardenx-mobile`; the repo is now `chartwarden-mobile`.
