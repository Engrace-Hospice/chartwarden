# Patient Admission Workflow — Implementation Validation

**Validation date:** 2026-11-14
**Branch:** `fix/pr1036-main-conflicts`
**Scope:** The frontend-only increment approved in §13 of
[`02-admission-current-state-audit.md`](./02-admission-current-state-audit.md)

## Outcome

The approved increment is implemented and runtime-verified. It preserves the existing referral and
direct-admission entry points, server readiness evaluator, state machines, authorization, evidence
model, and activation contract. No backend route, database schema, role grant, clinical policy, or
automatic assignment was added.

The admission detail now:

- groups server-provided requirements into **Required before activation**, **Awaiting another
  person**, and **After admission and follow-up**, without re-evaluating eligibility in the browser;
- checks the signed-in session's permissions before offering a corrective ceremony and explains who
  normally owns an unavailable action;
- displays an explicit post-activation continuation panel linking to the existing patient chart,
  care-team view, and HOPE workflow;
- prevents repeat activation commits while the first request is in flight;
- treats both `412` and the backend's `409 VERSION_MISMATCH` as stale readiness, reloads server
  blockers, and never displays false success;
- releases the activation ceremony after a transport failure and gives the user a retry path; and
- wraps dense header actions at narrow widths rather than introducing document-level horizontal
  overflow.

## Browser journey

`e2e/specs/admission.spec.ts` now contains a complete synthetic multi-role path:

1. A platform operator creates a new synthetic patient and direct admission through real UI lookup
   controls.
2. The operator completes admission facts, records Notice of Rights, and creates/signs the Election
   Statement.
3. The session signs out; a credentialed hospice prescriber signs the CTI from the patient-scoped
   Election & Certification workflow.
4. The session signs out again; the platform operator reopens the admission and activates it.
5. The test verifies the activated state and the patient-chart, care-team, and HOPE continuation
   links.

The journey also fails on any HTTP 5xx response, browser console error, or uncaught page error. At
pending and active checkpoints it runs axe WCAG 2A/AA checks and asserts that the document does not
overflow horizontally at 375×812, 768×1024, and 1440×1000.

## Safety and preservation checks

- Readiness and activation remain server-authoritative; the client only groups and explains returned
  requirements.
- Permission-aware controls are presentation safeguards. Server RBAC and ABAC remain decisive.
- Physician signer separation is exercised through separate authenticated sessions.
- Activation still requires explicit attestation and a user commit.
- No PHI is written to browser storage, analytics, URLs, or screenshots. Evidence uses the synthetic
  E2E patient fixture.
- No automatic care-team assignment, notification, task creation, or navigation occurs after
  activation.

## Known limitations

- The test proves a direct-admission handoff. Referral intake and conversion remain covered by their
  existing browser and module tests; they are not duplicated inside this already multi-role journey.
- Axe, accessible-name assertions, focus-aware DOM tests, and keyboard-operable native controls are
  automated. A manual screen-reader session and a dedicated 200% browser-zoom recording were not
  performed, so those should not be inferred from the axe result.
- Suggested owners remain static workflow guidance, not live assignments. Adding assignments would
  require a separately approved data/API design.
- The shared mobile detail layout's lower activation pane is preserved rather than redesigned.

## Rollback

Rollback is frontend-only: revert the admission-detail presentation/helpers/tests, the Playwright
additions, and the shared `CeremonyModal.commitDisabled` prop. Do not reverse or mutate any admission,
election, CTI, evidence, or audit data created during normal use. The backend state and contracts are
unchanged, so rollback requires no migration, repair job, or clinical-state transition.
