# ADR-0062 — Clinical handoffs are a thin M36 aggregate of pointers, accepted item by item, where the sender stays accountable for every item until the receiver accepts it

- **Status:** **Accepted** (2026-10-14; the decisions are closed in the WP 3.5 blueprint. No clinical-lead sign-off is recorded.)
- **Date:** 2026-10-14
- **Phase:** Messaging Hub Phase 3 (WP 3.5, Handoffs).
- **Extends:** [ADR-0059](ADR-0059-messaging-clinical-links-read-through.md) (ids only, nothing copied, display re-resolved at read time), [ADR-0060](ADR-0060-messaging-sbar-structured-messages.md) (tighten-only tenant policy, per-tenant ops flag default off), [ADR-0061](ADR-0061-messaging-communication-tasks.md) (the migration, audit and offboarding pattern, and the one record that really moves: the communication task), [ADR-0054](ADR-0054-realtime-transport-socketio-valkey.md) (the owned-item reassignment hook is now bound for handoffs as well as tasks), [ADR-0057](ADR-0057-escalation-ownership-m19-m36.md) (handoffs do not page or escalate; that stays Phase 4), [ADR-0010](ADR-0010-tenancy-rls-invariants.md) (tenancy rule for the new tables), [ADR-0011](ADR-0011-ownership-inversion-rls-bypass.md) (no cross-module table access).
- **Related:** [ADR-0005](ADR-0005-manifest-single-source-of-truth.md) (shared types live in `packages/types`; table ownership lives in the manifest).
- **Amends the data model in** `docs/messaging-hub/02-architecture-and-domain.md` (see "Deviations from the architecture note" below). That note is a plan, and this ADR records where the built design differs from it and why.

## Context

The hub plan (`03-phases-0-to-3.md`, WP 3.5) wants a shift handoff: a clinician picks patients from their caseload, the system pre-fills the open work, the clinician offers it to a colleague, the colleague accepts, and responsibility moves. The architecture note says that when an offer expires or is declined, accountability stays with the sender and a supervisor is alerted (Workflow B, risk H-07). The UX note says Handoffs is an inbox filter, not a separate app.

Six facts shape the design:

- There is no shift entity to bind to. M17 owns visits, availability and on-call rotation entries; M19 owns on-call coverage; M37 owns unit nurse coverage. None of them is a general day or night shift, and none offers a seam that returns one. A `shift_ref` column would have nothing honest to point at.
- A handoff shows a patient to a named colleague. That is a disclosure of identity ("First L." and the last four digits of the MRN) and of open-work status. It is not chart access, but it is still a disclosure, so who may receive it is the central security question.
- Some of the pre-fill sources exist as seams and some do not. A visit, a pending refill request and an open symptom follow-up have seams. A callback has none (M19 exposes no call state to other modules), and there is no seam for unsigned or draft medication orders.
- Two of those seams (open symptom follow-ups and pending refill requests) ignore their organisation argument and rely on the ambient request tenant context. Pre-fill and read-time summaries must therefore run inside a request. A timer or an offboarding sweep must never call them.
- Nothing fires on its own when a handoff is not accepted. If expiry were only checked when someone opens the handoff, an unopened offer would stay open forever and the sender would believe the patients were covered.
- Messaging is not the emergency path. A handoff alert must not be mistaken for paging.

## Decision

1. **A handoff is a thin M36 aggregate that holds pointers and no text.** Four tables: `clinical_handoff`, `clinical_handoff_item`, an append-only `clinical_handoff_event`, and `tenant_handoff_policy`. An item is a (patient, kind, reference) pointer. There is no note, title or summary anywhere. What the screen shows for an item (patient label, visit status and time, refill status, follow-up status, task status) is re-resolved at read time from the owning seam, in the same way as clinical links (ADR-0059). Narrative belongs in the care-team thread (SBAR, ADR-0060). So there is no PHI string to seal, scrub or lint. A sealed note is a recorded follow-up, not part of 3.5.
2. **The feature is an ops flag, `messaging.handoffs`, default off, per tenant.** With the flag off, every single-handoff, write, caseload, pre-fill and policy route answers the uniform 404, and the list route answers `200 {enabled:false, handoffs:[]}` so the web can hide the tab without a flood of 404s. The web reads that `enabled` field and not the shell feature-flag hook (which is dead in the real app, the lesson of WP 3.4). **One safety exception:** the expiry timer and the offboarding sweep run for tenants with the flag off. Rows exist only if the flag was once on, and accountability must never stall on a flag.
3. **Accountability sits on each item.** Every item carries `accountable_user_id`, never empty. It is the sender when the item is created, and it changes to the receiver only in the same transaction that sets that item to `accepted`. The accountable clinician for any item is therefore always one column, and the sender stays accountable for every pending, declined, expired or cancelled item because nothing moves it. A database trigger backs this: an item may become `accepted` only with the accountable user set to the handoff's receiver, any other change must keep the accountable user as it was, and an item that is no longer `pending` can never change again. A `BEFORE INSERT` guard closes the other door: a new item must be `pending` and owned by the parent handoff's sender, so no insert can plant a resolved item or start accountability with someone else.
4. **Acceptance is per item, and the handoff state is derived.** Item states are `pending`, `accepted`, `declined`, `expired`, `cancelled`. A handoff stays `offered` while any item is `pending`. When the last pending item is resolved, the handoff becomes `accepted` if at least one item was accepted, otherwise `declined`. At the deadline, pending items become `expired` and the handoff becomes `expired`, even if some items were accepted earlier; accepted items keep their new owner. When the sender withdraws an offer, pending items become `cancelled` and the handoff becomes `cancelled`. Closed handoffs are final (database trigger).
5. **A tighten-only expiry policy.** `tenant_handoff_policy` holds one number per tenant, `expiry_minutes`. The platform default and ceiling is 240 minutes. A tenant may set 15 to 240, so shorter is stricter and a tenant can never lengthen it. No row means 240. The effective value is applied again on every read, and the deadline used is the earlier of the stored `expires_at` and the offer time plus the effective minutes. Lowering the policy therefore tightens offers already in flight, and a hand-edited longer row cannot loosen anything. The numbers are provisional (no clinical-lead sign-off is recorded). Policy edits need `messaging.template.manage`, the same as the SBAR policy.
6. **Who counts as a supervisor is the existing alert rules.** The supervisor audience is the seeded rule `m36.handoff.supervisor_review`, aimed at the roles `clinical_supervisor` and `don`. A tenant re-aims it through the existing alert-rule admin (`alert.rules.*`). That is the "per policy" of the architecture note, and it adds no new configuration. M3's supervisor reader offers no "list the supervisors of X" call, so it is not used. Declining and expiry always alert; there is no toggle.
7. **"Not accepted" has four causes and one consumer.** An outbox event `m36.handoff.unaccepted` carries a cause (`declined`, `expired`, `recipient_left`, `sender_left`). Its consumer sends the sender an in-app alert, and sends the supervisor rule an in-app alert. If the supervisor alert reaches nobody (`resolvedRecipientCount` is zero), the consumer appends a `needs_attention` event to the handoff (which works on a closed handoff because the table is append-only) and sends the sender a second alert, "no supervisor could be reached". The handoff DTO shows `needs_attention` when such an event exists. This follows the loud-fallback precedent for alerts with no recipient. It is in-app only: no paging, retries, escalation chain or on-call routing (Phase 4.1, 4.3, 4.9). The copy says so.
8. **Expiry runs on a timer, and the write path also checks the deadline.** A per-minute job, `messaging.handoff_expiry`, closes due offers. Accept and decline also refuse a handoff past its (policy-capped) deadline with a 409 before the timer runs. Both paths take a row lock on the handoff, so accept against expiry is serialised: whoever locks first wins and the other sees a closed or changed row. The timer fans out per organisation through an org-explicit function under the system organisation context, isolates a failure to its own handoff, and rethrows at the end so the job retries. The queue name is declared once, by M36.
9. **A task item transfers for real.** Accepting an item of kind `task` reassigns that communication task to the receiver in the same transaction, with reason `handoff` and the receiver as actor. It requires that the task is still active and still assigned to the sender, that the receiver can see the task's channel, and that the receiver holds no other active task on that message. Otherwise the whole accept call fails with `422 HANDOFF_ITEM_NOT_TRANSFERABLE` and nothing changes; the receiver sends again without that item and it stays the sender's. No `m36.task.reassigned` event is published (the handoff events cover it, and it would alert the person who just accepted). Only the typed list of reassign sources gains `"handoff"`. **The other kinds (`patient`, `visit`, `refill_request`, `symptom_followup`) move accountability in the handoff record only. No other module is written.** M5's assignment (care team and caseload) stays the source of truth for the clinician of record. Handoff acceptance does not change it.
10. **No new permission.** Reads need `messaging.read`. Every write needs `messaging.send`. Offer, pre-fill and caseload also need `patient.read` at role level; the per-patient test is the caseload check. Only the sender and the receiver can read or act on a handoff; everyone else gets the uniform 404, the same as for a missing id. The policy read needs `messaging.send` (the composer shows it) and the policy write needs `messaging.template.manage`. A new permission would need an M3 mirror migration for a gate the per-row rule already gives.
11. **Receiver eligibility is a disclosure rule, and it is a decision for review.** A handoff is a sender-authorised disclosure to a named colleague, not chart access. The receiver may be off the caseload (covering a shift is the point), so the owning module's caseload-or-scope ABAC is deliberately not applied to the receiver. Instead, at offer and again at accept: the receiver is not the sender, is an active messaging user, holds `messaging.read`, `messaging.send` and `patient.read`, and passes the 42 CFR Part 2 gate for every patient in the offer. If any patient fails the gate for the receiver, the whole offer is refused with the uniform `422 HANDOFF_RECIPIENT_INVALID` and no reason is given. The Part 2 gate is applied again on every read for the caller: an item whose patient fails the gate, or whose gate cannot be read, shows as `restricted` with no label. The sender must have each patient on their own caseload and pass the Part 2 gate at offer time. A gate or seam outage on a write fails closed. Accepting does not give the receiver chart access.
12. **The server is the authority on items.** The client sends (kind, reference, patient) triples. The service collects the open work again for the chosen patients from the same sources as pre-fill and rejects, with the uniform `422 HANDOFF_ITEM_INVALID`, anything it cannot verify. It also rejects when a source is unavailable (fail closed). The patient anchor item is always valid for a caseload patient. An item can be pending in only one handoff at a time (a partial unique index on kind and reference where the item is pending); a clash is a generic `409 HANDOFF_ITEM_CONFLICT` with no data about the other offer.
13. **Offering twice is safe.** A partial unique index allows one open (`offered`) handoff per sender and receiver pair. A repeat offer by the sender to the same receiver while one is open returns the existing handoff (`200`, `created:false`), inserts nothing, publishes nothing, and ignores the new body. To change the items, cancel and offer again. The unique pair contains the caller's own id, so a replay can only ever return the caller's own record (the lesson of WP 3.4). An item clash with someone else's offer is the generic 409 above and never shows their data.
14. **Participant reads only.** Closed handoffs stay readable to both parties as history. There is no team-wide or supervisor view in 3.5: supervisors get the alert, which carries ids only, and contact the sender. The supervisor safety queue is Phase 4.9.
15. **Offboarding works in both directions.** On `m2.membership.revoked` and `m2.user.deactivated` (not `suspended`, which can be reversed), an open handoff where the leaver is the receiver is declined with reason `recipient_left` and the unaccepted path runs, so the sender is told straight away. An open handoff where the leaver is the sender gets one `sender_left` event and supervisors are alerted; the receiver may still accept. Accepted items need nothing because accountability already moved. The sweep runs under the system organisation context, takes batches of 100, isolates a failure to its own handoff, converges on redelivery, and rethrows at the end. It runs without the flag. The offboarding closure now runs both the task and the handoff reassignment, attempts both even if one fails, then rethrows the first error. The socket disconnect still runs before and even if reassignment fails.
16. **Retention and erasure.** Handoffs are compliance records. There is no foreign key to a message or to a patient, no cascade, and `wardenx_app` has no DELETE on any of the three handoff tables. `wardenx_destruction` holds SELECT and DELETE under an organisation policy for tenant destruction. Patient lifecycle (discharge, death; WP 3.8) is out of scope: a pending item for a discharged patient simply expires.
17. **No patient-context tile.** A tile would show non-participants that a handoff exists for the patient. The tile list therefore gets no handoff entry.
18. **Where it appears.** A Handoffs tab in the existing notifications inbox (`/notifications?tab=handoffs`), shown only when the list route says the feature is on. A single drawer composes an offer (caseload, pre-filled items, receiver, expiry sentence). A second dialog is the receiver's review (items unchecked by default, accept or decline) and the sender's read-only view with "Cancel offer". There is no new screen and no new navigation entry. The compose screen always says that handoffs do not page anyone and that the sender stays responsible for an item until the receiver accepts it.

## Deviations from the architecture note

`02-architecture-and-domain.md` describes `clinical_handoff` with `shift_ref` (M17) and a state of `draft`, `offered`, `accepted`, `declined`, `expired`. The built design differs in four ways, all on purpose:

| Architecture note | Built | Why |
|---|---|---|
| `shift_ref` (M17) | No column. The deadline is `expires_at`, the offer time plus the tenant's minutes. | No shift entity or seam exists. Inventing a free-text or enum "shift" would be a made-up clinical data source. A nullable uuid can be added once M17 publishes a shift read, under its own ADR. |
| State `draft` | No stored draft. The compose screen holds the draft in the browser; nothing is stored or visible to the receiver until Offer. | A stored draft would be a half-built record that every query must filter out. It adds no safety. |
| States `offered`, `accepted`, `declined`, `expired` | Adds `cancelled`. | A sender must be able to withdraw a mistaken offer, because the receiver sees patient identity. |
| `accepted_at` on the handoff, acceptance of the handoff as a whole | Acceptance, and the accountable user, are per item. The handoff state is derived from its items. | Workflow B says the receiver accepts per item. A whole-handoff accept would move accountability for items the receiver never looked at. |

## Data model

Migration `1101_m36_clinical_handoff.sql` (check `arch:migration-numbering` against `main` first; `main` ends at 1100).

- **`clinical_handoff`:** `id`, `organization_id`, `from_user_id`, `to_user_id`, `state`, `offered_at`, `expires_at`, `accepted_at`, `closed_at`, `closed_reason` (`all_resolved`, `deadline`, `sender_cancelled`, `recipient_left`), `version`, timestamps. Database CHECKs hold the state set, the reason set, "sender and receiver differ", "the deadline is after the offer", "closed_at and closed_reason are set exactly when not `offered`" and "accepted_at is set exactly when `accepted`". A partial unique index on (organisation, sender, receiver) where `offered` is the idempotency arbiter. A `BEFORE UPDATE` trigger refuses any change to a closed handoff, even for `wardenx_app` through raw SQL. Further indexes lead with `organization_id` for the receiver, sender and due-offer lookups.
- **`clinical_handoff_item`:** `id`, `organization_id`, `handoff_id` (composite foreign key, `ON DELETE CASCADE`), `patient_id` (a logical pointer with no foreign key, as for `clinical_link`), `item_kind` (`patient`, `visit`, `refill_request`, `symptom_followup`, `task`), `ref_id`, `state`, `accountable_user_id`, `resolved_at`. CHECKs hold the kind and state sets, "resolved_at is set exactly when not pending" and "a `patient` item's reference is the patient". A unique index per handoff on (kind, reference) and the partial unique index on (organisation, kind, reference) where `pending` (decision 12). A plain, non-partial (`organization_id`, `handoff_id`) index serves the cascade lookup, which a partial index cannot. A `BEFORE UPDATE` guard trigger and a `BEFORE INSERT` guard trigger enforce decision 3.
- **`clinical_handoff_event`:** append-only; `event_type` (`offered`, `items_accepted`, `items_declined`, `closed`, `cancelled`, `needs_attention`, `recipient_left`, `sender_left`), actor (a user, or the system actor with no user id), `item_count` (a count only) and `reason_code`. No patient id and no item reference.
- **`tenant_handoff_policy`:** one row per tenant, `expiry_minutes` with a CHECK of 15 to 240, who configured it. A pin test keeps the bounds equal to the constants in `@wardenx/types`.
- **Tenancy and grants:** organisation-keyed, FORCEd row-level security on `app.org_id` on all four tables. `wardenx_app` holds SELECT and INSERT on the three handoff tables; on the handoff a column-level UPDATE on only `state`, `accepted_at`, `closed_at`, `closed_reason`, `version` and `updated_at`; on the item a column-level UPDATE on only `state`, `accountable_user_id` and `resolved_at`. So the parties, the patient and the reference cannot be rewritten. The event table has no UPDATE. None of the three has DELETE. The policy table has SELECT, INSERT, UPDATE and DELETE.
- **Audit:** the handoff, event and policy tables use the generic audit trigger (ids, enums and instants only). The item table gets a bespoke write-audit trigger that scrubs `patient_id` and `ref_id`, and records the actor as `system` when no user is set.
- **Code mirrors:** closed unions in `packages/types/src/messaging-handoff.ts`, a pin test that compares them with the migration CHECK lists, the Drizzle schema, and `ownedTables` entries for all four tables in the manifest (`.ts` and `.cjs`).

## Events and the outbox

Three events are added to the M36 catalog. All are outbox-only, owned by M36, published inside the write transaction, and carry no patient id and no item reference:

- `m36.handoff.offered` (consumer: M36 handoff notifications; alerts the receiver only if the handoff is still offered and still addressed to them, so a stale event never alerts)
- `m36.handoff.accepted` (consumer: the same; alerts the sender, with a "part of your handoff" wording while items remain pending)
- `m36.handoff.unaccepted` (consumer: the same; decision 7)

A replay or no-op publishes nothing. Five alert rules are seeded in the platform defaults, in-app only, in the same shape as the mention rule: `m36.handoff.offered`, `m36.handoff.accepted`, `m36.handoff.unaccepted`, `m36.handoff.no_supervisor` and `m36.handoff.supervisor_review`. Alert correlation ids include the event id, so a second unaccepted event for the same handoff (for example `sender_left` and then `expired`) is not swallowed by the dedupe. Alert texts are fixed, generic, contain no name, patient or item, and are provisional.

## Routes

All under `/api/v1/messaging`; the organisation and the actor come from the request context only. Static paths are registered before `/handoffs/:handoffId`.

| Route | Guard | Behaviour |
|---|---|---|
| `GET /handoffs` | `messaging.read` | `scope=incoming\|outgoing`, `state=active\|closed\|all`, limit default 50, max 100; flag off answers `200 {enabled:false}` |
| `GET /handoffs/caseload` | `messaging.read` + `patient.read` | The sender's caseload patients (label only), up to 200 |
| `POST /handoffs/prefill` | `messaging.send` + `patient.read` | Pure read: open work per patient plus the kinds whose source was unavailable. Up to 50 patients, all on the caller's caseload |
| `POST /handoffs` | `messaging.send` + `patient.read` | Offer. `201 {handoff, created:true}`, replay `200 {handoff, created:false}` |
| `GET /handoffs/:handoffId` | `messaging.read` + `patient.read` | Sender or receiver only; items with live summaries and `allowed_actions`; read-audited with a resource id |
| `POST /handoffs/:handoffId/accept` | `messaging.send` + `patient.read` | Receiver; body is the item ids to accept |
| `POST /handoffs/:handoffId/decline` | `messaging.send` + `patient.read` | Receiver; item ids optional (omitted means all pending) |
| `POST /handoffs/:handoffId/cancel` | `messaging.send` + `patient.read` | Sender |
| `GET /handoffs/policy` | `messaging.send` | The effective policy |
| `PUT\|DELETE /template-admin/handoff-policy` | `messaging.template.manage` | Tighten-only; DELETE returns to the platform default |

Errors: the uniform `404` for flag off (single routes), missing and not a participant; `422` `HANDOFF_RECIPIENT_INVALID`, `HANDOFF_ITEM_INVALID`, `HANDOFF_ITEMS_REQUIRED`, `HANDOFF_TOO_MANY_ITEMS`, `HANDOFF_ITEM_NOT_TRANSFERABLE`, `HANDOFF_POLICY_INVALID`; `409` `HANDOFF_ITEM_CONFLICT`, `HANDOFF_STATE_CONFLICT`. Messages never echo ids, names or reasons. Responses carry a server-computed `allowed_actions` list, so the web never re-derives the policy. A limit is 50 patients and 250 items per offer. No `Idempotency-Key` header is needed: idempotency rests on state and the database index, so no header read is added.

## Alternatives considered

- **Bind `shift_ref` to a made-up shift value.** No source of shifts exists. Rejected until M17 publishes one.
- **Store a persisted draft.** It would be a half-built record visible to queries and to audit. Rejected; the browser holds the draft.
- **Accept the whole handoff at once.** It moves responsibility for items the receiver may not have read. Rejected for per-item acceptance.
- **Apply the receiver's caseload ABAC at offer.** It would defeat covering a shift for patients the receiver does not normally see. Rejected for the disclosure rule in decision 11.
- **Free-text handoff notes.** A second PHI store needing sealing, scrubbing and a lint. Rejected; narrative belongs in the SBAR thread.
- **Check the deadline only when someone reads the handoff.** An unopened offer would never expire and the sender would think the patients were covered. Rejected for the timer plus the on-write check.
- **Write the new clinician to M5, M12, M17 or M10 on accept.** That would add cross-module write surfaces and a real transfer without those modules' own rules. Rejected; only M36's own tasks move.
- **A patient-context tile for open handoffs.** It would show non-participants that a handoff exists. Rejected.
- **Page or escalate when nobody accepts.** The paging and escalation design is Phase 4 (ADR-0057). Rejected until then.

## Consequences

- **New flag `messaging.handoffs`, default off.** It gates the routes and the web tab, following `messaging.clinical_links`, `messaging.sbar` and `messaging.tasks`. The timer and the offboarding sweep ignore the flag.
- **Rollback is safe.** The flag hides the UI and the routes. The timer keeps closing open offers and the rows stay. Rolling the build back leaves the four tables in place and unused, which is harmless.
- **Migration `1101`**, one new queue (`messaging.handoff_expiry`, declared once), three catalog events, five seeded alert rules.
- **OpenAPI and client.** The routes are added to the generated OpenAPI document and the typed client.
- **Not built (non-goals).** Binding to an M17 shift and shift-aware deadlines; callback pre-fill (needs an M19 seam under its own ADR); pre-fill of unsigned or draft medication orders; writing to the owning modules (M5, M12, M17, M10) on accept; chart access for the receiver (accepting does not add them to the care team, so the owning module's own ABAC may still deny the chart); paging, escalation, retries, SMS or push for any handoff alert (Phase 4.1, 4.3, 4.9); a supervisor worklist or team-wide view (4.9); handoff templates; free-text or sealed notes; editing an offered handoff; automatic re-offer of declined items; offers to several receivers; a patient-context tile; discharge or death evaluation (3.8); analytics (6.2); smart-inbox ranking (6.1).
- **Known limits (accepted).**
  - A repeated offer ignores a changed body; cancel and offer again.
  - An item can be pending in one handoff only. A second sender who hits a clash gets a generic 409 until the first offer resolves or expires.
  - Only the next visit within 48 hours and pending refill requests are offered. A caseload above 50 patients needs several handoffs. A user with organisation-wide scope and an empty caseload cannot start a handoff.
  - The supervisor audience is organisation-wide by role (`clinical_supervisor`, `don`), not scoped by location; tenants re-aim it through alert-rule admin.
  - `GET /handoffs/:handoffId` writes one `clinical_handoff.viewed` read event per distinct patient (all against the handoff id), through an optional `patientIdsPayload` in the read-audit config, so every patient is attributed. The POST replies that also carry patient labels (offer, accept, decline, cancel) declare the same config, with `resourceIdPayloadPath: "handoff.id"` because they have no id param on offer, and so emit the same per-patient event; prefill emits `clinical_handoff_prefill.viewed` per patient. The read-audit plugin only GOVERNS GET and HEAD but emits for any route that declares the config, so no new mechanism was needed. Only a 2xx reply is audited.
  - The detail read and accept, decline and cancel re-check `patient.read` (as offer and prefill already did), so a participant who lost that permission cannot read patient labels through a handoff.
  - **Accepted risk (existence oracle, I-8/R-3).** The pending-item unique index is organisation-wide so that one item can never have two accountable owners. The cost: a caseload peer who offers a patient they share with another sender gets the generic `409 HANDOFF_ITEM_CONFLICT`, and so learns that an open handoff exists for that patient, and the clash blocks their own offer until the first handoff resolves or expires (at most the expiry, 15 to 240 minutes). The message names nothing, and only peers who already hold the patient can ask. Double accountability is the worse outcome, so the index stays.
  - **Accepted risk (recipient-validity oracle, low).** An offer names `HANDOFF_RECIPIENT_INVALID` (422) when the recipient is inactive, lacks a permission or fails the Part 2 gate, and `HANDOFF_ITEM_INVALID` for item problems. A sender can therefore tell the two classes apart. The two codes drive different wording in the compose drawer, so they are kept; the sender already sees the named colleague in the picker.
  - **Part 2 fail-open window.** The gate relies on the M5 flag read; while that read is unavailable the gate fails closed for handoffs (`restricted` / `HANDOFF_ITEM_INVALID`), but M5 itself is the source of truth for releases and a revocation there is only seen at the next read (see the receiver-revocation limit above). This is an M5 limitation, not one added by handoffs.
  - **Sender leaves while the task sweep fails.** Offboarding attempts task and handoff reassignment independently. If the task sweep fails for a leaving sender, the handoff step records `sender_left` before the task has moved, so a pending task item is not declined, and a redelivery skips the handoff because `sender_left` exists. The recipient's accept on that item is refused (`HANDOFF_ITEM_NOT_TRANSFERABLE`) and the offer ends at its deadline (at most 4 hours) with the usual alerts. Nothing is lost: the task itself is retried by its own sweep.
  - An open offer past its effective deadline that the minute sweep has not reached yet is treated as not open by a new offer to the same person: it is expired in the same transaction (the sweep's own code) and the new offer is created, so a sender is never handed a dead handoff. `expires_at` in the DTO is the effective enforced deadline (the stored value, never later than offered_at plus the tenant's current minutes).
  - A recipient who accepted some items and then left closes the handoff `accepted` (reason `recipient_left`), derived from the final item states like every other close. When a sender leaves, a pending `task` item whose task the task sweep already moved off the sender is declined at once (it can never transfer); if nothing else is pending the offer closes. The supervisor alert for a departed sender says the patients need a new owner and does not claim they stay with the sender.
  - Accept resolves the acceptor's channel membership (`canViewChannel`, its own connection) before it takes the handoff and task row locks, and fails closed if the task moved to a channel that was not checked.
  - A receiver whose Part 2 release is revoked mid-offer sees `restricted` items at the next read, but data already fetched cannot be recalled.
  - Display names are resolved per request.
  - The expiry minutes and every alert and screen wording are provisional; clinical-lead sign-off is not recorded.
  - Handoffs do not page anyone. A sender who needs someone now must use the emergency path.

## Migration / rollout

**Rollout order.** (a) Deploy this build to every instance (API and worker) with `messaging.handoffs` off. (b) Enable the flag for one pilot tenant. (c) Ask the clinical lead to review the expiry default, the supervisor roles and the alert and screen wording before wider use.

**Rollback.** Turn the flag off. The server stops accepting handoff routes within a few seconds (5-second flag cache) and the web hides the tab at the next page load. Open offers still expire on the timer and offboarding still resolves them. Rows stay.
