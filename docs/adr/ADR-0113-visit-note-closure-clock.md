# ADR-0113 — A clinical note is closed within a per-tenant number of hours of arrival: one computed documentation clock, a per-tenant policy (off, warn, block), a request-time gate that confines an overdue clinician to a safety allowlist, and a supervisor override

- **Status:** **Accepted** (2026-11-17). The product decisions below were made by the owner on 2026-11-17 (visit-note closure, slice 1).
- **Date:** 2026-11-17
- **Phase:** post-launch clinical documentation; builds on M8 (encounters), M17 (visits), M18 (EVV) and M36 (alerts).
- **Related:** [ADR-0007](ADR-0007-m8-m9-m10-read-direction.md) (M8 reaches other modules by outbox event and seam, not by import), [ADR-0043](ADR-0043-m8-completeness-seam-inversion.md) (the M8 completeness seams), [ADR-0090](ADR-0090-administrator-and-org-admin-org-wide-patient-scope.md) (the org-wide roles), Module 8 spec section 2.5 (D4, late-entry tiers), Security Hardening section 5.1 (step-up).
- **Amends:** nothing. The calendar-day late-entry tiers (`late_entry`, `significant_late_entry`, `administrative_override`) are unchanged and coexist with this clock: they classify a note when it is finalized, this clock asks for the note while it is still open.

## Context

Facts read from the repo on 2026-11-17:

- An encounter is `draft`, `finalized`, `signed`, `cosign_pending`, `cosigned` or `voided`. Nothing in the product ages an open note by hours. The only age-based signals are the two alert-rule seeds `m8.encounter.unsigned` and `m8.encounter.documentation_late` (a cron sweep every 15 minutes) and the calendar-day late-entry tiers, which fire at finalize, after the fact.
- A clinician who walks out of a visit without closing the note leaves an open draft that nobody is asked about. Compliance wants a number of hours, a per-tenant setting, and a hard stop for the tenants that choose one.
- Main auto-deploys to production, so any new refusal must ship off by default and be switched on per tenant, and must never lock a clinician out of the things that keep a patient safe.
- The not-yet-live organization already has a request-time confinement (`bootstrap/onboarding-org-gate.ts`, a stage in `bootstrap/plugins/authenticate.ts`): an exact `METHOD + route template` allowlist matched on `request.routeOptions.url`, an injected required reader, fail closed, a typed error. A second confinement of the same shape is a known pattern.
- `encounter` already stores `started_at` (clinician-entered or EVV) but nothing says when the duty to document began, and the visit, EVV and ad-hoc paths all disagree about what "arrival" is.

## Decision

**D1. One clock, started at arrival, stored on the encounter.** `encounter.clock_started_at` plus `encounter.clock_start_source` (`evv_check_in`, `visit_started`, `draft_opened`, `draft_created`; both set or both null). The first signal wins and a later one never moves it: the EVV check-in `capturedAt`; else the visit's `actual_started_at` (the M17 `m17.visit.started` event, which M8 now consumes); else the first AUTHORING write by the note's own author on a seeded draft (an edit by anyone else, a supervisor included, never starts the author's clock); else the creation of the note when nothing is left to wait for: an ad-hoc note, or a note that names a `visitId` which does not resolve, through the M17 `VisitReader` seam, to a visit in this organization assigned to the author (a typed visit id is not trusted, so it can neither defer the clock nor move it into the past). A note linked to such a visit that has not started leaves the clock to the arrival event; one linked to such a visit that HAS already started (the start event came and went before the note existed) is clocked at that visit's actual start, with the source the consumer would have used, bounded like the consumer's (not before the note's service day, never in the future). The M8 consumer clamps the value to the visit's service day and to the server time the start event was recorded (the outbox row's `created_at`, not the consumer's later delivery time), so a skewed device clock cannot back-date a deadline and a late delivery cannot widen the window the device chooses its arrival from; a device that reports an arrival later than the server recorded it is held to the recorded time. If M17 already left `published` (a self-attested visit) the consumer returns early and the late EVV instant is lost; self-attest wins, deliberately.

**D2. Closed means signed.** A note is closed when its status is `signed`, `cosign_pending` or `cosigned`. `voided` is excluded. For an LPN or CHHA the author's duty ends at the primary signature: `cosign_pending` is closed for the author (the cosigner has their own clock, `cosignature_request`).

**D3. Compute, do not materialise.** The deadline, the stage and the verdict are never stored. A pure function in M8 takes the clock, the tenant policy, the override and "now" and returns `ok`, `at_risk`, `overdue` or `escalated` plus the instant blocking may begin. SQL only finds "the member's oldest clocked open note" (`ORDER BY clock_started_at LIMIT 1`, served by the partial index `encounter_open_clock_idx`); the function decides. So the two cannot drift, and changing the threshold re-times every open note at once. The clock is absolute elapsed hours: no daylight-saving arithmetic, no calendar.

**D4. A per-tenant policy, default warn.** `documentation_obligation_policy`: one row per (organization, obligation kind) holding `mode` (`off`, `warn`, `block`), `threshold_hours` (1 to 168, default 24) and `enforce_from`. An absent row means `warn` and 24 hours, applied in code. Moving a tenant to `block` is an explicit act by a holder of `encounter.closure_policy_admin`, and the service sets `enforce_from = now()` at that moment: a note that is already overdue when blocking starts gets a fresh window (`blockFrom = max(clock, enforce_from) + threshold`) instead of locking clinicians out on the switch. Lowering `threshold_hours` while the mode stays `block` moves every deadline earlier, so it opens a fresh window the same way (`enforce_from = now()` again); raising it, or repeating the same write, keeps the existing instant, and the instant never moves earlier. Every policy write also records an explicit `m8.encounter.closure_policy_changed` audit event (severity warn: the previous and new mode and threshold, enums and numbers only), beside the row trigger's change record. Alerts use the true stage; only blocking uses `blockFrom`.

**D5. Alerts replace the old sweep, in place.** The `encounter.attention` cron keeps its queue name and `*/15` schedule; its body now reports closure stages: `at_risk` six hours before the deadline, `overdue` at it, `escalated` twelve hours after (to the author, then to the supervisors of the note's provider entity). Alert types `m8.encounter.closure_at_risk`, `closure_overdue`, `closure_escalated`, severities info, warn, warn (never critical), payloads of ids and instants only. The two superseded seed rules are removed from the seed, and migration 1512 disables the platform rows and every tenant clone of `m8.encounter.unsigned` / `m8.encounter.documentation_late` already in a database (the boot seed only inserts and updates the rules it names, so without it they would stay enabled for ever; rows are disabled, never deleted). The closure payloads are registered on the Foundation alert-payload registry and asserted valid at boot, and the workers' emitter checks every closure alert against that catalog before sending it. The sweep has no time window: each tick it plans, for every clocked open note, the alert of its current stage and emits only the ones whose `(organization, correlation id)` is not yet in the alert table, found by one batched read per organization (M36 answers it; the composition root hands it to the sweep as a function, because the alert table is M36's). The emitter resolves rules and recipients before it de-duplicates, so re-emitting every due alert each tick would pay that for nothing; its unique key stays the backstop for a race between two ticks. A late EVV instant, a lowered threshold or a worker outage therefore never skips an alert the gate could still block on; an earlier stage a note already passed is not emitted retroactively. The scan itself is unbounded in time and rows (an age ceiling would hide a note whose escalation was never sent; a row cap would starve the youngest notes, and the partial index already limits it to the organization's open clocked notes). An author who is no longer an active member cannot be told anything: the author-only stages are skipped for that note and the escalation goes to the supervisors with no author on the payload. A failing emit does not stop the rest of its organization's alerts; the failures are rethrown together. A note with no clock raises nothing (D9). That has a cost the retirement of the old rules makes real: `m8.encounter.unsigned` and `m8.encounter.documentation_late` were the only age-based signal on a note and did not need a clock, so once migration 1512 disables them a draft that already existed when this shipped (no clock, no backfill by design) loses its timeliness alerts altogether, and only a note created or stamped from now on is watched. Migration 1512 sets `enabled = false` on EVERY `alert_rule` row of those two event types: the platform rows (organization_id NULL) and each per-tenant clone a tenant made by editing a rule; nothing is deleted, and the alerts already raised keep their text event type. A restore of the previous release does not undo it symmetrically: that release's boot seed upserts the platform rows with `enabled = true` again, but never touches a tenant's clone, so a tenant that had customised either rule stays silent until an administrator re-enables its clone.

**D6. The block is a request-time gate, fail closed.** A stage in `bootstrap/plugins/authenticate.ts`, after the not-live-organization confinement, applies only to `staff` sessions. When the organization's mode is `block` and the caller's oldest clocked open note is past `blockFrom` with no active override, every route outside an allowlist answers 403 `NOTE_CLOSURE_REQUIRED` (details: the encounter id, the deadline, the count). The allowlist is an exact `METHOD + route template` list, tested against the real route table the way the onboarding allowlist is. It keeps reachable everything that closes the note (the encounter's own routes: selections, finalize, sign, vitals, addenda, cosignature, the late-entry override routes), everything that protects a patient (eMAR, orders and verbal orders, triage calls and on-call, field-safety SOS, incidents and check-ins, emergency messaging and its acknowledgement, the alert inbox), creating an ad-hoc note (which starts its own clock), and the read-only chart and shell calls the app chrome needs. It also keeps the regulatory and patient-safety duties that cannot wait for a note: reporting a patient incident or an abuse allegation (the reporter's own create, edit and submit routes; triage, investigation, resolution and closure stay refused), recording a death and acknowledging its notification, changing or correcting a code status, deploying a comfort kit at the patient's bedside, finishing a visit already in progress (EVV check-out and the offline syncs; checking in to a new visit stays refused), releasing or reassessing an inpatient restraint (42 CFR 418.110), and the break-glass cosignature and revocation. It does not include voiding a note, writing the policy (a blocked administrator must not release themselves), applying a new restraint, hospice election revocation, discharge, an allergy write, consent revocation, or starting a visit; each of these is pinned as refused, with its reason, in the allowlist test. The two EVV offline-sync routes are allowlisted for the check-OUT events a blocked clinician must be able to upload, but they also accept check-IN events, which start a visit: a batch that contains any check-in is therefore refused by the route itself (it asks the gate's policy+evaluator half, injected by the composition root so the EVV module imports nothing from the gate) with the same 403 or 503, and a check-out-only batch passes. A read failure in `block` mode on a non-allowlisted route answers 503 `NOTE_CLOSURE_UNAVAILABLE`, not a pass. The one softening is for the policy read: if refreshing an organization's policy fails and that organization's last known mode was `off` or `warn`, read less than 55 seconds ago (the shared policy cache can already hand out a value 5 seconds old, so the real worst case is the 60 seconds stated here), that last known policy is served; the remembered policy is the one whose read started latest, so a slow older read never replaces a newer one (those modes refuse nothing, so a database blip must not take every `warn` tenant down); with nothing known for the organization, a last known `block`, or a last known policy older than the bound, the gate fails closed with the 503. The failure is logged once per organization per 30 seconds with the number it suppressed. Only verdicts that pass are cached, for at most five seconds per organization and member: a `clear` until the earlier of the TTL and the block instant, and a `warn` (an overridden clinician, or the grace window after `block` was enabled) only on a proven bound, the end of the override or the block instant ahead, so an overridden clinician does not cost one evaluation per request and cannot meet the evaluation budget below. A block is never cached, so a signature or an override grant takes effect at once on every replica; an override revoke reaches a replica that cached the overridden clinician within the five-second TTL. Concurrent evaluations for one organization and member share a single in-flight evaluator call, which is dropped the moment it settles; a request that arrives after it settled starts a new evaluation, and a joiner can inherit a block computed just before a signature or an override committed (the window is one evaluator call; the client's refresh-on-403 recovers it). An evaluation that runs longer than 5 seconds answers 503 and frees its key, so a hung call cannot poison that member. A block is never cached, so a refusal sits in front of the rate limiter: each organization and member may START at most 20 evaluator calls a second (cache hits and joiners do not count), and past that the request is refused 429 `RATE_LIMITED` with `Retry-After: 1`, never passed. Refusals are reported as evidence that the control enforces: a throttled structured log line per organization (the organization id and a count only) and a `chartwarden_note_closure_refusals_total` counter. In `off` and `warn` the gate refuses nothing.

**D7. A supervisor can lift the block, briefly.** `documentation_obligation_override`: a supervisor (the four supervisor role keys: `clinical_supervisor`, `director_of_nursing`, `don`, `clinical_lead`) with `encounter.closure_override` grants one clinician one obligation kind for at most 24 hours (default 4), with a reason of 40 to 500 characters, behind step-up. The table is append-only for the application role: it inserts, it can only stamp the two revocation columns, it has no DELETE. A person cannot override themselves. The override lifts only the block: alerts, deadlines and the policy are unchanged, and it does not satisfy the late-entry override routes.

*Who may be released, and by whom.* A grant is refused unless all of these hold, checked in this order on the grant's own transaction by the same evaluator the gate and the banner use: (a) the granting supervisor has nothing of their own past its block instant (403 `NOTE_CLOSURE_GRANTOR_BLOCKED`, "Close your own overdue notes before releasing someone else."). This is judged on the grantor's OWN position with every override ignored (`evaluateMemberClosure` with `ignoreOverrides`; the gate and the banner still honour overrides). Grant and revoke are on the gate's allowlist, so a blocked supervisor reaches them; refusing only a *blocked* grantor would let two supervisors each hold the other's override, count as unblocked, and release each other for ever without closing a note. An override holder is therefore not fit to release others until they have closed their own overdue notes (earlier drafts of this ADR let an overridden grantor grant; that was reversed for exactly this loop). Only a genuinely clear supervisor releases others. (b) The clinician's oldest open note, the one that decides the block, is inside the grantor's location scope (403 `NOTE_CLOSURE_SUBJECT_OUT_OF_SCOPE`, "That clinician's note is outside your sites."). It is asked BEFORE the blocked question and decided on that note's location whether or not the note is blocked yet, so a site-scoped supervisor cannot learn whether a clinician outside their sites is blocked. Scope is the board's: org-wide roles see every site, a site-scoped supervisor sees their sites and any note with no site (the escalation alert falls back org-wide for such a note, so the board and the grant must too). (c) The clinician is blocked right now (409 `NOTE_CLOSURE_SUBJECT_NOT_BLOCKED`, "This clinician is not blocked right now, so there is nothing to lift."): a clinician with no open note at all, or who is clear, warn-only or already overridden, is refused. *Who may revoke.* The supervisor who granted the override, and any caller whose scope is org-wide; a site-scoped supervisor who did not grant it is refused with the same 403 `NOTE_CLOSURE_SUBJECT_OUT_OF_SCOPE` ("Only the supervisor who granted this override, or one who covers every site, can revoke it."). A blocked supervisor can still revoke what they granted: revoke stays on the allowlist.

*Who holds the permissions.* Two keys, two owners (user decision). `encounter.closure_override` is held by the four supervisor role keys (`clinical_supervisor`, `director_of_nursing`, `don`, `clinical_lead`) and nobody else: it is in `FULL_CATALOG_EXCLUDED_KEYS`, so `org_admin`, `administrator` and `superadmin` do not derive it (an administrator is not a clinical supervisor). `encounter.closure_policy_admin` is held by the DON keys (`director_of_nursing`, `don`) AND the tenant administrators (`org_admin`, `administrator`, and `superadmin` through the full-catalog rule): the people who set the policy answer for it, and an administrator can undo a mistaken `block` without a clinical supervisor. It is NOT given to `clinical_supervisor` or `clinical_lead`: they are the field supervisors the clock binds and must not set the deadline they are held to. A tenant that already has the roles gets the keys from migration 1511 (the policy key also to its existing `org_admin` / `administrator` roles, as earlier migrations grant a new catalog key); a tenant provisioned later gets them from the `director_of_nursing` template (the only supervisor key that is a template; `clinical_supervisor`, `don` and `clinical_lead` receive nothing when a tenant creates them by hand) and from the full catalog. The policy screen (`/admin/closure-policy`) shows for exactly the holders of `encounter.closure_policy_admin`; the board (`/work/overdue-notes`) for the holders of `encounter.closure_override`. Moving a key is not open to anyone: putting a key on a role needs the caller to hold it already (anti-escalation, `assertNoEscalation` in the authorization routes, on role create, patch and assign), so an administrator cannot hand out `encounter.closure_override`, which they do not hold, and only a caller who holds a key and `role.manage` / `role.assign` can move it; a tenant can still remove a grant from a role it owns.

*The reason.* It is free text of 40 to 500 characters typed next to a clinician's name, so it may hold an identifier. It is screened with the platform's SSN / MBI screen before anything is written (422 `VALIDATION_FAILED`, `details[0].field` `reason`, `details[0].code` `EVIDENCE_LOOKS_LIKE_PHI`, no value echoed), stored on the override row, and carried, screened, as `context.justification` of the explicit `m8.encounter.closure_override_granted` audit event (catalogued in `M8_ACTION_CATALOG`), the way `hope.late_deadline_override` carries its justification. The screen catches SSN- and MBI-shaped values only: names, dates of birth and record numbers pass it and are held back only by the hint on the grant form. The text therefore lives in two append-only places, the override row and the event, which is why the cap is 500 and not more (the row trigger scrubs it from the row's own audit snapshot, so the event is the one audit copy). No route returns it. A revoke writes `m8.encounter.closure_override_revoked` (severity warn; ids and instants only) on the first revoke, and its response says whether another active grant for the same clinician (`remainingActiveUntil`) still lifts them.

*Undoing a mistaken `block`.* A policy admin sets the policy back to `warn` or `off` on the Note Closure Policy screen. The policy routes are deliberately not on the gate's allowlist (a blocked administrator must not lift their own block by switching the policy off), so a policy admin who is blocked themselves must close their notes or be released by a clear supervisor; the audited database fallback for platform operations is in the runbook [`docs/runbooks/m8-note-closure-policy-reset.md`](../runbooks/m8-note-closure-policy-reset.md).

*The database enforces what the grants cannot express.* A revoked override can never be un-revoked (the column-level UPDATE grant alone would let the application role write both revocation columns back to NULL); an override's subject and grantor must be members of the override's own organization (the foreign keys are single-column and an FK check ignores RLS); and `encounter.clock_started_at` / `clock_start_source` are write-once (NULL to a value, never changed or cleared).

**D8. The engine is generic; slice 1 is visit notes.** `obligation_kind` is `visit_note`, `hope_window`, `cti` or `face_to_face` in the enum, the policy and the override, but the API accepts only `visit_note` in slice 1. HOPE windows, certifications of terminal illness and face-to-face encounters already have their own deadlines and alerts (M10, M6); moving them onto this engine is a later slice, each with its own clock source and its own decision about whether it may block.

**D9. No backfill.** An existing unsigned draft has no clock. My notes labels it "Legacy"; it raises no alert and never blocks. Only notes started after the deploy are clocked.

**D10. The supervisor role-key set is one set.** The alert recipients, the cosignature alert seeds and M8's `isSupervisor` all use the same four keys. `director_of_nursing` was missing from the M8 and alert sets; that correction rides in this change as its own commit (`a4600df96`, "treat director_of_nursing as an M8 supervisor in routes, ABAC, cosign cron and alerts"). It is not part of the clock, and on deploy it WIDENS who counts as a supervisor in four places: the M8 route guard `isSupervisor` (cosignature supervisor release, late-entry and administrative override) and the `is_author_or_supervisor` ABAC predicate (read and write any in-organization encounter's routes that use it) now admit the canonical-key `director_of_nursing` and `clinical_lead` (they used to admit only `clinical_supervisor` and `don`); the cosignature-SLA cron's supervisor lookup now considers all four keys (it used `clinical_lead`, `don` and `org_admin`) and prefers a real supervisor to a bare `org_admin`; and the cosignature alert seeds' audience gains `clinical_supervisor` and `director_of_nursing` (it was `clinical_lead` and `don`). A tenant's DONs and clinical leads gain those routes the moment this ships; a reviewer reading the clock's diff should read that commit separately.

## Consequences

- Migration 1510 (`-- compat: expand`) adds two nullable columns, two partial indexes (one for the per-author gate and sweep, one ordered by the clock for the supervisor board) and two tables, plus three triggers (a revoked override stays revoked, an override's memberships belong to its organization, the clock is write-once); a previous release never writes the new columns or tables, so it keeps working on the new schema. The `ADD COLUMN ... CHECK` scans `encounter` once under ACCESS EXCLUSIVE and each non-concurrent `CREATE INDEX` holds a SHARE lock for its build; both are accepted on a small table inside the transactional runner, and both columns stay NULL for every existing row. Both new tables are org-level (organization_id only, no patient column), FORCEd RLS, audited, with a destruction grant; the override's free-text reason is treated as potentially identifying, not as "no PHI".
- Every tenant starts in `warn`: clinicians see a banner and alerts, nothing is refused. A tenant opts in to `block`. Nothing changes for a tenant that does nothing except the new alerts replacing the old two.
- A confined clinician can always close the note, answer an emergency, give a medication, take a triage call or raise a safety alert. The allowlist is the part that needs a human each time a chart route is added: a test fails until a new chart GET is classified allowed or denied.
- The clock is as good as its start signal. A clinician can still delay the signal that starts it (the author's first authoring write on a seeded draft); the other signals are bounded rather than the clinician's to choose: the arrival instant is held between the service day and the time the server recorded the start, and a typed visit id that does not check out starts the clock at creation. A visit-linked note that the author creates before the visit has started leaves the clock to the arrival; one created after it started is clocked at that arrival, and one for a visit that is not theirs (or that does not resolve) is clocked at creation.
- Blocking is per clinician, not per patient or per organization; one overdue note confines its author only.
- Cost: one indexed read per non-allowlisted request in `block` mode (none in `off` and `warn`, none for allowlisted routes), plus one cached policy read per organization.

## Slice plan

1. **Slice 1 (this ADR):** the visit-note clock, stamping on the three start paths, the replacement alerts, the tenant policy (default warn), the gate and its allowlist, the supervisor override, My notes and the supervisor overdue board.
2. **Later:** HOPE windows, certifications of terminal illness and face-to-face encounters onto the same engine, each as its own `obligation_kind` with its own clock source and its own mode; a backfill only if the owner asks for one.

## Alternatives considered

- **Materialise a `due_at` column on the encounter.** Rejected: it drifts from the policy (a threshold change would need a backfill of every open note) and from the SQL that reads it; computing from the clock keeps one definition.
- **A cron that flips a "locked" flag.** Rejected: the lock would lag the clock by up to a tick and would need unlocking on sign, on override and on a mode change, on every replica; the request-time check reads the source of truth.
- **Block everything except the note.** Rejected: it would stop a clinician from giving a medication, answering a triage call or raising a safety alert. Safety routes are always reachable.
- **Reuse the calendar-day late-entry tiers.** Rejected: they classify at finalize in calendar days; they cannot ask for a note that is still open, and changing them would re-classify historic notes.
