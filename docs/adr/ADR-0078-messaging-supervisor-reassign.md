# ADR-0078 — A supervisor may reassign a waiting acknowledgment request (never acknowledge it): a reassign control on the request card, an audited `messaging.review` route with a fixed reason code, a database guard that admits it only for a waiting request, and the requester name and request reference on the queue row

- **Status:** **Accepted** (2026-10-19; decisions closed in the M36 gap-closure part A blueprint). **Provisional and OPEN for the clinical lead: that a supervisor (`messaging.review`) may reassign at all, the reason-code set, the notices to the previous assignee and the sender, and the rejection of "acknowledged by phone on behalf of" (G-1). Provisional and OPEN for compliance / Part 2 review: the requester display name, the request reference and the candidate display names shown for a request whose channel the supervisor cannot open.** No clinical-lead sign-off is recorded (`docs/messaging-hub/brief-clinical-lead-signoff.md`, section 13). No new flag: every messaging flag stays off for every tenant.
- **Amended by [ADR-0085](ADR-0085-messaging-audited-thread-read-for-escalated-assignee.md) (proposed, not accepted) for decision 7's "no read access" sentence only:** a holder of a live thread-access grant would be able to get, acknowledge and resolve that request and read that one thread; a supervisor still cannot. Until it is accepted and built, decision 7 stands as written.
- **Date:** 2026-10-19
- **Phase:** Messaging Hub Phase 4 (WP 4.11 follow-up, gap closure part A: G-2, G-6, G-7 and, for the reassign path, G-5, of `docs/runbooks/messaging-escalation-fallback.md`).
- **Implements:** the gaps the WP 4.11 runbook recorded: G-6 (reassign had no screen), G-2 (a supervisor could not move a stuck request), G-7 (the queue did not show the sender), G-5 for the reassign path (a `failed_unreachable` request moved by a person is watched again).
- **Extends:** [ADR-0069](ADR-0069-messaging-acknowledgment-request-aggregate.md) (the aggregate; decisions 5, 6, 10, 13, 14), [ADR-0076](ADR-0076-messaging-unacknowledged-queue.md) (the queue and its restricted rows), [ADR-0070](ADR-0070-messaging-escalation-timers.md) and [ADR-0071](ADR-0071-messaging-delivery-failure-handling.md) (the timer that a reassign re-arms).
- **Amends, for reassign only:** ADR-0069 decision 6 ("no supervisor override", oversight is the queue) and ADR-0076 ("a supervisor still cannot acknowledge, reassign or resolve") are **superseded for reassign only**. A supervisor may now reassign a waiting request. Nothing else in either ADR changes: the supervisor still cannot acknowledge, resolve, cancel or read a conversation.
- **Related:** [ADR-0056](ADR-0056-clinical-acknowledgment-vs-read-receipts.md) (the explicit-acknowledgment rule, untouched), [ADR-0010](ADR-0010-tenancy-rls-invariants.md), [`docs/runbooks/messaging-escalation-fallback.md`](../runbooks/messaging-escalation-fallback.md).
- **Numbering note:** the index still has two ADR-0069 files and a missing number between 0071 and 0073 (pre-existing irregularities that `arch:adr-docs` reports). 0078 is the next free number after ADR-0077; this change adds no `arch:adr-docs` violation naming 0078.

## Context

Checked in the code, not assumed:

- `POST /api/v1/messaging/escalations/:id/reassign` exists (ADR-0069 decision 6): the current assignee (any open state) or the sender (until the request is taken) may move a request to an eligible colleague. It had no screen: the card offered only "Take responsibility" and "Close this request". The runbook therefore had to say that no request could be moved from a screen.
- The update guard of migration 1120 let only the sender or the assignee reassign. A supervisor holding `messaging.review` (the audience of the WP 4.9 queue) could see a stuck request and call the people involved, but could not move it.
- A supervisor is typically not a member of the patient's care-team channel, and there is no supervisor read override (ADR-0069, ADR-0076). The queue shows such a request as a `restricted` row.
- The queue row carried the assignee's display name but no sender, so on a restricted row the sender could not be found at all.
- A `failed_unreachable` request is no longer watched by the deadline timer; a reassign returns it to `pending` with a new window and re-arms the timer through the existing `m36.ack.reassigned` arming consumer.

## Decisions

1. **A "Reassign" control on the request card (G-6).** The web card shows "Reassign" to exactly the people the API already allows (`viewer_actions.can_reassign`: the assignee at any open state; the sender until the request is taken). It opens a dialog with a colleague picker and calls the existing `POST .../reassign`. A new read, `GET /api/v1/messaging/escalations/:id/reassign-candidates` (`messaging.read`; the same visibility and party rules as reassign), returns only user ids and display names of colleagues who would pass the reassign checks: care-team member who can see the channel, holds `messaging.urgent.receive`, passes the Part 2 gate, is not the sender and is not the current assignee; capped at 50. The refusal wording is generic and never says why a person is ineligible. An `Idempotency-Key` is minted per dialog open, focus is managed, and the dialog shows no patient information.
2. **A supervisor route (G-2).** `POST /api/v1/messaging/escalations/:id/supervisor-reassign`, permissions `messaging.read` and `messaging.review`; `Idempotency-Key` required. Body: `assigned_user_id` and a **required** `reason_code`. A companion read, `GET .../supervisor-reassign-candidates` (same permissions), lists eligible colleagues. The route moves a request in status `pending`, `escalated` or `failed_unreachable` only; for `acknowledged`, `resolved` or `cancelled` it answers `409 ACK_STATE_INVALID`. The new assignee must pass the **same** checks as a normal reassign (decision 1); any failure is one uniform `422 ACK_ASSIGNEE_INVALID`. A supervisor can **never name themselves** as the new assignee (the same uniform 422). When the **Part 2 gate walls the supervisor off from the patient**, the candidates read returns an **empty list** and the POST refuses with the same uniform 422, so the care team is never named to them; the runbook then says to ask a person who is admitted, or the clinical lead (OPEN for compliance / Part 2 review). The candidate reads carry no patient id, so there is no patient-level read-audit: the audit is request-level only, and a walled-off supervisor receives nothing to audit. The route works on restricted rows: the supervisor need not be a channel member. The response names the request only by `request_ref` and returns no channel, message or patient id. Both candidate reads (`reassign-candidates` and `supervisor-reassign-candidates`) are read-audited against the request (`resourceIdParam: id`, no patient id in the response) because they disclose colleague names; the supervisor write carries no read-audit config (nothing patient-bound is returned) and is audited by the database triggers with the supervisor as actor.
3. **Reason codes: a fixed, non-clinical set.** `assignee_unreachable`, `assignee_unable_to_sign_in`, `assignee_off_shift`, `coverage_change`, `workload`, `other_operational`. No free text, so no way to type patient information. Stored in a new nullable column `message_acknowledgment_event.reason_code`, constrained to the set and only on a `reassigned` event written by a user.
4. **Effects and audit.** The status returns to `pending` with a new default window and deadline and tier 0, so the escalation timer is re-armed through the existing `m36.ack.reassigned` consumer. This also closes **G-5 for the reassign path only**: a `failed_unreachable` request moved by a supervisor is watched by the deadline timer again. G-5 for requests nobody reassigns stays open. The event-history row is `reassigned` with the **supervisor** as `actor_user_id` and the reason code; the request table's audit trigger records the change with the supervisor as actor. The request history (`GET /escalations/:id`, `events[]`) exposes `reason_code` (nullable, fixed set), so the thread and the drill can show who moved the request and why. The event insert guard of migration 1107 is unchanged (the event names the session's own user), so the supervisor is the recorded actor and a system-actor write cannot hide them.
5. **Notices (in-app, generic fixed text, no names).** The new assignee gets the existing `m36.ack.reassigned` alert. The previous assignee and the sender get a new seeded in-app-only, non-designated alert rule `m36.ack.supervisor_reassigned`. It is **not** an outbox event: the `ack-notifications` consumer emits it when the `m36.ack.reassigned` payload carries `supervisorReassign: true` (with `requesterUserId`; both are new optional payload fields). The supervisor is excluded from the notices. The notice to the previous assignee and the sender is sent only after the same stale checks as the new assignee's alert (still `pending`, same version, new assignee still qualified and able to see the channel); a stale event tells nobody. Whether the previous assignee and the sender should be told is OPEN for the clinical lead.
6. **Database guard (migration `1126_m36_ack_supervisor_reassign.sql`).** One migration, no new table, no new grant. It adds `reason_code` with its CHECK and **replaces** the update guard of 1120 (`CREATE OR REPLACE`, a copy of 1120 plus one rule): a person who is neither sender nor assignee may reassign only if the transaction carries the transaction-local setting `app.ack_supervisor_reassign = 'on'` **and** the request is `pending`, `escalated` or `failed_unreachable` **and** the write is the reassign itself (a return to `pending` with a new assignee). An `acknowledged` request can still be handed on only by its assignee. The actor rules for acknowledge, resolve and cancel are unchanged: a supervisor cannot acknowledge on behalf of anyone (and cannot assign the request to themselves, decision 2); they may acknowledge only if they are separately the assignee through a normal route. The permission (`messaging.review`) is decided by the route, not the database; the guard is a backstop against an **application bug**, not against a compromised role (see Known ceilings).
7. **What this deliberately does not do.** The supervisor cannot acknowledge on behalf of anyone, cannot resolve or cancel, cannot assign the request to themselves and cannot read the thread; they acknowledge only if they are separately the assignee through a normal route. No read access is granted: every route that reads a request, a thread or a patient still answers 404 without channel visibility. Only the new assignee, signed in as themselves, can take responsibility. This is **not an override of ADR-0056 / ADR-0069**: the explicit-acknowledgment rule (only a human who signs in and takes responsibility) is untouched.
8. **G-1 is rejected ("acknowledged by phone on behalf of").** It would let a request be recorded as taken by someone who did not sign in and take responsibility, which weakens the rule of ADR-0056 and ADR-0069 decision 6. The supported path is a supervisor reassign to a reachable, qualified clinician, who then takes responsibility in their own session. Nothing writes "acknowledged out-of-band" anywhere. Closed by decision; **OPEN for the clinical lead to revisit**.
9. **The queue row (G-7).** `GET /api/v1/messaging/escalations/unacknowledged` now carries `requester_display_name` (also on restricted rows; the same disclosure class as the assignee's display name already kept on restricted rows) and `request_ref` (the request's own id, present on **every** row including restricted ones; it is the handle the supervisor routes use). `request_ref` opens nothing: every route that reads a request, a thread or a patient still answers 404 without channel visibility. No requester id and no role class is returned; a role class was judged not cheap and is not built. The web queue shows "Sent by <name>" and a Reassign button per row. Both disclosures are **OPEN for compliance / Part 2 review**.
10. **Candidate lists disclose colleague names.** The supervisor candidate list returns display names of eligible care-team colleagues for a request whose channel the supervisor cannot open. Same disclosure class as the assignee name; eligible people only. **OPEN for compliance review.**
11. **Rate limit.** The supervisor route uses the **same** fail-closed limiter as reassign (ADR-0069 decision 13): 20 per minute per user, 200 per minute per organisation and 5 per 5 minutes per (actor, colleague) pair; keys only from validated UUIDs. Both candidate GET routes use the same limiter per user and per organisation (the per-pair bucket applies to the POST body only). **Per-request cap (provisional, OPEN):** at most **5 supervisor reassigns of one request in a rolling 24 hours** (counted from `reassigned` events with a reason code); the sixth is `409 ACK_SUPERVISOR_REASSIGN_LIMIT` with a generic message telling the supervisor to ask the clinical lead. This stops supervisors passing a request back and forth.
12. **Flags and errors.** No new flag. Like the sibling reassign, the routes are not flag-gated (a request that exists can always be settled); requests exist only when `messaging.ack_requests` was on, and every flag stays off for every tenant. Errors: `401`/`403` (missing `messaging.read` or `messaging.review`), `404` (malformed or other-tenant id), `409 ACK_STATE_INVALID`, `409 ACK_SUPERVISOR_REASSIGN_LIMIT`, `422 ACK_ASSIGNEE_INVALID`, `429`.

## Alternatives considered

- **An "acknowledge on behalf of" action** (G-1). Rejected: it weakens the explicit-acknowledgment rule (decision 8).
- **A supervisor read override** of the conversation. Rejected: not decided (ADR-0069 open item); the reassign needs no content.
- **A new permission `messaging.escalations.supervise`.** Deferred: it needs a seed migration and role re-grants. `messaging.review` is already the audience of the queue and of the supervisor alerts, so it is reused for now. Revisit if the clinical lead wants reassign split from the lifecycle review.
- **A system-actor write that hides the supervisor.** Rejected: the audit must name the person who moved the request (decision 4).
- **A free-text reason.** Rejected: free text invites patient information; the fixed set is enough for the log.
- **A new outbox event type for the notices.** Rejected: it would need a catalog entry and bindings; two optional fields on `m36.ack.reassigned` and an in-app rule reuse the existing pipeline.

## Consequences

- A supervisor can move a stuck request, including one whose channel they cannot open, to a reachable qualified clinician. The runbook's reassign-from-a-screen gap (G-6) and the supervisor gap (G-2) are closed; the supervisor still cannot read a conversation, so a supervisor who needs the content asks a channel member or the sender (ADR-0076 consequence stays).
- A supervisor reassign of a `failed_unreachable` request re-arms the deadline timer; other `failed_unreachable` requests remain unwatched (G-5, open).
- The previous assignee and the sender learn of a supervisor reassign through a generic in-app notice; the supervisor does not receive one.
- The history shows who moved the request and why, from the fixed set.

## Known ceilings

- **The guard trusts the marker.** The database admits a non-party reassign when the transaction-local `app.ack_supervisor_reassign` is `on`. Anything that can set a session setting in that transaction can set it. The guard still limits what the marker allows (waiting request, the reassign write only, no acknowledge, resolve or cancel), but it defends against an application bug, not a compromised role.
- **The permission is checked only in the route.** `messaging.review` is not re-checked in the database.
- **Candidate-list disclosure.** Eligible colleague display names are shown for a request the supervisor cannot open (OPEN, compliance).
- **`request_ref` disclosure.** The request id is returned on restricted rows (OPEN, compliance). It is a handle, not a key to any read.
- **Requester name on restricted rows** (OPEN, compliance / Part 2).
- **No role class.** The queue row does not say which role the requester or assignee holds.
- **The 5-per-24-hours cap** is a provisional number (OPEN, clinical lead); it is per request, not per supervisor.
- **Reason codes are self-declared.** The code is the supervisor's statement; the system does not verify it.

The supervisor logic lives in `apps/backend/src/modules/36-messaging/ack-requests/ack-supervisor.ts` (small shared helpers in `ack-shared.ts`). On the web, the card's reassign dialog is held above the list so a reload cannot lose it, 404 and 409 in the card dialog share one generic message, and the queue's Reassign button name includes assignee, sender and due time.
- **Insider lockout (OPEN).** The per-request cap (5 supervisor moves per rolling 24 hours) is shared by every supervisor: one `messaging.review` holder can use it up and block the others from moving that request for 24 hours. The 409 `ACK_SUPERVISOR_REASSIGN_LIMIT` names the clinical lead as the way forward. An alert or ops notice on that 409 is a follow-up, not built.
- **The Part 2 wall comes before the state.** For a supervisor the Part 2 gate walls off, the candidate read and the POST answer identically (empty list; uniform 422) whether the request is waiting, taken or closed, so they learn nothing about its state. The gate (`part2Admitted`) is a REQUIRED dependency of the ack service; an unanswerable gate reads as "not admitted".
- **Picker polling has its own limiter bucket** (key prefix `m36-ack-picker`, same numbers: 20 per minute per user, 200 per minute per organisation), so reading candidates can never starve a reassign or a create.
