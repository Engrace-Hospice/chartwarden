## Context

Checked in the code, not assumed:

- A session is a Better Auth `session` row (M2-owned, not org-RLS'd; the active organisation is a column). Every REST request resolves it through `getIdentitySession` in the authenticate hook; there is **no cookie or secondary-storage cache** (`cookieCache` is absent), so deleting the row makes the very next request anonymous, a 401 on every org route. M2 already revokes by **deleting** rows (`createDbSessionWriter.revokeForMembership` / `revokeAllForUser`, the idle-timeout enforcer, organisation suspension).
- The realtime server (ADR-0054) authenticates the handshake with the same snapshot, joins rooms the server chooses, and re-checks every live session every 60 s (`stillValid`, three failures tolerated). Worker-side code reaches every api node through a Valkey emitter (`createRealtimeEmitter(...).disconnectRoom(room)` is `io.in(room).disconnectSockets(true)` across nodes), which the membership-revocation consumer already uses for `user:` and `account:` rooms. There was no per-session room.
- A push endpoint (`delivery_endpoint`, M36, user-owned, RLS on `app.user_id`, no organisation column) records the user, the channel and the endpoint value. **Nothing linked it to a session**, so a revoke had no way to find "the endpoint this session registered". `verification_status` already has `expired`, and the delivery planner only targets `verified` endpoints.
- There was no list-my-sessions or revoke-by-id route in the product (Better Auth's own `revoke-session` takes the token). `/api/v1/devices/attestation*` already exists and is something else (M2 device attestation, SecHardening §12.4).
- No event-catalog entry is needed: nothing consumes "a session was revoked" (the realtime close and the endpoint expiry are in the same request), so the outbox is not used (`arch:outbox-bindings` is untouched).

## Decision (proposed)

1. **Revoke = one transaction, then the sockets.** `DELETE /api/v1/devices/:id` (own) and `DELETE /api/v1/messaging/governance/sessions/:id` (officer) run in one `withOrgContext` transaction: delete the staff `session` row; expire every `delivery_endpoint` linked to it; write the audit row (`m36.session.revoked`: ids, `byAdmin`, `current`, `endpointsExpired`; never a token, IP, user agent or endpoint value). **After the commit** the session's room is closed on every api node. If the close fails the revoke still stands (the session is dead for REST and for any new socket) and the 60 s re-check ends the old socket; the failure is logged without the error text. With realtime off there are no sockets and nothing to close.
2. **A per-session room, joined first.** The realtime server joins every socket to `session:<id>` synchronously on connection, before the (async) room set resolves, so a revoke that lands mid-handshake still finds it. The room name is M1's (`bootstrap/realtime`); M36 only receives a `disconnectSession(id)` port from the composition root (the Valkey emitter), so M36 imports no socket or Valkey code.
3. **The link is one nullable column, no foreign key (migration 1130).** `delivery_endpoint.session_id` (text, the Better Auth session id) is stamped by the registration route from the authenticated request context, never the body. No FK: `session` is M2's table and a hard FK would tie session deletion (sign-out, idle timeout, this revoke) to a user-RLS'd row. A partial index `(user_id, session_id) WHERE session_id IS NOT NULL` serves the revoke. An endpoint registered before the migration or without a session has no link and a revoke never touches it. Push re-registration with the same endpoint value (the browser re-subscribes after its session was revoked) is an upsert that re-verifies and re-links it to the new session instead of failing on the unique index (push only; sms/email keep the plain insert).
4. **Ownership stays where it is.** M2's `staff-session-store` is the only code that selects or deletes `session` rows (named columns, so the token, IP and scope can never be returned by accident; staff class only; unexpired only); M36's service orchestrates it with M36's endpoint link inside the one transaction through ports, so unit tests use fakes and the table-ownership gate is satisfied.
5. **No existence oracle.** A session that is not the caller's (admin: not bound to the caller's organisation, or pre-organisation), an unknown id and one already revoked are **the same 404** with the same message shape; a repeat DELETE is that 404 (the row is gone). Idempotent in effect: nothing changes on the repeat. An admin list for a user with nothing in the organisation, an unknown user or another tenant's user is an empty list, never an error.
6. **What a person sees.** `GET /devices` returns their own staff sessions across organisations (it is their own data; sign-up and pre-organisation sessions are real sessions and are listed): `id`, a **coarse label** (browser family and operating system, no version or model, "Unknown device" otherwise), `current`, `created_at`, `last_used_at` (the activity stamp, else the creation time), `push_registered`. Never the token, IP address, raw user agent or endpoint value. The session id is returned because it is the key of DELETE; it is not the credential (the token is), and a caller can only act on their own.
7. **Self-service needs no permission key; the officer does.** Own list/revoke require only an authenticated, organisation-bound caller and can reach only the caller's own sessions. The officer variant needs the **new** key `messaging.sessions.manage` (category `admin`; migration 1130 grants it to the two full-catalog admin roles only), list and revoke are audited (`m36.session.admin_listed`, `m36.session.revoked` at severity `warn`, actor and target named), the revoke also demands a **fresh step-up** (`messaging.sessions.revoke`, platform floor: webauthn or totp within the default window), and it is bounded to sessions bound to the officer's own organisation. The endpoint expiry for another user's session runs under that user's `app.user_id` scope (the `delivery_endpoint` policy is by user); the write-audit trigger on that table therefore attributes the endpoint update to the owner, and the explicit `m36.session.revoked` row is the record of who acted.
8. **The web.** `/messaging/devices` (every user) and `/messaging/governance/sessions` (`messaging.sessions.manage`): a flat list on the shared kit; "Current" and "Push on" are words (with a glyph), not colour alone; each Revoke names its device; "<device> revoked" is announced politely; a failed revoke stays listed with Try again; **revoking the current session asks first** (an alert dialog that says you will be signed out) and signs out only after the server confirms. The officer names a person by user id (`?user=`): there is no organisation-wide user picker to reuse, so the page never lists everyone.

## Conservative defaults proposed for SEC (not decided)

The decision sheet lists "app-lock and device policy (5.5, SEC)". This change does **not** decide it. It builds the least permissive interpretation that meets the WP acceptance and says so:

- **Immediate, no grace period, no undo.** A revoked session cannot be reinstated.
- **Revoking the current session is allowed** (with the confirm), because a lost-device or "that is not me" action must not require a second device.
- **An officer can revoke only staff sessions bound to their own organisation**, only with a fresh second factor, and every look is recorded.
- **Not built, because each needs a SEC decision first:** the **app lock** (device-local PIN or biometric after idle, tenant sets the *maximum* idle time, tighten-only: UI spec §5.5) and its tenant policy; **"Sign out everywhere else"** (a bulk revoke, and whether it is offered to the officer as "remote lockout"); a **notice to the revoked user**; whether the officer's revoke should also **suspend the account** or only end sessions; whether **sign-out and the idle timeout should also expire the device's push endpoint** (today only an explicit revoke does: see ceilings).

## Open questions (SEC, before this leaves Proposed)

1. Which role is "the security officer" who holds `messaging.sessions.manage` (today: the two full-catalog admin roles only)? Should a second person have to approve an officer's revoke of a clinician mid-shift?
2. Should revoking a session of a clinician with an open urgent request or unacknowledged escalation warn the officer (and notify the supervisor)? Today the revoke is silent about that.
3. App lock: the idle maximum, the unlock factor, and what a lock screen may show (UI spec §5.5 says no PHI).
4. Should a normal sign-out or idle expiry expire the endpoint that session registered? Proposed yes as a follow-on (an unlinked-session sweep), not built here.
5. Retention of the revoke audit rows is `compliance` (7 years) like the other `m2.*` session events; confirm.

## Consequences

- One migration (`1130_m36_session_device_controls.sql`): a permission row and its admin grants, one nullable column, one partial index. No table, so no manifest, ownership or tenancy change; `delivery_endpoint` keeps its user RLS and its write-audit trigger.
- Four routes (own list/revoke, officer list/revoke), one service with ports, one M2 store, two screens. OpenAPI enriched and the typed client regenerated.
- A live suite (`test:m36:session-devices:live`, CI job row added) proves, as `wardenx_app` with REAL Better Auth sessions, the real realtime server and a real Valkey emitter: next REST call 401, the socket closed (the periodic re-check is set to ten minutes, so the close is the revoke's), the endpoint expired while another session's stays verified, one audit row without secrets, foreign / other-tenant / repeat revoke is one 404, the officer variant (key, stale step-up, other tenant sees nothing), re-registration after revoke, current-session revoke.

## Known ceilings

- **Only an explicit revoke expires the endpoint.** A normal sign-out or idle expiry deletes the session but leaves its endpoint `verified` until the user removes it or it fails delivery. The link makes the follow-on sweep a one-query job; it is not built (open question 4).
- **Socket close is a race against an in-flight handshake.** A socket that authenticated just before the delete and joins just after the room was closed survives until the 60 s re-check. The room is joined before the room set resolves to keep this window to the authentication call itself.
- **Endpoints registered before 1130 have no link**, so revoking the session they were made from does not expire them. Only new registrations are linked.
- **A repeat revoke is a 404, not a 204.** Reporting "already revoked" would need a tombstone (a second session store); the uniform 404 is what keeps foreign and gone indistinguishable.
- **The officer cannot see pre-organisation sessions** (no organisation yet, so no tenant to authorise against) and sees no one outside the organisation; a user signed in only to another organisation is invisible to this officer by design.
- **The officer page takes a user id**; a user picker needs an M2 users-directory read that does not exist yet (UI gap, not a security gap).
- **`/api/v1/devices` shares a prefix with device attestation** (`/devices/attestation*`, M2). The static paths win over `/devices/:id`; a DELETE to `/devices/attestation` is a 404 here, not a collision.
