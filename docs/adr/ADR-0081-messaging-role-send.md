# ADR-0081 — Role-based send ("message the on-call RN"): resolved by the server at send time, confirmed by the sender, never a silent fallback

- **Status:** **Proposed** (2026-10-19). Built flag-off and fail-closed behind the tenant flag `messaging.role_send` and the new permission `messaging.oncall.send`, which no tenant role holds by default. **OPEN for the clinical lead: who may address a role, which roles, whether a gap may ever fall back to a telephone tree, and the confirmation wording (see "Open questions").** On `main` the real M19 router is still not bound ([ADR-0057](ADR-0057-escalation-ownership-m19-m36.md)), so every role send is refused as "roster not connected" until M19 binds one.
- **Date:** 2026-10-19
- **Phase:** Messaging Hub Phase 4, WP 4.12 follow-on (the role-based half of the proposed row in `docs/messaging-hub/10-ui-spec-phases-4-to-6.md` §4.12).
- **Resolves:** the "role-based send is not built and is an open decision" item (decision 6) of [ADR-0080](ADR-0080-messaging-oncall-directory.md), by proposing and building a flag-off slice of it. It does not change the read-only directory.
- **Extends:** [ADR-0080](ADR-0080-messaging-oncall-directory.md) (the guarded router, the patient gate), [ADR-0068](ADR-0068-messaging-urgency-model.md) (the urgent send this reuses), [ADR-0069](ADR-0069-messaging-acknowledgment-request-aggregate.md) (the request that stores the role), [ADR-0057](ADR-0057-escalation-ownership-m19-m36.md) (M19 owns rosters, M36 asks).
- **Related:** [ADR-0070](ADR-0070-messaging-escalation-timers.md), [ADR-0071](ADR-0071-messaging-delivery-failure-handling.md), [ADR-0078](ADR-0078-messaging-supervisor-reassign.md), [ADR-0010](ADR-0010-tenancy-rls-invariants.md).
- **Numbering note:** 0080 is the last ADR on `main` and no branch claims 0081 or 0082; migration 1129 is the next free ordinal (checked with `arch:migration-numbering` against `origin/main`).

## Context

Checked in the code, not assumed:

- Today an urgent message (WP 4.1) and a response request (WP 4.2) name ONE person. The sender picks that person from the care team; the server qualifies them (active, `messaging.urgent.receive`, Part 2, channel member, not the sender). Nothing in M36 addresses a role.
- The on-call directory (ADR-0080) already resolves "who covers role R for patient P now" through `getEscalationRouter()` wrapped by `guardEscalationRouter`. It returns user ids, the roster's zone, an optional shift end and `nextTier`. On `main` the router is the fail-closed deny-stub, so the answer is `roster_not_connected`.
- The ack request has no spare column for a role (ids, enums, instants only), and its update guard fixes identity and class. The `requested` event already records the first `assigned_user_id`.
- The failure to design against is hazard H-02: a message that goes to the wrong person, or to nobody, while the sender believes someone has it.

## Decision (proposed)

1. **A role is addressed only through the same guarded seam, never a new path to M19.** `createRoleSendService` takes the router that `buildOnCallDirectoryDeps` builds (`guardEscalationRouter` over `getEscalationRouter()`), so the real M19 router drops in unchanged. No roster, shift or role map is copied into M36.
2. **Two reads, one write, all under one patient gate.** `GET /api/v1/messaging/channels/:id/role-send/resolution?role&patient_id` (who covers now, for the sender to confirm) and `POST /api/v1/messaging/channels/:id/role-send` (send). Both require `messaging.urgent.send` and the new `messaging.oncall.send` (plus `messaging.read` / `messaging.send`), channel visibility, and the same chart gate the directory uses (`patient.read` plus `caseload_or_scope` on `patient_id`, no break-glass, then the org-scoped existence check, one identical 404; the shared `buildPatientGate`). The patient must also be THIS conversation's patient, else the same 404. A malformed role (closed list `rn`, `physician`), id or extra key is a 422 before any gate.
3. **Tier 1 only, and no fallback.** The server asks tier 1. A coverage gap, `roster_not_connected` (the deny-stub), "no ladder" and a router failure are all refusals: the resolution says so in its `status` with nobody to confirm; the send returns 422 `ROLE_SEND_NO_COVERAGE` whose message is the telephone-procedure wording ("Nobody is confirmed on call for this role right now. Use the agency telephone procedure; no message was sent."), and NOTHING is sent. There is no fall-back to a backup tier, to another role, to the primary of the care team or to a guessed person. A router exception propagates as a 5xx; it is never turned into a gap or a person.
4. **The sender confirms a named person; the server re-checks at send time.** The resolution returns the covering people (user id and display name, roster zone, shift end only if the roster supplied one). The sender confirms one (the send button names them) and the POST carries that `recipient_user_id`. The server re-resolves tier 1 at send time and sends only if that person STILL covers it. If not, it is a 409 `ROLE_SEND_RESOLUTION_CHANGED`, nothing is sent, the UI re-reads and asks the sender to confirm the new name. A changed resolution is never silently re-routed. The check-then-send window (the re-resolve and the commit of the same request) is milliseconds and is a known ceiling, not a guarantee: M19 may change the roster inside it, and the recipient is still the person the sender confirmed seconds earlier, who was on call when confirmed.
5. **It is the ordinary urgent send.** After the check the service calls the existing urgent service with the confirmed person, so qualification of the recipient (care team, `messaging.urgent.receive`, Part 2, not the author), SBAR, clinical links, the flags `messaging.urgent_clinical` and `messaging.sbar`, the atomic message-plus-request transaction, idempotency and the replay rules are unchanged. A person who covers the role but is not qualified is the urgent send's uniform 422; it never reroutes to someone else.
6. **The request stores the role and the person (migration 1129).** `message_acknowledgment_request.addressed_role` (nullable text, `CHECK IN ('rn','physician')`, a separate trigger refuses any change; the 1126 update guard is untouched). The resolved person is the request's `assigned_user_id` at creation and the first `requested` event's `assigned_user_id` after any reassign or escalation. A role send REQUIRES response tracking (flag `messaging.ack_requests`): with it off the send is refused (503 `ROLE_SEND_UNAVAILABLE`, nothing sent), so a role message never exists without a record of the role. The role is not yet shown on the request card or in the queue (follow-on).
7. **Idempotent.** The route requires an `Idempotency-Key`; the client message id replays the original (200). A retry of a send that already committed to the SAME person and the SAME role does not re-resolve and still answers with the original (200, `created:false`, the STORED role) even if response tracking was turned off since, so a shift change or a flag change between attempt and retry cannot turn a safe retry into a refusal; a retry naming a different person goes through the full check. A `client_message_id` already stored for a person-send or for another role is a typed 409 `ROLE_SEND_CLIENT_ID_REUSED` and is never echoed as this role. The idempotency middleware caches every response, refusals included, so the web mints a fresh Idempotency-Key after any clean refusal (a changed resolution, a gap) and keeps the key only after a failure that may have stored the message.
8. **Authority.** New key `messaging.oncall.send` (resource `oncall_role_send`, action `send`, category `clinical`, no ABAC), registered in `M36_CONTRIBUTED_PERMISSIONS` and mirrored by migration 1129. It is granted to NO tenant role by the migration (unlike `messaging.oncall.read`, addressing a role changes who is paged); the full-catalog admin template roles receive it, and a tenant grants it deliberately. The tenant flag `messaging.role_send` (absent = off) off is the uniform 404, decided in the service before any router call. The web control additionally needs the flag provider (no provider reads as off) and all three keys.
9. **Audit and logs.** The resolution read is audited against the patient (`oncall_role_resolution`, fields `role`, `resolved_person`); the send is audited against the message and the patient, and the database audit triggers record the request insert with `addressed_role` and `assigned_user_id`. A refusal (gap, changed, untracked) writes no message and no request and is logged with the organisation, the sender, the role and a status word only. No patient id, name, message text or recipient appears in a log.
10. **Rate limit.** The POST uses the urgent route's limiter unchanged (per user, per organisation, per sender-recipient pair, fail closed; the body field is `recipient_user_id` so the pair bucket reads it). The resolution read has no limiter, like the directory read.

## Open questions (clinical lead, before any tenant turns the flag on)

- **Who may address a role?** Proposed: only a clinician who may already send urgent messages and has been granted `messaging.oncall.send` (by role, e.g. RN case manager, physician, social worker, supervisor). Should an aide, a volunteer, or a coordinator ever be able to? Should a role send be limited to the patient's own care team members?
- **Which roles?** Proposed `rn` and `physician` only (the directory's closed list, mapped by M19 to its ladders). Social worker, chaplain, pharmacist, after-hours triage line and "supervisor on call" are not covered and need M19 ladders.
- **May a gap ever fall back?** Proposed: no. The refusal tells the sender to use the agency telephone procedure. If the clinical lead wants a tree (tier 2, the manager, a triage line), it must be an explicit, named, confirmed step the sender sees (a second resolution they confirm), never an automatic widening, and it is a separate decision here.
- **Several people on call?** Proposed: the sender confirms one of the tier-1 people; the app sends to that one only. Alternatives (send to all, send to the first) page more people or hide who has it and are not proposed.
- **Confirmation wording.** The provisional text is in `apps/web/src/modules/36-messaging/role-send-wording.ts`. The clinical lead should approve: "Confirm who is on call", "Send urgent message to {name}", "This goes to {name}, the on-call {role} right now, and is marked urgent. It cannot be edited after sending.", and the refusal "Nobody is confirmed on call for this role right now. Use the agency telephone procedure; no message was sent."
- **Staleness.** The confirm step reads the roster when it opens and the send re-reads it. Should the confirm expire after a fixed time (the spec says 60 s) and force a re-read, or is the send-time re-check enough?
- **Escalation of a role request.** The WP 4.4 timers escalate a request by tier using the router; a role request is assigned to a person and escalates like any other. Should a request addressed to a role instead re-resolve the role at each tier? Not proposed; it needs the real router and M19 ownership of tier semantics.

## Dependency on the real M19 router

Nothing here replaces or bypasses M19. The deny-stub on `main` makes the feature answer "roster not connected" and refuse every send, which is the correct, honest behaviour until a named M19 owner binds a router ([ADR-0057](ADR-0057-escalation-ownership-m19-m36.md), `docs/messaging-hub/brief-m19-owner.md`). When it does, M19 must (a) enforce the org check and that the patient belongs to the org, (b) answer tier 1 for `requiredRole` `rn` / `physician` at the given `asOf` in the roster's IANA zone (DST-correct), (c) answer `unavailable` / `no_route_configured` for an unknown role, and (d) ideally supply `shiftEndsAt`. Live acceptance (shift boundary and DST cases through the real router) remains open until then.

## Consequences

- One migration (`1129_m36_oncall_role_send.sql`): a permission row, one nullable column, one check, one trigger. No new table, so no manifest or ownership change. `arch:tenancy` is unaffected (the table already has its three-column rule and FORCEd RLS).
- Two routes, one service, a composer control (`Message on-call role`) behind the flag and three keys. The urgent service gains an optional `roleAddressed` input that is refused when tracking is off.
- The role is stored but not yet displayed on the request card, the unacknowledged queue or the supervisor reassign picker; showing "to the on-call RN" there is a follow-on.

## Known ceilings

- The check-then-send window described in decision 4; the flag read is cached a few seconds per organisation (like its siblings).
- Tier 1 only; several people on call means the sender chooses one.
- A person on call who is the sender is refused by the urgent send's uniform recipient rule, and the sender is told to use the telephone procedure.
