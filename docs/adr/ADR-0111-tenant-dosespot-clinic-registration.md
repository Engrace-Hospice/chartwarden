# ADR-0111 — A tenant registers its own DoseSpot clinic: a sealed per-tenant registration row (draft, registered, verified, active) in front of the env map, a named environment instead of a URL, and an e-prescribing gate that also needs a linked prescriber

- **Status:** **Accepted** (2026-11-06). The product decisions below were made by the owner on 2026-11-06 (tenant onboarding revamp, slice 4).
- **Date:** 2026-11-06
- **Phase:** post-launch tenant onboarding (the ops wizard's e-prescribing step); builds on the M12 DoseSpot adapter (GAP-037).
- **Related:** [ADR-0019](ADR-0019-controlled-substance-go-live.md) (EPCS is deferred; a lawful non-EPCS path exists, and this ADR keeps it that way), [ADR-0020](ADR-0020-integration-governance.md) (INT-014: a BAA executes before PHI flows), [ADR-0053](ADR-0053-clearinghouse-transport-port.md) (the per-tenant clearinghouse amendment of 2026-11-06 is the pattern this follows: a sealed per-tenant config in draft, verified, active, written by the tenant or by platform ops through the tenant's own scope), `docs/history/m12-dosespot-adapter.md`, `docs/architecture/CHARTWARDEN_INTEGRATIONS_v0_1.md` section 6.1.
- **Amends:** the M12 spec section 2.5 (D5) credential model, which put the clinic credentials "in `packages/dosespot/credentials/`", a path that was never created; the credentials lived in the `DOSESPOT_TENANT_CONFIGS` environment map, read once at boot.

## Context

Facts read from the repo on 2026-11-06:

- The DoseSpot adapter (`packages/dosespot`) is bound per tenant only through `DOSESPOT_TENANT_CONFIGS`, a JSON map in the environment. Enabling a tenant meant editing a secret and redeploying; the clinic key sat in the environment in the clear; a tenant could not register its own clinic and an operator could not do it for a tenant.
- The roster `enroll` route only wrote a local row. No production path set `dosespot_prescriber.dosespot_prescriber_id`, the id `transmit-newrx` sends under, so an API-enrolled prescriber's orders failed permanently as `prescriber_not_enrolled`.
- The sign path asked a synchronous boolean ("does this tenant have a config?") and then queued every signed order, linked prescriber or not.
- The tenant onboarding wizard has a step "e-Prescribing (DoseSpot)" (order 10, an `either` step) whose precondition read `context.dosespotKickoffRecorded`, a fact nothing produced.
- The M12 spec says the adapter's `baseUrl` is "env-derived, never branch".

## Decision

**D1 — A registration row per tenant.** `dosespot_clinic_registration` (migration 1426), one row per organization, RLS enabled and forced on `app.org_id`, column-level UPDATE (never the id or the organization), no DELETE, the M4 write-audit trigger scrubbing the sealed secret and recording that it changed. States: `draft` (saved, incomplete: the wizard can resume) -> `registered` (clinic id, service clinician and key all present) -> `verified` (a connection test passed) -> `active` (in use). Only `active` transmits. CHECKs make a half-state impossible.

**D2 — Sealed under the tenant key ring.** The clinic key (and the Subscription-Key when the tenant has its own) is one JSON envelope, AES-256-GCM under the tenant's M34 key-ring DEK, its AAD binding organization, environment and clinic. The DEK version rides in `secret_dek_ref`. A tenant shred makes it unreadable; a ciphertext copied to another tenant, the other environment or another clinic does not open. It is write-only: no view carries it, no log, error or audit row holds it. The unsealed key stays in a process's memory for about six minutes at most (and is dropped the moment the row stops being usable), so a shredded or deactivated tenant stops being served without a restart. That is the five-minute cache life plus, at most, the one minute between two runs of the sweep: the expiry does not wait for the tenant to be looked up again, because every lookup prunes the whole cache and an unref'd one-minute sweep drops an expired entry of a tenant that left the active set (as it does an expired bearer token, in the adapter), so the bound holds in an idle process and not only at the next call, but an entry added while the sweep is already armed can outlive its five minutes by up to a minute; the GCM tag must be the full 16 bytes. (Slice 3 sealed the clearinghouse credential under a key derived from the M24 KEK; the DoseSpot module already holds the key ring for its webhook receipts, so it uses the ring, which also gives DEK versioning and crypto-shred at offboarding.)

**D3 — An environment, never a URL.** A tenant (or an operator for it) picks `sandbox` or `production`; the host is platform configuration (`DOSESPOT_BASE_URL_*`, https and `dosespot.com` only, no credentials in the URL). Sandbox defaults to DoseSpot's public staging host. A sandbox registration can be verified on any deployment, but it goes LIVE only where the platform sets `DOSESPOT_SANDBOX_ENABLED` to exactly `true`: `activate` is refused otherwise (409 `DOSESPOT_SANDBOX_NOT_ENABLED`), and an already active sandbox row stops being served by the resolver, queued for by the sign gate (an order activates locally) and counted by the wizard fact the moment the flag is unset. All three read one predicate (`registrationIsLive`), so they cannot disagree. Production has no baked-in host and is refused (verify and activate answer 409) unless `DOSESPOT_PRODUCTION_ENABLED` is exactly `true` and its host is set: the flag is set only once the ChartWarden / DoseSpot BAA is executed and a sandbox run has confirmed the wire shapes. A URL a caller could type would let the clinic key and PHI go to any server.

**D4 — Database in front of env.** The adapter reads its config through an async resolver. A tenant WITH a row is served by that row alone: a draft, registered, verified-only or deactivated row is never served from the env map. A tenant with NO row still is, so the demo tenant keeps working; the boot log names each organization the map still serves. The row is read on every call and the sealed key opened once per row version; the token cache keys on that version, so a rotated key never reuses the old key's token.

**D5 — Who writes.** Both. The tenant administrator through `/api/v1/tenant/dosespot` (org-level `prescribing.clinic.read` / `.admin`, bound to `org_admin` and `administrator` only, fresh step-up, Idempotency-Key, `If-Match`, AI actors refused). Platform ops through `/api/v1/platform/tenants/:orgSlug/dosespot` (`tenant_dosespot.read_platform` / `.write_platform` on the exact `platform_ops` role, fresh step-up, a recorded reason, only while the tenant is provisioning or onboarding; a deactivation, the one write a live tenant also needs, is not status-gated). Both run the same M12 service under the tenant's own RLS. **Activation is the tenant's alone** (the owner's decision of 2026-11-08 for the clearinghouse, CW-AC-17, extended to DoseSpot on 2026-11-09, CW-AC-21): the platform lane registers, tests and may deactivate (which only stops e-prescribing), but has no activate route, and M12's service refuses an activation by the platform lane with 403 `DOSESPOT_ACTIVATION_TENANT_ONLY`, even over an already-active registration. Wizard step 10 (`either`) settles off the tenant's own activation, whose route runs the advance pass, or by attestation, so go-live never waits on an operator. The tenant lane may rotate a Subscription-Key platform support set but never introduce one (it may be the platform's own); ops may set it, and a platform environment key per environment applies when a row carries none. Whether DoseSpot's Subscription-Key is per clinic or ours to share is unconfirmed: the sandbox run decides.

**D6 — Rotation.** Any change to the environment, clinic, service clinician or a key puts the row back to `registered` (or `draft` while incomplete) and clears what the old credential earned; a change of environment or clinic also drops the stored key, **and every id DoseSpot issued under the old clinic**: in the same transaction as that change (and when a row takes over from the env binding, whose clinic is not compared) the roster's vendor prescriber ids, enrolment markers and NPIs are cleared, each patient's vendor patient id is cleared (the sync row reads `failed`, class `registration_retargeted`), and the created-prescription id of every transmission still waiting is cleared, which also gets a fresh idempotency key so the new clinic never sees the old one (a finished transmission, one whose vendor call has begun, and one HELD for a person whose prescription may exist at the old clinic, keep their id and their key: a worker that is alive clears its own created id when it sees the move, and a dead one's is what the administrator looks for). Those ids are scoped to one clinic of one environment: sent under another, DoseSpot refuses them for good, which the worker would record as a permanent `transmission_failed` that no route recovers. The effect is deliberate and recoverable: after the new registration is tested and activated, an administrator re-enrols each prescriber (the enrolment, which returns early for an already-linked prescriber, now runs again), a queued order whose prescriber is on the roster, not revoked, and not yet re-enrolled is not claimed at all (it costs no write per tick and cannot fill the batch ahead of an order that can go; it becomes claimable the moment the prescriber is linked, and the queued-order age alert tells the tenant's administrators), and a patient is re-synced when an order needs it. An order signed in the meantime activates locally, because the sign gate sees an unlinked prescriber. A revoked prescriber's queued order still fails as `prescriber_not_enrolled`. A key rotation or a change of the service clinician within the same clinic keeps the ids. The field-level audit row names `vendorBindings` among the changed fields (names only, never an id). The reset also covers what was already in flight: the adapter's in-process memory of a created-but-unsent prescription is keyed by the clinic it was created under (host and clinic id) and is never served under another, and a vendor round trip that BEGAN under the old clinic (a prescriber enrolment, a patient upsert, a prescription create and the send that follows it) never writes its id after the move. Each captures the registration's target (`<environment>:<clinic id>`, or `env` for a tenant with no row) before the call and, in the transaction that writes the id, takes a shared advisory lock that the reset holds exclusively and compares the target again: a write that began first commits first and the reset then clears what it wrote, a write that starts later waits for the reset and sees the new target. A refused write is dropped and logged (ids and a class only): the enrolment answers 409 `DOSESPOT_REGISTRATION_MOVED` (the clinician then exists at the old clinic as an orphan, DoseSpot's dedupe being unverified), a patient sync row goes back to `pending` and runs again under the new registration, and a transmit worker that sees the move clears its own created id and settles the order as an outage (back to `queued`, no retry spent). A move A to B to A inside one round trip reads as unchanged, which is harmless: the ids a trip under A wrote are valid under A. A prescriber enrolled in the sandbox, where D9 lets an NPI that NPPES does not list proceed (flagged `nppesVerified: false`), therefore cannot carry that enrolment into production: the move to production clears it, and the re-enrolment passes production's NPPES gate. Re-enrolling may meet DoseSpot's dedupe of an existing clinician, which is unverified until the sandbox run (D9). The patient-sync and MedHx drain applies the same rule to its rows: a tenant that registered DoseSpot but is not live (deactivated, rotating its key, not yet activated, or its config unreadable) has its `dosespot_sync_queue` rows left `pending` and unclaimed, never failed and never recorded as a failed patient sync, and they run when it is live again; a tenant that never registered anything keeps the old behaviour (its rows fail as "not enabled", so the demographics of every patient of a tenant that does not use DoseSpot are not parked for the day it does); a transient vendor failure backs off (1, 2, 4 ... 60 minutes from the last claim) and ends the row after 8 attempts, so a vendor that never recovers is not retried every two minutes forever. A MedHx fetch for a patient whose vendor id the reset cleared ends the row with a message that says the patient is not registered at the clinic the registration now names (a patient never synced keeps its own message): nothing here auto-registers every patient at the new clinic, and only an order or a demographic change syncs a patient, so the next admission or recertification pulls the history; the admission trigger enqueues a MedHx fetch only, never a patient sync, so this is also what happens to a patient who was never synced. A rotation of an active registration pauses e-prescribing: newly signed orders activate locally, queued ones wait, the outbox publishes `m12.dosespot_config.deactivated` (cause `credential_changed`) and the tenant's administrators are alerted (each change is its own alert). An order the transmit sweep had already claimed when the registration stopped being live goes back to `queued` with no retry spent (`NotEnabledError`), exactly like an open circuit. An `activate` also needs the latest test to have passed. A plain deactivation goes to `verified` (the credential is unchanged, so no new test is owed).

**D7 — No separate BAA step.** DoseSpot's BAA is ChartWarden's with DoseSpot (Surescripts coverage flows through it), not tenant-held, so unlike the clearinghouse there is no per-tenant BAA record. The gate is D3's production flag. The vendor BAA stays a prose-tracked row in `CW-BA-01`.

**D8 — EPCS stays off.** There is no EPCS column: a registration resolves `epcsCertified: false`, so the D18 certification gate stands and no route here can change it. Enrolling a prescriber never starts EPCS or IAL2 (the adapter already says so).

**D9 — A prescriber's vendor enrolment, and the sign gate.** Create-then-record, never a transaction across the vendor call: commit `vendor_enrollment_requested_at` on the member's roster row (migration 1427), call `addClinician`, record the vendor's id and NPI, publish `m12.prescriber_enrolled` with the real id. Allowed once the registration is `verified` or `active`, for an ACTIVE membership of THIS organization only, and it never reinstates a revoked prescriber (the roster `enroll` route does that). **Who the clinician is is never typed.** The enrolment body is empty (a typed `npi`, `firstName` or `lastName` is a 422); the NPI and legal name are derived from the physician record the roster links the member to (`dosespot_prescriber.external_physician_mdm_id` to M40's canonical `external_physician`, an NPPES-sourced record no tenant can write an NPI into), so the member must already be on the roster with that link (409 `DOSESPOT_PRACTITIONER_NOT_LINKED`), the record must be active with a name and an NPI that passes the check digit (409 `DOSESPOT_PRACTITIONER_NOT_ACTIVE` / `_NPI_MISSING` / `_NAME_MISSING`, 422 `DOSESPOT_NPI_INVALID`), and it is cross-checked against NPPES's public directory (`nppes_provider`, read through M29's `NppesProviderReader` seam): where NPPES lists the NPI it must be an active individual (NPI-1) whose last name matches (409 `DOSESPOT_NPPES_MISMATCH`). Where NPPES has NO row, a production registration refuses (409 `DOSESPOT_NPPES_UNVERIFIED`: the nightly NPPES sync covers every NPI a master-data record references, so the wait is short) and a sandbox one proceeds with the audit row flagged `nppesVerified: false` (the synthetic demo NPIs are not in the real registry). The link itself is a roster administrator's assertion that this member IS that physician (as for a verbal order's named prescriber), so it is not enough on its own: the PRESCRIBER confirms it from their own account before the vendor enrolment (migration 1430). `GET /api/v1/me/dosespot-prescriber-link` (`prescribing.sign`; a read, not step-up gated) shows the signed-in member the linked record's name and NPI, and `POST …/confirm` (the member's own session selects the roster row, `prescribing.sign`, a fresh step-up, a human actor, an Idempotency-Key) records it pinned to the link and the NPI they were shown (409 `DOSESPOT_ROSTER_CHANGED` if either moved). Enrolment on BOTH lanes is refused 409 `DOSESPOT_PRACTITIONER_UNCONFIRMED` until a confirmation BY THE ROW'S OWN MEMBER matches the current link and the record's current NPI; a re-link or a revoke clears it, and the claim and the recording (the vendor id is only linked while the confirmation still stands) re-check it under the row lock. What is enforced where, exactly. **The application:** no platform route exists for confirming (the operator's roster list only shows `linkConfirmed`), the actor's own membership selects the row so the service cannot be pointed at another member's, and the route's guards (own session, step-up, human actor) and the enrolment gate are code. **The table (migration 1430):** a CHECK binds the recorded confirmer to the row's own member (`by = membership_id`, every column non-NULL, a ten-digit NPI), whoever wrote it. **A trigger:** a write that sets or changes a confirmation is refused unless the transaction's declared actor (`app.user_id`, which `withOrgContext` sets from the session and the write-audit triggers also read) is that member's own user, so an operator-lane transaction, an administrator's request or a worker cannot do it; clearing is open to any actor. The trigger is a backstop on the declared actor, not authentication: code that can set that variable could declare any user, so it relies on the application never declaring anyone but the session's user. The confirmation is recorded by this service's own audit row with ids only (the roster row, the physician record, the actor); the table's write-audit trigger also records the row's columns, NPI included, which is public provider data. What the administrator can no longer do is choose the NPI or the name, or put an identity on a member without that member agreeing. What remains is a prescriber who confirms a record that is not theirs: the name and NPI are shown to them to make that unlikely, not impossible. Step 1 is a claim: the roster row is locked `FOR UPDATE`, refused if the roster re-linked meanwhile (409 `DOSESPOT_ROSTER_CHANGED`); a second enrolment while one is in flight (a marker younger than five minutes with no vendor id) is refused 409, and a definitive vendor refusal releases the claim. The operator lane checks the tenant's onboarding status BEFORE the roster claim and the vendor call (and `verify` before the token mint), then again, authoritatively, when it records. No request to DoseSpot follows a redirect. The sign path now queues an order for transmission only when the org's DoseSpot is live AND the signing prescriber is linked to DoseSpot, read inside the signing transaction; otherwise it activates locally, as for an unconfigured tenant.

**D10 — The wizard fact.** Step 10 settles from `context.dosespotSettled` (migration 1428, a `contract` migration like 1418: the previous release cannot evaluate the new field), true while the registration is `active`. The prescriber count is shown and does not gate: a prescriber needs a membership, and the first-admin step comes after this one. A human may still attest the step.

## Consequences

- Enabling a tenant is now an API call (and a sandbox test), not an environment edit and a deploy; `DOSESPOT_TENANT_CONFIGS` shrinks to a fallback and is removed once the demo tenant has a row.
- A registration written during onboarding by an operator also voids a pending go-live attestation (the attestation said the data was ready).
- Not verified against DoseSpot (docs/history): the token endpoint, the `addClinician` field names, whether the Subscription-Key is per clinic, DoseSpot's dedupe of a clinician by NPI (a crash between the vendor create and the record can leave an orphan clinician and a retry may meet a duplicate), and the production host. The connection test proves the credential was accepted; it does not prove our payload field names.
- Not built: a vendor-side clinic creation (DoseSpot issues the clinic id and key; no creation endpoint is in the public swagger), a runtime credential guard that holds orders and alerts once on a vendor rejection of the key (a rotated key rejected at the vendor currently fails the order permanently, as before), a per-prescriber revoke at DoseSpot (no endpoint), and webhook-secret storage (the webhook scheme is itself unverified).
- Open: `verify` is a guessing amplifier. A tenant administrator with a fresh step-up can call it repeatedly with candidate clinic keys (each call sends the stored or newly supplied key to DoseSpot's token endpoint) and read the accepted / rejected outcome, so the vendor's answer is an oracle on whether a guessed key is valid for a clinic. The exposure is bounded, not removed: the route is rate limited to 6 per minute per user and 30 per minute per organization (fail-open: the limiter is an availability control, so it stops being a bound if its store is down), needs the organization-administrator role, a human actor and a step-up, and the clinic keys are high-entropy vendor-issued values, so the practical risk is low. A failure counter that locks `verify` after repeated rejections is not built; revisit when DoseSpot publishes its own lockout behavior or when the platform adds a shared attempt-throttle primitive.
