# ADR-0112 — `superadmin`: one platform-owned role that supersedes `administrator` and `org_admin` and holds every platform role

- **Status:** **Accepted** (2026-11-25), by the owner, who validated it after Proposed (2026-11-16). The owner asked for a single account above sysadmin and orgadmin that belongs to ChartWarden, not to a tenant, and chose a real catalog role over a dev-only seed. The names of the people who may hold it are still the owner's to record: production has no holder, and a grant is a separate, ticketed change (OPS_RUNBOOK §16.5) made only once `CHARTWARDEN_MFA_ENFORCEMENT=true` is verified.
- **Date:** 2026-11-16
- **Related:** [ADR-0090](ADR-0090-administrator-and-org-admin-org-wide-patient-scope.md) (`administrator` and `org_admin` are the org-wide roles), Module 3 spec D3 (`org_admin` / `platform_ops` are roles in the catalog, not flags), Module 34 (platform ops; the consented support session), Security Hardening section 5.1.2 (passkey for high-privilege roles) and section 17 (break-glass), GAP-003 / GAP-096 (platform authority lives only on platform-owned role rows).
- **Amends:** nothing. It adds one key to the set GAP-003 reserved.

## Context

Facts read from the repo on 2026-11-16:

- Platform authority is a role **key** in `context.roles`, and each predicate matches specific keys: M22 and M26 admit `platform_admin` alone, M29, M33 and M35 admit the `PLATFORM_OPS_ROLE_KEYS` list, and the tenant-lifecycle predicate admits `platform_ops` alone. No role held them all.
- The two tenant admin roles are `administrator` (the CoP-418.100 role, sysadmin's) and `org_admin` (orgadmin's). Many predicates list `administrator` without `org_admin` (M19, M20, M30, M32, M41, the code-status and SSN grants), so holding one does not satisfy the other.
- Both hold the whole permission catalog, kept whole by materialization and `db:sync:permissions`, which write **tenant-owned** rows only. A platform-owned row is never touched by either.
- GAP-003 reserved platform keys to platform-owned rows (`organization_id IS NULL`): no tenant route can create or assign one, and migration 0318/0321 refuses a tenant row that carries one.

## Decision

**D1 — One reserved key.** `superadmin` is reserved by exact key (like `ai_safety_owner`), is in `PLATFORM_GRANTABLE_ROLE_KEYS`, and migration 1501 widens the `role_platform_authority_platform_owned` CHECK (NOT VALID, like 0318/0321). It is bound only by the ticketed operator CLI (`bun run db:platform-role grant --role superadmin`), audited by the M4 triggers. The CLI refuses any organization that has a `tenant_account`, and a `membership_role` trigger in the same migration refuses that binding for ad-hoc SQL and seeds too, so a mistyped `--org` cannot make a tenant member a superadmin. The trigger is `SECURITY DEFINER` with a pinned `search_path` (the M4 audit-function shape), checks the membership's own organization as well as the row's (no composite FK ties the two), and is `ENABLE ALWAYS`, so a session in `replica` mode (the seeds) does not skip it. A second trigger on `tenant_account` refuses the reverse order: giving an organization a `tenant_account` while it already holds a superadmin binding. The two take opposite row locks on the `organization` row (SHARE in the binding trigger, NO KEY UPDATE in the other), so a binding and a `tenant_account` committed at the same instant cannot each pass its own check. Both are `SECURITY DEFINER` and assume the function owner (the migration role, a superuser in production's compose) bypasses RLS on `organization`, `membership`, `role` and `tenant_account`; on a managed Postgres without a superuser owner the lookups would see only what RLS allows. Revoking it also ends the holder's sessions (see Consequences).

**D2 — It belongs to ChartWarden.** The membership lives in the ChartWarden platform organization, never in a tenant. That org is an `organization` row only: no `tenant_account`, no key ring, so it is not billed or provisioned as a tenant and the tenant lifecycle surfaces do not list it. It is still an `active` organization, so every background job that enumerates active orgs (the cron fan-outs, the outbox relay, role-template materialization at boot) includes it; how each behaves for an org with no `tenant_account` or key ring has not been verified (see Consequences). The dev seed `bun run db:seed:superadmin` creates it locally and runs only with `NODE_ENV` unset, `development` or `test` against a local database (an allow-list: `staging`, `prod` and any other spelling are refused, because production's seed-runner also reaches the host `postgres`); it is deliberately not part of `db:seed:all`, which production's reseed workflow runs, and a test pins that. It also refuses whenever `CHARTWARDEN_SEED_ALLOW_PRODUCTION` is set (production's seed-runner sets it, whatever `NODE_ENV` says). It checks the organization is not a tenant before it drops or creates anything. No tenant onboarding path produces an active organization without a `tenant_account` (M34 always adds one; a bare organization made by `POST /api/v1/orgs` starts `created`, and I found no route that activates it without one, which was not checked for single-tenant deployments). Both the CLI and the trigger refuse an organization that has a `tenant_account` for this role, so in production the platform org and its first membership are created by an operator with SQL (runbook §16.5), then granted with the CLI.

**D3 — Roles are expanded at one choke point.** The enrichment reader turns a held `superadmin` into `administrator`, `org_admin` and every platform-grantable key (`expandSuperadminRoles`), and that is what lands in `context.roles`, which every authorization decision reads. No predicate is edited, so none can be missed. The side readers that report a membership's role keys for display or derivation (the M3 batched role-key read behind M14 attendance, the `roleKeysOf` fallbacks of M16, M20, M21 and M32, `actor_role`) answer the key actually held, `superadmin`, not the expanded set. They fail closed (a predicate that lists `administrator` does not see a superadmin through them) and are not an authority path, so they are left as they are.

**D4 — Permissions come from the code catalog.** The effective-permission store answers `superadmin` with every key the catalog declares (`effectivePermissionKeys`), never from stored rows, so a module that adds keys tomorrow is granted tomorrow and the role cannot fall behind the two it supersedes. It withholds the same keys the admin roles are denied on purpose (`FULL_CATALOG_EXCLUDED_KEYS`: messaging redaction request and approve, review, urgent send and receive), so one account never holds both halves of the redaction two-person control (ADR-0055 D9): `superadmin` is exactly what a materialized `org_admin` holds plus the platform-category keys, and a test pins that equality (a seeded demo admin holds more; see Consequences). The key set is returned only for the platform-owned row. The `role_permission` rows the CLI writes are a visible record only.

**D5 — A passkey.** `superadmin` is in `PASSKEY_REQUIRED_ROLE_KEYS`.

**D6 — What it does not do.** It does not bypass RLS, the consented support session or break-glass, so another tenant's PHI is still reached only through those. It does not use `withPlatformContext`, skip step-up, or count as `isAdmin` (the tenant last-admin guard).

## Consequences

- One credential now concentrates every platform authority. Hold it for at most two named people, review the holders quarterly, and extend "every use of platform_ops or org_admin is logged and reviewed" to it. Nothing raises an alert on a grant or a use today (CW-MON-01 is a gap), and the grant is a database-owner CLI call attributed only to a change-ticket string, so until that exists the quarterly review is the only detective control.
- **The passkey rule is policy, enforced by the server unless `CHARTWARDEN_MFA_ENFORCEMENT=false`** (amended 2026-11-26 by CW-AC-45: when this ADR was accepted it was opt-in and enforced only when `=true`; see `mfa-policy.ts` and `docs/runbooks/mfa-enforcement-rollout.md`). Do not grant `superadmin` in production while it is relaxed.
- Alert audiences sourced from `platform_ops` holders (`bind-platform-staff`) do not include a holder of `superadmin` alone. Hold `platform_ops` as well if that holder should receive them.
- The role list may show a platform-owned row named "Superadmin", as it already does for the other platform roles. The role screens and the role-assignment dropdown never offer a platform role (the assign route refuses every one with 422 `RESERVED_ROLE`, a superadmin included), and say where one is granted.
- The API caches a permission set per replica for up to five minutes, keyed by (organization, user) and not by session, and the CLI is another process that cannot invalidate it. The resolver therefore never caches a set that contains `superadmin` (one grant read per request, for at most two people), so a revoke takes effect on the next request even if the holder signs in again at once. Revoking also deletes the holder's sessions, but only when a binding was actually removed, so a repeated revoke signs nobody out. The CLI revokes a suspended holder too (a grant still needs an active membership), so an offboarded holder's binding cannot lie dormant and return on reactivation. Role-key predicates deny immediately either way, because roles are re-read on every request.
- **Unverified:** how each background fan-out behaves for the platform org (no `tenant_account`, no key ring): it may no-op or it may error on every tick. Making the enumerator require a `tenant_account`, or excluding the platform org by name, is a change to every cron fan-out and is the owner's call.
- Anti-escalation compares permission keys only and `superadmin` holds all of them, so inside the platform org it could create a tenant-owned role carrying platform-category keys and assign it to a member without the CLI, a ticket or a passkey (`platform_ops` has the same shape, narrower). The role create and edit routes now refuse a platform-category key on a tenant-owned role (422 `RESERVED_ROLE`, naming the keys), which materialization already never grants. An edit refuses only keys it would ADD: the dev seed and `db:sync:permissions` give a demo tenant's `administrator` and `org_admin` every catalog key (platform ones and the five withheld messaging keys included, unlike materialization), and the editor sends the whole set back, so refusing what a role already carries would lock those roles. The role editor's clone leaves platform keys behind. That is a route rule: there is no database backstop for `role_permission`, so ad-hoc SQL by someone with database access is not covered (such a person can also bind the platform role directly).
- **Seeded admin roles hold more than `superadmin` does.** "`superadmin` is exactly what `org_admin` holds plus the platform keys" is true of a MATERIALIZED `org_admin` (what a real tenant gets). The dev seed and `db:sync:permissions` grant the demo tenants' `administrator` and `org_admin` the whole catalog, so on a seeded stack they hold the five withheld messaging keys (both redaction halves, review, urgent send and receive) and `superadmin` does not. Aligning those scripts with the materialization set is the owner's call (it changes what the demo admins can do and needs a reseed of the demo tenants); until then the two-person control is intact for `superadmin` and not for a seeded demo admin.
- The assign route's anti-escalation refusal now answers 403 `ESCALATION_BLOCKED`, the code the invite path already used, so a client can tell it from any other 403 (a missing `role.assign`, a step-up, an ABAC deny) and the role editor words each one accurately.
- A refused binding leaves no audit row: the trigger's `RAISE` rolls its transaction back, and an audit row written in that transaction goes with it. The refusal is visible to the operator (CLI error) and in the database log only. An out-of-band audit write would need a second connection and is not done.
- A tenant that already made a custom role keyed `superadmin` loses what it granted: migration 1501 warns at apply time (the migrate script prints the notice), the reader ignores it from then on. A role key cannot be edited, so the remedy is to delete that role.
- `superadmin` is not a reserved username; the dev seed uses it as the sign-in name.

## Alternatives rejected

- **Bind each platform key and `org_admin` individually.** No single revoke, and it drifts as roles are added.
- **Add `superadmin` to every predicate.** About fifteen sites; one missed is a control that exists on paper only.
- **Bypass all checks.** Conflicts with Security Hardening and HIPAA minimum necessary; it would need its own ADR superseding them.

## Verification

`auth.live.test.ts` (as `chartwarden_app` on a private Postgres) proves the grant, the expanded roles, the permission set (the catalog less the withheld keys) with every stored row deleted, the CHECK refusal of a tenant row, a legacy tenant-owned `superadmin` row conferring nothing through the real reader and store, and the refusal of a tenant binding by both the CLI and the trigger: on INSERT and UPDATE, with the membership in a tenant but the row filed under the platform org, from a `replica` session, as `chartwarden_app` in the tenant's own context, and in the reverse order (a `tenant_account` for an org that already holds one). It also proves revoke ending the holder's sessions only when it removed a binding, and reaching a suspended holder; that the grant and the binding delete land in `audit_event` under the change ticket's correlation id, and the session delete is audited too (by the session trigger, under its own correlation id, not the ticket's); and that scoped to the platform org a superadmin reads none of a tenant's memberships. `rbac-resolve.test.ts` proves a superadmin set is never cached; `authz-routes.test.ts` the platform-key refusal on role create and edit and the `ESCALATION_BLOCKED` code; `seed-all.test.ts` that the production reseed chain never reaches the superadmin seed; `migration-permission-keys.test.ts` that no key seeded by a migration is missing from the catalog superadmin reads (so a materialized org_admin cannot exceed it). The live suite also proves the resolver over the real store never caches a superadmin set, the two triggers refusing each other's race on two connections, definer rights (the app role in the platform org's context pointing at a tenant's membership), and the CLI's revoke of a suspended holder against its grant refusing one. Isolation from a tenant is asserted on the `role` table only. On the dev stack the session resolved 988 permissions (before the withheld keys were removed) and listed 0 of the demo tenant's patients; that check was made by hand, not by a test.
