# ADR-0076 — The supervisor's unacknowledged queue: one read-only list of every request still waiting for a human, restricted rows instead of hidden ones, narrowing-only filters and ops gauges

- **Status:** **Accepted** (2026-10-19; decisions closed in the WP 4.9 blueprint). **The thresholds, the ordering, who counts as a supervisor and what a restricted row still shows are PROVISIONAL: no clinical-lead sign-off recorded** (brief section 11).
- **Date:** 2026-10-19
- **Phase:** Messaging Hub Phase 4 (WP 4.9, Unacknowledged-urgent queue).
- **Implements:** `docs/messaging-hub/04-phases-4-to-6.md` WP 4.9 (`GET /escalations/unacknowledged` plus a supervisor screen; ops dashboard and alerts on overdue count and ack latency; acceptance: "Supervisor sees every pending/overdue item in their scope; none hidden by filters"). Closes the items earlier WPs deferred here: the "supervisor work item" of [ADR-0071](ADR-0071-messaging-delivery-failure-handling.md) (until now only an alert) and the visibility of `route_unavailable` / `ladder_exhausted` / `failed_unreachable` requests ([ADR-0070](ADR-0070-messaging-escalation-timers.md)).
- **Extends:** [ADR-0069](ADR-0069-messaging-acknowledgment-request-aggregate.md) (the aggregate; a supervisor still cannot acknowledge, reassign or resolve), ADR-0070, ADR-0071.
- **Numbering note:** the index still has two ADR-0069 files and a missing number between 0071 and 0073 (pre-existing irregularities that `arch:adr-docs` reports). 0076 is the next free number after ADR-0075; this branch adds no `arch:adr-docs` violation naming 0076.

## Context

Checked in the code, not assumed:

- Until now a supervisor learned of a stuck request only from a generic in-app alert (`m36.ack.ladder_exhausted`, `m36.ack.failed_unreachable`) sent to the seeded role audience `clinical_supervisor` / `don`. There was no list, so an alert that scrolled away left the request invisible.
- `message_acknowledgment_request` already has the partial index `message_ack_request_open_deadline_idx (organization_id, deadline_at) WHERE status IN ('pending','escalated','failed_unreachable')`: exactly the queue's rows in exactly its order. No migration is needed.
- The supervisory permission already exists: `messaging.review` (migration 1103) is held by `clinical_supervisor`, `director_of_nursing`, `don` and `clinical_lead` and withheld from the full-catalog admin roles. It is the same audience the alerts above reach.
- `canViewChannel` (the check the rest of M36 uses) requires an active channel membership and re-asks the Part 2 gate. A supervisor is typically **not** a member of every patient's care-team channel, and there is no supervisor read override (ADR-0069). So for most requests the viewer cannot open the thread.
- The repo has a Prometheus registry (`/metrics`, `bootstrap/metrics.ts`) with platform-wide gauges fed by the audited active-org enumerator (`geocode-coverage.ts`), and an org-less ops notice sink (`platform-ops-notices.ts`: an always-on log line plus the optional `OPS_ALERT_WEBHOOK_URL`). It has no Alertmanager rules, no Grafana and no per-tenant label convention.

## Decisions

1. **One read-only list, in the organisation.** `GET /api/v1/messaging/escalations/unacknowledged` (permissions `messaging.read` and `messaging.review`; a clinician without the second gets the contract's 403 and keeps the per-channel list they always had). Scope is the caller's organisation (RLS plus an explicit organisation predicate). It writes nothing, emits no event and never acknowledges. No flag and no migration: with the ack flags off no request exists and the answer is an empty, complete list; a request that exists while a flag is later switched off is still listed (stranding it would be worse).
2. **What is in the queue.** Requests whose status is `pending`, `escalated` or `failed_unreachable` (the partial index's set). `acknowledged` is open but has an owner; `resolved` and `cancelled` (the state a deleted message leaves) are closed. Overdue means the current window's deadline has passed, computed at read time on the service clock; `failed_unreachable` is listed whether or not it is overdue, because every route to it failed.
3. **Order: oldest deadline first** (overdue longest first, then soonest due), a total order with a hash tie-break. Provisional: a clinical lead may prefer failed_unreachable or urgent-class first; the counts and the `status` filter already put them one click away.
4. **Nothing is hidden by a filter, by paging or by visibility.**
   - The default view is everything. The only filters are `status` and `overdue`, and both are fields every row shows, so a filter can only narrow. An unknown query key, an unknown status or an out-of-range limit is a 422 (never silently ignored); a malformed cursor is a 400 `INVALID_CURSOR` (never a first page).
   - Every response states `counts.unfiltered` (every waiting request in the organisation, whatever the filters), `counts.matching`, `counts.overdue`, `counts.failed_unreachable`, `filtered` and `complete` (no further page). The web screen always says "Showing x of y".
   - Paging is keyset on `(deadline_at, sha256(id))`: stable under inserts between pages (a request that arrives after page one is found from its position onward; none already read is repeated), and the cursor carries **no request id** (decision 5). Live proof: paging at limits 1, 2, 3, 7 and 100 reproduces the default list exactly, including three requests that share one deadline.
5. **Restricted rows, not missing rows.** Channel visibility is re-checked for the caller on every distinct channel of the page. A request the caller cannot open (not a member, a Part 2 patient they are not released to, or a visibility check that throws, which fails closed) is still returned and still counted, as a `restricted` row with the request, channel, message, patient **and assignee ids withheld**. It keeps what a supervisor needs to chase it without learning who it is about: the assignee's display name, the class, the status, the requested/deadline instants, overdue and overdue seconds, the tier, the escalation note and the delivery-failed flag. The counts include restricted rows as numbers; no id is counted or revealed. **Why not drop them:** a request nobody on the call list can open is exactly the one that goes unnoticed. **Why not show everything to `messaging.review`:** that would be a supervisor read override of the conversation, which ADR-0069 deliberately does not have; a row's ids are the handle to a patient's conversation. **OPEN for the clinical lead and compliance (not decided here, behaviour unchanged):** restricted rows still disclose the assignee's name, class, tier, escalation note and times, and the counts include rows the viewer cannot open. For Part 2 gated channels this may need redaction (collapse to "restricted, overdue by N"). **Ceiling / provisional:** the assignee's name on a Part 2 request reveals that some request exists for that clinician (no patient is named); the stricter reading (no name, no class on restricted rows) is a one-place change in `unacknowledged-service.ts` (brief section 11).
6. **What a visible row carries.** Ids (request, channel, message, patient), class, status, assignee id and display name, `requested_at`, `deadline_at`, `overdue`, `overdue_seconds`, `current_tier`, `escalation_note` (`route_unavailable` / `ladder_exhausted`, the same read-time derivation as the card) and `delivery_failed` (= status `failed_unreachable`). **No message body, no patient name, no MRN, no label** (the review queue shows patient labels; this queue does not, because its job is chasing the assignee, not reading the chart). The patient id is in the response only so the read-audit accounting can attribute the disclosure; the screen never renders it. The deep link is the existing `/messaging?channelId=&messageId=`.
7. **Read audit.** The list is audited as a multi-patient single read like the lifecycle review queue: one `message_acknowledgment_request.viewed` event per distinct patient the page discloses (`patientIdsPayload`). The audit plugin needs one resource id per call and a restricted row has none, so the response carries `audit_request_id` (the first request shown in full; null when none is). That keeps the trail alive when the oldest row is restricted; a page that shows nothing in full discloses nobody and emits nothing. A 403, a 422 and an all-restricted page write no audit row (live-asserted).
8. **Ops numbers, minimal and real.**
   - Gauges on the existing `/metrics`, registered for every role like `geocode-coverage`: `wardenx_m36_ack_overdue_total`, `wardenx_m36_ack_failed_unreachable_total`, `wardenx_m36_ack_oldest_overdue_seconds`, `wardenx_m36_ack_latency_samples` and `wardenx_m36_ack_latency_seconds{stat="mean"|"max"}` (acknowledgment latency = `acknowledged_at - requested_at` over the trailing 24 h; the original request time is kept across a reassign, so a reassign does not hide a slow response). They are platform-wide sums and maxima over the active organisations (an audited platform read of the organisation list only; each figure is a count under that organisation's RLS). **No organisation, user, request or patient label**: the only label is the fixed two-value `stat`. An organisation that cannot be counted makes the whole reading `-1` (not measured), never `0`. One read is shared by the gauges and by scrapes within 30 s; the organisations are read four at a time, under their own audited platform job id (`m36.ack_queue_metrics`), and a sample that takes longer than 8 s reads `-1` for every gauge so a hung database cannot hang a scrape (the abandoned query is not cancelled).
   - **`/metrics` exposure (checked):** the route is unauthenticated in the application (the `/health` / `/ready` posture) and `deploy/production/nginx/wardenx-backend.conf` answers `location = /metrics { return 404; }`, so it is not reachable through the public proxy; it is for internal scraping on the backend port. The gauges are counts and maxima only, so an internal reader learns volumes, never a request, patient or tenant.
   - A threshold notice through the existing ops notice sink (log line plus the optional `OPS_ALERT_WEBHOOK_URL`), evaluated once per organisation per minute by the existing `messaging.ack_escalation_sweep` job, **whatever the escalation flag says** (an overdue request while the escalation action is off is exactly when ops should hear of it). Kinds: `m36.ack.queue_overdue` (the longest-overdue waiting request is at least 15 minutes past its deadline) and `m36.ack.latency_high` (mean latency of the last 24 h at least 15 minutes, with at least five acknowledgments). A breach notifies once, repeats at most hourly while it lasts and re-arms on recovery. **The dedupe is per process, not fleet-wide:** the sweep runs on whichever worker takes the job, so with several workers or after a restart the same breach can notify again immediately; "at most hourly" holds only within one process. The notice carries the organisation id and counts only. A failing read is reported through the worker's error hook and never fails the sweep. Constants are in `bootstrap/ack-queue-metrics.ts`.
   - **Honest limits:** there is no Alertmanager or Grafana in the repo, so "dashboard and alert rules" are the gauges plus the notice; the ops runbook lists the gauge names for whoever scrapes them. Percentiles are not offered because they cannot be merged across organisations (mean and max can). The notice state is process-local: a restart, or a different worker taking the sweep, re-notifies. The sweep runs only where the worker role and `DATABASE_PLATFORM_URL` exist (as the escalation sweep itself).
9. **The screen.** `/messaging/unacknowledged` (`messaging.unacknowledged`, nav group General, `requiredPermission: messaging.review`; the API demands `messaging.read` as well, and a 403/404/401 shows a plain "not permitted" / "sign in again" with no list). A flat list on the shared kit (page header, state pills, buttons): a status pill in words (Waiting / Escalated / Could not be delivered), "Overdue by 12 min" or "Due in 5 min", class, tier, assignee, the note, a link into the thread, and for a restricted row the plain sentence that the viewer cannot open it. Filters are toggle buttons with `aria-pressed`; the polite status line states the totals; empty, filtered-empty (with "Show everything waiting"), loading, error with Retry and a stale-list banner exist. It refreshes through the thread's own safety-net poll (15 s, backs off after failures, pauses in a hidden tab, re-reads on focus) and stops on unmount; "Show more" appends the next page with the server cursor. It never writes.
10. **Wording is data.** Every string is in `unacknowledged-wording.ts`; the page says it does not page anyone and is not the emergency path.

## Alternatives considered

- **A `supervisor_work_item` table** (ADR-0071's alternative). Rejected again: the request in one of the three statuses is the item; a second table would be a second truth.
- **A new permission `messaging.escalations.supervise`.** Rejected for now: it needs a migration to seed the key and re-grant roles, and `messaging.review` is already the supervisory audience of the same alerts. Revisit if the clinical lead wants queue access split from the lifecycle review.
- **Drop rows the caller cannot open** (the lazy reading of "scope"). Rejected: it hides the very requests nobody around can open (decision 5).
- **Show every row in full to `messaging.review`.** Rejected: a supervisor read override of patient conversations is not decided (ADR-0069 open item).
- **Offset paging / `channel_id`, `assignee`, `class` filters.** Rejected: offsets skip or repeat under inserts; those filters are not fields a restricted row shows, so applying them would be an existence oracle on restricted rows.
- **A Prometheus histogram observed at acknowledgment time.** Rejected for now: it needs the ack service to know the registry and would record before commit; the trailing-window mean/max is read from committed rows.
- **A per-organisation label.** Rejected: unbounded cardinality for the platform and tenant identity in a scrape.

## Consequences

- A supervisor who is not a member of a patient's channel sees that the request exists, how late it is and whom to call, but cannot open it. Giving them a way in is a separate decision.
- The first page costs two index-range reads (counts and rows) plus one visibility check per distinct channel and one name lookup per distinct assignee (both bounded by the page size, at most 100).
- A new organisation-wide number appears on `/metrics`; it is a count, never a list.
- The operator procedure that uses this queue when delivery fails, and its quarterly drill, is [`docs/runbooks/messaging-escalation-fallback.md`](../runbooks/messaging-escalation-fallback.md) (WP 4.11).

## Known ceilings

- **Span cap on refresh:** the screen's 15 s poll re-reads the whole loaded list by chaining cursor pages of up to 100 rows, at most 10 requests (1000 rows) per tick. A list the person extended beyond that restarts from the top on the next refresh and the screen says so ("Show more" loads the rest); until then a tick can cost up to 10 requests. The poll waits while "Show more" is in flight, and "Show more" supersedes any read already in flight.
- **Cursor integrity:** the cursor is opaque and strictly validated (shape, a real instant, a 64-hex tie) but **not signed**: the codebase has no cursor/token signing helper and this ADR does not invent key management. A caller can forge a cursor from a hash, which only moves where *their own* organisation-scoped, permission-checked list resumes; it cannot reach another tenant (every statement names the organisation) and the hash of a request id reveals nothing. A signed cursor is the upgrade if that ever matters.
- Percentiles of acknowledgment latency; per-tenant dashboards; a real alert-rule file.
- `audit_request_id` is an API field that exists for the audit plugin's one-resource-id limit.
- The channel and name checks run sequentially per page (bounded at 100); a batch visibility API would make them one call.
