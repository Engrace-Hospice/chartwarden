# ADR-0100 — Commercial hospice billing is its own module (M41), submitting only through the shared `ClearinghouseTransport`; M23 stays Medicare-FFS-only

- **Status:** **Accepted** (2026-10-24; proposed 2026-10-23). The product owner chose "new module 41 — Billing — Commercial" on 2026-10-23. D1-D10 are ratified. No billing expert was available, so the product owner directed that professional judgement be used: every billing-domain fact the proposal marked UNVERIFIED was checked against the primary sources named in "Billing facts review" below and either corrected or restated as a **confirm-with-payer-contract** item. Those items are configuration the tenant supplies per payer (they live in the M41 plan, route and rate tables), not open blockers; live sending still stays off until D10's enrollment and sandbox gates pass.
- **Date:** 2026-10-23
- **Phase:** post-launch billing work (commercial claim lane); follows the Medicare submission-path decision.
- **Related:** [ADR-0053](ADR-0053-clearinghouse-transport-port.md) (one `ClearinghouseTransport` port; conformance is the definition of done), [ADR-0005](ADR-0005-manifest-single-source-of-truth.md) (manifest is the source of truth; one ADR per module), [ADR-0052](ADR-0052-dde-work-queue.md) (Medicare-only DDE queue, unaffected), [ADR-0010](ADR-0010-tenancy-rls-invariants.md) (RLS keyed on `app.org_id`). Plan: `docs/audits/billing-e2e/IMPLEMENTATION_PLAN_20261023.md`, Track 6.
- **Amends:** the Module 23 spec decision D15 (Medicare FFS only; its guard is kept, and its "commercial billing out of scope" pointer now names M41) and the Module 25 spec decision D9 ("Commercial Phase 2" starts). These are module specs, so this ADR wins on conflict until they are re-locked.

## Context

Facts read from the repo on 2026-10-23:

- M23 rejects any claim whose primary payer on a service date is not Medicare FFS, with `NON_MEDICARE_PRIMARY_PAYER`, and points to Medicaid (M24) or "commercial billing (out of scope for Phase 1)" (M23 spec D15).
- Commercial exists today only as data: a payer kind in M40 (`packages/db/src/schema/mdm/payers.ts`, table `payer`), the `m25_payer_kind` enum on `remittance_advice`, and patient payer ranking in the M23 claim-assembly seam (a commercial payer at rank 1 makes Medicare not primary). There is no commercial claim, submission, acknowledgment, authorization or eligibility code.
- M25 receives commercial 835s as a discriminator value but has no commercial claim owner and no payer-keyed candidate provider, so a commercial advice yields zero automatic matches and goes to manual review (`25-remittance/ingest/service.ts`; M25 spec D9: "Commercial Phase 2").
- `ClearinghouseTransport` lives in `packages/x12-837-client`, a code path of M23. Any module that imports it or the 837I builder needs `dependsOn` to include 23 (the dependency-cruiser boundary rule enforces this).
- Module ownership is enforced by the manifest. Adding a module is a deliberate architecture change: one ADR, then the manifest (`.ts` and `.cjs` mirror), then `bun run scaffold` (ADR-0005 D5; `docs/DEVELOPMENT.md`).

## Decisions

**D1 — A new module, M41 "Billing — Commercial".** Commercial hospice billing gets its own module with its own tables, routes and UI. M23 is not extended and D15's guard stays true, so a non-Medicare-primary claim is still refused by M23 with a message that now names M41. Rejected: extending M23 (loosens a safety guard and mixes Medicare rules with payer-contract rules); deferring (commercial would stay outside the system).

**D2 — Dependencies: `[1, 23, 40]`.** M1 foundation; M23 for the shared 837I builder and `ClearinghouseTransport` in `x12-837-client`; M40 for the payer master. M41 does **not** import M23's or M40's schemas. Claim facts (coverage, election, diagnoses, visits, charges) come through M23's existing claim-assembly seams and an M40 payer-master seam (exact export is an open question: today the only payer definition found is the `packages/db/src/schema/mdm/payers.ts` schema, which M41 must not import), per the cross-module rule (seam or outbox event, never a schema import). M25 gets **no** new `dependsOn` edge: it reads commercial claims through a `CommercialClaimReader` seam in `@chartwarden/types`, mirroring M23's `ClaimSubmissionReader`.

**D3 — Code paths: the two app directories only.** `apps/backend/src/modules/41-billing-commercial` and `apps/web/src/modules/41-billing-commercial`. No package until a second consumer exists (YAGNI). There is no commercial adapter package: submission is the transport, not a per-payer adapter.

**D4 — Submission only through `ClearinghouseTransport`.** M41 calls `submitClaim`, `checkEligibility`, `fetchAcknowledgments` and `fetchClaimStatus` on the platform binding. There is no direct-to-payer channel and no per-payer HTTP client. An unbound transport answers `CH_NOT_WIRED` and nothing is sent.

**D5 — Enrollment gates every send, per payer and per provider entity.** Enrollment is per payer and per provider regardless of vendor (ADR-0053 D8). M41 records it in `commercial_payer_enrollment` and refuses to enqueue a submission for a payer the active clearinghouse does not route or for a provider entity that is not enrolled. The refusal is a stable code and a user-facing message; no queue job is created. There is no fallback to another clearinghouse.

**D6 — Hospice claim shape is payer-contract driven.** The claim is an 837I (X12 005010X223A2) with a claim filing indicator (SBR09), the payer id the chosen clearinghouse routes on (loop 2010BB NM109), payer-specific edit rules and contract rate terms, all held per tenant in `commercial_payer_plan`, `commercial_payer_route` and `commercial_contract_rate` (issue #721, migration 1260). Pre-authorization is a first-class check (`commercial_authorization`); a plan whose authorization requirement is unknown is stored as `confirm_with_payer` and the send gate treats it as required. The default code set is the standard hospice one: type of bill 081x (non-hospital-based hospice; 082x when hospital-based) and revenue codes 0651 routine home care, 0652 continuous home care, 0655 inpatient respite, 0656 general inpatient. Payers commonly follow that set but a contract can differ (HCPCS site-of-service lines such as Q5001-Q5010 that Medicare requires may or may not be wanted, continuous-care billed per hour or per diem, physician services under 0657), so each rate row stores the revenue code and rate basis its contract uses and nothing is inferred from Medicare's rules. The commercial claim filing indicators M41 accepts exclude government and self-pay codes (see the review below).

**D7 — Coordination of benefits is explicit, and Medicare Advantage is not commercial.** When Medicare or Medicaid is secondary, the commercial claim carries the COB data and M41 does not emit a Medicare claim as primary. A Medicare Advantage enrollee who elects hospice is **not** an M41 patient: Original Medicare pays the hospice, so the claim goes to the Medicare Administrative Contractor through M23, not to the plan (42 CFR 422.320(c)); M41 refuses a plan for a payer whose M40 kind is not `commercial`, enforced in the database. Which commercial patients exist (for example under-65 members, or Medicare-eligible patients whose employer group plan may be primary under the Medicare Secondary Payer rules) is decided per patient from the coverage ranking and a payer eligibility check (270/271); that is data, not an assumption in code.

**D8 — Remittance matching is owned by M25, fed by M41.** M41 supplies claim ownership through the `CommercialClaimReader` seam; M25 adds a payer-keyed candidate provider for `payerKind: "commercial"`. Auto-post only when the match is certain, otherwise manual review. A commercial advice for another tenant or payer quarantines and posts nothing. This starts M25 D9's "Commercial Phase 2".

**D8 amendment (issue #725, M25 D9 "Commercial Phase 2" is now live).** The seam is `CommercialClaimReader` (owner M41, PHI, fail-closed deny-stub), registered at boot by `registerM41PublishedSeams` and consumed by M25's `buildM41BackedClaimMatchCandidateProvider` for `payerKind: "commercial"`. No migration and no new table: M41 already owns `commercial_claim` and `commercial_payer_plan`. The rules, each proven live as the NOBYPASSRLS `chartwarden_app` role (`m25-commercial-remit-matching.live.test.ts`):
1. **Payer-keyed.** M25 now passes the advice's `payerId` to every candidate lookup (Medicare and Medicaid ignore it). A commercial candidate must belong to a plan whose `payer_id` equals the advice's payer, in the advice's organization and provider entity. A missing `payerId` means no candidates.
2. **Only a sent claim can be paid.** Candidates are claims in `submitted`, `ack_pending` or `accepted`; a draft, ready, rejected or void claim is never a candidate.
3. **Certain match only.** A commercial claim holds no payer ICN or member id in this lane, so only CLP01 equal to the claim control number (unique in the database) can auto-bind, at confidence 100. Everything else, including the heuristic strategy, is manual review. A wrong payer, a wrong tenant or a wrong provider entity yields no candidate: the line is `unmatched`, nothing posts, no ledger row is written, the claim is untouched.
4. **Exactly once.** A redelivered 835 is a duplicate on its ISA/ST keys and a second post of the same advice is `already_posted`.
Not in this slice: moving a commercial claim to `paid`/`adjudicated`/`denied` from the posting events (those states do not exist yet in `commercial_claim`; they need a migration and an M41 outbox consumer of `m25.remittance.*`, tracked separately).

**D9 — Same safety rules as M23.** Idempotency key on every mutating route; validation results with rule id, severity and evidence; hard blocks that cannot be overridden without a policy change; audited overrides with permission, reason and step-up; "submitted", "acknowledged", "adjudicated" and "paid" are distinct states; a duplicate 835 cannot double-post.

**D10 — Delivery order and gates.** (1) This ADR, the spec and the skeleton. (2) Payer and plan model, enrollment and authorization tables. (3) Assembly and validation. (4) Submission through the transport, after the Medicare submission-path decision wires the binding into workers. (5) Eligibility. (6) Remittance matching. (7) UI. Live sending stays disabled until payer enrollment, sandbox testing with synthetic data and a billing review pass.

**D11 — Who may send a commercial claim: `commercial_billing.submit` follows `billing.claim.submit` (decided 2026-10-26, #817).** Migration 1274 granted the key to every role that already holds the Medicare analogue, plus the three roles 1265 named (compliance_officer, administrator, org_admin). We keep that and do not narrow it. Reasons: (1) it is the same act, sending a claim to a payer through the same `ClearinghouseTransport`, and the tenants' claim-filing staff already hold the Medicare key by an administrator's explicit assignment, so a narrower set would either lock billing staff out of half their job or force a second, parallel assignment that nobody would keep in step; (2) the key is not the only control. The route also needs the claim's provider-entity and caseload scope (an out-of-scope claim is a 404), a FRESH step-up, a human actor (an AI actor is refused) and an Idempotency-Key, and nothing is sent unless the claim is enrolled, routed, validated and the drain is scheduled; (3) the blast radius is bounded: nothing leaves the process by default (unbound transport answers `CH_NOT_WIRED`, the 837I parties source is not bound), and an ambiguous send is never resent. The grant is a one-time copy, not a live coupling: a role given the Medicare key later does NOT get the commercial one automatically, so each tenant widens it deliberately. A fresh tenant gets the key only through compliance_officer (explicit), administrator and org_admin (catalog); `commercial_billing.submit` is in no clinical, auditor or platform template (pinned by `packages/auth/src/roles/commercial-submit-grant.test.ts`; the route's permission, step-up, AI and caseload refusals by `m41-commercial-submission-routes.test.ts`). Revisit D11 when live sending is enabled for a tenant (list the holders of the key per tenant first), and if a tenant reports a Medicare filer who must not send commercial claims: that is a per-tenant role edit, not a platform default.

## Consequences

- `architecture/module-manifest.ts` and `.cjs` gain module 41; `docs/modules/README.md` and `scripts/check-module-docs.ts` move from 40 to 41 modules; `bun run scaffold` creates the two empty directories.
- Issue #721 adds migration 1260 and three owned tables (`commercial_payer_plan`, `commercial_payer_route`, `commercial_contract_rate`), so the manifest now lists 14 proposed tables for M41; the remaining 11 land with their own migrations, RLS and audit triggers, checked by `arch:tenancy` and `arch:migration-numbering`. No routes or events are added yet.
- Issue #722 adds migrations 1261 and 1266: seven owned tables (`commercial_authorization`, `commercial_claim`, `commercial_claim_line`, `commercial_claim_state_history`, `commercial_validation_run`, `_result`, `_override`), three permission keys, nine routes, three ABAC predicates and three `m41.claim.*` events (record-only). M23's `NON_MEDICARE_PRIMARY_PAYER` message now names M41 for a commercial primary.
- The submission slice (D10 step 4; migration 1274, the Medicare submission-path decision being ADR-0053 D10) adds `commercial_submission` and the claim states `submitted`, `ack_pending`, `accepted`, `rejected`, three routes (`POST .../claims/:id/submit`, `GET .../send-gate`, `GET .../timeline`), three events (`m41.claim.submit_requested`, `.submitted`, `.submit_failed`) and a submission drain worker. `ClearinghouseTransport` is the only path; unbound answers `CH_NOT_WIRED` and writes no submission row, so no job exists. `submitted` is written only from the transport's receipt. The 837I parties source (submitter, receiver, billing provider) still has no production binding, so a real send ends `failed` (`COMMERCIAL_837I_INCOMPLETE`) until it is bound: live sending stays impossible by default.
- Migration 1275 adds `commercial_acknowledgment` and `commercial_ack_cursor` (so the manifest lists 16 tables for M41 with the quarantine table below) and the `m41.ack-pull` worker: two stages, never conflated (a clearinghouse acceptance is `ack_pending`, only the payer stage is `accepted`); duplicates collapse on the vendor event id; events that are not this tenant's commercial submissions change nothing.
- An ambiguous send is never `failed` (ADR-0053 D5): it ends `in_doubt`, which is never resent automatically, holds the claim's single live slot, and has two exits: a later clearinghouse-stage acknowledgment, or a person's `POST .../reconcile` (permission `commercial_billing.submit`, fresh step-up, outcome only). All submissions of one claim share one transport key and a deterministic payload, so a second row replays the first receipt. `direct_mac` is refused for commercial claims. Acknowledgments that need attention and are not applied (malformed, another provider entity's, another clearinghouse's, or a payer answer for a row with no receipt, which is held and replayed) are stored in `commercial_ack_quarantine` (so M41 owns 16 tables in the manifest); events that are not commercial submissions at all are counted, not stored. What was sent is frozen by a payload hash, and a changed payload ends with `COMMERCIAL_PAYLOAD_CHANGED`. Migrations 1274 and 1275 were amended in place before any push: a database that applied the earlier text must be reset and the claim state machine is enforced by a database trigger.
- Drain readiness for `submit`/`reconcile` is read from shared state (both repeatable jobs present in Valkey, probed with a 2-second timeout), so a split API and worker deployment works and a Valkey outage cannot hang requests. It proves the schedules exist, not that a consumer is running: with the worker scaled to zero submissions are accepted and wait as durable rows until a worker returns. A transport answer flagged `ambiguous` (`DegradedError.ambiguous`: a timeout, a 5xx, sent-but-unrecorded) is never treated as a clean refusal even when its code is `CH_UNAVAILABLE`.
- Follow-ups (#818, #820): the readiness probe owns ONE Valkey client per probe cycle and ends it the moment a probe times out (a bare BullMQ `Queue` opens a hidden second connection and its `close()` waits for QUIT, so against a dead store it leaked a connection per cycle; proven live against a paused and a dead Valkey). Migration 1279 lets `scope_mismatch` and `vendor_mismatch` keep their validated event for replay and adds the resolution `applied_status_inquiry`; every abandoned held acknowledgment is the event `m41.claim.ack_abandoned` (record-only). The jobs now live in `ack-apply.ts` (apply one event), `ack-held-replay.ts` (replay and abandonment) and `ack-worker.ts` (the pull).
- The status matrix and UI parity reports need regenerating when the skeleton lands.
- Two adapters passing the same conformance suite (Track 4 of the plan) is a precondition for relying on the transport as the only submission path; M41 inherits that.

## Billing facts review (2026-10-24, replaces the UNVERIFIED markers)

Checked against primary sources without a billing expert; each line says what changed.

| Item | Finding | Source |
|---|---|---|
| Who is billed for hospice when the patient has Medicare Advantage | **Corrected.** Once an MA enrollee elects hospice, Original Medicare (the MAC) pays the hospice at the hospice rates; the MA plan stops paying for hospice-related care and keeps covering services unrelated to the terminal illness and any supplemental benefits. A hospice therefore never sends the hospice claim to the MA plan. The CMS Value-Based Insurance Design hospice-benefit test, which briefly returned hospice to some MA plans, ended with calendar year 2024. | 42 CFR 422.320(c); 42 CFR 418.24; Medicare Benefit Policy Manual ch. 9; Medicare Claims Processing Manual ch. 11 |
| Claim filing indicator codes | **Confirmed and bounded.** SBR09 carries the filing indicator: 12 PPO, 13 POS, 14 EPO, 15 indemnity, HM HMO, BL Blue Cross Blue Shield, CI commercial insurance, CH CHAMPUS/TRICARE, FI FEHBP, VA Veterans Affairs plan, WC workers' compensation, AM automobile medical, LM liability medical, DS disability, OF other federal program, 11 other non-federal, 17 dental maintenance organization, ZZ mutually defined. The plan guard accepts an active M40 payer of kind `commercial` or `other` (TRICARE, FEHBP, VA, workers' compensation). M41 refuses MA/MB (Medicare Parts A/B, M23), MC (Medicaid, M24), 16 (HMO Medicare risk), 09 (self-pay), 10 and TV. Which code a given payer wants is a **confirm-with-payer** value held in the plan. | X12 005010X223A2 (837I) code list 1032; NUCC/CMS code maintenance |
| Commercial hospice code set | **Corrected from "unknown".** Type of bill 081x/082x and revenue codes 0651/0652/0655/0656 are the NUBC hospice codes and are the default; 0657 (physician) and the HCPCS Q-codes are Medicare conventions a contract may or may not require. Rates, per diem versus hourly continuous care, and payer edits are **confirm-with-payer-contract** and are stored per contract, not coded. | NUBC UB-04 manual; Medicare Claims Processing Manual ch. 11 |
| Notice of election and timeliness | The 5-calendar-day NOE rule is Medicare's. Commercial notification and timely-filing windows are **confirm-with-payer-contract**; M41 stores no default. | 42 CFR 418.24; payer contract |
| Which patients have a commercial primary | Not a code fact. It follows the patient's ranked coverage and the payer's eligibility response. Under-65 members are the usual case; Medicare Secondary Payer rules can make an employer group plan primary for a Medicare-eligible patient, so the rank and the 271 decide, per patient. | Medicare Secondary Payer Manual ch. 1, 3 |
| Pre-authorization | Varies by plan and by level of care. Stored as `not_required`, `required_at_admission`, `required_per_level_of_care` or `confirm_with_payer`; the last is the default and blocks like "required". | payer contract |
| Enrollment and payer ids | A payer id is clearinghouse-specific and enrollment is per payer and per provider (ADR-0053 D8); both are tenant data in `commercial_payer_route` / `commercial_payer_enrollment`. | ADR-0053 |

**Notes for the next issues (honored by #722).** Route and rate periods are not bounded by their plan's period in the database, so claim assembly intersects plan, route and rate periods (a stretch with no rate in effect is an unpriced line that blocks). The payer guard runs on insert only, so a payer merged or deactivated afterwards is caught at read time: assembly and every re-validation run the hard rule `plan_payer_active` (through the `m41_payer_state` function, so M41 reads no M40 table) and name the surviving payer; plans are not rewritten behind the tenant's back. Per-hour rates are used only for continuous home care (database CHECK) and only from whole documented hours. A Medicare Advantage enrollee never reaches M41: the lane refuses any primary coverage that is not `commercial`, and the Medicare-contractor claim is M23's.

**Medicare Advantage coverage in M23 (issue #772, decided).** Hospice for a Medicare Advantage enrollee is an Original Medicare claim, but M23 stamps the coverage row's id on the claim and reads the MBI from that row, so a plan member id must never stand in for the MBI. The coverage is therefore modelled as a PAIRED `medicare_ffs` row (with the MBI) ranked 1 for the hospice benefit, alongside the Medicare Advantage row. A patient recorded only as `medicare_advantage`, or whose Advantage row outranks the Original Medicare row, is refused with the specific, actionable `MEDICARE_ADVANTAGE_NEEDS_ORIGINAL_MEDICARE_COVERAGE` (409) instead of the generic `NON_MEDICARE_PRIMARY_PAYER`. M23's refusal of a non-Medicare primary payer now names M41 for a commercial primary.

## Eligibility and enrollment (issue #724, migration 1265)

Built: `commercial_payer_enrollment`, `commercial_eligibility_check`, the per-plan `eligibility_staleness_policy` (`warn` by default) and `eligibility_max_age_days` (30 by default), the pure send gate `evaluateSendGate` (bound, routed, enrolled; codes `CH_NOT_WIRED`, `COMMERCIAL_PAYER_NOT_ROUTED`, `COMMERCIAL_PROVIDER_NOT_ENROLLED`) and the pure `evaluateEligibilityFreshness` for the assembly lane. The port's eligibility request gained a commercial shape (`memberId`); the payer is the context's routed payer id. The member id is read from M5's coverage seam for the one call and is never stored, returned or logged; relaxing a plan's policy needs `commercial_billing.manage_enrollment` and a fresh step-up.

**Known limits.**
- No vendor adapter answers a commercial 270 yet: the Stedi and direct-MAC transports answer `CH_NOT_WIRED` (not implemented) and Episode Alert refuses a member id (Medicare only). Only the in-memory test double answers, so a production check returns 503 until a vendor adapter implements it. Nothing is sent in the meantime.
- The 30-day staleness window is our default (matching M23's HETS window), not a payer fact; payers differ, so it is a per-plan setting. Which payers require a recent 271 before billing is a confirm-with-payer item, not asserted here.
- How a vendor's 271 maps to `active` / `inactive` / `unknown` for a commercial plan (benefit codes, hospice service type) is UNVERIFIED until a sandbox run; the port contract returns the three-valued outcome and anything unreadable must be `unknown`, which follows the plan's policy.
- An inactive answer blocks regardless of the staleness policy; whether a payer's "inactive" can be overridden for a retroactive-eligibility case is left to the override lane (#722).
- Eligibility checks hold a patient id, so the M4 eraser registration for them is still to do with the patient-erasure work; they hold no name, member id or 271 body.
- Two concurrent requests with the same Idempotency-Key can each send one 270 before the first row lands (one row is kept and the other request is answered from it, or refused if it differs). The M1 middleware serializes by key per organization; a worker retry path would need an advisory lock. Eligibility is a read-only query, so the cost is a duplicate vendor transaction, not a duplicate effect.
- Freshness for a claim must be asked with the claim's date of service (`latest(..., serviceDate)`): a check made for another date of service does not count. Without a service date the newest check of any date is used.
- `commercial_eligibility_check.location_id` exists for the three-column rule but is not set by the API yet (no M1 location reader is wired here).
- Rate limiting on the mutating routes relies on the platform-wide limiter; there is no per-route budget.
