# ADR-0069 — The acknowledgment request is its own aggregate: one request per message, an append-only history, four explicit transitions and a state machine the database enforces, with no timers, tiers or paging in WP 4.2

- **Status:** **Accepted** (2026-10-15; decisions closed in the WP 4.2 blueprint). **Every deadline number, the qualified-role map and the stricter readings below are PROVISIONAL: no clinical-lead sign-off is recorded.** The sign-off items are listed in `docs/messaging-hub/brief-clinical-lead-signoff.md` (section 5) and creating a request ships behind the ops flag `messaging.ack_requests`, default off.
- **Date:** 2026-10-15
- **Phase:** Messaging Hub Phase 4 (WP 4.2, Ack-request aggregate).
- **Implements:** [ADR-0056](ADR-0056-clinical-acknowledgment-vs-read-receipts.md) (the aggregate, its state machine, the D4 deadline table, the eligible roles, the edit lock). ADR-0056 stays **Proposed** until the clinical lead signs the numbers; this ADR records what was built and which of its open points were closed provisionally.
- **Extends:** [ADR-0068](ADR-0068-messaging-urgency-model.md) (the urgent entry creates the request in its own send transaction; the 4.1 note "delete must cancel the request" is met here).
- **Related:** [ADR-0057](ADR-0057-escalation-ownership-m19-m36.md) (who is paged and when is WP 4.3 - 4.5, not here), [ADR-0010](ADR-0010-tenancy-rls-invariants.md), [ADR-0011](ADR-0011-ownership-inversion-rls-bypass.md).

## Context

WP 4.2 (`docs/messaging-hub/04-phases-4-to-6.md`) is the aggregate that turns "an urgent message was sent" into "a named clinician took responsibility", with the routes `POST /escalations`, `/acknowledge`, `/reassign`, `/resolve`. Acceptance: open or read never acknowledges; an unqualified user cannot acknowledge; every transition is audited with the actor. WP 4.1 shipped a marker and one generic in-app alert and said plainly that nobody tracks whether the recipient acted; the flag `messaging.urgent_clinical` therefore stays off until 4.2 - 4.4 ship.

Facts that shape the design:

- Timers, tiers, the `EscalationRouter` seam, overdue handling, backup routing and delivery-failure handling are WP 4.3 - 4.5. WP 4.2 stores `deadline_at` and the state, exposes the transitions and emits events. Nothing in it times, routes, escalates or pages anyone.
- `message_receipt` keeps `delivered` and `read` only (WP 1.6). An acknowledgment is a different record on a different table, written by one explicit action.
- The 05 matrix: acknowledge clinical responsibility = a qualified role; an aide is receipt only; admin and compliance not by default.
- A message is immutable once urgent (ADR-0068) and, per ADR-0056 D8, once it has a request.
- Hazards: H-01 (urgent treated as handled when only delivered), H-02 (wrong recipient), H-09 (duplicate acknowledgment on retries).

## Decision

1. **Two tables, migration `1107_m36_message_acknowledgment_request.sql`.** `message_acknowledgment_request`: `message_id`, `channel_id`, `patient_id` (server-derived from the channel, scrubbed from the audit log), `ack_class`, `status`, `requester_user_id`, `assigned_user_id`, `requested_at` (never changes), `window_started_at` (equals `requested_at` until a reassign), `deadline_at`, `current_tier`, the acknowledged / resolved / cancelled stamps and `version`. `message_acknowledgment_event`: the append-only history (`event_type`, the actor or the system, from and to status, the assignee, the previous assignee, the tier). Both have RLS enabled and FORCED, the organization policy, an audit trigger (the request's is the PHI-scrubbing kind) and the destruction-role policy. `organization_id` plus the server-derived patient id is the tenancy shape of the handoffs (M36 carries no provider or location). **One request per message, ever** (a unique index on the organization and the message): the request binds to the message as sent. The `required_role` and `resolution_note_ref` columns of ADR-0056 are **not** created (a named individual only, as in 4.1; an outcome link is a later owner-module workflow).
2. **What the states mean.** `pending`: waiting for the assignee (and the state a reassign returns to). `acknowledged`: the assignee took clinical responsibility by an explicit action. `escalated`: the deadline passed and the request was routed to tier n (`current_tier` >= 1); **only WP 4.4 writes it**. `failed_unreachable`: every tier was exhausted or every route failed; **only WP 4.5 writes it**; it is never terminal in effect (a human acknowledges, reassigns or resolves it). `resolved` and `cancelled` are terminal. The event types `delivered`, `opened`, `overdue`, `escalated` and `delivery_failed` exist in the enum so 4.3 - 4.5 do not need `ALTER TYPE`; **WP 4.2 writes none of them** (a static test pins it, and in particular nothing writes `opened`: opening a message is not an event).
3. **The state machine, in code and in the database.** One table (`ACK_TRANSITIONS` in `packages/messaging/src/ack-requests/ack-rules.ts`): `pending -> {acknowledged, escalated, failed_unreachable, cancelled}`; `escalated -> {acknowledged, failed_unreachable, cancelled, pending}`; `acknowledged -> {resolved, pending, cancelled}`; `failed_unreachable -> {acknowledged, resolved, pending, cancelled}`; nothing leaves `resolved` or `cancelled`. Two same-status updates exist: `pending -> pending` is a reassign (a new assignee) and `escalated -> escalated` is a tier-up (the tier strictly increases). The BEFORE UPDATE trigger `message_ack_request_update_guard` repeats the table, makes identity, class, requester and `requested_at` immutable, demands `version = old + 1`, lets the assignee change only on a return to `pending`, and a window restart only with it. A pin test compares the SQL with the TypeScript table, so WP 4.4 cannot step outside it, and the live suite proves that the transitions 4.4 and 4.5 need (`pending -> escalated -> tier-up -> failed_unreachable -> acknowledged`) are accepted while the rest are refused. CHECKs tie `acknowledged_by` to the assignee, keep the outcome columns consistent with the status, and forbid an assignee equal to the requester; the trigger also reads the session's `app.user_id`, so **nobody acknowledges or resolves on another person's behalf even through a direct write** (the actor must be the assigned user), a reassign must be by the current assignee or, until the request is taken, the requester (once `acknowledged`, only the assignee can hand it on), a cancel by the requester, and an empty actor (a system write, WP 4.4 / 4.5) can only reassign or escalate. **This actor binding is a backstop against application bugs (a code path acting as the wrong person), not a defence against a compromised application role, which can set `app.user_id` to anything;** authentication and the service checks are the control and the audit trigger records the result. A second trigger, BEFORE INSERT on the history table, refuses an event that does not name the session's own user (a system event only from a session with no user) or whose `to_status` is not the request's own resulting status, so an event cannot be forged beside a real transition. The history's DELETE exception for the destruction role also survives the referential cascade from a request or message it erases (the cascade runs as the table owner, so the trigger recognises the session's own role: `session_user` membership of `wardenx_destruction` for a non-superuser login, or the `role` setting); `wardenx_app` still cannot delete anything (live test). A window can only start within five minutes of the database's `now()` (insert and reassign), because the platform maximum is relative to the window start and a forged start would stretch the deadline. A BEFORE INSERT trigger requires the patient to be the care-team channel's own subject, the requester to be the message's author, the message to be live, the class to follow the message (an `urgent` request names the urgent recipient; `critical_symptom` has **no writer**), and the assignee to be an active member of the organization; it lets an existing row through so a caller's `ON CONFLICT` replay is never defeated by it.
4. **Deadlines (ADR-0056 D4), provisional.** Platform defaults and maxima per class in minutes: `important` 60 / 120, `urgent` 15 / 30, `critical_symptom` 5 / 10 (`ACK_DEADLINE_POLICY` in `@wardenx/types`). The default is applied at create and again at each reassign. The maximum is a database CHECK relative to `window_started_at`, pinned to the constants by a test, so no code path can store a longer window. **Tenant tightening is deferred**: it needs a policy table with its trigger, an admin route and screen, audit and the clinical lead's numbers, none of which fits 4.2; the platform values and the immutable maximum ship. A reassign restarts the window for the new assignee (status back to `pending`, tier 0, a new default deadline) and keeps `requested_at`, as ADR-0056 requires.
5. **Creation, two paths, one class rule.** (a) The urgent entry creates the request **in the same transaction as the message** through the send core's `inTransaction` hook when `messaging.ack_requests` is on (read just before the send; the urgent entry is unchanged when it is off). A failing publisher rolls the message back with its request (live test). (b) `POST /api/v1/messaging/escalations` with `message_id` and `assigned_user_id`: the caller must be the message's author, the message live and in a patient care-team channel, and the assignee a care-team member who can see the channel, holds `messaging.urgent.receive`, passes the Part 2 gate and is not the caller (one uniform 422 `ACK_ASSIGNEE_INVALID`, no reason named). **The class is derived** (an urgent message gives `urgent` and the assignee must be its named recipient; any other message gives `important`); the body has no class, status, deadline or role field. An existing request for the same message, requester and assignee replays with 200 **before eligibility is re-run**; a different assignee is 409. `important` is therefore created by this route for an existing message the caller wrote; **the composer control for `important` is deferred** (it needs a recipient chooser that does not depend on the urgent flag; the user's decision was to build the backend and a minimal web slice only if clean). `message.urgency` stays `routine` for such a message (the column is immutable, ADR-0068); the class lives on the request.
6. **Authorization, per action, re-decided on every call from the stored request and the caller's live qualification.** No new permission key: creating needs `messaging.send` and `messaging.urgent.send` (the 05 matrix "initiate urgent escalation"); acknowledge and resolve need `messaging.urgent.receive` **and** the caller must be the assigned user **and** still qualified now (active, the keys, the Part 2 gate for the channel's patient, able to view the channel); so an aide, the author, another recipient, a supervisor, an outsider and another tenant all refuse and write nothing. A lookup error while checking the assignee **propagates** (the caller retries); only a clean "no" is a refusal. Reassign is for the **current assignee** (any open state, with **no qualification check**, because a hand-off must never strand the item when the assignee's own role lapsed) or the **requester only until the request is taken**; the requester must still hold `messaging.send` and `messaging.urgent.send` right now (a lookup error propagates), and once `acknowledged` a requester gets 403 `ACK_NOT_ASSIGNEE` (the database mirrors the rule). The earlier acknowledgment stays in the event history when the assignee hands the request on (live test). The new assignee passes the create checks and differs from the current one and from the requester. **No supervisor override in 4.2** (stricter than the matrix's "team lead if qualified"; oversight is the WP 4.9 queue). Reading a request needs `messaging.read` and sight of its channel; a missing, malformed, other-tenant or hidden-channel id is one 404.
7. **Idempotent and race-safe.** A repeated acknowledge by the person who acknowledged, resolve by the person who resolved, or reassign by the actor who just did it is 200 with `changed: false`: no write, no event, no outbox row. Every transition runs in one transaction that locks the request `FOR UPDATE` and compares `version`; a lost race becomes the repeat answer or 409 `ACK_STATE_INVALID`. Resolving before acknowledging is 409 `ACK_NOT_ACKNOWLEDGED`. A concurrent triple acknowledge leaves exactly one event (live test).
8. **Routes**, all under `/api/v1/messaging`, registered from `routes/ack-routes.ts`: `POST /escalations`; `GET /escalations/:id` (the request and its history); `GET /channels/:id/escalations` (the channel's requests for the thread card: **every open request first** so an old unanswered one never falls off, then the most recent closed ones up to a total of 100; each carries `viewer_actions`, a hint from identity and state that is never an authorization); `POST /escalations/:id/acknowledge`, `/reassign`, `/resolve`. Create requires an `Idempotency-Key`. Every route is read-audited with a resource id (the request, or the channel for the list) and the patient where the payload carries it; every transition is audited **with the actor** twice over: by the database audit trigger (the app sets `app.user_id` for the transaction) and by the event row.
9. **Flag.** `messaging.ack_requests` (ops flag, default off, absent = off) gates **creating** a request, on both paths. **A failed flag read is not "off":** on the explicit `POST /escalations` it is 503 `ACK_UNAVAILABLE` (logged; never a fake 404 "message not found"), and on the urgent send it fails the send closed (an urgent message never silently loses its request on a blip). Acknowledge, reassign, resolve and the reads of a request that already exists stay available when the flag is off: stranding an open safety item behind a flag switch is worse than the flag being a soft off. **Both flags, `messaging.urgent_clinical` and `messaging.ack_requests`, stay off for every tenant until WP 4.2 - 4.4 ship** (there is no timer, so nothing yet makes an unanswered request visible beyond its card). They exist for development and sign-off review only.
10. **Delete cancels.** `deleteMessage` cancels the message's open request **in the same transaction, before the tombstone**, with an event naming who deleted the message and `m36.ack.cancelled` (plain SQL in `ack-cancel.ts`, so no flag or service wiring can strand a request). A BEFORE UPDATE trigger on `message` refuses to tombstone a message while its request is open, so a future delete path that forgets fails loudly; a request raised in the instant between the cancel and the tombstone (a race) surfaces as 409 `ACK_MESSAGE_HAS_OPEN_REQUEST`, not a 500 (live test). Database guards that fire on a race in the other transitions are mapped to 409 only when they are the migration's own guards, by constraint or trigger name, and logged by name with ids only; any other check violation stays a logged server fault. The same trigger refuses an edit once a request exists (the service answers first with 422 `ACK_MESSAGE_NOT_EDITABLE`); body re-encryption updates are untouched. A correction is a new message.
11. **Events (outbox-only, ids and one instant, no patient, name or text).** `m36.ack.requested`, `.acknowledged`, `.reassigned`, `.resolved`, `.cancelled`, each published in the transition's transaction (an idempotent repeat publishes nothing). Payload: organization, request, message, channel, class, assignee, actor (nullable for the future timers), request version, instant (reassigned adds the previous assignee). The ADR-0056 names (`m36.ack_request.created.v1` and so on) are superseded: the catalog has no version suffix and the lifecycle the plan lists is these five; `.overdue` and `.failed_unreachable` arrive with WP 4.4 / 4.5.
12. **One alert per request and assignee, never a duplicate of the 4.1 alert.** The urgent class keeps `m36.message.urgent_sent`'s alert (`urgent:<message>:<recipient>`); the consumer `m36.ack-notifications` is silent on `m36.ack.requested` for it. It alerts the assignee of an `important` request, and the **new assignee of a reassign** (any class). At consume time the request must still be **waiting (`pending`)**, still assigned to the recipient **and still at the event's `requestVersion`** (a stale event alerts nobody, including one for a request that was taken since), the recipient must still see the channel and still be qualified; a clean "no" is an id-only warn-level skip and **a lookup error is rethrown** so the outbox retries. The correlation id is `ack:<request>:<version>:<assignee>`. In-app only (two seeded, non-locked rules); fixed provisional text with no name, patient or message text. Nobody is told on acknowledge, resolve or cancel in 4.2 (the sender's view arrives with the WP 4.9 screens; those three events have no consumer and are not in the deferral list because they declare none).
13. **Rate limit (provisional).** Create and reassign (the two that notify somebody) are limited fail-closed: 20 per minute per user, 200 per minute per organisation, 5 per 5 minutes per (actor, colleague) pair, keys only from validated UUIDs, no replay exemption (a refused request pays again). Acknowledge and resolve notify nobody and are not limited.
14. **Web.** A card under a message that has a request in a patient care-team thread: status in text and icon, the deadline, "Take responsibility" (only when `viewer_actions.can_acknowledge`) and "Close this request" (only when `can_resolve`), a permanent notice that taking responsibility is an explicit action, that opening or reading the message does not do it, that it pages nobody and is not the emergency path. Each failure has its own words (no answer, 408 and 5xx: may not have been saved; 429: wait; 401: sign in; 403: role cannot take or close it, or not permitted; 404: no longer available; 409: changed; 422: could not be accepted) and the list is re-read; the busy state holds until that reload settles; a transient reload failure keeps the last good requests of the channel with a "may be out of date" banner; results are announced in a persistent polite live region and focus moves to the card after a saved action; the list is re-read on a new message, on window focus and on a modest interval while a request is open; a stale result after a channel switch (even a switch and back) is ignored. The fixed notice is shown once per thread. **Reassign UI is deferred.**
15. **Guards.** `m36-ack-static.test.ts`: the aggregate does not time, route, escalate or page (no `oncall`, `bullmq`, timers, M11/M12/M19 imports), never writes `escalated`, `failed_unreachable` or the later event types, the `acknowledged` status is written in exactly one place (the acknowledge transition), the read methods and GET routes cannot write, only five listed files import the aggregate, and no file outside it names its tables. `m36-ack-semantics.test.ts` (the receipt ratchet) now allows the words in the aggregate's own directories and an exact list of files (the web card, its wording and its hook are listed one by one; no prefix). Web reads: only the first open and the user-caused ones count as activity; the 60 s poll and new-message refresh send the background header and the poll skips a hidden tab (a deliberate relaxation of the wording check only: the `"ack"` status literal and the retired `acked_at` stay banned everywhere). `m36-urgent-no-escalation.test.ts` still pins that the urgent code pages, times and acknowledges nothing; it now lists the four aggregate files that READ the message's urgency (none writes it).

## Data model

- Migration `packages/db/migrations/1107_m36_message_acknowledgment_request.sql`: enums `message_ack_status`, `message_ack_class`, `message_ack_event_type`; the two tables; the insert and update guards, the append-only event trigger, the message guard; RLS, grants, audit triggers, destruction policies. `wardenx_app` gets SELECT and INSERT on both tables, UPDATE only on the transition columns of the request, no DELETE.
- Code mirrors: `packages/db/src/enums.ts`, `packages/db/src/schema/messaging/message-acknowledgments.ts`, `packages/types/src/messaging-ack.ts` (statuses, classes, event types, the deadline policy, DTOs, error codes), `architecture/module-manifest.ts` and `.cjs` (both tables owned by M36). The covering index for the message foreign key is the first index; the user foreign keys point at the soft-deleted `user` parent.
- Events: five entries in `events-by-m36.ts`; alert rule seeds for `m36.ack.requested` and `m36.ack.reassigned`.

## Alternatives considered

- **Reuse `message_receipt.ack`.** One row per message and user cannot hold a deadline, an assignee or a reassignment, and keeps the open and acknowledge conflation one code path away. Rejected (ADR-0056).
- **Let a supervisor acknowledge on behalf.** Accountability is the assignee's; a supervisor who takes it reassigns to themselves if qualified. Rejected for 4.2 and listed for sign-off.
- **A new permission key for acknowledge.** The qualified role map already lives in `messaging.urgent.receive`; a second key would let the two drift. Rejected; a separate key is a sign-off option.
- **Tenant-configurable deadlines now.** Needs the policy table, trigger, admin route and screen, and the numbers. Deferred with the reason above.
- **Make the flag a hard off for existing requests.** Strands open work. Rejected (decision 9).
- **A separate cancel route for the sender.** The sender's withdrawal is deleting the message, which already cancels. No second path.
- **Write events from a database trigger.** Moves transition logic into SQL the unit tests cannot reach; the application writes the event in the same transaction and the live suite proves every transition has one.

## Consequences

- A named, qualified clinician can take responsibility by one explicit action, and the sender can see that it happened; opening, reading, a receipt or a push tap cannot.
- Nothing yet detects a missed deadline: `deadline_at` is stored and shown, but no timer acts on it until WP 4.4. The feature stays flag-off for every tenant until then.
- The database, not only the service, rejects an illegal transition, a longer-than-maximum window, an acknowledgment by the wrong person, a Critical request, an edit or delete that would orphan a request, and any change to the history.
- Accepted limits: the deadline numbers, the role map and the reassign rules are provisional; tenant tightening, supervisor override, role or on-call assignees, a sender notification (and telling an assignee that the message was deleted and the request withdrawn), a reassign screen and the composer control for `important` are deferred; offboarding an assignee, a discharged or deceased patient and a care-team change do not yet touch an open request (they belong with the 4.9 queue and the review queue work; until then the request simply stays open and visible); `required_role` and `resolution_note_ref` do not exist; the in-memory rate-limit store is per replica (production boot logs a loud warning when no shared store is configured, for these limiters and the 4.1 urgent one). Further accepted limits: (a) a **system write** (an empty `app.user_id`) is reserved for WP 4.4 / 4.5 and is the only way a user-less event or transition can be written, which no 4.2 code path does; (b) **delete by a non-author** with an open request is refused by design (only the author deletes a message, and there is no moderator override in 4.2); (c) the assignee's qualification is checked just before the transaction, not inside it, so a role removed in that instant is honoured one call late (the database still enforces the actor binding); (e) the history table has no statement-level TRUNCATE guard: `wardenx_app` holds no TRUNCATE privilege, so only the table owner or a superuser could truncate it, which is outside the application threat model; (d) the actor binding is an application-bug backstop, not a compromised-role defence (decision 3).
- The rollback is safe: the flag stops new requests, existing rows stay settleable, and no rich-body node type was added.

## Open questions

- Clinical-lead sign-off of every user-facing sentence, the deadline numbers, who may acknowledge (the stricter reading is `messaging.urgent.receive` held by the named assignee only), who may reassign and resolve, and whether a supervisor may acknowledge on behalf (brief section 5).
- How many times a request may be reassigned (4.2 sets no cap; the rate limit bounds the rate), and what happens to an open request when its assignee is offboarded, the patient is discharged or dies, or the care team changes (plan Workflow F; WP 4.9 and the review queue).
- Critical (`critical_symptom`): the class exists in the enum and has no writer until the clinical lead decides who may raise and take it (ADR-0056 D7).
- Tenant tightening of the deadlines (a tighten-only policy table and trigger, audited), and role or on-call assignees (WP 4.3).
- The composer control for `important` and the reassign screen.
- Flag policy (decided): `messaging.urgent_clinical` and `messaging.ack_requests` stay off for every tenant until WP 4.2 - 4.4 ship.
