# ADR-0102 — Messaging alarm ingest, watch only: a signed third-party alarm becomes an ordinary alert, never a call for help

- **Status:** **Proposed** (2026-10-23). Built behind the tenant flag `messaging.alarm_ingest` (default off). Decisions D1 to D13 are the build team's defaults. The clinical lead, compliance, security and legal have not signed off, and **no customer need is recorded**: WP 6.10 was "not scheduled, only on a real customer need" until the product owner asked for it to be built. See Open owner decisions.
- **Date:** 2026-10-23
- **Phase:** Messaging Hub Phase 6, WP 6.10 (the "Alarm management" row of the comparison in `docs/messaging-hub/10-ui-spec-phases-4-to-6.md` §6).
- **Related:** [ADR-0070](ADR-0070-messaging-escalation-timers.md) and [ADR-0073](ADR-0073-messaging-notification-policy.md) (what escalation and out-of-band paging are, and the platform floor this feature stays outside), [ADR-0074](ADR-0074-messaging-lock-screen-privacy.md) (no PHI out of band), [ADR-0096](ADR-0096-messaging-external-partner-share.md) (the trusted-proxy gate D17, the uniform-refusal and step-up patterns reused here), [ADR-0010](ADR-0010-tenancy-rls-invariants.md), `docs/messaging-hub/README.md` (the design rule that M36 is not an emergency path).

## Context

WP 6.10: "Receive third-party alarms as alerts only on a real customer need; reuse the alert catalog. Not scheduled." Hospice has little bedside telemetry, so this is the thinnest possible slice: a tenant's own nurse-call, bed or fall sensor, or monitor gateway can POST a small signed notice, and it appears as an **alert** in the inboxes the tenant's alert rules already name. The module's standing rule is that M36 is not an emergency path and not a nurse-call system. This ADR keeps to that rule and records what it costs: an alarm that arrives here is **information about an alarm**, never the alarm.

## Decision (proposed)

1. **D1: alerts only, through the existing catalog and fan-out.** An accepted alarm calls the ordinary `AlertEmitter` with one of three new platform catalog alert types, `alarm_ingest.nurse_call`, `alarm_ingest.patient_sensor` and `alarm_ingest.equipment` (seeded rules in `@chartwarden/messaging`: category `operational`, severity floor `info`, **not** system-locked, **not** a designated or supervisor-page route, channel override `in_app`). Nothing in the ingest code creates or reads an acknowledgment request, an escalation timer, a message, a task or a page; the words and imports are banned from the module by `m36-alarm-ingest-static.test.ts`. The alert is paged by nobody: it lands in the in-app inbox. Default audience: the holders of `messaging.review` (supervisors), the tenant administrators when nobody holds it, so an enabled source is never silently audience-less. A tenant re-aims or widens it through the existing alert-rule admin.
2. **D2: source authentication, per tenant and per source.** A **source** is a credential, `keyId = <organizationId>.<sourceId>`, with a 256-bit secret (`wxas_` + base64url, shown once). The sender signs `"<timestamp>.<keyId>." + <raw body bytes>` with HMAC-SHA256 and sends three headers: `x-wx-key-id`, `x-wx-timestamp` (epoch seconds, within +-300 s, the M36 webhook window) and `x-wx-signature` (`v1=` + hex). The timestamp and the key id are inside the signed text. There is no session: the route is public by session and authenticated by the HMAC (classified in `scripts/check-request-header-auth.ts`, and in the tenant-IDOR guard suite as a justified exception). **Storage:** HMAC needs the key itself, so a hash would verify nothing. The secret is stored **sealed under the tenant ring DEK** (the M36 body cipher over the M34 key ring, `secret_cipher bytea`), so a database copy holds no secret and a tenant crypto-shred destroys every credential with the rest of that tenant's ciphertext. It is opened only after the cheap secret-free checks pass. The audit trigger scrubs it. **Uniform refusal (for every authentication failure; the framework body cap, content type and the per-address 429 come before it):** an unknown credential, a disabled one, a wrong secret, a tampered body, a stale timestamp, a malformed header and a tenant with the flag off are the SAME 401 body; an unknown source still costs the same HMAC (the envelope open is not mirrored; a caller would need both 122-bit ids to time it). Refusals are logged with ids only, with a reason. The tenant flag is read only after the signature is proven, and the per-address budget fails closed. *Known limit:* if the key ring is unavailable the route answers 503 only for a credential that exists and is enabled, which tells an unauthenticated caller who guessed a real key id (two random uuids) that the ring is down.
3. **D3: a strict, tiny body with no free text.** `{ eventId, alarmKind, severity?, occurredAt? }`, `additionalProperties: false`, 1 KiB cap enforced by the framework before the handler, JSON only. `eventId` (1 to 64 of `A-Za-z0-9._:-`) is the idempotency key; `alarmKind` (1 to 40 of `a-z0-9_`) is the sender's code; `severity` is a request, capped (D5); `occurredAt` is optional and refused when more than 24 h from the server clock (a skewed device clock is not silently trusted). **No field can carry a name, a room or a sentence**, so a sender cannot put PHI into an alert; the alert text is the constant `ALARM_INGEST_ALERT_MESSAGE`.
4. **D4: idempotency and the failed-emit retry.** `alarm_ingest_event` has a unique index on (organization, source, `eventId`) and stores the SHA-256 of the exact bytes. A replay is `202 {status: duplicate}` and never alerts twice; the same id with a different body is 409. The event is inserted `received` first, then the alert is emitted with correlation id `alarm:<event row id>` (the emitter's own `(organization, correlation)` dedupe makes a concurrent or repeated emit a no-op), then the row settles once to `alerted` or `no_recipients`. If the emit fails the answer is 503 `ALARM_NOT_ALERTED` and the row stays `received`, so the sender's retry with the same `eventId` alerts exactly once. Proved live with 6 concurrent copies.
5. **D5: the mapping and a tighten-only severity ceiling.** Each source maps sender alarm kinds to one of the three catalog types with a `severityCeiling` that is only `info` or `warn`; the table CHECK, the effective-severity CHECK on every event row and the API all refuse `critical`. The effective severity is the sender's request (default `info`) **capped** at the ceiling, never raised and never refused for being high (a refusal would be a silent drop). Because the mappable types are non-locked info-floor rules, **no existing floor is weakened and no locked, designated, urgent, acknowledgment or SOS type is reachable**: the alert type CHECK is a closed list of the three, pinned against the seed by a test. Mappings are written at source creation and never changed (no UPDATE grant); to change one, create a new source. An alarm kind that is not mapped is recorded (`unmapped`, counted on the screen) and refused 422 `ALARM_KIND_UNMAPPED` so the sender learns it reaches nobody.
6. **D6: abuse limits, through the trusted-proxy gate.** Per client address, **before any database work** (300 per minute), then per source **after** the signature is proven (60 per minute), so a forged request cannot exhaust a real sender's budget. The address is `request.ip`, which is only meaningful behind a valid `TRUSTED_PROXY_CIDRS`; the ADR-0096 D17 gate is reused: without it the **inbound route is not mounted** and create and rotate answer 503 `ALARM_INGEST_UNAVAILABLE`, so a credential nobody can use is never made. Over budget is 429; the sender must retry (see Hazards).
7. **D7: no PHI over out-of-band (ADR-0074).** The payload carries ids and codes only (event row id, source id, alarm kind, catalog type) and the fixed message. Every out-of-band transport takes its text from the allowlist sanitiser (a content-free generic line and a deep link), never from the payload. The default rules are in-app only. The source *name* is staff-typed and shown only on the staff list, never in an alert; the screen and this ADR tell staff not to put a patient name or room in it.
8. **D8: staff management.** New permission `messaging.alarm_ingest.manage` (category compliance, no ABAC), granted by migration 1250 to `compliance_officer`, `administrator` and `org_admin` only (existing tenants) and by the compliance_officer template (new tenants). `POST /alarm-sources` (create), `POST /alarm-sources/:id/rotate-secret` and `POST /alarm-sources/:id/disable` each require a **fresh step-up** (key = the permission). Create and rotate also require the tenant flag (uniform 404 before the step-up is asked); `GET /alarm-sources` and disable never depend on the flag. Rotation replaces the sealed secret and bumps the generation by exactly one; the old secret stops verifying at once (nothing is cached). Disable is **one way** (create a new source to resume). At most 20 enabled sources per tenant, serialised under a tenant advisory lock.
9. **D9: audit with ids and counts only.** All three tables carry audit triggers (the source's omits the sealed secret). The inbound route runs as the system actor under the credential's own tenant, so every audit row says so. Logs carry organization id, source id and counts. **No outbox event is published**: the alert and its `notification_delivery` rows are the trail, and a second event stream would be a second place for an alarm to be double counted. (This is a deliberate omission relative to ADR-0096, whose share events feed a trail; revisit if compliance wants a reporting event.)
10. **D10: a silent drop is a number.** Every event settles to `alerted`, `no_recipients` (the fan-out found nobody), `unmapped` (a code nobody mapped) or stays `received` (accepted, not yet alerted). The staff list shows the last 24 hours of each by source, the last accepted instant and the secret version, and says in words when alarms did not reach a person.
11. **D11: the screen is read only.** `/messaging/alarm-sources` (nav group Admin, `messaging.alarm_ingest.manage`) lists sources and outcomes. Its only control is Refresh and it never shows a secret; the secret exists only in the create and rotate responses. Every view states that an alarm here is a notice only, that nobody is paged, and that it does not replace the nurse-call or monitoring system. Creating, rotating and disabling are API calls for now (open item 8).
12. **D12: flag and defaults.** Tenant flag `messaging.alarm_ingest`, absent = off; an unreadable flag reads as off. Off: the inbound route is the uniform 401, create and rotate are the uniform 404, and nothing else changes. Permission default: three admin roles, no clinical role.
13. **D13: tenancy.** Three tables with `organization_id`, composite (organization, id) keys, FORCEd RLS on `app.org_id`, no DELETE for the app role, destruction grants for tenant offboarding. The key id names the organization, so the one credential lookup runs under that tenant's RLS; a credential of one tenant under another tenant's key id matches nothing and is the same 401. Proved live as `chartwarden_app`.

## Hazards

- **Alarm fatigue.** Every distinct `eventId` alerts, up to 60 per minute per source. A flapping sensor can fill an inbox within its budget; there is no suppression, aggregation or "N repeats" yet (open item 6). The ceiling keeps them at `warn` at most, in-app only, and the fixed text keeps them uniform, but a flood still buries real alerts. Do not enable a noisy source without a plan for it.
- **Silent drop.** Several paths lose an alarm unless the sender retries: 401 (wrong, rotated or disabled credential, flag off), 429 (budget), 413/422 (too big or invalid), 422 unmapped, `no_recipients`, 503 not alerted. Each is distinguishable to the sender except the 401 family, by design. The screen counts what the platform can see; it cannot see what never arrives, and **there is no dead-man heartbeat**: a source that goes quiet is not detected (open item 5). A sender that fires and forgets will drop alarms during any outage on either side.
- **False assurance that this replaces a nurse-call system.** It does not and must not be described as doing so. It has no delivery guarantee, no acknowledgment, no escalation, no paging, no latency target and no redundancy; an alarm may appear minutes late or never. Every surface says so (the screen, the API description, the alert text). Sales, onboarding and training material must not call it an alarm system, a safety system or an emergency path, and a tenant must keep its primary alarm system and its telephone procedure. This is the main reason the ADR stays Proposed until the clinical lead and legal have read it.
- **A forged or replayed alarm.** Needs the secret (HMAC) and, replayed, is an idempotent no-op within the window and refused outside it. A leaked secret lets an attacker raise `warn`-capped, in-app notices in that one tenant until it is rotated; it reaches no PHI and no other tenant.
- **A channel override widens it.** A tenant that adds push or SMS to an `alarm_ingest.*` rule through the alert-rule admin makes it page. That is the tenant's right under the tighten-only rule for non-locked rules, but it contradicts "never pages by itself" (open item 3).
- **Staff typing PHI into the source name.** It is never copied into an alert, but it is stored and shown to managers.

## Threat model

| Threat | Control |
|---|---|
| Unauthenticated caller raises alerts | HMAC over timestamp, key id and exact bytes; one 401 body; equal timing for unknown sources; per-address budget before any database work |
| Cross-tenant raise or read | Key id selects the RLS scope; composite keys; foreign credential is the same 401; FORCEd RLS; live attacker tests |
| Replay | +-300 s window, signed timestamp, unique (source, `eventId`) with body digest |
| Severity escalation by the sender | Capped at the mapping ceiling; CHECK forbids `critical`; mappable types are non-locked info-floor in-app rules; static test |
| Reaching urgent, acknowledgment, SOS or locked types | Closed alert-type CHECK; static test bans the machinery from the module |
| PHI in an alert or out of band | No free-text field; constant message; ids and codes only; allowlist sanitiser |
| Secret theft from the database or a backup | Sealed under the tenant ring DEK; scrubbed from audit; tenant shred destroys it |
| Brute-forcing a secret | 256-bit; per-address budget; per-source budget only after a valid signature |
| Resource exhaustion by large or malformed bodies | 1 KiB framework cap, strict schema, JSON only, budgets before database work |
| Proxy-address spoofing defeating the budget | ADR-0096 D17 gate: inbound route unmounted and create/rotate 503 without a valid trusted-proxy list |
| Staff misuse | Separate permission, three admin roles, fresh step-up, audit, 20-source cap, one-way disable |

## Open owner decisions (not recorded)

1. **Is there a customer need?** None is named. Building it was the product owner's instruction; keep the flag off and the ADR Proposed until a tenant asks.
2. **Clinical lead:** the default audience (supervisors, then tenant admins), whether any alarm kind should ever reach a clinician's inbox at all, and the on-screen wording.
3. **May a tenant add push or SMS to an alarm rule?** Today yes (non-locked rule). Locking the channel set to in-app would make "never pages by itself" structural.
4. **Compliance and legal:** the statement that this is not an alarm system or medical device function, the wording for contracts and training, and whether any regulator would read an alarm that reaches M36 as M36 being in the alarm path.
5. **Dead-man monitoring:** alert when an enabled source has been silent for a tenant-set period.
6. **Flapping policy:** suppress or aggregate repeats of one alarm kind from one source (and whether a counted "occurrences" alert like the cron-alert correlation is acceptable).
7. **Real devices rarely sign HMAC.** A gateway or adapter at the tenant edge would be needed for most vendors; which vendors, and who owns that gateway.
8. **A management UI** (create, rotate, disable) with the one-time secret panel, and whether mappings should become editable.
9. **Retention** of `alarm_ingest_event` rows (kept until tenant destruction today, no sweep) and who may read them beyond the counts.
10. **Which roles hold `messaging.alarm_ingest.manage`.**

## Known limits

- (a) No heartbeat, aggregation, suppression or delivery guarantee (above). (b) No management screen; the list is read only. (c) A secret is shown once and cannot be recovered; a lost one is rotated. (d) Mappings are immutable; a change is a new source and a disable. (e) The 24 hour counts are read live per list request. (f) The key-ring outage signal in D2. (g) `text/plain` bodies are accepted by the framework's parser and verified by the same HMAC; only JSON content parses to fields. (h) No outbox event (D9). (i) An unauthenticated caller causes one tenant-flag read per request for an organization id of its choosing, bounded only by the per-address budget (the same exposure and the same choice as ADR-0096 D10: no per-organization budget, because a junk flood naming a tenant must not be able to exhaust it for its real senders).
