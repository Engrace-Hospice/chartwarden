# ADR-0077 — Snooze and reminders: a per-conversation snooze quiets only the out-of-band copies of an allowlisted non-urgent alert and can never be set where an acknowledgment request is open; a per-message reminder returns through the ordinary alert pipeline with fixed generic text

- **Status:** **Accepted** (2026-10-19; decisions closed in the WP 4.10 blueprint). **Every number (24-hour snooze ceiling, 25 reminders, 30-day horizon, 7-day staleness), the one-alert allowlist and the wording are PROVISIONAL: no clinical-lead sign-off is recorded** (`docs/messaging-hub/brief-clinical-lead-signoff.md`, section 12). Behind the existing ops flag `messaging.notification_policy` (off for every tenant); no new flag.
- **Date:** 2026-10-19
- **Phase:** Messaging Hub Phase 4 (WP 4.10, Reminders & snooze).
- **Implements:** `docs/messaging-hub/04-phases-4-to-6.md` WP 4.10 ("Snooze non-urgent only; urgent cannot be snoozed past deadline; unread digest (P2)"; acceptance "Snooze on urgent rejected") and capability register NE-07 (reminder & snooze, P1). NE-06 (unread digest, P2) is **deferred**, see below.
- **Extends:** [ADR-0073](ADR-0073-messaging-notification-policy.md) (the designated routes a snooze can never touch; the fan-out the snooze plugs into), [ADR-0069](ADR-0069-messaging-acknowledgment-request-aggregate.md) (what "open request" means), [ADR-0074](ADR-0074-messaging-lock-screen-privacy.md) and [ADR-0075](ADR-0075-messaging-deep-link-landing.md) (the PHI-free text and the opaque authenticated link a reminder's out-of-band copy uses).
- **Related:** [ADR-0010](ADR-0010-tenancy-rls-invariants.md), [ADR-0070](ADR-0070-messaging-escalation-timers.md) (the sweep pattern).

## Context

Checked in the code, not assumed:

- Notification is **per alert, per recipient**: the AlertEmitter resolves an alert's recipients and the fan-out planner (`planFanOutDetailed`) writes one `notification_delivery` row per recipient and channel; the in-app row is the always-planned floor. There is no per-message notification object and no per-conversation preference.
- Only the **conversation mention** (`m36.message.mentioned`) is a non-urgent alert that carries a `channelId`. Every other messaging alert is about assigned work (tasks, handoffs), about an urgent or acknowledgment-bound request (the four designated routes of ADR-0073 and the sender's / supervisors' request alerts), or about the platform. Today the seeded rule for the mention is in-app only, so a snooze has an observable effect only for a tenant or user who has chosen phone / email copies; the mechanism is built so that it does the right thing from the day they do.
- An acknowledgment request is open while `pending`, `acknowledged`, `escalated` or `failed_unreachable`. Urgency is fixed at send (trigger from migration 1105).
- Timed server work follows one pattern (scheduled send, handoff expiry, the ack sweeper): a per-minute BullMQ tick fans out over the active organisations, a narrow SECURITY DEFINER lister finds due rows, and each row is acted on under its owner's context.
- There is no per-user schedule, digest template or digest queue anywhere.

## Decision

1. **What is snoozable: one user's notices from one conversation, for the non-urgent alerts on an allowlist.** The snooze row is `(organisation, user, channel)`. It is applied in the fan-out planner and only there: for a recipient whose conversation is snoozed, the OUT-OF-BAND rows of an alert whose event type is in `SNOOZABLE_EVENT_TYPES` are planned as `skipped_quiet_hours` with `fail_reason = 'snoozed'` (the existing skipped status; no enum change, the same reuse ADR-0073 made for `off_shift`). The allowlist is **an allowlist, not a deny list**, so an alert type added later is never snoozable by default. It holds exactly the conversation mention. It is disjoint from the designated events (a test pins it) and a platform constant: no tenant row can add to it.
2. **Snooze never hides anything.** The in-app row is planned first and is untouched; unread state, the inbox and the thread are not read by the snooze. It only changes whether a push / SMS / email copy is sent.
3. **Urgent is never snoozable, on every path.** (a) The service refuses a snooze in a conversation in which the caller is the **sender or the assignee of an open acknowledgment request** with the typed 409 `SNOOZE_URGENT_NOT_ALLOWED` (a literal reading of "cannot be snoozed past its deadline" would allow a snooze that ends before the deadline; this is stricter on purpose: a snooze that ends before a deadline still quiets a reminder-type notice about it, and there is nothing a clinician gains by snoozing a conversation with an open response request). (b) The store re-checks inside the same write, and (c) a database trigger (`message_snooze_no_open_request`) refuses the insert or update from any caller. (d) The planner ignores a snooze for every designated route by construction (`snoozeApplies = !designated && …`), so an urgent alert arriving while snoozed still gets its push; (e) a request opened **after** the snooze **voids** it for as long as it is open: the lookup excludes any user who is sender or assignee of an open request in that conversation; and (f) a snooze **never applies to a message whose urgency is above routine**, request or not: the mention alert carries the message id and the lookup reads that message's urgency (a message that is missing, unreadable or named by no id is treated as not snoozable, so the notice goes out). Ending a snooze is always allowed.
4. **Reminders are a separate, per-message object.** `message_reminder` is `(organisation, user, channel, message, remind_at)`, one per user per message (setting again replaces the time), at most **25** pending per user (counted under a per-user advisory lock inside the write, so concurrent sets cannot pass the cap), `remind_at` between **1 minute and 30 days** ahead. A reminder cannot be set on an urgent message or one with an open acknowledgment request (service and trigger `message_reminder_non_urgent`). An instant must carry an offset; a time without one is refused rather than read in the server's zone.
5. **A reminder returns through the ordinary alert pipeline.** The per-minute sweep `messaging.reminder_sweep` (same shape as `handoff_expiry`: one repeatable tick, active-org fan-out, concurrency 1) lists due rows through `message_reminder_due(org, limit)` and, per row: drops it unfired if it is more than 7 days overdue, the message was deleted or the owner can no longer see the conversation; otherwise emits ONE alert `m36.reminder.due` (category `clinical_routine`, severity `info`, recipient = the owner only, `channels_override = NULL` so the user's own routing map decides any out-of-band copy) and deletes the row. The alert's correlation id is `reminder:<id>`, so a retry, an overlapping tick or a crash between the emit and the delete is absorbed; the row is deleted only after the alert exists. **The alert payload is an allowlist**: recipient, channel and message ids, the fixed sentence "You asked to be reminded about a message in a conversation" and an in-app link. Out-of-band copies are produced by the ADR-0074 renderer (fixed generic line, no body, no patient, no sender) with the opaque `/n/<delivery id>` link of ADR-0075, which resolves for its own recipient only. A reminder is not snoozable: the user asked for it.
6. **Flag.** The existing `messaging.notification_policy` gates the routes (off = the one uniform 404), the sweep (off = skipped, rows wait, nothing is deleted) and the snooze lookup (off = empty). All messaging flags stay off for every tenant. A flag read that throws propagates (a failed read is never a fake 404 or a fake "not snoozed").
7. **Isolation.** Both tables are `FORCE ROW LEVEL SECURITY`, owner-strict (organisation AND `app.user_id`, the 1087 pattern): a colleague, a context with no user and another tenant read, update and delete nothing; `UPDATE` is column-limited (identity and owner cannot move). The two system readers are SECURITY DEFINER (owner `wardenx_admin`, a policy and a column grant limited to ids and instants, `REVOKE … FROM PUBLIC`, `GRANT … TO wardenx_app`), pinned to the session tenant (`p_organization_id = app.org_id`), bounded to 500 ids / 500 rows, and return ids only. Org and actor always come from the request context. Not found, not visible, other tenant and feature off are one identical 404.
8. **Routes** (typed, OpenAPI-enriched, `messaging.read`, `Cache-Control: no-store`): `GET|PUT|DELETE /channels/:id/snooze`, `GET /reminders`, `PUT|DELETE /messages/:id/reminder`. The PUTs require an `Idempotency-Key` (a replay returns the stored answer; the end of a snooze is not recomputed) and are idempotent by shape as well. The two GETs are read-audited (channel / list). Both tables carry the generic audit trigger.
9. **UI** (the shared kit, flat, no polling): a snooze control in the conversation header (presets 1, 4, 8, 24 hours; "Snoozed until …" with "End snooze"; where the server says the conversation cannot be snoozed, no button, a short note and a full sentence for assistive technology); a "Remind me" control on non-urgent message rows (presets 1 h, 3 h, tomorrow morning, 3 days; "Reminder …" with "Cancel reminder"); results announced in a polite live region; focus returns to the trigger. Nothing renders while loading or when the feature is off.

## Alternatives considered

- **A per-notification snooze (snooze one alert).** Rejected: alerts are not durable user-facing objects (the inbox is a projection of deliveries) and a snoozed alert is already delivered in-app; the conversation is the unit a person actually wants quiet.
- **A user-wide "pause out-of-band notices" switch.** Rejected for this WP: it is the quiet-hours / vacation mechanism of the preferences engine (M20), it would silence conversations the person never chose, and it cannot be refused conversation by conversation when an urgent request opens.
- **Refuse a snooze only when it would run past the deadline.** Rejected (decision 3): needs the deadline in the snooze check and still leaves a window in which a reminder-type notice is quiet.
- **Let the planner read the open-request table directly.** Rejected: the planner is pure; the lookup port already does this read (and the SECURITY DEFINER reader needs no grant on the request table).
- **A DB-resident "fired" state for reminders.** Rejected: delete after the alert is raised; the alert row is the durable record and there is no state to stick.
- **A new feature flag.** Rejected (instruction and YAGNI): the existing policy flag already means "out-of-band behaviour is governed by the clinical rules".
- **Reuse the ack sweeper or the handoff-expiry tick for reminders.** Rejected: both are flag- and aggregate-specific; a third small tick of the same shape is simpler than coupling them.

## Consequences

- **Plainly: with the seeded rules a snooze has NO observable effect.** The seeded mention rule is in-app only and snooze never touches the in-app row, so nothing is quieted until a tenant routes mentions out of band (a rule with push / SMS / email) or a user adds a routing map for `clinical_routine`. The UI copy says "if you get push, text or email copies ..." and never claims they are being paused by default.
- With the flag off (every tenant today) nothing changes and every new route is the uniform 404.
- With the flag on and the seeded in-app-only mention rule, a snooze changes nothing observable (there is no out-of-band copy to quiet); it starts to matter when a tenant routes mentions out-of-band or a user adds a routing map for `clinical_routine`.
- A reminder's alert is a normal `clinical_routine` / `info` alert: with no routing map it is in-app only; with one it can be delivered out-of-band, as the generic line with the opaque link (and is then subject to that user's quiet hours like any routine alert).
- Message deletion removes the reminder (`ON DELETE CASCADE`); the sweep also drops a reminder whose message is soft-deleted.

## Known ceilings

- The snooze list is per conversation; there is no "snooze everything", no snooze of tasks or handoffs, and no shift-based end of snooze (no shift data, ADR-0057).
- The sweep runs once a minute: a reminder can arrive up to a minute late. A permanently failing emit retries every minute until the 7-day staleness rule drops the row.
- App-clock versus database-clock skew is not corrected: the app computes `snoozed_at` / `set_at` and the end / time; the readers compare with the database's `now()`. A few seconds of skew moves an end by a few seconds; the CHECKs compare columns to each other, not to `now()`.
- The sender-as-well-as-assignee exclusion (decision 3) is provisional.
- **Starvation.** The sweep lists due rows oldest first, 200 at a time; failures within a tick are skipped by offset for up to 5 pages (1000 rows) so a permanently failing row cannot starve newer ones. More than 1000 permanently failing due rows in one organisation would still starve the rest until the 7-day staleness rule drops them (no attempts column, to keep the schema minimal).
- **The two readers are callable by any `wardenx_app` session of the organisation** (they are pinned to the session tenant and return ids and instants only; requiring an empty `app.user_id` inside them is rejected by `arch:tenancy`, ADR-0010 D2, which allows only `app.org_id` in RLS-adjacent SQL). `GET /reminders` lists the caller's own ids without re-checking channel visibility, deliberately: a person who lost access must still be able to see and cancel their reminder (ids only, no text).
- **Audit of the sweep's delete:** the owner-strict policy needs the owner's context, and the generic audit trigger records every change to these tables as actor `system` (correlation `db-trigger`) with the row (incl. `user_id`) in before/after; it cannot tell the sweep's delete from the owner's own cancel. The durable record of a delivered reminder is the `m36.reminder.due` alert with correlation id `reminder:<id>`.
- An alert that reached nobody (the owner is no longer an active member) is a counted, logged drop (`no_recipient`), not a silent delete.

## Deferred: unread digest (NE-06, P2)

**Not built.** A digest of unread counts needs a per-user cadence and channel preference, a schedule per user (or per shift), an unread-count read that matches the inbox's definition, and a PHI-free template and send path. None of these exists, and the only nearby seam (the preferences row) belongs to the M20 owner. Adding them here would be new infrastructure, not use of a seam. When built it should reuse the reminder sweep's shape (a per-minute tick, a narrow lister, one alert per recipient with a correlation id per period) and the ADR-0074 renderer, carrying counts and no content. Cadence, channel and who gets one are OPEN (brief section 12).
