# 03 — Phases 0–3: Audit → Foundation → Collaboration → Clinical Integration

> Part of the [Messaging Hub plan](./README.md). Work packages (WP) are bounded to one bounded context or vertical slice. Each WP lists
> **scope**, **explicitly out of scope**, **acceptance**, and the gates it must keep green. Vertical-slice order inside every WP:
> domain types → DB + RLS → domain engine → module seams → API routes → outbox + jobs → frontend → tests → audit evidence.

## Dependency graph

```
P0 audit ─► P1 foundation ─┬─► P2 collaboration ──────────────┐
                           ├─► P3 clinical integration ───────┼─► P4 escalation ─► P5 mobile/governance ─► P6 advanced
                           └─► (P1 WP-1.1 realtime) ──────────┘
P3 WP-3.x clinical_link ─► P4 (ack request needs patient context)
P1 WP-1.4 offboarding   ─► P4 (escalations must reassign on offboarding)
```

After Phase 1, **P2 and P3 can run in parallel** (different bounded contexts, different tables). P4 starts once P3's patient-context and
task primitives exist.

## Phase 1 — Secure messaging foundation (4–6 weeks)

**Goal:** a trustworthy, real-time, idempotent, access-revocable base. Controlled internal testing only.

| WP                                               | Scope                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Out of scope                         | Acceptance                                                                                                                                                             |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1.1 Realtime transport (Socket.IO, D1)** | **Day-1 spike** (Fastify/Bun handshake with Better Auth session, room join, Valkey adapter across two instances, forced disconnect on revocation; fallback SSE + REST if it fails), then write the ADR that **supersedes ADR-0036 §2–3** and implement; handshake via Better Auth session; rooms from `packages/messaging/src/realtime/rooms.ts` computed server-side; per-user payload sanitisation; recompute on `permissions.changed`/membership change; **reconnect = cursor reconcile from DB**; keep polling as degraded fallback | Presence/typing (P2)                 | New message reaches a connected authorized member p95 < 2 s in the load test; revoked member receives nothing on the next event; reconnect produces no duplicates/gaps |
| **1.2 Idempotent durable send**            | **Reuse the existing `Idempotency-Key` HTTP middleware** (`bootstrap/plugins/idempotency.ts`); require the key on send routes; `client_message_id` + unique index only as a DB backstop (audit F6/F13); transactional write (row + audit + outbox); replay returns original; sender/org derived from principal                                                                                                                                                                                                                                                                                                                                                        | Scheduled send (P2)                  | Same key ×N concurrent → exactly one row, one outbox event; failure injection after commit/before response is recoverable                                            |

**Phase 1 gate:** the six acceptance tests in the source spec (tenant isolation, revoked participants, idempotency, failed-scan blocking,
reconnect reconciliation, restore consistency) pass; a restore drill proves DB + object-store consistency within the recorded RPO/RTO.

## Phase 3 — Clinical integration (5–7 weeks) — parallel with Phase 2

| WP                                           | Scope                                                                                                                                                                                                                                           | Acceptance                                                                                                                                       |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **3.1 Patient context panel**          | `GET /patients/:id/context` = **projection via seams** (care team, status, allergies/code status as permitted, active meds count, open tasks, next visit, last IDG); each tile deep-links to the owning module and re-checks permission | A user lacking medication access sees no medication tile and cannot fetch it via the context API; stale source data is labelled with`as_of`    |
| **3.2 Clinical links**                 | `clinical_link` for medication/order/care_plan/assessment/visit/document/IDG; widen `reference_kind`; link-picker in composer                                                                                                               | A link to an order**cannot** modify it; opening re-checks source permission; link survives source edit (shows current state, not snapshot) |
| **3.3 SBAR & clinical templates**      | Structured SBAR form → rendered message + machine-readable sections; urgency preselect only suggests (no auto-escalation until P4)                                                                                                             | SBAR content validated (required S/B/A/R); template overlay tenant-tightenable                                                                   |
| **3.4 Communication tasks**            | "Convert message to task": assignee, due, link back; lifecycle events; inbox integration; IDG-sourced items delegate to M14                                                                                                                     | Task create is idempotent per`(message, assignee)`; closing requires reason for clinical concerns; reassign on offboarding                     |
| **3.5 Handoffs**                       | Outgoing nurse selects caseload patients (M17) → system pre-fills unresolved symptoms, pending meds, visits, callbacks, tasks (via seams) → offered → incoming accepts specific items; shift inbox                                           | Acceptance records accountable clinician; unaccepted handoff keeps accountability with sender and alerts supervisor per policy                   |
| **3.6 IDG coordination**               | IDG-linked patient discussion; outcomes become`communication_task` or a promotion request                                                                                                                                                     | A message can never mark an IDG meeting complete or change the plan of care                                                                      |
| **3.7 Chart promotion**                | `chart_promotion_request` → owning-module workflow (M8 note/addendum, M7 care-plan proposal, M14 IDG item); attribution copies author + time + source message ref; reviewer authenticates in the owning module                               | Promotion creates an*attributed* record in the target, never an unreviewed copy; **no path to M11 orders**                               |
| **3.8 Lifecycle rules**                | Consume discharge/death/transfer (M5/M6): restrict new routine messages per policy, evaluate open tasks/handoffs, require reassignment-or-close-with-justification; retained records stay accessible only per retention + authorization         | Death event never deletes records; open tasks surface in supervisor queue                                                                        |
| **3.9 Care-team sync**                 | Patient reassignment updates membership + routes outstanding responsibilities for review                                                                                                                                                        | Removed clinician loses access immediately; their open items appear in a review queue                                                            |
| **3.10 Medication-clarification flow** | Aide → patient-linked thread → medication link → RN task; RN contacts prescriber; any order via M11                                                                                                                                          | Typed "increase morphine" never becomes an order; aide has no ordering permission through any route                                              |

**Phase 3 gate:** link-cannot-modify, source-permission-on-open, handoff-accountability, chart-promotion-attribution, lifecycle-no-delete and
reassignment-updates-access acceptance tests pass, with simulated hospice cases (Workflows B, C, D, E in [`05`](./05-clinical-workflows-and-safety.md)).
