# 03 — Phases 0–3: Audit → Foundation → Collaboration → Clinical Integration

> Part of the [Messaging Hub plan](./README.md). Work packages (WP) are bounded to one bounded context or vertical slice. Each WP lists
> **scope**, **explicitly out of scope**, **acceptance**, and the gates it must keep green. Vertical-slice order inside every WP:
> domain types → DB + RLS → domain engine → module seams → API routes → outbox + jobs → frontend → tests → audit evidence.

## Dependency graph

```
P0 audit ─► P1 foundation ─┬─► P2 collaboration ──────────────┐
                           ├─► P3 clinical integration ───────┼─► P4 escalation ─► P5 mobile/governance ─► P6 advanced
                           └─► (P1 WP-1.1 realtime) ──────────┘
P3 WP-3.x clinical_link ─► P4 (ack request needs patient context)
P1 WP-1.4 offboarding   ─► P4 (escalations must reassign on offboarding)
```

After Phase 1, **P2 and P3 can run in parallel** (different bounded contexts, different tables). P4 starts once P3's patient-context and
task primitives exist.

> **Defect found by row 5 and fixed.** The message keyset cursor was encoded from a JS `Date` (millisecond precision) while `message.created_at` is microsecond: every page boundary re-served the row the cursor pointed at (duplicate on each forward page), and an anchored page could omit the anchor. The cursor now carries `created_at::text`. **Known, accepted:** a request replayed with a pre-revocation `Idempotency-Key` re-serves that user's own recorded 201 (their own message id; nothing is written) because the M1 store answers before authorization; a fresh key is refused. `created_at` defaults to `now()` (transaction start), so a long-running send transaction that commits after a later one could still sit behind a client's forward cursor; sends are single short transactions, so this is not exercised, and a commit-order sequence would be the fix if that ever changes. The hint-to-socket-drop chain on revocation is proven in two halves (consumer with its ports; gateway disconnect on a live Valkey), not end to end in one test.


> **Phase 1 gate status:** five acceptance tests mapped and passing (one real defect fixed: the message cursor lost microsecond precision, so paging from a cursor repeated a message at each page boundary). The restore drill is built and proven at demo scale, but the gate is **not** "within the recorded RPO/RTO": production has no scheduled Postgres backup (only the manual `pg_dump | gzip` taken by `reseed-demo.sh`), no WAL archiving or PITR, no off-host copy, no object-store (MinIO) backup, and nothing coordinates the two; `MESSAGING_ENCRYPTION_KEY` and `M34_TENANT_KEK` are in no backup, so a restored database cannot decrypt message bodies without them. Open decisions for a person: which DR tier messaging belongs to (Tier 1 is 5 min / 1 h, Tier 2 is 15 min / 4 h) and approval of those targets; funding the missing backups (scheduled dump at minimum, WAL archiving for a minutes-scale RPO, an off-host object-store copy, a DB-then-objects ordering rule); where the two keys are escrowed. The drill's MinIO tar of the stopped volume and its write quiesce are not production behaviour.

> **Model:** `message_body_kind` gains `rich` (migration `1082`). The encrypted plaintext of such a row is the canonical JSON of `{ schemaVersion: 1, doc }`, so `body_sha256` is the SHA-256 of that exact plaintext and `messaging.hash_verify` is unchanged (proved live over a rich head and a rich revision; it still catches a tampered rich body). The closed AST (`packages/types/src/messaging-rich-body.ts`, shared by server and web): `doc` > `paragraph` | `bulletList` | `orderedList` (> `listItem` > paragraph or list) | `codeBlock`; inline `text` (marks `bold`, `italic`, `code`, `link`), `mention` (`kind`, `entityId`, `label`) and `hardBreak`. Nothing else: no raw HTML, image, embed or attribute bag; every node is rebuilt field by field and an unknown key or type is a rejection.
>
> **Authority and limits:** `sanitizeRichBody` runs on every write (send, edit, seam) and again on every read and in the web renderer; the client is never trusted. Limits (`RICH_BODY_LIMITS`): depth 8, 500 nodes, 10,000 characters of visible text, 64 KiB of canonical JSON, 50 links, 2,048 characters per link (checked on the NORMALISED href, because percent-encoding can expand it about six-fold), 4 marks per text node. Links are `https:` or `mailto:` only; credentials in a URL, whitespace/control/invisible characters, `javascript:`, `data:`, `vbscript:`, `http:` and relative links are refused. A `mailto:` target must be a plain address list (`[A-Za-z0-9._+-]@host.tld`, comma separated, no query or fragment, no percent escape, no non-ASCII). A link mark on text with no letter, digit, symbol or punctuation left after cleaning (whitespace, NBSP, U+3000, a lone combining mark such as U+0301/U+20DD/U+0E31/U+1AB0) is rejected; digit-only link text is allowed. Every rejection is the standard `422 INVALID_RICH_BODY`, which never echoes the content, on write and on the bounded read-time re-sanitise.
>
> **Text cleaning:** control characters, bidi overrides/isolates, `Default_Ignorable_Code_Point`, `Cf` and U+2800 are stripped from text, labels and link text; a ZWJ survives only between two pictographs and a VS16 only after a pictograph or a keycap base followed by U+20E3. Cleaning runs strip, normalise, strip again until nothing changes, so `sanitize(sanitize(x)) === sanitize(x)` and write-time mention offsets stay valid against the body as read back (asserted by a property-style test over 400 seeded random sequences, and live by reading back stored offsets). Mention labels and the directory name are compared under NFKC with invisibles removed. **ZWNJ is stripped too (known limit):** it is meaningful in Persian and some Indic scripts; this stays until a script-aware rule exists.
>
> **Projection:** `richBodyToPlainText` is deterministic and visible-text only (no JSON, no marks, no link targets; mentions as `@label`; lists as `- ` / `1. ` lines). It is what `body` carries on the wire for a rich message (so an older client renders safe text), what the channel preview uses, and what the blank-message check and the existing `@displayName` range validation run on. Mention offsets are computed in the same pass as the projection.
>
> **API (additive):** `POST .../messages` and `PATCH /messages/:id` accept `bodyDoc` as an alternative to `body` (exclusive; `references` must then be absent, mentions are nodes and become `message_entity_reference` rows at projection offsets, validated against the same mention-candidate rule). A plain string `body` and `bodyKind: plain|markdown` work exactly as before. A message read returns `bodyKind: "rich"`, `body` (the projection) and `bodyDoc`. **Edits** carry their own format: a `bodyDoc` edit stores `rich`; a `body` edit of a rich message stores `plain` (its plaintext would otherwise be parsed as a document); the `message_revision` row keeps the previous body with its own `body_kind`. A stored rich row that no longer parses is returned with an empty `body` and `bodyUnreadable: true` (never as JSON, never a 500); the server logs a warning with organization, channel and message ids (no content) and the web shows "Message could not be displayed" instead of "Message deleted". The seam (`MessagingProvider.sendMessage`) cannot store `rich` without a document, and the in-memory service sanitises `richBody` itself.
>
> **Link destination rule (final).** `RichBodyView` builds React elements from the AST (no `innerHTML`/`dangerouslySetInnerHTML`, asserted by a source test; links re-checked against the allowlist at render; the server's mention label wins over the one frozen in the document). Every link shows its real destination host inline as `text (host)` UNLESS the visible text is exactly that host. "Exactly" is a character-for-character comparison with the destination's canonical lower-case ASCII host after one normalisation of the text (NFKC and lower case, brackets/quotes/sentence marks around the token trimmed, an `http(s)://` or `//` prefix stripped, one trailing dot dropped), plus the port when it is not the protocol's default (80 for `http:`, 443 for `https:`; a scheme in the text must equal the destination's). For `mailto:` the text must be exactly the address list. Anything else is not exact: non-ASCII text, a `%`, a second trailing dot or an ellipsis, a path/query/fragment/userinfo/`@`, any non-canonical IPv4 spelling (`127.1`, `0x7f.1`, `2130706433`), and any other `x://` prefix. **A destination with an `xn--` label always shows the suffix**, even when the text spells it identically (text and href made of the same look-alike letters would otherwise hide the tell); legitimate IDN links therefore carry a redundant punycode suffix, accepted. The only allowed difference is that the text may omit the DESTINATION's own leading `www.` (`bank.com` for `www.bank.com`); `www.bank.com` for `bank.com` shows the host. There is no prose heuristic, dot look-alike list or neighbour rule: prose, brand words, other scripts, full-width look-alikes, digits and IPv6 literals all simply show `(host)`. Noise is accepted by design. `https:` links keep the sr-only "(opens in new tab)" hint and the hover title `Opens <host>`; `mailto:` links do not open a tab. All scans are linear.
>
> **Composer:** one accessible `<textarea>`. On send a small markdown subset (`**bold**`, `*italic*`/`_italic_`, `` `code` ``, `[text](https://...)`, `- `/`* ` lists, `1.` lists, fenced code) becomes a `bodyDoc`; an unformatted draft still goes out as plain text with offset references, so existing behaviour is unchanged. A fence is a block only when the whole trimmed line is the fence (optionally with a language word); an ordered run is a list only if it starts at 1; markers may span a mention (the mention node itself is not marked, and no stray markers remain); a mention inside a fenced block stays literal text. Keys: Ctrl+B/I/E (Cmd on macOS only, Ctrl elsewhere, by physical key `event.code` so non-Latin layouts work); Enter sends; Shift+Enter inserts a line; Escape closes the mention popup first and blurs only an EMPTY composer (a draft is never lost to a stray key; Tab is never intercepted outside the mention popup). Nothing in the composer handles a key while an IME is composing. A format shortcut is built from the textarea's live value and goes through `execCommand("insertText")` where available (native undo) or `setRangeText` plus an `input` event; `applyTextEdit` verifies the value afterwards and applies the edit itself only when the command left the text untouched. jsdom has no `execCommand`, so undo is asserted with a stub (the call and the selection it sees), not in a real browser. `MessageRow` is memoised and the document is sanitised once per `bodyDoc` (asserted by counting `sanitizeRichBody` calls). Legacy `plain`/`markdown`/`system` rows render exactly as before (a markdown row is still literal text).

> **Ownership model (decided).** One table, three scopes. `platform` rows (`organization_id` NULL) are seeded by the migration, read-only to every tenant, and carry `required_phrases`: the platform floor. `org` rows are shared templates a tenant admin authors. `personal` rows are one user's saved replies. > **Model (migration `1087`, `scheduled_message`):** a private, sealed message-to-be, one row per scheduled message, `pending` or `blocked`. The body is sealed under the tenant DEK like a draft (`body_cipher`); everything else is plaintext and PHI-free (ids, an instant, an IANA zone name, status, reason code, attempt count). `FORCE` RLS with the `NULLIF`-guarded `app.org_id` shape AND the owner (`app.user_id`; the dispatcher lists due rows as the system actor with no user bound and then handles each row under its owner's context, so a request that forgets `user_id = ...` still cannot read a colleague's row). Composite FKs to `channel` and to the thread root (`ON DELETE CASCADE`); audit trigger on INSERT/UPDATE/DELETE with the cipher scrubbed; `wardenx_destruction` policy; the tenant eraser deletes the rows explicitly. A successful send DELETEs the row in the same transaction that inserts the message; a cancel DELETEs it, so cancel is idempotent (`{ cancelled: false }` when nothing was left). Not a column on `message` (the baseline gap matrix suggested `message.scheduled_for`): a scheduled message is not yet a message, so it must not appear in reads, receipts, search or hash-verify until it is sent.
>
> **API (`/api/v1/messaging`):** `POST /channels/:id/scheduled-messages` (`messaging.send` + `channel_visibility`, `messaging.announce` for the announcement channel, `Idempotency-Key` required, 201), `GET /scheduled-messages?channelId=` (the caller's own, `no-store`, read-audited), `PATCH /scheduled-messages/:id` (reschedule; a `blocked` row becomes `pending` again), `DELETE /scheduled-messages/:id` (cancel). List and cancel need only `messaging.read`, so a user who lost access can still see and withdraw what they queued. Another user's id is a 404 (no oracle); a malformed id is a 404 before any cast. Limits: at least 1 minute and at most 30 days ahead (`422 SCHEDULE_TOO_SOON` / `SCHEDULE_TOO_FAR`), at most 50 pending + blocked per user (`409 SCHEDULE_LIMIT_REACHED`, per-user advisory lock like drafts), 8000 characters, `410 CHANNEL_ARCHIVED` for a closed channel. The web picker offers 2 minutes to 30 days so a time picked "now" is still valid on arrival.
>
> **Dispatch (`messaging.scheduled_send`, owner: this module, one name in `arch:queue-names`):** one repeatable per-minute tick (not one delayed job per message, so a cancel or reschedule never has to find a queued job) fans out over the active orgs (`fanOutOrgs`, like the integrity and attachment jobs); each org's due rows (`status = pending`, `scheduled_for <= now()` by the database clock, batch of 100, soonest first) are handled one at a time under the sender's own tenant context, not a request. For each row the sender's right to send is decided NOW: `messaging.send` still held (and `messaging.announce` for the announcement channel) through the same M3 resolver `requirePermission` uses (`resolveActorPermissions`), the sender still sees the channel (`canViewChannel`: active user, live membership, Part 2 gate) and, inside the send transaction, still holds a live `channel_member` row, the channel is not archived, a reply's root is still live. Then, in ONE transaction: claim the row `FOR UPDATE SKIP LOCKED`, re-check, insert through `insertEncryptedMessage` (the live write core) with `client_message_id` = the scheduled row id, delete the row, publish the `m36.message.sent` hint. Two overlapping ticks, a retry, or a crash between commit and ack therefore cannot send twice (the second finds no row, or the `client_message_id` backstop returns the original). **Patient status** is the channel's archive state: M36's own lifecycle consumers archive a patient's care-team channel on discharge or death (`channel-membership-sync.ts`), so an archived channel IS the "discharged patient" signal; no M5/M6 table or seam is read from the dispatcher. **Patient-context links:** the M36 model has none yet (WP 3.1/3.2), so there is nothing to re-check; when they land the dispatcher gains one more reason code.
>
> **Blocked (the acceptance):** a failed re-check does NOT send. The row becomes `blocked` with a reason code (`channel_archived`, `not_member`, `permission_revoked`, `announcement_not_permitted`, `parent_unavailable`) and `m36.message.schedule_blocked` (ids and a code, never the body) is published in the same transaction. Its consumer (`outbox-consumers/schedule-blocked.ts`, bound in `apps/backend/src/index.ts` beside the mention consumer) emits one generic in-app alert to the sender (platform alert rule `m36.message.schedule_blocked`: recipient `payload.senderUserId`, in-app only; text "A scheduled message was not sent because ...", no channel title, patient or content; deep link `/messaging?scheduled=1`, which opens the Scheduled list). It is deliberately not access-gated like a mention: the sender may have just lost the channel, which is the reason it was blocked. An unexpected error (not a failed re-check) is counted per attempt, one try per tick, and after 3 the row is blocked as `dispatch_failed` and the sender told. A consent (M39 Part 2 gate) or care-team seam that cannot answer is an outage, not a verdict: the dispatcher's visibility check throws (`throwOnSeamUnavailable`), so the row stays `pending` and is retried on later ticks, never sent while consent is unknown, and is counted as an attempt only once 15 minutes overdue (then `dispatch_failed` after 3, the sender told); only an explicit denial blocks as `not_member`. A blocked row is never swept again; the sender reschedules it (retry) or cancels it.
>
> **Web:** a "Schedule" button beside Send opens a "Send later" dialog: native `datetime-local` input, the viewer's IANA time zone stated and the chosen time echoed in it, plain-language refusals, idempotency key per request (reused on a lost reply, rotated after an answered failure). Success clears the composer (which also discards the WP 2.5 server draft) and says when it will go out. A "Scheduled" button in the inbox header opens the list: loading, error with Retry, empty, rows with channel name, time in the viewer's zone, preview, the reason for a blocked one, Cancel and Reschedule (to retry). `use-auto-grow-textarea.ts` was extracted so `conversation-thread.tsx` stays under the 800-line ceiling (799).
>
> **M19 / ADR-0057:** scheduled send needs nothing from `EscalationRouter` or any M19 table: M19 owns who is paged and when for escalation (Phase 4), while a scheduled message is an ordinary message sent later. The least-coupled default was taken and nothing of M19 is defined, stubbed or imported here; the open M19-owner decision is not on this work package's path.
>
> **Known limits (accepted defaults):** (a) plain text only: a scheduled message carries no attachments and no structured mentions (the dialog says so; scheduling is disabled while attachments are attached); a mention typed as text stays text and notifies nobody. (b) The web composer schedules channel messages only; the API and the dispatcher already support a scheduled thread reply (`parentMessageId`), the thread panel has no control yet. (c) Send time has the minute granularity of the sweep (a message goes out within about a minute after its time, never before). (d) If `DATABASE_PLATFORM_URL` is unset the sweep is disabled (warned at boot) and scheduled messages stay queued, like the other fan-out jobs. (e) The in-memory slice has no scheduled-send twin (routes are tested over a service double; the Drizzle service and dispatcher over live Postgres). (f) `blocked` rows keep their sealed body until the sender cancels or reschedules them; there is no automatic expiry.

(5) `conversation-thread.tsx` is kept under the ceiling by `use-mention-candidates.ts`, `insertMention` and `composer-footer.tsx`. A thread draft needs a live root that is itself a root; a blank `PUT` goes through the same conflict check (`DELETE` is the unconditional discard and needs no channel access, so a user who lost the channel can still remove their own draft; it still requires `messaging.send`, the accepted default); a user holds at most 200 drafts (`DRAFT_LIMIT_REACHED`, 409). (8) **Malformed ids** on the reaction, pin and draft routes are a 404 (path ids, before any predicate or cast) or a 422 (`parentMessageId`). (9) **Templates:** creates are serialised per owner (shared: per organisation) by an advisory lock so the caps hold under concurrency; an overlay can no longer switch off a template that carries required wording (422 `TEMPLATE_FLOOR_VIOLATION`; a disabled overlay stored earlier is ignored for such a template); stored title and body have bidi and zero-width characters removed (what is linted is what is stored); the PHI lint (version 2) maps any Unicode decimal digit to ASCII, ignores separators between digits, folds common Cyrillic and Greek look-alike letters before keyword matching, and also flags an unspaced `MRN12345` and a bare host such as `example.com/p/abc`; its documented over-rejections (a counted list adding to six digits, a word followed by `.net`) are pinned in the lint tests, and names and spelled-out digits remain misses. Round two also strips variation selectors, the combining grapheme joiner, Arabic letter mark, Mongolian selectors and tag characters before linting and storing; treats any Unicode dash, connector punctuation (underscore), the minus sign and the Arabic separators as digit-run separators; and flags `MRN-12345` / `mrn_12345`. The stricter lint is the accepted default: it also refuses `2.5/day` (read as a host and path), `Steps 1, 2, 3, 4, 5, 6` and `notes.net`, a user rewords; `bob at example dot com` stays a documented miss. The lint examines at most 2000 characters (callers refuse longer text first), runs in linear time on adversarial input (timing test), and every seed template and required phrase is asserted to pass it. (10) The template audit triggers keep the **title** in the audit row on purpose (it is linted non-PHI text and is what identifies the template in an audit trail); only the body is scrubbed. (11) RLS policies of `1085` and `1086` use the `NULLIF`-guarded `app.org_id` shape like `1084` (edited in place; none of the three is on `main`).

> **WP 2.7a note: in-conversation search (option A, no index).** `GET /api/v1/messaging/channels/:id/search?q=&senderUserId=&from=&to=&hasAttachment=&cursor=&limit=`. **Design:** bodies are sealed under the tenant DEK, so a request walks ONE channel newest-first in keyset batches of 500 on `message_channel_created_idx`, opens each candidate body, and matches the NFKC-folded, case-insensitive query words in memory (every word must be a substring). Nothing derived from a body (token, hash, n-gram, cache) is stored or logged. The SQL pre-filter applies the sender, date window (`from` inclusive, `to` exclusive) and attachment filter (the same visibility rule as `loadAttachmentViews`: clean for everyone, pending only for its uploader, quarantined for no one) and excludes `status = 'deleted'` before any body is opened. **Defaults (decided here):** per channel only, no cross-channel search; member-only, re-checked with `canViewChannel` in the service as well as the route guard (a non-member, a removed member, a Part 2 gated channel, another tenant and an unknown id all get the same refusal: the shared route guard answers 403 like every other channel route, the service answers the no-oracle 404); an archived channel is 410 `CHANNEL_ARCHIVED`, so the web hides search there; a query is 2 to 100 characters and at most 5 words, otherwise 422 `INVALID_SEARCH_QUERY` (a query or at least one filter is required); pages are 20 by default, 50 at most; deleted messages and tombstones never match; an edit is searched by its current body only (the cipher is replaced in place); results are the shared `ResolvedMessage` hydration, so reactions, pins and scan-gated attachments are exactly what the history shows. **Performance ceiling (the honest bound):** one request opens at most `SEARCH_MAX_SCAN_PER_REQUEST` = 5000 bodies. If the page is not full by then it returns `scanCapped: true` and a continuation `nextCursor`, and the UI offers "Search older messages"; a channel with more history than that is searched in 5000-message slices, newest first, never with a longer wait. **Measured** (`bun run test:m36:search:live`, real `wardenx_app` role, private `pgvector/pgvector:pg18`, sealed 100-character bodies, 30 timed runs after a warm-up, service call without HTTP): 5000-message channel, no match (worst case, 5000 bodies opened): p50 44 ms, p95 48 ms; 20000-message channel, no match (scan cap hit): p50 124 ms, p95 134 ms; 20000 messages, common term (page of 20 in 1000 bodies): p50 30 ms, p95 32 ms; the oldest match beyond the cap was reached by following the cursor. The "p95 < 1 s" bar is met with about a 7x margin at the cap on that hardware (a laptop, local Postgres: add network and a busier database before extrapolating). **Read audit:** every page writes one `message.list_viewed` event attributed to the care_team channel's patient, with the count and the filter SHAPE; the new `filterOmit` option on `config.auditRead` replaces the value of `q` with `[omitted]`, and the list event also records the channel id (`resourceIdParam: "id"` is folded into the filter), so the search text never reaches `audit_event`. **D3 / D10 boundary:** this is not the global index. 2.7b (option B) must be built from its own design review and ADR; it must not reuse this scan, and numeric/ID-like tokens and free-text identifiers stay out of any future index (here they are matched like any other word, in memory, for a viewer who can already read the message). **Web:** Ctrl/Cmd+F in an open, unarchived conversation (or the Search button) opens a bar with the query, sender / after / before / has-attachment filters and a keyboard-navigable result list (arrow keys, Enter, Escape); choosing a result uses the same jump as pins and thread links (anchored page with "Back to latest" when the message is not loaded); required states are loading, empty, error with Retry, a capped-scan note, and "Show more results". **Known limits:** the "From" choice lists you and the authors of the messages loaded in the timeline, not every member; search is substring, not ranked, and has no phrase or stemming support; a `hasAttachment` message whose only pending scan has expired is matched by SQL and dropped after hydration, so a page can hold fewer than `limit` results without being the last; the p95 is for the service on a local database, not an end-to-end browser measurement. **Proof:** `message-search.test.ts` and `in-memory-message-search.test.ts` (matcher and in-memory twin), `m36-message-search-routes.test.ts` (gates, 422, audit without the query), `read-audit-coverage.test.ts` (`listAuditFilter`), `message-search.dom.test.tsx` and `search-snippet.test.ts` (web), and the live suite `m36-message-search.live.test.ts` (`test:m36:search:live`: isolation across channel and tenant, tombstone and edit, filters, scan-gated attachments, paging, removed member, archived 410, audit without the term, p95).

> - `POST /attachments/uploads`, header `Idempotency-Key` required (400 `IDEMPOTENCY_KEY_REQUIRED`), permission `messaging.send`. > - `GET /attachments/:id`, uploader only: `200 AttachmentStatus` (poll while `availability` is `scanning`).
> - `GET /attachments/:id/access`: `200 { url, expiresAt, fileName, mimeType, byteSize }` with `Cache-Control: no-store`. The URL lives at most 120 s; call again for each open, never store it. Only a **current** member who can still view the channel, for a `clean` attachment on a live (not deleted) message. Every other case is the same 404 a random id gets (removed member, other org, non-member, pending, quarantined, deleted message) so the UI should show "unavailable", not distinguish.

Each id must be the author's own, completed, not quarantined, not already attached, uploaded for this channel; otherwise one uniform `422 ATTACHMENT_NOT_BINDABLE` and the message is not created. A still-`pending` attachment is accepted.
> - Message list: each message gains `attachments: [{ attachmentId, fileName, mimeType, byteSize, availability: "available" | "scanning" }]`. `scanning` appears only for the uploader; recipients get no entry until the file is clean, quarantined files are never listed (for anyone), and a deleted message lists none. No object key, document reference or permanent URL is ever returned. The list re-reads on the next fetch; there is no realtime hint for "became clean" yet.

> **Review hardening (the security + code review of the first cut).**
> - **Tenant erase destroys the bytes (H1).** `deleteStructuralRows` first lists every `object_key` of the org, destroys each object (`AttachmentStoragePort.destroyObject` -> M22's `destroyAllVersions` over the `tenant-<orgId>` bucket, bound in `m36-attachment-storage.ts` and injected as `attachmentStorage` into `createDrizzleMessagingEraseStore`), and only then deletes the rows (the M22 document-eraser order). A store failure throws with every row still in place, so the erase is retryable (destroy is idempotent); if rows with object keys exist and no store is bound, the eraser throws a typed `DEGRADED` error rather than certify destruction. Retention is plan-only and the eraser is the only hard-delete of `message`, so there is no other path that strands bytes. Consequence: the messaging erase now needs the `wardenx_destruction` credential (`DATABASE_DESTRUCTION_URL`); on the app role the attachment delete is refused by Postgres (loud, like the `presence` leg).

> - **Abuse and liveness (M3).** (a) At most 20 open uploads per user (unbound and either unfinished-and-unexpired or finished); the 21st `POST /attachments/uploads` is `429 TOO_MANY_OPEN_UPLOADS` (additive to the contract; a per-user advisory lock stops racing requests slipping under it; sending or waiting frees slots). (b) An orphan reaper runs as a second step of the existing `messaging.attachment_scan` tick: uploads never completed and expired for more than 15 minutes, and finished uploads no message adopted within 7 days, have the object destroyed and then the row deleted (a failed destroy keeps the row for the next tick). A send refuses an upload older than 6 days, so the reaper never races a bind. Row deletion needs the destruction credential, so the reaper is wired only when `DATABASE_DESTRUCTION_URL` is set (a boot warning says so otherwise). (c) The scan sweep orders by least-recently-attempted (`last_scan_attempt_at`, `scan_attempts`), so a poison row cannot block the rows behind it; a row the scanner could not judge for a day is NOT quarantined (an outage must not condemn legitimate files unscanned): it stays `pending`, is retried with exponential backoff capped at hourly (see Round-4) and is reported `availability: blocked` until a real verdict settles it, so the verdict-final invariant holds and `scan-unavailable` no longer exists; an object that 404s is finalised `object-missing` only after 3 CONSECUTIVE misses spanning 15 minutes (dedicated `object_missing_count` / `first_object_missing_at`, reset by any successful read; scanner outages never touch them). `complete` makes at most 3 inline scan attempts per attachment (claimed atomically in `scan_attempts`). There is NO shared circuit breaker (see Round-3 hardening); the reap step runs for an org even when its scan step throws. The open-upload cap ignores quarantined rows and rows older than the 7-day reap age, so a missing reaper credential cannot lock a user out (flagged rows have their own cap, below). The tenant eraser preflights with a REAL delete of the first row inside a transaction that is rolled back (privilege, RLS policy, triggers and FKs all exercised) and refuses (`DegradedError`) BEFORE destroying any byte, then destroys objects and deletes their rows in batches of 100 in short transactions (a row is deleted only after its object is gone). **Retention warning:** any future hard delete of a message or channel (retention jobs) must destroy the attachment objects first: the FK cascade removes the `message_attachment` rows without destroying bytes. Finding: that test still passes with `.for("update")` removed, because the UPDATE's `message_id IS NULL` predicate and the guard trigger already make the bind atomic; the row lock is defence in depth.
> - **Round-3 hardening (security re-review of round 2).**
>   - **No cross-org coupling in the scan sweep.** The shared circuit breaker is gone (two tenants, one hostile and one with a broken bucket, could open it for everyone, it never half-opened, and tenant-store errors were counted as scanner failures). Instead, with no state shared between orgs: each org's sweep stops after 2 failures of its own per tick (scanner transport or its own bucket/database; reported separately as `scannerFailures` / `storeFailures`); the scan phase has a 20 s wall-clock budget shared by FAIR SHARE (see Round-4 below) after which no new scan is started; every scan has a 20 s hard deadline (read + scanner) that now ABORTS the work, so a tick ends inside the 60 s cron period even against a hung clamd; the starting org still ROTATES every tick (`floor(now / 60 s) mod orgCount`, stateless) as the tiebreak when there are more orgs than time; within an org the order stays least-recently-attempted. A total clamd outage therefore fails closed (rows stay `pending`, nothing delivered) at a bounded cost (2 attempts per org per tick, connect-refused fails fast) and recovers on the next tick with no cooldown.
>   - **Abuse caps.** Rows the scanner flags stop counting toward the open cap (so a missing reaper credential cannot lock anyone out) but have their own cap: at most 20 quarantined unbound uploads per user created in the last 24 h, then `429 TOO_MANY_QUARANTINED_UPLOADS` (an authorize -> upload EICAR -> complete loop can no longer mint unlimited rows, objects, CRITICAL audit rows and outbox events). `authorize` and `complete` are rate limited per user (60 per minute; `429 RATE_LIMITED`; authorize counts the user's recent rows under the same advisory lock, complete uses a per-process counter; the org-wide limiter in the security plugin stays in front of both). `complete` after the upload URL's TTL is refused with `410 UPLOAD_EXPIRED` (additive; an expired row no longer counts toward the open cap, so it must not be completable), start a new upload instead.
>   - **Inline scans are bounded.** At most 4 inline (`complete`) scans in flight per process and 2 per org (each reads up to 25 MB). When saturated the inline scan is skipped and the row stays `pending` for the sweep (not an error, no attempt is claimed).
>   - **Reaper.** Picks its 25 rows in random order (25 permanently failing rows can no longer be re-selected forever ahead of healthy ones) and destroys the object and deletes the row per row in short transactions, so no network IO is held inside a transaction.
>   - **Eraser.** The privilege preflight is now a real rolled-back delete (a role with the grant but no matching RLS policy is refused before any byte is destroyed). The structural step repeats "destroy every object" until a pass finds none (bounded, 5 passes) and re-checks inside its own transaction, so an upload that lands during the erase has its bytes destroyed too. If the real delete removes nothing after a batch's objects were destroyed (only a grant revoked mid-run), it throws; the retry re-destroys idempotently and then deletes.
> >   - Known gap in the same area: an eraser connection whose RLS shows it zero org rows (a role with no policy at all) sees "no attachments" and proceeds; the supported credential is `wardenx_destruction`, which has the policy.
> - **Round-4 hardening (the five gaps the round-3 review left open).**
  - **Hung calls really stop.** `AttachmentStoragePort.inspect/readBytes/destroyObject` and `ScanPort.scan` take an `AbortSignal`. `runWithDeadline` aborts it at the deadline and the caller waits until the work has actually stopped: the clamd socket is destroyed, the object-store `fetch` is aborted (`AbortSignal.any([deadline, 30 s])`, which also errors the body read), and M22's `inspectObject` / `destroyAllVersions` accept an optional `signal` (additive). The inline-scan gate slot is therefore released only when the scan has stopped, not at the deadline while it keeps running. Backstop: a port that ignores the signal is given up on `ABORT_SETTLE_GRACE_MS` (5 s) after the abort (reported as the deadline failure; the abandoned work then runs to its own timeout, the old behaviour) so a broken adapter cannot wedge the tick. `complete`'s object inspect (15 s), the reaper's destroy (8 s) and the eraser's destroy (60 s) are bounded the same way; a hung inspect is a typed 503 `DEGRADED`. No verdict or 404 is recorded after an abort.
  - **Reap has its own budget.** The tick is two phases with separate budgets: scan 20 s, reap 8 s (`SCAN_TICK_BUDGET_MS`, `REAP_TICK_BUDGET_MS`). The reap runs even when the scan phase threw (both errors are reported), a slow reap cannot eat scan time and a slow scan cannot eat reap time. Worst case per tick: 20 + 20 (one scan overrun) + 8 + 8 (one destroy overrun) = 56 s < 60 s.
  - **Deterministic fair share.** An org's time slice is the phase budget still unspent divided by the orgs still to go (`fairShareMs`): an org that finishes early passes its time on, an org that drags is cut at its share, and an org with due work always gets its FIRST scan (or destroy) started while the phase budget lasts (a slice of 0 means the tick is over). Pinned by a live tick test where every scan "takes" 10 s: three orgs with four pending files each get exactly two scans each (the greedy loop gave the first org four and the last none). Rotation stays only as the tiebreak when there are more orgs than time. An org's overrun is bounded by one scan deadline.
  - **Late erase upload is closed, not just checked twice.** Migration `1076` adds `messaging_erase_block` (one row per org; the app and destruction roles can SELECT and INSERT it, nobody can clear it; RLS+FORCE). `authorize` and `complete` take `pg_advisory_xact_lock_shared(erase lock)` and refuse (409 `TENANT_ERASURE_IN_PROGRESS`) if the flag exists. The eraser, after its privilege/store preflight (so a misconfigured run never locks a live tenant out), takes the SAME lock exclusively to insert the flag: it waits for every in-flight authorize/complete to commit, so their rows are visible to its sweeps, and every later one sees the flag. A presigned PUT minted before the flag stays valid until its own expiry, so the eraser then refuses (retryable `DEGRADED`, naming the instant) until every upload URL the org ever minted has expired plus a 60 s skew grace; only then does it destroy the bytes and delete the rows. After that nothing can create an object for the tenant, so the delete cannot orphan one. The old in-transaction late check and 5 destroy passes remain as defence in depth. Consequences: an erase started within 10 minutes of an upload needs a retry; the flag is permanent (an org whose erasure began is never uploaded to again). Proof (live): the eraser WAITS behind an uncommitted authorize and then sees its row; a flagged org refuses authorize and complete; an object PUT after the first attempt is destroyed by the second; a mutation test (removing either the lock or the flag check) fails these tests.
  - **Scan retries back off; nothing is ever decided by an outage.** A pending row the pipeline could not judge is retried after `min(60 s * 2^(n-1), 60 min)` for its n-th failed attempt (1, 2, 4, ... 32, then 60 min), enforced in the sweep's SQL (`scan_attempts`, `last_scan_attempt_at`; no new column). It keeps being retried at that slow cadence forever. A verdict is final and "the scanner was down" is not a verdict, so there is no age-quarantine and no auto-clean; the only terminal states stay `clean` / `quarantined` (a real verdict, or `object-missing` after 3 consecutive misses over 15 minutes). The "scan-unavailable" signal is DERIVED, not stored: from `SCAN_UNAVAILABLE_ATTEMPTS` (8) failed attempts the sweep counts the row in `scanUnavailable` and calls `onScanUnavailable` (logged at `error` in the composition root: alert on it), and the uploader already sees `availability: blocked` after 24 h. Chosen over a stored `scan-unavailable` status because a stored state would need a transition back (a verdict arriving later), which the verdict-final trigger deliberately forbids.
  - **Total storage quota.** At `authorize`, under a per-org advisory lock (always taken after the per-user lock), the service sums `byte_size` of every row that still holds or may yet receive bytes (completed rows of ANY scan state, including bound-but-pending and quarantined, plus unfinished uploads whose URL is still live; reaped/erased rows are gone, expired unfinished ones do not count) and refuses a request that would pass the user's or the org's allowance with `413 ATTACHMENT_QUOTA_EXCEEDED` (standard envelope, `details[0] = {field: "scope", message: "user" | "organization"}`). Env: `MESSAGING_ATTACHMENT_USER_QUOTA_BYTES` (default 2 GiB) and `MESSAGING_ATTACHMENT_ORG_QUOTA_BYTES` (default 20 GiB); unset or anything but digits (`0`, `-1`, `1e9`, `abc`) falls back to the default (a typo never switches the quota off). Not done: there is no per-user override, no usage endpoint and no UI string for the 413 yet; the reaper (7 days) and the eraser are the only things that free quota (a bound file is kept as long as its message).
- **Cheap fixes.** `Cache-Control: no-store` on the uploads and complete responses; `readBytes` checks `Content-Length` against the limit before buffering, caps the streamed body, and rethrows sanitized errors (the signed internal URL never reaches a log; the scan/reap log sites log the message only); the clamd client waits for `drain` and caps the reply at 1 KB; bidirectional control characters (U+200E/200F, U+202A-202E, U+2066-2069) are stripped from file names.
> - **Operator requirements.** ClamAV: `AlertEncrypted yes`, `AlertEncryptedArchive yes`, `AlertExceedsMax yes`, `StreamMaxLength >= 25000000`; clamd receives PHI in plaintext over TCP, so reach it only over loopback, a pod-local sidecar, or mTLS. The MinIO public endpoint (the host in presigned URLs) must be served from a separate origin from the app, so a rendered attachment can never run script with the app's cookies even if a browser ignores the download hint. Env: `MESSAGING_ATTACHMENT_SCANNER=clamd` + `CLAMD_HOST`/`CLAMD_PORT`; `ALLOW_BUILTIN_ATTACHMENT_SCANNER=1` only for dev/CI/demo; `MESSAGING_ATTACHMENT_USER_QUOTA_BYTES` / `MESSAGING_ATTACHMENT_ORG_QUOTA_BYTES` (digits only, defaults 2 GiB / 20 GiB). Alert on the `M36 attachment scan unavailable` error log.
