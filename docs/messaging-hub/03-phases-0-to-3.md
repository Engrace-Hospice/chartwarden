# 03 — Phases 0–3: Audit → Foundation → Collaboration → Clinical Integration

> Part of the [Messaging Hub plan](./README.md). Work packages (WP) are bounded to one bounded context or vertical slice. Each WP lists
> **scope**, **explicitly out of scope**, **acceptance**, and the gates it must keep green. Vertical-slice order inside every WP:
> domain types → DB + RLS → domain engine → module seams → API routes → outbox + jobs → frontend → tests → audit evidence.

## Dependency graph

```
P0 audit ─► P1 foundation ─┬─► P2 collaboration ──────────────┐
                           ├─► P3 clinical integration ───────┼─► P4 escalation ─► P5 mobile/governance ─► P6 advanced
                           └─► (P1 WP-1.1 realtime) ──────────┘
P3 WP-3.x clinical_link ─► P4 (ack request needs patient context)
P1 WP-1.4 offboarding   ─► P4 (escalations must reassign on offboarding)
```

After Phase 1, **P2 and P3 can run in parallel** (different bounded contexts, different tables). P4 starts once P3's patient-context and
task primitives exist.

> **What shipped.** Migration `1075` rebuilds `message_attachment` as a real tenant row: `organization_id`, `channel_id`, `uploaded_by`, `object_key`, `sha256_hex`, `scan_state` (`pending|clean|quarantined`, CHECK) + `scanned_at` + `scan_signature`, `completed_at`; composite FKs `(organization_id, message_id)` and `(organization_id, channel_id)` (cascade kept), `UNIQUE (organization_id, id)`, RLS + FORCE keyed on `organization_id` (the parent-join policy and the `check-tenancy` allowlist entry are gone), the PHI-scrubbing write-audit trigger (the file name and object key never enter `audit_event`), and a guard trigger: a verdict is final (`quarantined`/`clean` can never change), and tenant/channel/uploader/object identity is immutable. `message_id` is nullable because the upload precedes the message; `document_ref` is now nullable and unused. New append-only `attachment_access_event` (`open|denied` + a reason code; app role SELECT+INSERT only). Events `m36.attachment.cleared` / `m36.attachment.quarantined` (record-only, no declared consumer, so nothing is deferred) and audit actions of the same names. Queue `messaging.attachment_scan` (every minute).
>
> **How "via M22" is meant.** M36 does not depend on M22, so it owns two ports (`AttachmentStoragePort`, `ScanPort`); `apps/backend/src/m36-attachment-storage.ts` binds storage over M22's per-tenant SigV4 MinIO store (same `tenant-<orgId>` bucket, checksum-enforced presigned PUT, short presigned GET). No M22 `document` row is created for a chat attachment; the object key is opaque (`messaging/<channelId>/<attachmentId>`).
>
> **The rule.** Nothing is delivered unless `scan_state = 'clean'`. `complete` verifies the object (size, type, SHA-256), then tries one scan inline; a scanner that cannot answer leaves the row `pending` and the sweep retries. There is no code path that turns a scanner error into `clean`. Scanner binding is by env: `MESSAGING_ATTACHMENT_SCANNER=clamd` (+ `CLAMD_HOST`, `CLAMD_PORT`) is the production path (clamd INSTREAM client, unit-tested against a fake clamd); `=builtin` is EICAR + declared-type-vs-magic-bytes only and is **not** an antivirus engine (dev/CI/demo); unset means no scanner, so every attachment stays `pending` and nothing is ever delivered. Still needed for production: a ClamAV sidecar (and its signature-update job) in the deployment, `CLAMD_*` env, an alert on `deferred` scans / old `pending` rows, and an orphan sweep for uploads that are never sent (the object and row stay until then).
>
> **API contract (all under `/api/v1/messaging`, session auth, org and user are server-side).**
> - `POST /attachments/uploads`, header `Idempotency-Key` required (400 `IDEMPOTENCY_KEY_REQUIRED`), permission `messaging.send`. Body `{ channelId: uuid, fileName: 1..255 chars, contentType, byteSize: 1..25000000, sha256Hex: 64 lowercase hex }`; `contentType` is one of `application/pdf`, `image/jpeg`, `image/png`, `image/tiff`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `text/plain`. `201 { attachmentId, upload: { method: "PUT", url, headers, expiresAt }, status: AttachmentStatus }`. The browser computes the SHA-256 and PUTs the bytes to `upload.url` with **exactly** `upload.headers` (the store enforces the checksum and content type). Errors: 404 (not a member / unknown channel, identical to a random id), 410 `CHANNEL_ARCHIVED`, 415 `UNSUPPORTED_MEDIA_TYPE`, 422 `UPLOAD_SIZE_INVALID` / `VALIDATION_FAILED`, 503 `DEGRADED` (no object storage configured).
> - `POST /attachments/:id/complete`, `Idempotency-Key` required, uploader only. `200 AttachmentStatus`. 409 `ATTACHMENT_NOT_UPLOADED` (retry after the PUT), 410 `UPLOAD_EXPIRED` (the upload URL's TTL passed before completion; authorize again), 429 `RATE_LIMITED`, 422 `ATTACHMENT_UPLOAD_MISMATCH` (authorize again), 404 for anyone else.
> - `GET /attachments/:id`, uploader only: `200 AttachmentStatus` (poll while `availability` is `scanning`).
> - `GET /attachments/:id/access`: `200 { url, expiresAt, fileName, mimeType, byteSize }` with `Cache-Control: no-store`. The URL lives at most 120 s; call again for each open, never store it. Only a **current** member who can still view the channel, for a `clean` attachment on a live (not deleted) message. Every other case is the same 404 a random id gets (removed member, other org, non-member, pending, quarantined, deleted message) so the UI should show "unavailable", not distinguish.
> - Send: `POST /channels/:id/messages` body gains `attachments: [{ attachmentId }]` (max 10; the old `{storageKey, fileName, contentType, byteSize}` shape is rejected, 422). Each id must be the author's own, completed, not quarantined, not already attached, uploaded for this channel; otherwise one uniform `422 ATTACHMENT_NOT_BINDABLE` and the message is not created. A still-`pending` attachment is accepted.
> - Message list: each message gains `attachments: [{ attachmentId, fileName, mimeType, byteSize, availability: "available" | "scanning" }]`. `scanning` appears only for the uploader; recipients get no entry until the file is clean, quarantined files are never listed (for anyone), and a deleted message lists none. No object key, document reference or permanent URL is ever returned. The list re-reads on the next fetch; there is no realtime hint for "became clean" yet.
> - `AttachmentStatus = { attachmentId, channelId, fileName, mimeType, byteSize, scanState: "pending"|"clean"|"quarantined", availability: "uploading"|"scanning"|"available"|"blocked", attached: boolean }`. `blocked` is shown to the uploader only (via `GET /attachments/:id`).
>
> **Limits and honest gaps.** (1) A signed URL minted a moment before a member is removed stays valid for up to 120 s; the next open is refused. (2) The signed GET asks the store for `response-content-disposition=attachment` and `response-content-type=<the stored allowlisted type>` (signed into the URL, so it cannot be dropped), which makes a browser download rather than render the bytes; the filename in the header is the object key, so use `fileName` from the response when saving. (3) The uploader of a quarantined file learns of it only by polling its status; there is no notification. (4) A tenant with `MESSAGING_ATTACHMENT_SCANNER` unset can upload but nothing is delivered. (5) `X-Content-Type-Options: nosniff` on the object response is a proxy/MinIO concern, not something a presigned URL can set: add it at the edge in front of the MinIO public endpoint.
>
> **Review hardening (the security + code review of the first cut).**
> - **Tenant erase destroys the bytes (H1).** `deleteStructuralRows` first lists every `object_key` of the org, destroys each object (`AttachmentStoragePort.destroyObject` -> M22's `destroyAllVersions` over the `tenant-<orgId>` bucket, bound in `m36-attachment-storage.ts` and injected as `attachmentStorage` into `createDrizzleMessagingEraseStore`), and only then deletes the rows (the M22 document-eraser order). A store failure throws with every row still in place, so the erase is retryable (destroy is idempotent); if rows with object keys exist and no store is bound, the eraser throws a typed `DEGRADED` error rather than certify destruction. Retention is plan-only and the eraser is the only hard-delete of `message`, so there is no other path that strands bytes. Consequence: the messaging erase now needs the `wardenx_destruction` credential (`DATABASE_DESTRUCTION_URL`); on the app role the attachment delete is refused by Postgres (loud, like the `presence` leg).
> - **Least privilege (M1), in migration 1075 (still unmerged, edited in place).** `wardenx_app` has no DELETE on `message_attachment`, and UPDATE only as a column grant on `message_id, completed_at, scan_state, scanned_at, scan_signature, scan_attempts, last_scan_attempt_at, object_missing_count, first_object_missing_at` (identity columns cannot be rewritten). The guard trigger also requires a completed upload with an object key for `pending -> clean`, makes `completed_at` immutable, and refuses a bind to a message in another channel. `attachment_access_event` cannot be deleted by the app role (and now cannot be reached by a cascade from it, since the parent cannot be deleted either).
> - **Builtin scanner (M4).** `MESSAGING_ATTACHMENT_SCANNER=builtin` is refused at boot in every `NODE_ENV` unless `ALLOW_BUILTIN_ATTACHMENT_SCANNER=1` is also set (docker-compose runs deployments with `NODE_ENV=development`), and a loud boot warning is printed when it is used. Never use it with real PHI.
> - **Abuse and liveness (M3).** (a) At most 20 open uploads per user (unbound and either unfinished-and-unexpired or finished); the 21st `POST /attachments/uploads` is `429 TOO_MANY_OPEN_UPLOADS` (additive to the contract; a per-user advisory lock stops racing requests slipping under it; sending or waiting frees slots). (b) An orphan reaper runs as a second step of the existing `messaging.attachment_scan` tick: uploads never completed and expired for more than 15 minutes, and finished uploads no message adopted within 7 days, have the object destroyed and then the row deleted (a failed destroy keeps the row for the next tick). A send refuses an upload older than 6 days, so the reaper never races a bind. Row deletion needs the destruction credential, so the reaper is wired only when `DATABASE_DESTRUCTION_URL` is set (a boot warning says so otherwise). (c) The scan sweep orders by least-recently-attempted (`last_scan_attempt_at`, `scan_attempts`), so a poison row cannot block the rows behind it; a row the scanner could not judge for a day is NOT quarantined (an outage must not condemn legitimate files unscanned): it stays `pending`, is always re-tried first (hourly once expired) and is reported `availability: blocked` until a real verdict settles it, so the verdict-final invariant holds and `scan-unavailable` no longer exists; an object that 404s is finalised `object-missing` only after 3 CONSECUTIVE misses spanning 15 minutes (dedicated `object_missing_count` / `first_object_missing_at`, reset by any successful read; scanner outages never touch them). `complete` makes at most 3 inline scan attempts per attachment (claimed atomically in `scan_attempts`). There is NO shared circuit breaker (see Round-3 hardening); the reap step runs for an org even when its scan step throws. The open-upload cap ignores quarantined rows and rows older than the 7-day reap age, so a missing reaper credential cannot lock a user out (flagged rows have their own cap, below). The tenant eraser preflights with a REAL delete of the first row inside a transaction that is rolled back (privilege, RLS policy, triggers and FKs all exercised) and refuses (`DegradedError`) BEFORE destroying any byte, then destroys objects and deletes their rows in batches of 100 in short transactions (a row is deleted only after its object is gone). **Retention warning:** any future hard delete of a message or channel (retention jobs) must destroy the attachment objects first: the FK cascade removes the `message_attachment` rows without destroying bytes. > - **Round-3 hardening (security re-review of round 2).**
>   - **No cross-org coupling in the scan sweep.** The shared circuit breaker is gone (two tenants, one hostile and one with a broken bucket, could open it for everyone, it never half-opened, and tenant-store errors were counted as scanner failures). Instead, with no state shared between orgs: each org's sweep stops after 2 failures of its own per tick (scanner transport or its own bucket/database; reported separately as `scannerFailures` / `storeFailures`); the whole tick has a 35 s wall-clock budget after which no new scan is started; every scan has a 20 s hard deadline (read + scanner), so a tick ends inside the 60 s cron period even against a hung clamd; the starting org ROTATES every tick (`floor(now / 60 s) mod orgCount`, stateless), so no org is permanently scanned first or last; within an org the order stays least-recently-attempted. A total clamd outage therefore fails closed (rows stay `pending`, nothing delivered) at a bounded cost (2 attempts per org per tick, connect-refused fails fast) and recovers on the next tick with no cooldown.
>   - **Abuse caps.** Rows the scanner flags stop counting toward the open cap (so a missing reaper credential cannot lock anyone out) but have their own cap: at most 20 quarantined unbound uploads per user created in the last 24 h, then `429 TOO_MANY_QUARANTINED_UPLOADS` (an authorize -> upload EICAR -> complete loop can no longer mint unlimited rows, objects, CRITICAL audit rows and outbox events). `authorize` and `complete` are rate limited per user (60 per minute; `429 RATE_LIMITED`; authorize counts the user's recent rows under the same advisory lock, complete uses a per-process counter; the org-wide limiter in the security plugin stays in front of both). `complete` after the upload URL's TTL is refused with `410 UPLOAD_EXPIRED` (additive; an expired row no longer counts toward the open cap, so it must not be completable), start a new upload instead.
>   - **Inline scans are bounded.** At most 4 inline (`complete`) scans in flight per process and 2 per org (each reads up to 25 MB). When saturated the inline scan is skipped and the row stays `pending` for the sweep (not an error, no attempt is claimed).
>   - **Reaper.** Picks its 25 rows in random order (25 permanently failing rows can no longer be re-selected forever ahead of healthy ones) and destroys the object and deletes the row per row in short transactions, so no network IO is held inside a transaction.
>   - **Eraser.** The privilege preflight is now a real rolled-back delete (a role with the grant but no matching RLS policy is refused before any byte is destroyed). The structural step repeats "destroy every object" until a pass finds none (bounded, 5 passes) and re-checks inside its own transaction, so an upload that lands during the erase has its bytes destroyed too. If the real delete removes nothing after a batch's objects were destroyed (only a grant revoked mid-run), it throws; the retry re-destroys idempotently and then deletes.
>   - **Known limitation (MEDIUM-2, not fixed here).** A pending row bound to a message is not an "unbound" upload, so it neither counts toward the open cap nor is reaped, and the sweep rescans it indefinitely (hourly once past 24 h) if the scanner never gives a verdict. Follow-up: a per-user / per-org total attachment storage quota, and expiring (quarantining or detaching) bound-but-never-scanned files after a long window with an alert.
>   - Known gap in the same area: an eraser connection whose RLS shows it zero org rows (a role with no policy at all) sees "no attachments" and proceeds; the supported credential is `wardenx_destruction`, which has the policy.
> - **Cheap fixes.** `Cache-Control: no-store` on the uploads and complete responses; `readBytes` checks `Content-Length` against the limit before buffering, caps the streamed body, and rethrows sanitized errors (the signed internal URL never reaches a log; the scan/reap log sites log the message only); the clamd client waits for `drain` and caps the reply at 1 KB; bidirectional control characters (U+200E/200F, U+202A-202E, U+2066-2069) are stripped from file names.
> - **Operator requirements.** ClamAV: `AlertEncrypted yes`, `AlertEncryptedArchive yes`, `AlertExceedsMax yes`, `StreamMaxLength >= 25000000`; clamd receives PHI in plaintext over TCP, so reach it only over loopback, a pod-local sidecar, or mTLS. The MinIO public endpoint (the host in presigned URLs) must be served from a separate origin from the app, so a rendered attachment can never run script with the app's cookies even if a browser ignores the download hint.
