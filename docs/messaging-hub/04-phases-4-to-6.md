## Phase 4 — Urgency, on-call & notification reliability (4–6 weeks)

**Reuse, don't rebuild.** Delivery (in-app / push / SMS / email / voice), quiet hours, vacation forwarding, retry sweeps and the PHI sanitiser
already exist in M36. On-call rosters, tiers and `triage_escalation` live in **M19**. Phase 4 adds the *acknowledgment-request aggregate* and
wires the two together through seams.

### Acknowledgment deadline policy (decision D4)

Per-urgency defaults; each tenant may **shorten** any value but never exceed the platform maximum (same tighten-only rule as alert routing,
enforced by DB trigger, every change audited). Tier timing is read from M19's escalation configuration where it defines one — M36 does not keep a
second copy. **These numbers are proposed defaults; the clinical lead must sign them off before Phase 4 ships.**

| Urgency          | Initial ack deadline (default) | Platform max | Next tiers                                                       | First delivery                                                                                    |
| ---------------- | ------------------------------ | ------------ | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Important        | 60 min                         | 120 min      | each tier gets half the previous window (30, 15 …), floor 5 min | in-app + push                                                                                     |
| Urgent           | 15 min                         | 30 min       | 7 → 5 → 5 min (floor 5)                                        | in-app + push, SMS (no PHI) after 5 min with no open                                              |
| Critical symptom | 5 min                          | 10 min       | 3 → 2 → 2 min                                                  | all configured channels**at once**, voice allowed per M36 rule, supervisor copied at tier 2 |

Rules: quiet hours never delay Urgent/Critical; a reassign restarts the window for the new assignee but keeps the original `requested_at` for
reporting; a tenant cannot disable Critical escalation; `failed_unreachable` fires when tiers are exhausted or every route to the current tier
failed. Acknowledge-eligible roles follow the matrix in [`05`](./05-clinical-workflows-and-safety.md#2-authorization-matrix) (aide = receipt only).

**Phase 4 gate:** all six acceptance tests from the source spec (ack ≠ open, overdue→backup w/o duplicates, quiet-hours can't suppress safety
routes, no PHI on lock screen, unreachable→fallback event, shift/time-zone correctness) plus a chaos run (queue, push vendor, DB failover).

> **Implementation status (WP 5.5, session & device controls):** decisions are in [ADR-0083](../adr/ADR-0083-messaging-session-device-controls.md) (**Proposed**: the session policy is open for SEC); always on (a security control, no tenant flag); migration 1130. **In this change:** `GET /api/v1/devices` and `DELETE /api/v1/devices/:id` (own staff sessions: coarse label, last used, push flag, current marked; no token, IP or raw user agent), `GET`/`DELETE /api/v1/messaging/governance/sessions` for a security officer (new key `messaging.sessions.manage`, a fresh step-up on the revoke, bounded to the officer's organisation, both audited), `delivery_endpoint.session_id` stamped at registration, and screens at `/messaging/devices` and `/messaging/governance/sessions`. A revoke is one transaction (the session row, its linked endpoints expired, an `m36.session.revoked` audit row) followed by closing the session's sockets on every api node through a new per-session realtime room; a foreign, unknown or already-revoked session is the same 404. Live proof: `test:m36:session-devices:live` (real Better Auth sessions, real realtime server and Valkey emitter). **Not in this change:** the app lock and its tenant policy, a bulk "sign out everywhere else", a notice to the revoked user, expiring the endpoint on a normal sign-out or idle expiry (only an explicit revoke does), endpoints registered before 1130 (no link), an organisation-wide user picker for the officer page (it takes a user id), and native-app device revoke (5.11).

> **Implementation status (WP 5.1–5.4, web):** web closure only; no migration, no route, no flag. 5.1 offline gate (risky sends disabled offline; the web outbox stays memory-only because bodies are PHI, so the "encrypted IndexedDB" in the WP row is NOT built and is the native app's job), 5.2 backward-until-overlap catch-up with a visible gap row and a Live / Catching up / Paused chip (no `after` cursor was added), 5.3 camera capture with client-side EXIF/GPS strip plus a server quarantine of JPEG/PNG that still carry metadata (the server cannot strip: the object is checksum-bound), 5.4 touch targets, focus and axe evidence. **Open:** the screen-reader and keyboard scripts in [`evidence/phase-5-accessibility.md`](./evidence/phase-5-accessibility.md) are unsigned, the Playwright spec is unexecuted, canvas re-encode on real phones is unverified, and the native app (chartwarden-mobile: SQLCipher outbox, catch-up, camera, push, app lock; 5.11 needs a provider field on endpoint registration) is not started.

> **Implementation status (WP 5.11, server side of native push, W6):** migration 1153; no flag. `delivery_endpoint.provider` (`web` | `fcm` | `apns`, default `web`, a CHECK keeps native providers on the push channel); `POST /api/v1/notifications/endpoints` takes an optional `provider` (a native token must match its provider's shape and must come from a signed-in session so a session revoke expires it; otherwise 422). One `push` channel, three transports behind a router: Web Push unchanged, FCM v1 (service-account JWT, no SDK) and APNs (ES256 token auth over HTTP/2); each binds on its own env names (`FCM_SERVICE_ACCOUNT_JSON`; `APNS_KEY_P8`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`, optional `APNS_ENVIRONMENT=sandbox`) and an unbound provider settles `failed/transport_not_configured`. A native push carries a FIXED generic title/body and an opaque `{type, alertId}` (type is still the legacy `wardenx.alert` the mobile parser checks); never message text, a deep link or PHI. A dead native token settles terminally with `push_token_unregistered` and that endpoint is expired (a Web Push failure is never expired, it only counts). Proof: unit tests with fake vendors (`native-push-transports.test.ts`, binding tests), live `test:m36:delivery:live` and `test:m36:session-devices:live` cases on private containers. The decisions behind this are recorded in ADR-0072 decisions 8-10 (still Proposed). **Not in this change:** a real FCM/APNs send (credentials are deploy secrets; nothing has been sent to a vendor), the mobile client (token registration, permission prompt, listeners, app lock), and silent/background push.

> **Implementation status (WP 5.9, workforce offboarding):** decisions are in [ADR-0084](../adr/ADR-0084-messaging-workforce-offboarding.md) (**Proposed**: the second approver, draft retention, on-call vacancy ownership with M19 and the auto-trigger are open); always on (a security control, no tenant flag); migration 1131 (one permission, no table). **Already event-driven since WP 1.4/3.4/3.5 and left as is:** memberships ended, sockets dropped, tasks and handoffs moved on `m2.user.deactivated` / `m2.membership.revoked`. **In this change:** `GET /api/v1/messaging/governance/offboarding/:userId` (dry run, new key `messaging.offboarding.manage`, audited) and `POST …/execute` (that key plus `messaging.read` + `messaging.review` plus a fresh step-up): per item what was done and what still needs a person, derived from the live rows (no run table), safe to repeat. It revokes every live session and expires every endpoint (the ADR-0083 service), re-runs the task/handoff/membership sweeps, moves each waiting acknowledgment request through the ADR-0078 supervisor reassign (a request nobody can take stays assigned and visible in the unacknowledged queue and raises one supervisor alert), removes scheduled sends, reminders and snoozes, counts untracked urgent messages and acknowledged-unresolved requests as needing a person, keeps drafts and past messages, and surfaces the on-call roster as advisory (M19 owns it). Screen: `/messaging/governance/offboarding/:userId`. Live proof: `test:m36:workforce-offboarding:live` (real Better Auth sessions). **Not in this change:** an automatic run on deactivation, a per-row "Reassign…" dialog and a stored "Mark complete" (complete is derived), a user picker, an M19 roster reader, a dedicated ack reason code.

> **Implementation status (WP 5.10, recovery rehearsal):** no migration, no route, no flag; a script and a runbook ([`docs/runbooks/m36-restore-drill.md`](../runbooks/m36-restore-drill.md)). **Built:** `bun run m36:restore-drill` starts its own private Postgres 18 (pgvector) and MinIO containers on free loopback ports (never the shared cluster), migrates and provisions roles, seeds two tenants through the real M36 routes (messages, edits, presigned-upload attachments, one reaper-destroyed quarantined attachment), takes the production-style `pg_dump | gzip` plus a MinIO data-volume copy, writes more data, kills the source, restores into scratch containers and verifies: row counts, RLS/policy/grant/trigger fingerprint, audit count and M4 hash chain, every attachment object byte-identical (size, sha256, etag), no orphan objects, RLS as the real `chartwarden_app` role, `runHashVerifyForOrg` over every message and revision, and (added in 5.10) an intrinsic message <-> attachment <-> audit reconcile (every message, revision and attachment has its `<table>.insert` audit event, no orphan audit event, every attached attachment has a same-org message) plus an RTO-vs-target comparison. `bun run m36:restore-drill:detect` injects six faults (missing object, same-size corrupted object, tampered body hash, orphan audit event, missing audit event, deleted message that owns an attachment) and requires exit 1 with the matching check named. Pure verdict logic is unit tested (`scripts/__tests__/restore-drill-report.test.ts`). **Verified:** the drill passes and all six faults are detected, on one developer machine at demo scale (about 15 messages, 6 attachments, under 1.2 MB); measured RTO about 12 s and RPO window about 1.8 s (by construction: the drill fails the source seconds after the backup), figures and caveats in the runbook. **Not done:** a drill against production-scale data or a production-sized dump; a restore from the real production object-store provider (production has no object-store backup at all, so the drill uses a volume copy as a stand-in); WAL/PITR restore (production takes no WAL archive); a restore of `MESSAGING_ENCRYPTION_KEY` escrow; the RPO/RTO owner decision (Tier 1 or 2 for M36 is not recorded, so "RPO/RTO met" is shown only for RTO against the Tier 1 *target*, and RPO cannot be met by anything that runs today); the drill is run by a person per release and is not a CI job (it needs Docker-in-Docker; `arch:live-suites` does not require it).
