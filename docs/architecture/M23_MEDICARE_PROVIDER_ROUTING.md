# M23 Medicare provider routing

<!-- verified-against: develop working tree · 2026-11-12 -->

M23 owns `medicare_provider_routing`, an organization-scoped, effective-dated record of the Medicare Administrative Contractor jurisdiction for an M40 provider entity. The provider entity remains the authoritative source for provider identity (CCN/NPI); M23 owns the billing-specific jurisdiction fact. `mac_submitter_credential` remains the separate encrypted direct-MAC portal authentication/configuration record.

Intervals are inclusive (`effective_from` through `effective_to`; NULL end is unbounded). PostgreSQL rejects overlapping intervals for an organization/provider pair. Claim assembly resolves jurisdiction on the claim's `service_from` date and snapshots it into the claim. Submission retries and preview fingerprints resolve against that same service date; changing today's provider configuration does not rewrite an existing claim.

Migration 1487 backfills only when a legacy credential references a provider entity in the same organization. The credential's `created_at::date` is the earliest evidenced date, not evidence of prior historical validity. No address-based inference is performed. Orphan/wrong-organization rows and records encountered alongside a pre-existing canonical route are retained as non-secret rows in `medicare_provider_routing_backfill_issue` for review. Credential records and ciphertext are not modified or copied.

The provider setup workflow is the existing M23 Billing → MAC Credentials screen, extended with a separate Medicare provider-routing section. The section calls `GET /api/v1/billing/medicare-provider-routing/:providerEntityId` for history and migration issues and `POST /api/v1/billing/medicare-provider-routing` to configure an interval. These endpoints use provider-scoped billing credential permissions, step-up, AI-actor rejection, and idempotency for writes. Reasons are controlled codes rather than free text to prevent PHI entering the audit trail. Routing setup works without creating a portal credential.

The rollout is expand-first: apply migration 1487, review the backfill issue table under organization context, explicitly configure any missing/conflicting intervals, then deploy the application that reads the canonical table. Do not delete or rewrite legacy credential rows. Rollback is application-only: revert application reads while retaining the additive tables and backfill; do not drop the new tables because claims may have been assembled from them.

## Claim.MD Medicare payer route and enrollment (CM-3)

`claimmd_medicare_payer_route` and `claimmd_medicare_payer_enrollment` are M23-owned, organization-scoped and non-secret. A route refers to the canonical M40 Medicare payer UUID, M23 provider entity, effective MAC jurisdiction, the resolved Claim.MD account identity, account usage, transaction (`837i`), and the Claim.MD payer id stored as text (leading zeroes preserved). The route does not imply enrollment. Enrollment evidence is an independent effective-dated row keyed to provider, payer, account, usage and transaction. States other than `verified` or an explicitly evidenced `not_required` hold Claim.MD claim dispatch. The current implementation applies that conservative gate to both test and production usage; it does not infer exemptions from an absent row or from a working account key.

For a claim-specific preview or dispatch, the resolver follows the claim's `patient_payer_id` to the organization-scoped M5 coverage, validates the linked M40 payer is active Medicare, then resolves the unique route for the provider's canonical jurisdiction on `service_from`. It requires exactly one effective enrollment decision. Preview fingerprints bind route identity/version, external payer id, account and usage, provider jurisdiction, payer version, and enrollment identity/status/version. The Worker repeats the same lookup before vendor I/O; any changed/missing route or enrollment blocks new dispatch. The M40 payer UUID and external payer id are not returned in claim preparation responses.

Account identity is derived server-side: active tenant Claim.MD config uses `tenant:<organization-id>` and its persisted test/production mode; platform credentials are available only to organizations selected by `CLEARINGHOUSE_ENV_FALLBACK_ORG_IDS`, and use the platform account reference and usage. API clients cannot choose an organization or account. Secret values never enter either new table.

Migration 1488 creates the route and enrollment structures but does not import `CLAIMMD_M23_PAYER_ROUTES`: environment values cannot prove the organization/provider/M40 payer/account relationship or enrollment. During rollout, an administrator must review an existing environment mapping against the selected tenant or allowlisted platform account, canonical M40 payer, M23 jurisdiction, and vendor evidence, then enter a durable route and a separate enrollment decision through the existing Billing → MAC Credentials/provider setup screen. Route existence alone is not approval. `CLAIMMD_M23_PAYER_ROUTES` remains for legacy non-claim context callers during transition, but a claim-specific path requires the durable records and will not use that variable as fallback.

Admin APIs are `GET /api/v1/billing/claimmd-medicare-routing/:providerEntityId`, `POST /api/v1/billing/claimmd-medicare-routing/routes`, and `POST /api/v1/billing/claimmd-medicare-routing/enrollments`. They are tenant/provider scoped and use existing M23 billing read/admin permissions, ABAC provider scope, step-up, AI actor refusal, request idempotency, DB RLS and write audit. Verification is manually recorded with a source and non-PHI evidence reference; no vendor enrollment endpoint is presumed. No M23 claim is sent by route configuration.

Deploy migration 1488 before the application. Then review existing environment routes and tenant-account ownership, verify M40 payer and MAC jurisdiction, enter route and evidence, and confirm readiness by claim preparation in test mode. Do not configure production usage until the vendor's transaction-specific authorization and response reconciliation are verified. Rollback is application-only; retain migration data and do not drop the new tables. Reverting the application disables the new resolver, not any already-recorded audit evidence. Migration 1488 is additive and safe to leave in place.

An effective jurisdiction is not evidence of payer enrollment, Claim.MD payer-route readiness, MAC portal credentials, or production authorization. Claim.MD payer routing and response reconciliation remain separate readiness gates. Direct-MAC transport still requires its credential and gateway. No configuration change in this PR enables outbound submissions.

## Medicare notices (CM-4 capability boundary)

NOE/NOTR drafts originate from M6 election-period and terminating-event sources; transfer notices carry a separate M6 transfer-event identity and M23 snapshot. Their existing deadline watches and acknowledgment reducers remain authoritative. Notice submissions use durable `claim_submission` rows and deterministic outbox/BullMQ jobs. Worker registration now includes NOE, NOTR, and transfer queues regardless of the legacy gateway; a preflight holds the durable queue job and raises a critical alert when a required capability is unavailable.

The X12 package contains executable `build837iNotice` and `build837iTransferNotice` serializers and golden fixtures. CM-4A.1/4A.2 connect authoritative notice-fact loaders, render identity, and encrypted artifact storage to the internal renderer. The renderer is composed into M23 worker dependencies, but submission preflight does not invoke it while the external path is guaranteed held. Claim.MD/Stedi remain held, and Direct-MAC remains delayed because no repository server contract binds immutable artifact/submission/account identity or supports verified ambiguous-outcome reconciliation.

The proposed `m23-direct-mac-notice.v1` contract preserves the historical jurisdiction and account already frozen into the render/dispatch identity; replay and lookup never substitute current provider routing. That contract does not prove the provider's EDI enrollment with its HHH MAC, submitter authorization, transaction support, or MAC connectivity. Those are separately evidenced external readiness requirements and the absence of any one retains the dispatch hold.

Vendor capability is transaction-specific. The checked [Claim.MD supported file formats](https://docs.claim.md/docs/supported-file-formats) documentation describes 837I institutional claims but does not verify hospice NOE, NOTR, 8xC, or 8xD processing. [Stedi's institutional claim submission guide](https://www.stedi.com/docs/healthcare/submit-institutional-claims) likewise describes claim submission and subsequent claim acknowledgments, not these hospice notice workflows. Consequently, all Claim.MD and Stedi notice queues remain held, even if `M23_CLAIMMD_NOTICE_UPLOAD_ENABLED=true`; the transport also refuses these notices with `CH_NOT_WIRED`. Direct-MAC notice work remains the legacy X12/MAC path and requires both gateway capabilities. A clearinghouse receipt never advances the notice to payer/MAC acceptance; that lifecycle still depends on the existing verified acknowledgment path. Transfer processing is registered with the same lifecycle/shutdown ownership as NOE and NOTR.
