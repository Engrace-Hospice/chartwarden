# Capability - ADR Documentation Readiness (advisory)

## Purpose
Before staff submit an Additional Documentation Request (ADR) response packet, shows a reviewer where the attached documents appear to leave a checklist item uncovered, so a gap is seen before filing rather than after a denial. The output is a readiness review: a list of findings, each `{ checklist key, looks_present | possibly_missing | cannot_tell, cited packet document ids with a page or section pointer, plain-language note }`. It is advisory only. It never ticks the checklist, attaches a document, changes `adr_case`, claim, appeal or `submission_attempt` state, gates sign-off or filing, or writes any text sent to the MAC. It asserts presence with a citation or says "cannot tell"; it never judges whether documentation is sufficient under CMS rules and never emits an "all clear". A deterministic baseline (checklist keys with no attached document) is always shown and is the control arm for evaluation.

## Risk Classification
Medium, with High-class controls. Financial and compliance decision support with no clinical surface, like `denial_outcome_prediction`. The harmful error is false reassurance: a reviewer trusts the panel and files a deficient packet. Because of that, the capability carries the High-class controls from Governance section 4.2 (human in the loop, deterministic fallback, full audit, annual re-evaluation, explicit tenant consent). Classification is the recommended default and is awaiting the AI Safety Owner (open decision D2 in the Stage 1/2 proposal); the alternative is High.

## Architecture
Module 25 Remittance and Denials consumes; Module 32 AI Platform owns inference. M25 does not depend on M32 in the module manifest, so M25 uses a locally declared structural port resolved to a deny-stub (the M22 DocLens pattern), bound later to an opaque seam. No vendor, model or backend is chosen: `defaultBackendKey: null` until the user decides (open decision D1). Registered as capability key `adr_documentation_readiness`. M25 passes ids and counts only; document text is read inside the M32 boundary under the caller's tenant scope (source of readable text is an open investigation, not assumed). Design, PHI flow and threat model: `docs/ai/proposals/adr-documentation-readiness-stage-1-2.md`. Prompt design (unregistered): `packages/ai-platform/prompts/adr-documentation-readiness/readiness.design.md`. Evaluation design: `docs/ai/evaluation/adr-documentation-readiness-dataset-spec.md`.

## Lifecycle
State: PROPOSED. No consumer surface, no active prompt template, no model reachable. Advancing past PROPOSED requires the Governance section 5 workflow, the user's vendor decision, a signed BAA and ZDR (not assumed: documented as in negotiation), and SME confirmation of the requirement list.

## Controls
Kill switch: activate an `ai_kill_switch_state` row for capability_key `adr_documentation_readiness` - platform-wide (`organization_id IS NULL`) or for one tenant; the two rows OR together and neither overrides the other. With the capability off, killed, timed out, schema-invalid after one retry, or low-confidence, the result is `available: false` or "cannot tell" and the deterministic baseline remains; nothing in packet work is blocked. Every finding needs a human disposition (acknowledge, dismiss, dispute) before the panel is marked reviewed, but that is never a sign-off requirement. Findings citing a document not in the packet are dropped. M25 entities (`adr_case`, `appeal_case`, `submission_attempt`, packet and checklist state) are an AI-prohibited zone: no prompt template may target them. Default off; tenant opt-in only after the BAA covers AI; per-tenant token cap required before enabling. Audit through the immutable M32 `ai_invocation` ledger (ciphertext payloads, model pin, template version). Annual re-evaluation required.
